Agent harness architecture map: what fills each concern, on every stack

An agent harness is the same set of concerns whatever you build it on: a loop, a model door, tools, state, waits, identity, records, configuration. What changes between Azure, Databricks, AWS, GCP and an open-source stack is only the product that fills each one. This page puts all of them on one view, with a verdict on what to pick.

Written 20 November 2026 from the open stack files, one per platform. Open Stack is the only column that has run end to end. Azure and AWS are decided in writing and not yet built. Databricks is part built. GCP has no stack file at all: that column is a proposal, shaded grey, to be checked before anyone relies on it. Product names and features change; check current documentation.

The same map, cut three ways

The first table says which product fills each concern. This one asks a different question for each platform: for every concern, how much does the platform hand you, how much comes from assets we already share across all our agents, and what is left that every single agent must write for itself.

X · The platformWhat the cloud or data platform gives out of the box. Different on every stack.
Y · Shared assetsThe harness library, its adapters, AgentTwin, the evaluation library, the catalogues. Written once, reused by every agent. Where a platform has no adapter yet, that is the work of the stack, not of any agent.
Z · Each agentIts specification, tools, rules, world, scenarios and thresholds. The same on every platform, and the only part that is yours.

Boxes show who carries the concern: platform, shared assets, agent. A darker first box means the platform carries more.

What this shows. Z does not change with the platform. Y shrinks or grows with the stack: Azure, AWS and the open stack have most adapters; Databricks and GCP need the library to grow before an agent can run there on platform services. X is where platforms differ most, and it is the column to read when choosing, but a platform that carries a concern does not remove the need for the agent to write its own rules and checks.

The levels in this view are our reading of each platform, not a measurement. The adapter status comes from the shared library as of 20 November 2026; GCP and Databricks adapters do not exist yet. Platform product lists change quickly.

How to decide, in three rules

1 · Build the middleThe loop, limits, cost meter, policy rules and start-once triggers are the same few lines on every stack. Writing them is cheaper than adapting a product, and they must see your task.
2 · Lean on the cloud you are onFor hosting, identity, secrets, telemetry and configuration, take the platform's own service. It is already approved, billed and audited there.
3 · Keep one open default for the restPostgreSQL, a library for durable waits, MCP for tools, OpenTelemetry for records. They run on any cloud, so moving stacks is a change of adapter, not of code.
Why this works. Every product sits behind a port: a small interface the harness owns. A stack is a file that says which product fills each port. Changing cloud means changing that file and writing one adapter per changed port. The agent, its specification and its tests stay put.

What to check before relying on this

  • The GCP column. It is our proposal, not a tested stack. Confirm each service against Google's current documentation and region availability.
  • Azure and AWS cells. They record decisions. Few have been built against the real service.
  • Databricks limits. On the free edition we found Vector Search and custom model serving refused, which also rules out AI Gateway on a custom endpoint. A paid workspace may differ.
  • Prices and tiers. Not shown here on purpose. Get them from each vendor for your volume.
