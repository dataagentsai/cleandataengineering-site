Data platform architecture mind map: every concern, on every platform

A data platform is the same set of concerns whatever you build it on: it must run, be trusted, be seen, be guarded and, one day, help fix itself. What changes between Azure, Databricks, AWS, Google Cloud and an open-source stack is the product that fills each concern. This page puts all 24 concerns in one table, then cuts each one three ways: what the platform gives you, what we write once for all of them, and what each platform still has to implement.

Written 20 November 2026. The Azure and Databricks entries in column Z come from real builds: a 3-day run passed on Azure Databricks that day. AWS entries come from the repository's files, not from a fresh run. GCP has no binding at all, so everything in its column is a plan. Product names for concerns the rest of this site already maps are taken from there; the others were written from general knowledge and are not checked against each vendor's current documentation.

The map

The table

X · The platformWhat the cloud or data platform gives out of the box. Different on every stack, and often just a building block.
Y · The horizontal assetWhat we write once and reuse unchanged on every platform: the manifest, the rules, the stages, the checks, the simulated world. It is the same code on Azure as on AWS.
Z · Still to implementThe thin layer that each platform still needs before the asset can run there: an adapter, a job definition, a renderer. This is the real work of moving platform.

How much of each concern comes from where

For each concern, how much of the work does the platform give you (X), how much do we write once for every platform (Y), and how much does each platform still have to implement (Z)? On average, by our judgement, about 34% comes from the platform, 44% is the horizontal asset we write once, and 22% is what each platform still has to implement.

Our judgement, not a measurement: a typical platform of the five, the work of having the concern running, each bar summing to 100. The platforms differ (Databricks hands over more lineage and access than an open stack does), so read the bars as the usual case, not as one platform's score.

What this shows. Read down column Y: most of the platform is horizontal, written once. Read column Z: the work per platform is small and concrete (adapters and definitions), not a rewrite. The expensive rows are the ones where X says "nothing": reconciliation (X6), self-healing (X20) and simulation (X22). No cloud sells them, so the horizontal asset is the whole answer, or, for X20 and X21, there is no answer yet.

What to check before relying on this

  • GCP. No cloud-layer file exists for it. Treat the whole column as a proposal and confirm each service against Google's current documentation and region availability.
  • Product names. Cells for concerns that the site already maps agree with the architecture page. The rest were written without re-reading each vendor's page, and product names change often.
  • Column Z status words such as "done" or "none" describe our own builds as of 20 November 2026. They are not a statement about the products.
  • Prices and tiers. Not shown on purpose. Get them from each vendor for your volume.
