AI · Agent Harness

When to use an agent SDK or framework, and when to write the loop yourself

The loop is small: build the messages, call the model, run the tool, repeat. A framework does not sell you the loop. It sells you what surrounds it: keeping the context under control on long runs, surviving a restart, waiting days for a person, and replaying a run. So the choice is one question: do you need the surroundings?

Written 20 November 2026. The method is from our own framework research notes. Product facts were checked against public reports on that date, several of them secondary, and these products change fast. The last section says what to verify.

The mind map: six questions

Work round it in order. Most teams answer the first two and stop; the last four are where choices go wrong a year later.

Five positions, not two

"No framework" and "framework" hide five different things. Most simple agents belong in position 1 or 2 and never need more.

1 · Plain loopYou write about 200 lines: build the messages, call the model, run the tool, repeat to a cap.You still own: Everything: control flow, context, budget, errors.
2 · Provider tool-runnerThe model vendor's own SDK runs the loop over tools you define, with hooks for approval and errors. No built-in tools.You still own: Context policy, durability, delegation.
3 · Harness SDKLoop plus context management, permissions, built-in tools and a sandbox. Example: the Claude Agent SDK.You still own: Process shape, and survival past one session.
4 · Graph runtimeLoop as a graph, with saved state, waits for a person and replay. Examples: LangGraph, Google ADK 2.0 workflows, Microsoft Agent Framework workflows.You still own: Context policy, autonomy, your own limits.
5 · Managed runtimeA cloud runs the agent and its operations for you. Examples: Foundry hosted agents, Bedrock AgentCore, Google's agent runtime.You still own: Very little. The exit cost is the highest here.

A decision path in four steps

1 · Do you need the surroundings?Write what your agent does in plain sentences first. If runs are short and a crash means an acceptable retry, stop here: write the loop, or use the model vendor's tool-runner.
2 · Does something else own durability?If a workflow engine, a job scheduler or a queue already handles retries and restarts, keep the inner loop plain. Two systems that both think they own restarts will disagree at the worst moment.
3 · What shape is the work?Conversational and routing: handoff-style SDKs. Long-horizon with waits for people: a graph runtime. Autonomous and needs a computer: a harness SDK. Then let your cloud and model choice break ties.
4 · Can you leave?Whatever you pick, state, traces and tool contracts stay yours. Write down the trigger that would make you revisit, for example "runs exceed an hour" or "approvals enter the flow".

Six situations where a plain loop wins

  • Short, stateless runs. This is the commonest case and the one where adopting a framework is most often reflex, not reasoning.
  • You are learning the mechanics. Build it once by hand and the concerns stop being a list.
  • Something else owns durability. One durability system per run.
  • The control flow is unusual. If you cannot name what the framework forbids, you do not have this case.
  • You must own the stop rules. Step budget, repeat detection and cost ceiling live in the only place that sees the whole trajectory. We keep the loop ourselves for this reason and adopt everything around it.
  • Auditability. The exact bytes sent to the model must be yours.

Where we landed, and why

Our own agents keep the loop in-house and adopt the rest. The loop is a small piece of code whose limits (steps, repeat detection, cost) must sit where the whole run is visible, so we write it. Around it we adopt: a model gateway, a database for state, a library for durable waits, OpenTelemetry for traces. Frameworks are a supported choice on our stacks, but the stack files for a Claude Agent SDK stack and a LangGraph stack are still placeholders: we have not built agents on them, so we do not claim a verdict from experience. Our scores for each framework are a dated starting hypothesis, not a measurement.

How to run the choice

  • Mark the concerns first. Take the list of fourteen concerns and mark each Must, Should or Won't. At most five Musts. The Won'ts are the most useful marks, because they let you reject a capable product cleanly.
  • Count what you would still build. For each candidate, list the Musts it scores low on. That is your build list. Identity, evaluation and cost limits are supplied by none of them.
  • Pilot two tasks. One representative real task, and one that breaks things: a long run, an approval, a tool failing halfway, an adversarial user. Every framework demos well on the first. Differences show only in failure.
  • Write the decision down with the alternatives, what you accepted, the exit cost and the trigger to revisit.

Check before you rely on this

  • Names and versions move. The Microsoft framework merged Semantic Kernel and AutoGen (reported 1.0 in April 2026). Google's agent platform was renamed during 2026 and reports disagree on ADK version dates. The Claude Agent SDK was formerly the Claude Code SDK.
  • Model support. Whether the OpenAI SDK works well with non-OpenAI models, and which models each cloud's framework supports, should be tested on your own task.
  • Hosted runtimes. Features, regions and exit paths differ by cloud and change; read the vendor's current documentation.
  • Sources used for the product facts (mostly secondary reports; confirm against vendor pages): Visual Studio Magazine on Microsoft Agent Framework 1.0, InfoQ on the Agent Framework harness, Google Developers Blog on ADK and Agent Engine, Rubin Lake radar on Google ADK, Claude Agent SDK vs OpenAI Agents SDK, Claude Agent SDK vs OpenAI Agents SDK vs LangGraph.
