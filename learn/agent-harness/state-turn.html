Which step touches which table

Follow one turn down the page and watch which table each step touches. The pattern is simple: read once at the start, guard each write in the middle, save once at the end.

The checkpoint is saved once per turn, with "insert, or update if this run id is already there", so a retried save can't make a duplicate.

The delivery row is always settled, even when the turn failed, so a retry of the same message gets the same answer rather than running again.

Not built yet: saving a checkpoint after every trip of the loop (today it is once per turn), and an outbox so the reply and the checkpoint are written in one transaction.

Code view: input, process, output, the call stack, the classes

Goes inA chat request that may name an earlier conversation
What happensThe newest checkpoint of that conversation is loaded at the start; at the end the history is bounded and written as one row per run, and the delivery claim is settled
Comes outA checkpoint row in agent_state.checkpoints and a settled delivery
