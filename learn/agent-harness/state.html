State and memory

The harness server can be switched off between two messages, and Azure does exactly that when it is quiet. So the server keeps nothing that matters. Every turn loads what it needs from PostgreSQL at the start and writes it back at the end.

Goes inRohan's conversation id, from his browser
What happensLoad the newest checkpoint; during the turn write ledger rows; at the end save a new checkpoint
Comes outA conversation that survives any restart
Kind of memoryKept inHow long
This turn: messages, tool calls, raw resultsthe process's memoryone turn, never saved
The conversationagent_state.checkpoints30 days
What was already doneagent_state.requests (the ledger)the row expires after 600 s in flight
Work waiting for a personagent_state.approvals, escalations, and DBOS's tables24 h for an approval
Who you arethe token in the browser; refresh token encrypted in agent_state.sessions1 h; 12 h unused
Policies and claimsthe claims system's own databasethe system of record
Long-term memory across conversationsnot built yet

Two databases, two logins. The agent's login cannot even connect to the claims database. The claims system's login may read exactly one agent table: approvals, to check a payout was really approved.

    session_key: {key_vault: agent-session-key}

    adapter: postgres
    url: {key_vault: agent-database-url}
