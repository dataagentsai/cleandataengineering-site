The core loop

The loop is the heart of the harness. It is surprisingly small: about 400 lines of plain Python, no framework. On each trip it asks the model one question. If the model wants tools, the harness runs them and goes round again. If the model answers in words, the loop ends.

Goes inRohan's message and the earlier conversation
What happensUp to 12 trips of: build context, check, ask the model, run any tools it asks for
Comes outA candidate reply, or a clear reason why we stopped

Why a loop? Rohan asks "what is the status of my claim?" without a number. The model can't answer yet. On trip 1 it asks for the tool list_claims. The harness runs it and puts the result into the context. On trip 2 the model has what it needs and answers in words. Two trips, two model calls, one tool call.

The model only ever asks. It never runs a tool itself. It writes "please call list_claims", and the harness decides whether that is allowed, runs it, and hands back the result. That one fact is what makes every check possible.

Before the first trip, the harness fetches the list of tools Rohan is allowed to use. If the claims system can't be reached, the turn ends right there with "I cannot reach the system", and no money is spent on the model.

The real numbers for "what is the status of my claim?"2 trips · 2 model calls (652 then 1,535 tokens in) · 1 tool call (list_claims, 51 ms) · 7,076 ms · $0.00058 · 38 spans in the trace.
