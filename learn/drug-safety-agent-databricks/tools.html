Drug-Safety Agent on Databricks · Tools

The three tools

The model can call three tools and nothing else. All three are read-only. None takes free text that could be used as a database query: each takes a drug name and an event name. That makes the question "what could the agent do wrong with its tools?" easy to answer: it can look things up.

Goes inA drug name and an event name
What happensLook up a row by key; for the statistics, code computes the ratios from the counts
Comes outA small JSON result, or an error that lists what the data does hold
ToolTakesReturnsWhere the arithmetic is
get_report_countsdrug, eventa, b, c, d and the fetch datenone: it is a lookup
get_signal_statsdrug, eventcases, PRR, ROR and its 95% interval, whether it screens as a signalcode, never the model
get_label_mentionsdrug, eventon the label or not, boxed warning or not, short quotes with the sectionnone: text search with listed synonyms

A note on names. The specification calls the tools get_report_counts, get_signal_stats and get_label_mentions, and the tool facade presents those names. The local Python versions have shorter names (report_counts and so on), as the registry below shows.

Why not let the model write SQL? A model that writes its own queries can read what it should not and can be tricked by text in the data into running something unintended. Three fixed tools remove that whole class of risk.
