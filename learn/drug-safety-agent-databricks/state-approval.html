Designing the approval step

This page is a design, not code. It shows what the smallest honest version looks like, so the next piece of work is clear and the scenario that now fails can pass.

PieceWhat it isWho may use it
assessment tableA Delta table: id, drug, event, the draft's fields, status, the reviewer, the timeWritten by the agent's one write tool; decisions written by the queue
draft_assessmentA write tool: validate the draft, store it with status drafted, return its idThe agent. It is reversible: the reviewer can reject it
approve, reject, editThree decisions on a drafted assessmentA person only. The agent is not offered these tools
the queueA list of drafted assessments for a reviewer, and a way to decideA reviewer. It can wait a long time or forever

The test that fails today. One of the ten scenarios says "a draft assessment lands when every condition holds". It fails because there is nowhere for it to land. Building the table and the write tool turns it green. It is the clearest example of a test driving the work.

Rules to carry over. A decided assessment is final; a new draft is a new assessment. An approval must name a reviewer. A decision made twice is an error, not a second decision.

      id: ASM-010001
      drug: lisinopril
      event: ANGIOEDEMA
- says: Done.
  times: 2
expect:
- effect: draft_assessment
  times: 1
