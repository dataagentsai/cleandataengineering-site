Table-driven tests

The tests are written as tables. A test function walks a list of rows, each row a request and the answer it must get. This keeps tests short, makes a missing case obvious, and lets a non-programmer read what is promised.

Tests carry the ids they prove. Each test is tagged with the specification ids it discharges, such as R-CAUSALITY. The gates read those tags to know which promises have evidence.

The loop is tested without a real model. A scripted model returns fixed replies, so a test can say "the model asks for two tools, then replies with this JSON" and check the draft, the steps and the spend.

@pytest.mark.discharges("P-NUMBERS-FROM-TOOLS", "Q-GROUNDED", "P-OUTPUT-CONTRACT", "P-MODEL-ERROR")
@pytest.mark.asyncio
@pytest.mark.parametrize("name,script,status,problems,tools", CASES, ids=[c[0] for c in CASES])
async def test_investigate(name, script, status, problems, tools):
    d = await investigate(ScriptedClient(script), "amiodarone", "PULMONARY TOXICITY")
    assert d.status == status
    assert [t["name"] for t in d.trace] == tools
    found = grounding(d)
    assert len(found) == len(problems)
    for want in problems:
        assert any(want in f for f in found)
