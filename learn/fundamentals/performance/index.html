Performance fundamentals: where the time goes in a data job

A slow job is almost never slow for a mysterious reason. Time goes to a short list of places: reading bytes, moving bytes, doing work on bytes, waiting, or doing the same thing twice. This page is that list, organised as a mind map so you can walk it when a job is slow. Storage choices are explained in the abstract; the engine is not the point.

Start here

The data physics

Five plain facts that explain almost everything below. Read these and the rest follows.

Bytes are the unit of cost.Almost every speed-up in data engineering is the same move: touch fewer bytes, or touch the same bytes fewer times.
Distance sets the price of a byte.Memory is fast, local disk is slower, object storage over a network is slower again, another region is slower still. Each step is roughly 10 to 1,000 times slower than the one before (orders of magnitude, not benchmarks).
Many small things are slower than a few big things.Every file, task, request and query pays a fixed start-up price before it moves one byte. A million tiny items pay it a million times.
Workers must agree.Joins, group-bys and sorts need rows with the same key in the same place. Moving them there (the shuffle) is the most expensive thing a cluster does.
Doing nothing is also a cost.A job waiting for a cluster to start, a lock, a slow source or one straggler task still holds the clock, and often the bill.

Where the time goes

Seven buckets for a slow job

When someone says 'the job is slow', find the bucket first. Most jobs have one dominant bucket; fixing a small one first is the usual mistake.

Where the time goes: find the biggest bucket before tuning anything. Illustrative proportions.

BucketWhat it looks likeTypical causeFirst moveVerdict
ReadingStage reads far more bytes than the result needsNo partition or file skipping, wide rows, SELECT *Filter early on the layout key; read fewer columnsPursue first
ShufflingBig shuffle read/write, long exchange stagesJoins and group-bys on big data, wrong partition countBroadcast the small side; filter before joiningPursue
ComputingExecutors busy, CPU highPython UDFs, regex, JSON parsing, heavy window functionsUse built-in functions; parse oncePursue when CPU-bound
SpillingMemory spills to diskPartitions too big, skewed keysMore, smaller partitions; fix skewPursue

Storage model decisions, in the abstract

These choices are made once, when a table is designed, and then pay or cost on every read. Names differ by engine; the ideas do not.

Why analytics uses column storage: a query about one column reads one column.

File skipping: each file records its min and max. Clustering makes those ranges tight so the engine can skip files. Partitioning, Z-order and liquid clustering are different ways to get this.

DecisionWhat it doesHelps whenHurts whenVerdict
Row-oriented storageStores each row's values togetherYou fetch whole rows by key (transactions)You scan a few columns across millions of rowsRight for OLTP, wrong for analytics
Column-oriented storageStores each column's values togetherAnalytics: read three columns of fiftyYou fetch single full rows all dayDefault for analytics
CompressionShrinks bytes on disk and on the wireAlmost always: less to read and moveVery high CPU codecs on data read oncePursue; pick a balanced codec
Encoding (dictionary, run-length)Stores repeated values as small codesLow-cardinality columns (status, country)Unique values like ids and free textFree win on suitable columns
PartitioningSplits data into folders by a column valueQueries filter on that column; low-to-medium cardinalityToo many values, or queries rarely filter on itUse sparingly; wrong key is costly
Sort / Z-order style co-locationPuts similar values near each other in filesFilters on several columns, so file min/max ranges are tightData is rewritten constantlyPursue for big tables
Liquid-style clusteringAdaptive co-location that changes without rewriting everythingQuery patterns change or keys are high-cardinalityTiny tablesPrefer over fixed partitions when available
File statistics (min/max per file)Lets the engine skip whole filesData is clustered so ranges do not overlapData is random, every file spans every valueFree if layout cooperates
Bloom filtersA tiny index answering 'is this value definitely not in this file?'Point lookups on high-cardinality columnsRange filters, low-cardinality columnsTargeted use
Right-sized filesFiles big enough to amortise open cost, small enough to paralleliseRoughly 128 MB to 1 GB per fileThousands of tiny files, or one giant filePursue

Why compression matters so much

Fewer bytes is the cheapest speed-up there is

Compression is not a space-saving afterthought. Smaller files mean less disk read, less network, more data per memory page and faster scans. Columnar storage compresses far better than rows because each column holds similar values.

ColumnKind of valuesHow well it compressesWhy
Order status (5 values)Low cardinalityExtremely well, often 50x or moreDictionary encoding stores a tiny code per row
Country codeLow cardinality, repeatedExtremely wellSame reason; sorted data adds run-length gains
Date / timestampOrdered, many repeatsWellDeltas and repeats are small
Integer measureNarrow rangeWellBit-packing stores only the bits needed
Customer id (unique)High cardinalityModestlyFew repeats to exploit
Free text / JSON stringUnique, longPoorly, and costly to parseLittle structure; parse once into typed columns
Random UUID stringUnique, no orderPoorlyStore as a binary or numeric key if you can

Driver, executors, tasks: how a cluster spends your job

The driver plans and coordinates; executors do the work in parallel, one task per partition per core. Most tuning is picking the right number of tasks and not overloading the driver.

Driver, executors and tasks. The driver coordinates; executors do the work in parallel, one task per partition per core.

ThingPlain meaningToo little looks likeToo much looks likeVerdict
Number of tasks / partitionsPieces of work run in parallelIdle cores, huge partitions, spillScheduler overhead, tiny files, long tail of tiny tasksAim for partitions of about 100 to 200 MB
Executors and coresThe parallel workersJob crawls, partitions queueCores idle, bill highSize to the work, enable autoscaling with a sensible floor
DriverPlans the job, collects small resultsDriver out of memory on collect or large broadcastOver-sized driver paid for nothingKeep data off the driver
Executor memoryRoom to hold a partition and its joinsSpill, out-of-memory errorsWasted money on memory-optimised nodesFix partition size before buying memory
Actions and job overheadEach action (count, collect, write, show) launches a job with planning and scheduling costNot the issueHundreds of tiny jobs in a loop; seconds of fixed cost eachBatch work into one job; this is the gap embedded engines like DuckDB close for small data
Python UDFsRow-by-row Python outside the engineNot the issueSerialisation cost on every row, no optimiser helpUse built-ins, or vectorised functions where unavoidable
Serverless vs classic computeWho manages start-up and sizingCold-start waits on classicPay for always-on serverless idleMatch to the job's shape

Move less

Shuffles, joins and skew

A shuffle sends data across the network so rows with the same key meet. It writes to disk, reads from every other worker and waits for the slowest one. Reduce what you shuffle, shuffle less often, or avoid it entirely.

Why a shuffle is the expensive step: all-to-all movement across the network. Filter before it, not after.

SituationWhat happensBetter approachVerdict
Join big to smallBoth sides are shuffled by keyBroadcast the small table to every worker; no shuffle of the big onePursue
Join big to bigBoth sides shuffled; expensive but sometimes unavoidableFilter and project first; pre-partition both by the join key if reusedPursue; accept the cost
Skewed keyOne task gets most of the rows and runs far longerSplit the hot key, salt, or use skew handlingPursue
Function wrapped around a join or filter columnThe engine cannot use file statistics or the join planCompare the raw column; fix types at write timePursue
Too many shuffle partitionsThousands of tiny tasks, tiny output filesLet adaptive execution coalesce themPursue
Too few shuffle partitionsHuge tasks, spill to diskRaise partitions or let adaptive execution splitPursue
Cartesian joinEvery row meets every rowAdd the missing join conditionAlways fix

Do less

The unnecessary work list

The biggest wins are often not tuning at all, but stopping the job from doing things nobody needed. These patterns are the common ones.

Wasteful patternWhy it hurtsFixVerdict
Processing data nobody usesEvery unused column, row and table is paid for on every runRead only needed columns and rows; retire unused outputsPursue first
Full reload when only changes arrivedReprocesses yesterday's data againIncremental loads with a watermark or change feedPursue
collect() inside a loopPulls data to the driver once per iteration, serial and slowDo it as one set-based queryAlways fix
Same query run in a loopPays planning and scan cost every timeRun once with a join or group-by; or read once and reuseAlways fix
Reading the same table repeatedlyEach read scans the files againRead once, reuse (cache only if it truly pays)Pursue
Recomputing an unchanged resultSame inputs, same answer, paid againCache, incremental, or materialisePursue
SELECT * and no filterReads every column and rowName columns, filter earlyPursue
Sorting without LIMITSorts everything to show ten rowsSort only what you needPursue
DISTINCT used to hide a bad joinFan-out then dedupe doubles the workFix the join grainPursue

Some time is not compute at all. It is the clock running while something else finishes.

Kind of waitWhat it isHow it shows upFixVerdict
Waiting for computeCluster start or a busy warehouse queueLong gap before the first taskWarm pools, right-sized concurrency, schedule off-peakPursue

Precompute

Why we build performance objects in the gold layer

Raw tables are shaped for capture; business questions need a different shape. Gold objects pay the cost once, at load time, so thousands of reads pay almost nothing. This is the same trade as indexing in a database: spend write time to save read time.

Why gold has performance objects: spend write time once to save read time many times.

ObjectWhat it precomputesSaves on every readCostsVerdict
Fact table at a fixed grainJoined, cleaned, typed rows at one clear grainJoins and cleaningStorage and load timeCore gold object
Dimension tableSmall, descriptive lookup with stable keysRepeated lookups and text columnsMaintenance of historyCore gold object
Aggregate / summary tableDaily or monthly totalsScanning billions of rows for a chartMust stay in step with its basePursue for hot dashboards
Materialised viewA stored query result refreshed on changeRecomputing the queryRefresh cost, stalenessPursue when refresh is incremental
Clustered / sorted layoutCo-locates by the common filterBytes scannedRewrite costPursue for big gold tables
Semantic / metric layerDefinitions computed onceEvery tool recomputing differentlyGovernance effortPursue
Result and disk cachesRecent answers and filesRepeated identical queriesMemory, stalenessPursue, but do not rely on

FAQ

Questions people ask

Where should I look first when a Spark job is slow?

Open the slowest stage and ask which bucket it is: reading too much, shuffling, computing, spilling, one straggler task, or waiting. Fix the dominant bucket. Tuning a small bucket first rarely changes the total.

Is more parallelism always faster?

No. Parallelism helps until each piece is so small that starting it costs more than doing it. Aim for partitions of roughly 100 to 200 MB, and watch for tiny tasks and tiny output files.

Why do small files hurt so much?

Every file costs an open, a metadata lookup and a task slot before any data moves. Ten thousand 1 MB files do far more overhead than ten 1 GB files holding the same data.

Why does a low-cardinality column compress so well?

A column with five distinct values can be stored as a short code per row plus a five-entry dictionary, then run-length encoded. Unique values like ids have no repeats to exploit.

When does an embedded engine like DuckDB beat a cluster?

When data fits on one machine. A cluster pays job start-up, planning and shuffle cost on every action. For small and medium data on one node, that fixed overhead dominates, and a single-process engine avoids it.

Are the time and size numbers on this page measured?

No. They are orders of magnitude to build intuition. Measure your own job with the engine's query profile before deciding.
