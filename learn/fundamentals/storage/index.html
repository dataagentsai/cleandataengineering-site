Storage fundamentals: how data is kept and why layout matters

Storage is where performance, cost and correctness begin. A table is just files in a folder plus a record of which files belong to it. This page explains what that means, how layout decisions affect every read, and what maintenance keeps a table healthy, organised as a mind map.

Start here

The data physics

Five plain facts that explain almost everything below. Read these and the rest follows.

A table is files plus a ledger.Modern lake tables are many immutable files and a log that says which files are current. Updates write new files; they do not edit old ones.
Files are never edited, only replaced.That makes writes safe and readers consistent, but a small change can rewrite a large file.
Layout is a bet on how the data will be read.Sort or group by what people filter on and reads skip most files. Guess wrong and every read pays.
Object storage is big and patient.It handles huge sequential reads well and tiny random ones badly. Design for fewer, larger files.
Old data accumulates.Versions, logs and small files pile up unless something tidies them.

Choosing the kind of store

Analytics data lives in object storage because it is cheap, durable and shared. Other stores suit other access patterns.

Block / local diskLow latencyTied to a machineCaches, shuffle, scratchTemporary

How it is encoded

Row, column and compression

The format decides how many bytes a query must read to answer. Columnar formats store each column together so a query reads only the columns it names.

Why analytics uses column storage: a query about one column reads one column.

Format ideaHow data is storedGood forNot forVerdict
Row-based (CSV, JSON, Avro)One record after anotherWriting fast, streaming, whole-record readsAnalytics scans; CSV loses typesLanding and exchange
Column-based (Parquet, ORC)Column by column, with per-file statisticsAnalytics, skipping files and columnsSingle-record updatesDefault for tables
CompressionShrinks bytesEverythingNothing, if the codec is balancedAlways on
Dictionary and run-length encodingRepeated values become tiny codesLow-cardinality columnsUnique valuesAutomatic in columnar formats
Right data typesNumbers as numbers, dates as datesCompression, comparison, pruningEverything as stringsFix at silver
Nested / semi-structured columnsStructures inside a columnVariable data from APIsHeavy filtering on nested fieldsFlatten what you filter on

How it is laid out

Partitioning, clustering and file sizing

Layout is how rows are grouped into files. The engine uses each file's minimum and maximum values to skip files, so grouped data skips well and scattered data does not.

File skipping: each file records its min and max. Clustering makes those ranges tight so the engine can skip files. Partitioning, Z-order and liquid clustering are different ways to get this.

Partition only on a column people filter on, and only so each partition stays large.

TechniqueIdeaGood whenBad whenVerdict
Partition by a columnOne folder per valueCommon filter, few to hundreds of values, big dataHigh cardinality, small tables, or filter on other columnsUse carefully
Sort / cluster within filesSimilar values land in the same filesFilters on one or several columnsNever filteredPursue for large tables
Multi-column co-location (Z-order style)Interleaves several columns' orderFilters vary across columnsA single dominant filter (sort on it)Pursue when filters vary
Adaptive clustering (liquid style)Keys can change without rewriting the worldPatterns change; high-cardinality keysTiny tablesPrefer where available
Right-sized filesLarge enough to amortise cost100 MB to 1 GB filesThousands of tiny filesAlways aim for it
Over-partitioningToo many folders, each tinyNeverAlwaysAvoid

How it is a table

Table formats and the transaction log

A table format keeps a log of which files are current, so readers see a consistent snapshot and writers can commit atomically.

How lake tables work: update = write new files and record it in the log.

FeatureWhat it givesWhy you care
Transaction logAtomic commits, consistent readsNo half-written tables
Schema enforcement and evolutionRejects bad writes; allows controlled changePrevents silent corruption
Time travel / versionsRead an earlier snapshotDebugging and recovery; storage cost if kept long
Optimistic concurrencyWriters check for conflict at commitOverlapping writes may fail and retry
Statistics in the logFile-level min/max, countsSkipping without opening files
ConstraintsNot-null, check rulesCheap correctness at write time

What an update really does

Because files are immutable, a row-level change must write new files. How much it writes decides cost and conflict risk.

OperationWhat is writtenCost shapeVerdict
AppendNew files onlyCheapestPrefer when possible
Overwrite partitionReplaces the files of one partitionPredictableGood for idempotent loads
Merge / upsertRewrites every file that holds a matching rowLarge if matches are scatteredNarrow the condition; cluster by the key
Delete / updateRewrites files or marks rows deletedDepends on deletion markersUse markers on busy tables

Tiers and lifecycle

Cold data on cold tiers is cheap to keep and costly to read. Hot data on cold tiers is a slow, expensive mistake.

ChoiceEffectVerdict
Hot tier for active tablesFast, higher price per byteActive data
Cool or archive tier for historyCheap to keep, slow or costly to readData read rarely

Duplicate copiesPays twice and driftsAvoid; share instead

FAQ

Questions people ask

Why is partitioning not always good?

Each partition is a separate folder of files. Partition on a column with too many values, or one nobody filters on, and you get thousands of tiny files and no skipping.

What is the difference between partitioning and clustering?

Partitioning splits data into folders by value. Clustering orders rows within and across files so similar values sit together. Clustering is more flexible and works with high-cardinality columns.

Why do updates seem slow on a data lake?

Files are immutable, so a changed row means rewriting the file that holds it. Scattered matches rewrite many files. Cluster by the match key and narrow the merge condition.

How big should files be?

Roughly 100 MB to 1 GB each is a common starting point. Too small wastes overhead; too large limits parallelism.

Do I need to keep time travel forever?

No. Keep what you use for recovery and debugging. Longer history costs storage and slows clean-up.

Are the file sizes here fixed rules?

They are starting points. Check your engine's current guidance and measure.
