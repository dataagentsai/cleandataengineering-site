The run log: what every run writes down

The run log is the platform's diary. Every run of every layer writes what it did: which datasets it touched, which steps ran, how many rows, which files were loaded or held, and which errors it met.

Without it, a question such as why yesterday's order lines are missing can only be answered by reading job output. With it, the answer is one query, and the same records feed freshness, alerts and every screen.

What is recorded, level by level

The table lists the five record kinds. The first column is the record. The second is what one row of it describes. The third lists its fields as the read side returns them.

RecordOne row isFields
RunOne run of one domain in one environmentrun id, domain, environment, trigger, run type, status, start time, end time
Dataset runOne dataset handled inside a runrun id, source, dataset, status, configuration fingerprint, watermark before and after, counts, message, start time, end time
StepOne stage of the pipeline, or one check, for one datasetrun id, source, dataset, step name, status, counts, message, time
FileOne batch that ingestion handledrun id, source, dataset, batch key, file name, window, rows, status, reason, time
ErrorOne error that was caughtrun id, source and dataset when known, step, error class, message, time

Three terms in that table need a definition. A configuration fingerprint is a hash of the dataset's settings at the time of the run, so a later reader can tell which settings a run used. A watermark is the highest change position or time already taken from the source. A batch key is the identity of one delivery, used to recognise the same delivery sent twice.

The one step format

A step is either a pipeline step, such as one ingestion read or one silver stage, or a check result. Check results follow one format so that operations can treat them all alike. The name starts with one of four words and a dot.

Name starts withWritten byMeaningScreen with the detail
detect.The engine: ingestion and the gold harness todayA detector met something in a load, for example detect.DEL-01 for deletes at the sourceSources and ingestion
quality.Data expectation servicesThe verdict of one quality ruleData expectations
recon.Data expectation services, and the live source check after silverOne reconciliation entryData expectations
profile.Ingestion's profiling stepOne profile and whether it driftedData expectations

The status of a check row is the severity operations reads. succeeded reads as passed. warned means the condition was handled, or flagged for a later layer. failed reads as blocked: the load was stopped.

src/dataplatform/obs/steps.py:23The four kinds, who owns each, which screen holds the detail, and how a status is read.
DETECT = "detect"
CHECK_KINDS = ("quality", "recon", "profile")
KINDS = (DETECT, *CHECK_KINDS)
OWNER = {DETECT: "engine", "quality": "des", "recon": "des", "profile": "des"}
SCREEN = {"engine": "sources_ingestion", "des": "des_data_expectations"}  # where the detail lives
SEVERITY = {"succeeded": "passed", "warned": "warned", "failed": "blocked"}
MAX_MESSAGE = 4000
_NAME = re.compile(r"^(detect|quality|recon|profile)\.[A-Za-z0-9][A-Za-z0-9_.:-]{0,127}$")
src/dataplatform/obs/steps.py:48The contract every check row must keep. It returns what is wrong, or an empty list.
def violations(step: str, status: str, counts: Mapping[str, object], message: str) -> list[str]:
    """What breaks the one step format in this row (empty when it keeps it)."""
    out = []
    if not _NAME.match(step):
        out.append(f"step {step!r} is not <detect|quality|recon|profile>.<id>")
    if status not in SEVERITY:
        out.append(f"status {status!r} is not one of {sorted(SEVERITY)}")
    bad = [k for k, v in counts.items() if not isinstance(k, str) or isinstance(v, bool) or not isinstance(v, int)]
    if bad:
        out.append(f"counts {bad} are not name -> integer")
    if not isinstance(message, str) or len(message) > MAX_MESSAGE:
        out.append(f"message is not text of at most {MAX_MESSAGE} characters")
    if status == "failed" and not message:
        out.append("a blocked step says why")
    return out

Walk through it. The name must be one of the four kinds, a dot, and an identifier. The status must be one of the three known words. Every count must be a whole number under a text name, and a true or false value is refused even though Python treats it as a number. The message is text of at most 4000 characters. The last rule is the one people forget: a blocked step must say why.

The recorder: one id from start to finish

The recorder is a helper around the store for code that wants the run, the dataset and the step as nested blocks. Opening a run opens a root trace span. A trace is the record a tracing tool keeps of one piece of work, and a span is one timed part of it. The trace id of that root span becomes the run id.

src/dataplatform/obs/recorder.py:187Opening and closing a run. The run id is the root span's trace id.
    @contextmanager
    def run(self, domain: str, env: str, trigger: str = "manual", run_type: str = "normal") -> Iterator[RunHandle]:
        span = self.tracer.start(f"run {domain}", {"dp.domain": domain, "dp.env": env, "dp.trigger": trigger,
                                                   "dp.run_type": run_type})
        self.store.start_run(span.trace_id, domain, env, trigger, run_type)
        handle = RunHandle(self, span, domain, env)
        try:
            yield handle
        except Exception as exc:
            if id(exc) not in handle.logged:
                self.store.log_error(handle.run_id, None, None, "run", type(exc).__name__, str(exc))
            for ds in list(handle.open):
                if ds.status is None:
                    ds.fail(f"run stopped: {type(exc).__name__}")
            handle.status = self.store.finish_run(handle.run_id)
            span.set({"dp.status": handle.status})
            span.end("error", type(exc).__name__)
            self._finished(handle.run_id)
            raise
        handle.status = self.store.finish_run(handle.run_id)
        span.set({"dp.status": handle.status})
        span.end("error" if handle.status in ("failed", "partial") else "ok")
        self._finished(handle.run_id)

Walk through it. A root span starts, and its trace id is passed to the store as the run id. The block's body then runs. If the body raises, the error is logged against the run unless a dataset already logged it, every dataset still open is closed as failed, the run is finished, the hooks are called, and the error is raised again. If the body ends normally, the store works out the run's status from its dataset runs. A run with one failed dataset out of two comes back as partial. Either way the on_finish hooks receive the run id last.

src/dataplatform/obs/recorder.py:76A step as a block. An exception inside it becomes a failed step row, then travels on.
    @contextmanager

        try:
            yield handle

            span.end("error", type(exc).__name__)
            raise
        self._log(name, handle.status, handle.counts, handle.message)
        span.set({f"dp.count.{k}": v for k, v in handle.counts.items()})
        span.end()
src/dataplatform/obs/recorder.py:89How a check and a detector become step rows in the one format.
    def check(self, kind: str, name: str, passed: bool, counts: dict[str, int] | None = None,
              message: str = "", warn_only: bool = False) -> None:
        """A quality rule, a reconciliation entry or a profile: its verdict as a step of this dataset run."""
        if kind not in CHECK_KINDS:
            raise ValueError(f"check kind {kind!r} is not one of {CHECK_KINDS}")
        status = "succeeded" if passed else ("warned" if warn_only else "failed")
        self._log(f"{kind}.{name}", status, counts, message or ("" if passed else f"{kind}.{name} did not pass"))

    def detect(self, detector: str, counts: dict[str, int] | None = None, message: str = "",
               blocked: bool = False) -> None:
        """A detector fired (DAC id, e.g. DEL-01). Handled is warned; blocked (the load stopped) is failed."""
        self._log(f"{DETECT}.{detector}", "failed" if blocked else "warned", counts,
                  message or f"{detector} {'blocked the load' if blocked else 'handled'}")
        self.span.set({f"dp.detect.{detector}": "blocked" if blocked else "handled"})

A check that did not pass is failed unless the caller said it should only warn. A detector that fired is warned when the platform handled the condition and failed when it blocked the load.

Tracing wrapped around the store

The ingestion, silver and gold runners were written before the recorder and call the store directly. To trace them without changing them, the store itself is wrapped. The wrapper forwards every call and adds a span for each run, dataset run and step.

src/dataplatform/obs/traced_store.py:29Five calls are intercepted. Every other call goes straight through.
    def __getattr__(self, name: str) -> Any:  # every other operation goes straight through
        return getattr(self._store, name)

    def start_run(self, run_id: str, domain: str, env: str, trigger: str = "manual", run_type: str = "normal") -> None:
        self._store.start_run(run_id, domain, env, trigger, run_type)
        self._runs[run_id] = self._tracer.start(f"run.{trigger}", {RUN_TAG: run_id, "domain": domain, "env": env,
                                                                   "run_type": run_type})

    def start_dataset_run(self, run_id: str, source: str, dataset: str, config_fingerprint: str,
                          config: dict[str, Any]) -> None:
        self._store.start_dataset_run(run_id, source, dataset, config_fingerprint, config)
        parent = self._runs.get(run_id)
        if parent is not None:
            self._datasets[(run_id, source, dataset)] = parent.child(
                f"dataset.{source}.{dataset}", {RUN_TAG: run_id, "fingerprint": config_fingerprint})

    def log_step(self, step: StepRecord) -> None:
        self._store.log_step(step)
        parent = self._datasets.get((step.run_id, step.source, step.dataset))
        if parent is not None:
            span = parent.child(f"step.{step.step}", {RUN_TAG: step.run_id, **{f"count.{k}": v for k, v in
                                                                              step.counts.items()}})
            span.end("error" if step.status == "failed" else "ok", step.message[:200])
src/dataplatform/obs/traced_store.py:59Finishing a run ends its span and pushes the run id to the hooks.
    def finish_run(self, run_id: str) -> str:
        status = self._store.finish_run(run_id)
        span = self._runs.pop(run_id, None)
        if span is not None:
            span.set({"status": status})
            span.end("error" if status == "failed" else "ok", status)
        for hook in self._on_finish:
            hook(run_id)
        return status

Two details matter. First, here the run id is the one the runner chose, and it is put on every span as the tag dp_run_id. The trace id is the tracer's own. Second, the hooks are called after the store has finished the run, so the monitor reads a complete record.

src/dataplatform/obs/trace.py:63The same 128 bits written as a UUID, the form lineage events want for a run id.
def as_uuid(trace_id: str) -> str:
    """The run id in the UUID form lineage events want for their run id (same 128 bits)."""
    if not valid_trace_id(trace_id):
        raise ValueError(f"not a trace id: {trace_id!r}")
    return str(uuid.UUID(hex=trace_id))

The settings that drive it

The run log reads no settings from the metadata store. What it records is fixed by the code. The only choices are made by the binding, which is the script that picks adapters: which store, which clock, and which tracer.

Not built yet, or known gaps
  • The recorder, with its run id equal to the trace id, is not used by the ingestion, silver or gold runners. They record through the store with their own run ids, and the tracing wrapper links the two by a tag.
  • The tracing wrapper's start_dataset_run does not hand back the watermark that the store returns. No runner reads that return value today, so nothing breaks, but the wrapper is not a perfect stand-in for the store.
  • Silver does not yet write detect. rows for the conditions it handles. They are judged on what the silver tables hold.
  • Silver records all its stages together after the run, so the time of a whole silver run shows on its first stage in the step timings.
