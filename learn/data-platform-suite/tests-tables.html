Table-driven tests and port contract tables

Almost every test in this platform is a table. One test function holds the logic of the check. A table beside it holds the cases, one per row: a name, an input and the expected result.

The reason is readability. A reader sees every case a function is proven on at a glance, and adding a case means adding one row. A failing case is reported by its name.

Contract tables for ports

A port is an interface the platform's core calls, such as the bronze writer. An adapter is one implementation of it for one product. The core is only safe to move between products if every adapter behaves the same. A contract table states that behaviour once, and the test runs every row against every adapter.

        with pytest.raises(expect):
            act(w)
    else:

The two decorators above the function are the whole mechanism. One lists the adapters and the other the cases, and the test framework runs every combination. An adapter that is not available on the machine, such as PostgreSQL with no local server, is skipped with the reason.

The history contract

Silver can run on two engines, the job engine and the declarative engine. They store history differently. Type 2 history keeps one row per version of a key. To make sure both engines mean the same thing, the cases are held in a file of pure data that names no engine.

The engines also differ in how they store a deleted key. The job engine keeps the last version current and flags it deleted. A managed change-capture engine closes the version. So each engine's output is first brought to one common shape, and then compared.

src/dataplatform/silver/history_contract.py:53Bringing an engine that closes deleted versions to the contract's shape.
def normalise_closed(rows: Iterable[Mapping[str, Any]], key: str, value: str, start: str, end: str) -> list[Version]:
    """An engine that closes a deleted key's last version (end set, nothing after it): the last version of a key is
    'current'; it is 'deleted' when it is closed."""
    by_key: dict[Any, list[Mapping[str, Any]]] = {}
    for r in rows:
        by_key.setdefault(r[key], []).append(r)
    out: list[Version] = []
    for k in sorted(by_key):
        vs = sorted(by_key[k], key=lambda r: int(r[start]))
        for i, r in enumerate(vs):
            last = i == len(vs) - 1
            out.append((str(k), int(r[value]), int(r[start]), last, last and r[end] is not None))
    return out

The option is --engine spark, which is the default, or --engine duckdb. The engine cannot be chosen per test, because the DuckDB library takes the place of the Spark imports for the whole process. So conformance is two test processes over the same files.

The recorded result is in the DuckDB design note. On 5 November 2026, 143 stage and gold-build cases passed on Spark and the same 143 passed on DuckDB. Spark took 74 seconds and DuckDB 133 seconds. Getting there took 13 rewrites into forms both engines read the same way, and the note lists each. Four cases pin known differences between the engines, such as how a record hash treats empty fields, which is why one table is always written by one engine.

How the tests themselves are kept honest

RuleWhere it shows
A check with nothing to compare is never a passThe reconciliation function fails a hop with no value.
Pending is said, not hiddenAn adapter or layer that does not exist yet is a skipped row with its reason.
The core names no productSeveral test files scan the core's source for product names and fail on any.
Generated files are checked for driftA test regenerates the dashboard and view files and compares them.
Not built yet, or known gaps
  • The history contract runs against the job engine in the test suite. The declarative engine's run of the contract is in the spikes folder and needs a workspace. It is not part of the tests.
  • The gold tables contract has one adapter, so it proves that adapter and not yet that two agree.
  • The silver tables contract runs on Spark. The DuckDB silver adapter is exercised by the end to end run, not by this contract table.
  • Conformance covers four test files. The day-by-day golden tests run on Spark only in the test suite.
  • The design note says continuous integration runs the DuckDB conformance step. The public snapshot contains no workflow folder, so I could not verify that from the repository. The Makefile target exists.
