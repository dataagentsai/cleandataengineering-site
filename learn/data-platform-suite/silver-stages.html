The thirteen stages and the stage runner

Between bronze and silver every dataset passes the same thirteen stages in the same order. A stage is a plain function: it receives rows and the dataset's plan, and it returns rows. It never reads a table, never writes one and never looks at the clock.

Without a fixed list each table would grow its own cleaning job, and nobody could say what silver guarantees. With the list, one table of test cases per stage proves the behaviour once, and the only thing that differs between datasets is their settings.

The stages at a glance

Each line of this table is one stage. The fourth column says whether a dataset may switch the stage off. The last column says which rows the stage can set aside in the quarantine table. To quarantine a row means to take it out of the batch and store it with the reason, so that the good rows go on.

No.StageWhat it doesCan be switched offWhat it can quarantine
1Contract checkChecks that every contract column the plan keeps is present. A missing column stops the dataset run.NoNothing. It stops the whole run instead.
2ProjectPicks the columns, renames them to their contract names, extracts columns held in _extra, leaves out excluded columns.NoNothing.
3HygieneCleans text: byte-order mark, control characters, line endings, spaces at the ends, runs of spaces, empty text to a missing value.YesNothing.
4Parse and typeCasts each column to the contract's type. A value that does not convert is never silently lost.YesRows with a value that does not convert, unless the column says to empty the value instead.
5TimeAdds the local wall-clock time beside a timestamp when the column asks for it.YesNothing.
6StandardiseApplies declared value maps and upper or lower case.YesNothing.
7Personal dataChecks that every restricted column holds tokens, never the plain value.YesRows with a plain value in a restricted column.
8Row filterDrops rows that a declared filter does not want, and counts them.NoNothing. Dropped rows are counted, not stored.
9QualityRuns the row rules. The rule's severity decides whether a failing row is quarantined or kept with a flag.NoRows that break a rule whose action is quarantine. A critical failure also holds the batch.
10DuplicatesRemoves repeats inside the batch and, for appended events, rows already in silver.YesNothing. Dropped and replayed rows are counted.
11KeysChecks that every part of the business key is present and adds the key hash.NoRows with an empty key part.
12HistoryLays the rows out as versions, latest state, appended events or snapshots, by the kind of dataset, and marks deletes.NoOnly for datasets whose source keeps the versions itself: keys whose versions overlap or leave a gap.
13ProvenanceStamps the silver run, the load time and a record hash, and puts the columns in a fixed order.NoNothing.

What a stage is

Three small definitions in one file describe every stage. StageCtx is what a stage is told besides the rows. Out is what it gives back. Stage is the shape of the function itself.

src/dataplatform/stages/common.py:22What every stage receives besides the rows.
@dataclass(frozen=True)
class StageCtx:
    plan: SilverPlan
    current: DataFrame | None  # silver as it stands; None before the first write
    run_id: str
    as_of: str  # the business date of the run (ISO)
    loaded_at: datetime | None = None  # when the write edge takes the rows (passed in: no clock inside a stage)
FieldWhat it is
planThe dataset's plan: columns, keys, history kind, rules. It is frozen, so no stage can change it.
currentThe silver table as it stands, handed over by the read edge. It is None before the first write. A stage may join with it. Only the duplicates and history stages do.
run_idThe id of this silver run. The provenance stage stamps it on every row.
as_ofThe business date of the run, as text. The duplicates stage counts its lookback back from this date, not from today's date.
loaded_atThe load time, read from the clock once by the adapter and passed in. A stage that read the clock itself would give different rows on every run and could not be tested with fixed answers.
src/dataplatform/stages/common.py:31What every stage returns, and the type of a stage.
@dataclass
class Out:
    df: DataFrame
    quarantine: DataFrame | None = None  # QUARANTINE_COLUMNS
    tally: dict[str, DataFrame] = field(default_factory=dict)  # name -> rows to count (dropped, emptied, ...)


Stage = Callable[[DataFrame, StageCtx], Out]

df is the rows that go on to the next stage. quarantine is the rows this stage set aside, or nothing. tally is a dictionary of named frames whose rows are to be counted, for example the rows a filter dropped. A stage hands over frames to count, not numbers, because counting runs a job, and a pure function should not run jobs. The adapter counts them all at once at the end.

The order is checked when the module is imported, so a build with a stage missing, added or moved fails before any data is read. The order itself follows from what each stage needs from the ones before it. The table gives the reason for each position.

PositionWhat the position gives
Contract check firstEvery later stage addresses columns by name. A missing column must stop the run with a clear message, not fail somewhere in the middle with an engine error.
Project secondAfter it, every column carries its contract name, so all later stages and all rules can use contract names only. It also creates the _dq_flags column that later stages add to.
Hygiene before parse and typeThe text ' 42 ' is trimmed before it is cast to a number, and empty text becomes a missing value before the cast, so neither counts as a failed cast.
Parse and type before time, standardise and qualityThe time stage needs real timestamps. The rules in the quality stage compare typed values, for example a quantity with zero.
Standardise before qualityA rule that lists the valid values of a column sees the values after the value map and the letter case were applied.
Personal data, row filter and quality before duplicatesA row that is set aside or dropped takes no part in choosing which of two duplicates is kept.
Keys before historyHistory groups and joins on the key hash that the keys stage adds.
Provenance lastIt stamps the run and fixes the column order after history has added its own columns.

A dataset switches a stage off with the setting processor_groups.<group> set to disabled. The group names differ from the stage names because the setting keys were kept from an earlier framework. The other seven stages have no switch and always run.

The comparison is with the exact word disabled. The settings registry also allows enabled, opt_in and dataset_decides for these keys, with no default. The plan treats all three, and a missing setting, the same way: the stage runs. How a setting's value is chosen between the default, the domain and the dataset is on the settings page.

How the stages are chained

src/dataplatform/stages/__init__.py:53The whole stage runner. It is a loop over the fixed tuple.
def run_stages(
    plan: SilverPlan,
    bronze: DataFrame,
    current: DataFrame | None,
    run_id: str,
    as_of: str,
    loaded_at: datetime | None = None,
    hold: Callable[[DataFrame], DataFrame] | None = None,
) -> tuple[DataFrame, DataFrame | None, dict[str, DataFrame]]:
    """Every stage in order; a stage the plan switches off is skipped. Returns the rows to write, the quarantined
    rows of every stage, and the frames to count, named <stage>.<what>. `hold`, when the engine adapter passes one,
    fixes each stage's output before the next stage reads it (an engine that compiles a frame's whole lineage into
    one query, as SQLFrame does, otherwise recompiles every earlier stage at every step; docs/DUCKDB-SPIKE.md)."""
    ctx = StageCtx(plan, current, run_id, as_of, loaded_at)
    df = bronze
    held: list[DataFrame] = []
    tally: dict[str, DataFrame] = {}
    for name in STAGES:
        if not plan.runs(name):
            continue
        out = FUNCTIONS[name](df, ctx)
        df = out.df if hold is None else hold(out.df)
        if out.quarantine is not None:
            held.append(out.quarantine)
        tally.update({f"{name}.{k}": v for k, v in out.tally.items()})
    quarantine = reduce(lambda x, y: x.unionByName(y), held) if held else None
    return df, quarantine, tally
  1. Build the context. One StageCtx is made from the plan, silver as it stands, the run id, the business date and the load time. Every stage receives the same one.
  2. Start from bronze. df starts as the new bronze rows.
  3. Walk the tuple. For each stage name in STAGES, the runner asks plan.runs(name). A switched-off stage is skipped and df passes through untouched.
  4. Call the stage. The function is looked up by name and called with the rows and the context. Its df becomes the input of the next stage.
  5. Collect the quarantine. If the stage set rows aside, that frame is added to a list.
  6. Collect the counts. Each frame in the stage's tally is kept under the name <stage>.<what>, for example duplicates.dropped.
  7. Return three things. The rows to write, one quarantine frame made by stacking the list, and the dictionary of frames to count.

Nothing has been computed when run_stages returns. On Spark a frame is a recipe, and the thirteen stages have only extended the recipe. The work happens later, when the adapter asks for the rows.

What a quarantine row holds

Four stages can set rows aside: parse and type, personal data, quality and keys. History can do it for one kind of dataset. They all use the same helper, so every quarantine row has the same five columns whatever stage made it. That is what lets the runner stack them with unionByName.

src/dataplatform/stages/common.py:41The helper that splits a frame into good rows and quarantine records.
def quarantine_rows(
    df: DataFrame, reason: Column, stage: str, record: list[str] | None = None
) -> tuple[DataFrame, DataFrame]:
    """Split a frame on `reason` (null = good row): (good rows, quarantine records keeping every original value of
    the `record` columns, all columns by default)."""
    marked = df.withColumn("_q_reason", reason)
    good = marked.where(F.col("_q_reason").isNull()).drop("_q_reason")
    data = list(record if record is not None else df.columns)
    bad = marked.where(F.col("_q_reason").isNotNull()).select(
        F.lit(stage).alias("_stage"),
        F.col("_q_reason").alias("_reason"),
        (F.col("_batch_key") if "_batch_key" in df.columns else F.lit(None).cast("string")).alias("_batch_key"),
        (F.col("_source_file") if "_source_file" in df.columns else F.lit(None).cast("string")).alias("_source_file"),
        F.to_json(F.struct(*[F.col(c) for c in data])).alias("_record"),
    )
    return good, bad

Walk through it. The stage passes a column expression called reason. It is text for a bad row and null for a good row. The helper adds it as a working column, keeps the rows where it is null as the good rows, and turns the others into records. Each record carries the stage name, the reason, the batch and the file the row came from, and the row itself as one JSON text. The record argument says which columns go into that JSON. By default it is all of them.

ColumnWhat it holds
_stageThe stage that set the row aside, for example parse_type.
_reasonEvery check the row failed, in plain text.
_batch_keyThe bronze batch the row came from, or null if the frame has no such column.
_source_fileThe file the row came from, or null.
_recordThe whole row as JSON text, with the values as they were when the stage looked at them.
src/dataplatform/stages/common.py:59How several failed checks on one row become one reason text.
def reasons(parts: list[tuple[Column, str]]) -> Column:
    """One text naming every failed check, or null when none failed."""
    if not parts:
        return F.lit(None).cast("string")
    texts = [F.when(cond, F.lit(text)) for cond, text in parts]
    joined = F.concat_ws("; ", *texts)
    return F.when(joined == "", F.lit(None)).otherwise(joined)

A stage builds a list of pairs: a condition that is true when the check failed, and the text that names the failure. reasons turns each pair into a column that is the text when the condition holds and null otherwise. concat_ws joins the texts and skips the nulls, so a row that failed two checks gets both texts, and a row that failed none gets an empty text. The last line turns that empty text into null, which is the sign of a good row.

ExampleOne quarantine record for an order line whose quantity was sent as 4.5. The values are made up.
_stage       parse_type
_reason      ordered_qty is not a integer
_batch_key   2026-11-09T10:15|3f9a...
_source_file sales_order_line_1015.json
_record      {"order_id":"SO-1002","line_no":"10","ordered_qty":"4.5", ... }

How the counts are collected

The stage runner returns frames, not numbers. The adapter turns them into the counts that go to the run log. This table lists every count name the code can produce.

CountWhere it comes from
rows_inThe adapter counts the bronze rows it was given.
rows_out, rows_removedThe adapter groups the final rows by their _action: upsert and delete.
<stage>.quarantinedThe adapter groups the quarantine records by their _stage column.
parse_type.emptiedRows where a value was emptied instead of quarantined.
row_filter.droppedRows a declared filter dropped.
quality.flagged, quality.criticalRows kept with a flag, and rows that broke a critical rule.
duplicates.dropped, duplicates.replayedRepeats inside the batch, and rows already in silver.
src/dataplatform/silver/runner.py:191After a successful write the runner logs one step per stage that has counts.
    for stage in STAGES:
        mine = {k.split(".", 1)[1]: v for k, v in counts.items() if k.startswith(f"{stage}.")}
        if mine:

The runner cuts the stage name off each count and writes one step record per stage. The step's status is warned when the stage quarantined or emptied anything, and succeeded otherwise.

The hold argument

run_stages takes an optional function called hold. When it is given, the runner passes each stage's output through it before the next stage reads it. Its job is to fix the rows in place, so that the next stage starts from stored rows and not from a recipe.

Spark does not need it and passes nothing. The DuckDB adapter does need it. There, every frame is one SQL query, and each stage would make the query of all earlier stages longer. The adapter passes a function that runs the query once into a table.

src/dataplatform/adapters/duckdb_silver.py:67The DuckDB adapter passes its checkpoint function as hold.
            rows, quarantine, tally = run_stages(plan, bronze, current, run_id, as_of, datetime.now(UTC),
                                                 hold=checkpoint if self.hold_each_stage else None)

The design note docs/DUCKDB-SPIKE.md records the effect: holding each stage's output halved the time of the stage tests on DuckDB, from 194 seconds to 92 seconds, and without any hold a history test over three batches did not finish in five minutes.

How the Spark adapter calls the stage runner

src/dataplatform/adapters/spark_silver.py:92The adapter between the silver runner and run_stages on Spark.
class SparkStageRunner:
    """stage_runner on PySpark: the stages' frames are checkpointed once so the counts and the write read the same
    rows (and a merge into the table the stages read from sees a fixed input)."""

    def __init__(self, cache: bool = True):
        self.cache = cache  # serverless refuses cache() (PERSIST TABLE, probed 13 Nov): off there

    def run(self, plan: SilverPlan, bronze: DataFrame, current: DataFrame | None, run_id: str,
            as_of: str) -> StageResult:
        if self.cache:
            bronze = bronze.cache()
        rows, quarantine, tally = run_stages(plan, bronze, current, run_id, as_of, datetime.now(UTC))
        try:
            rows = rows.localCheckpoint(eager=True)
        except Exception as exc:  # an engine error on this batch's data (e.g. a cast the plan did not foresee)
            if self.cache:
                bronze.unpersist()
            raise StageError(f"{plan.table}: {type(exc).__name__}: {str(exc)[:500]}") from exc
        counts = {"rows_in": bronze.count()}
        by_action = {r["_action"]: r["n"] for r in rows.groupBy("_action").agg(F.count(F.lit(1)).alias("n")).collect()}
        counts["rows_out"] = int(by_action.get("upsert", 0))
        counts["rows_removed"] = int(by_action.get("delete", 0))
        # everything else counted in one job: quarantine per stage and each tally (dropped, replayed, emptied, ...)
        parts = [f.select(F.lit(name).alias("_what")) for name, f in tally.items()]
        if quarantine is not None:
            parts.append(quarantine.select(F.concat(F.col("_stage"), F.lit(".quarantined")).alias("_what")))
        counts.update({name: 0 for name in tally})
        if parts:
            for r in reduce(lambda x, y: x.unionByName(y), parts).groupBy("_what").count().collect():
                counts[str(r["_what"])] = int(r["count"])
        if self.cache:
            bronze.unpersist()
        return StageResult(rows, quarantine, counts)
  1. Cache bronze. The new bronze rows are cached, because they are read several times below. The cache can be turned off, because serverless compute refuses it.
  2. Read the clock once. datetime.now(UTC) is passed as the load time. This is the only place the clock is read.
  3. Run the recipe once. localCheckpoint(eager=True) computes the final rows now and keeps them. The counts and the write then read the same rows. It also matters for the merge: the stages read the silver table, and a merge into that same table must see a fixed input.
  4. Turn engine errors into a stage error. If Spark fails on the data, the adapter raises StageError with the first 500 characters of the message. The silver runner knows what to do with that error.
  5. Count the rows. Bronze rows in, then the final rows grouped by action.
  6. Count everything else in one job. Each tally frame is reduced to one column holding its name. The quarantine frame is reduced to its stage name with .quarantined added. All of them are stacked and grouped once. Every tally name starts at zero, so a count that found nothing is still reported.
  7. Return. A StageResult with the rows, the quarantine frame and the counts.
src/dataplatform/silver/runner.py:172What the silver runner does with a StageError.
    except StageError as exc:
        return _fail(store, run_id, view, "silver.stages", exc)

A StageError from any stage fails the dataset run at the step silver.stages. Nothing is written and the bookmark does not move, so the next run takes the same batches again. The reader page explains the bookmark.

The design decisions behind this page

DecisionWhat it meansWhy
Stages are pure functionsFrames in, frames out. No reads, no writes, no clock.The same functions run on Spark and on DuckDB, and a test needs only a few rows in memory.
The order lives in one tupleThe kernel owns the list. An engine must supply exactly these names in this order.An engine cannot quietly leave a stage out.
Switches are settings, not codeSix stages can be skipped per dataset by a registered setting.A dataset never needs its own version of the pipeline.
Bad rows are set aside with a reasonA row that fails a check goes to quarantine. The good rows of the same batch go on.One bad record must not stop a load, and nothing may disappear without a trace.
Not built yet, or known gaps
  • On Spark only the final rows are checkpointed. The quarantine frame is computed again when it is counted and again when it is written. The DuckDB adapter checkpoints both.
  • There is no setting that adds a stage or changes the order. That is deliberate, but it means a dataset with a special need has to be handled before bronze or after silver.
  • The settings registry also has the keys processor_groups.provenance and processor_groups.case_normalize. No code reads them, so setting them changes nothing.
  • Rows dropped by the row filter and the duplicates stage are counted but not stored anywhere.
