The facts the harness builds

A fact holds the numbers people add up. The harness builds every fact the same way: it calls the fact's model over the silver inputs, and replaces the windows whose content changed.

A reader coming from other platforms may expect a setting that names the kind of fact, such as transaction, periodic snapshot or accumulating snapshot. This harness has no such setting. There is one kind of fact build. What makes facts differ is the model, the grain and the window. The tyre company has three facts, and between them they cover three common shapes.

The three facts side by side

Each row is one fact. The columns say what one row of the fact means, which silver tables it reads, the window it is rebuilt by with the lookback in brackets, and what kind of model it has.

How a model is called

src/dataplatform/adapters/spark_gold.py:166The harness calls the model through one method, whatever kind it is.
    def build(self, plan: GoldPlan, inputs: dict[str, DataFrame], params: dict[str, str]) -> DataFrame:
        if plan.build_kind == "sql":
            text = (self.models_root / plan.build_ref).read_text()
            for name, df in inputs.items():
                df.createOrReplaceTempView(_safe(name))
            return self.sql(text, {k: v for k, v in params.items() if f":{k}" in text})
        fn = self._function(plan.build_ref)
        return fn(dict(inputs), dict(params))

For a SQL model, each input frame is registered as a view under its name, the file is read, and the query is run with the parameters the text actually uses. The parameters are bound by the engine, never pasted into the text. For a dataframe model, the function is loaded from the models folder and called with the frames and the parameters. Both kinds return one frame and neither may read or write anything.

fact_otif: a row that changes as deliveries arrive

OTIF stands for on time in full. One row is one open order line. It says whether the line was delivered by the date first promised, and whether the full quantity arrived.

models/tyre/gold/sales/fact_otif.sql:31The judging step and the final select of the model.
judged AS (
    SELECT o.order_id, o.line_no, o.dealer_code, o.material_code, o.ordered_qty, o.order_ts,
           f.promised_date,
           COALESCE(d.delivered_qty, 0) AS delivered_qty,
           COALESCE(TO_DATE(FROM_UTC_TIMESTAMP(d.delivered_ts, :business_tz)) <= f.promised_date, FALSE) AS on_time,
           COALESCE(d.delivered_qty, 0) >= o.ordered_qty AS in_full
    FROM open_lines AS o
    INNER JOIN first_promise AS f ON o.order_id = f.order_id AND o.line_no = f.line_no
    LEFT JOIN delivered AS d ON o.order_id = d.order_id AND o.line_no = d.line_no
)

SELECT order_id, line_no, dealer_code, material_code, promised_date, ordered_qty, delivered_qty,
       on_time, in_full,
       CASE WHEN on_time AND in_full THEN 1 ELSE 0 END AS on_time_in_full,
       order_ts
FROM judged

The row for an order line exists as soon as the order does, with a delivered quantity of 0 and both flags false. When deliveries arrive, the same row is rebuilt with the new quantity and flags. A delivery counts on its local date: the delivery time is moved to the business time zone before it is compared with the promised date. Cancelled and rejected lines are left out, because the earlier step keeps only lines whose status is open.

How it is rebuilt. The window is the promised date, one day at a time, and each run recomputes the last 35 days of promised dates. A delivery that arrives three weeks after its promised date still lands in the right day. A promised date in the future is published but flagged incomplete, because the day is not over. The fact allows corrections, so a recorded correction to a promised date is laid over silver before the model runs.

fact_sales: a total per month from two sources

One row is one dealer, one material and one month. It holds what the company sold to the dealer, called sell-in, and what the dealer reported selling on, called sell-out.

models/tyre/gold/sales/fact_sales.sql:6Two totals per dealer, material and month, joined so that a row exists if either side has one.
WITH sell_in AS (
    SELECT dealer_code, material_code,
           CAST(DATE_TRUNC('MONTH', FROM_UTC_TIMESTAMP(order_ts, :business_tz)) AS DATE) AS sale_month,
           SUM(ordered_qty) AS units_sold_in,
           SUM(net_value) AS net_value
    FROM erp__sales_order_line
    WHERE _is_current AND NOT _is_deleted AND line_status = 'open'
    GROUP BY 1, 2, 3
),

sell_out AS (
    SELECT dealer_code, material_code,
           CAST(DATE_TRUNC('MONTH', sale_month) AS DATE) AS sale_month,
           SUM(units_sold) AS units_sold_out
    FROM partner__dealer_sellout
    WHERE _is_current AND NOT _is_deleted
    GROUP BY 1, 2, 3
)

SELECT COALESCE(i.dealer_code, o.dealer_code) AS dealer_code,
       COALESCE(i.material_code, o.material_code) AS material_code,
       COALESCE(i.sale_month, o.sale_month) AS sale_month,
       COALESCE(i.units_sold_in, 0) AS units_sold_in,
       COALESCE(o.units_sold_out, 0) AS units_sold_out,
       CAST(ROUND(COALESCE(i.net_value, 0), 2) AS DOUBLE) AS net_value
FROM sell_in AS i
FULL OUTER JOIN sell_out AS o
    ON i.dealer_code = o.dealer_code AND i.material_code = o.material_code AND i.sale_month = o.sale_month

Sell-in comes from order lines, counted in the local month of the order time. Sell-out comes from the file each dealer sends once a month. A dealer who resends a month replaces that month in silver, so the model reads only the current rows. The two sides are joined with a full outer join. A dealer with orders but no file yet still gets a row, with sell-out 0, and the other way round.

An example. The inputs are on the left and the fact row on the right.

Order linesDealer fileunits_sold_inunits_sold_out

D-1, M-1, 7 tyres in NovemberD-1, M-1, November, 3 sold73

How it is rebuilt. The window is the sale month and each run recomputes the last 3 months. A month stays flagged incomplete until every dealer who owes a file for it has sent one. When the last file arrives, the month is replaced and logged as a restatement. Windows and completeness follows that case through.

fact_scrap: a total per hour, where single rows can wait

One row is one press, one material and one hour. It holds the tyres cured and the tyres scrapped at inspection. Reworked tyres are not scrap.

models/tyre/gold/manufacturing/scrap.py:20The one dataframe model of the tyre company.
def build(inputs: dict[str, DataFrame], params: dict[str, str]) -> DataFrame:
    """The build signature every dataframe build shares (D18); scrap needs no parameter (cure_hour is an instant)."""
    del params
    production = _current(inputs["mes__production"])
    results = (
        _current(inputs["lims__inspection_result"])
        .groupBy("production_id")
        .agg(F.sum("tyres_scrapped").alias("scrapped"))
    )
    rows = production.join(results, "production_id", "left")
    return (
        rows.groupBy("press_id", "material_code", F.date_trunc("hour", "cured_ts").alias("cure_hour"))
        .agg(
            F.sum("tyres_cured").cast("long").alias("tyres_cured"),
            F.sum(F.coalesce(F.col("scrapped"), F.lit(0))).cast("long").alias("tyres_scrapped"),
            F.min(F.col("scrapped").isNotNull().cast("int")).cast("boolean").alias("_input_complete"),
        )
    )

Production rows are joined to the inspection results by a left join, so an hour of production appears even before its inspection is filed. The last aggregate is the interesting one. It computes _input_complete, which is true only if every production row of that press and hour has an inspection result. The harness reads that column. A row that says it is still waiting is flagged incomplete on its own, even if its window is otherwise complete. The column is not in the contract and is dropped before the write.

An example. The inputs are on the left and the fact row on the right.

How it is rebuilt. The window is the cure hour, an instant in UTC, and each run recomputes the 48 hours up to the end of the business date. This fact does not allow corrections.

Why the row-level flag exists

The full-scale attempt of 4 November 2026 found the reason. One plant's lab files were held back by a planted incident, and the whole hour was flagged incomplete, including the rows of another plant whose files had arrived. The numbers were equal to the oracle and only the flag differed. The fix was to let a model say per row whether its own input has arrived. The run of 5 November at one tenth of full scale confirmed it. Both are recorded in docs/W1D-GOLD.md.

Not built yet, or known gaps
  • There is no setting for the kind of fact, and no build that appends new rows only. Every fact is recomputed by window and replaced. A very large fact of pure events would pay for that.
  • No fact reads the press readings stream. A press-hour fact from readings would be a fourth model with an hour window.
  • The cure hour is the UTC hour of the curing time. The plants' time zones are declared nowhere the platform reads, so plant-local hours and shifts cannot be built.
  • Net sales value is built into fact_sales, but its measure in the semantic layer is still a draft.
  • A model's purity is not enforced at run time. It is checked by a static scan of the models folder before a change is merged.
