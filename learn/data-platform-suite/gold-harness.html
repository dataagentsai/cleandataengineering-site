The gold harness, step by step

The harness is the code that builds a gold table from its plan. For a fact it does everything except the business logic: it reads the inputs, calls the model, attaches dimension keys, decides which windows to rebuild, checks the result, writes it, and records what happened.

It exists so that the hard parts are written once. Without it, every fact would have its own handling of reruns, late rows and missing dimension members, and each would be wrong in its own way.

One fact build, in the order the code runs

  1. Read the table's bookmarks. The fact's own bookmarks say how far it has published and which correction plans it has already applied.
  2. Read each input. For every input the harness notes the silver table's version, reads every row silver holds, lays active corrections over the rows if the fact allows corrections, and works out how far that input has loaded in source time.
  3. Record what was read. Two rows go to the run log: the version of each input, and the text of the model with its parameter values. A past window can be rebuilt later from these two rows alone.
  4. Call the model. The model returns one row per grain with business keys and measures.
  5. Look up the keys. Each dimension's key is attached by a left join as of the event time. The row count before and after must be equal. The row ledger is written.
  6. Choose the windows. The range is the lookback from the business date, plus windows a correction plan names, plus published windows that still hold rows on the unknown member.
  7. Decide completeness. Each window in the range is complete only if every input has loaded past the window's end.
  8. Finish the rows. The harness adds _is_complete and _run_id, and puts the columns in contract order.
  9. Check. The grain must be unique, the share of rows on the unknown member must be under the limit, and the totals must equal the model's totals. A failure stops here and nothing is written.
  10. Replace what changed. A digest of each window's content is compared with the published window. Only windows whose digest differs are replaced, in one transaction.
  11. Log restatements. A changed window that readers had been entitled to treat as final is logged as a restatement, with its numbers before and after.
  12. Move the bookmarks. The input watermarks, how far gold has published, and the plans applied are saved together with the success status.

What it reads from silver, and how

The read edge hands over every row silver holds for an input: every version of every key, with deleted rows marked. It does not filter to the current rows and it does not read only what changed since last time. The model decides which rows it wants. An input that silver has never written comes back as an empty table with the right columns, so a fact can be built before all of its inputs have delivered.

Walk through the loop. silver_version records the table version that was read. silver reads the rows. The lines about plans deal with corrections and withdrawn batches, which Windows and completeness explains. The frame is stored under the name the model will see, the source and dataset joined by two underscores. The last lines pick one of two ways to say how far the input has loaded. If ingestion keeps one bookmark per feed, for example one per dealer file, those are used. Otherwise the input has one watermark.

src/dataplatform/gold/harness.py:102How far an input has loaded: the end of the newest business day whose delivery silver has taken.
def silver_watermark(store: MetadataStore, dataset: str, tz: str) -> datetime | None:
    """How far an input has loaded in source time (ADR-018): the end of the newest delivery window silver has taken
    (silver's bookmark counts the file records it took; an empty delivery still moves it)."""
    source, name = dataset.split(".", 1)
    taken = int(store.bookmarks(source, name).get(SILVER_BOOKMARK, "0"))
    days = [f.window for f in store.dataset_files(source, name)[:taken] if f.status == "loaded" and f.window]
    return W.day_end(max(days), tz) if days else None

A watermark here is the latest point in source time up to which an input is known to be loaded. It is not read from the data. It comes from the metadata store: silver's bookmark says how many file log records it has taken, the harness looks at the delivery window of each loaded record among those, and takes the end of the newest day. An empty delivery still moves it, which is right, because a day with no orders is still a day that has been loaded.

Where the as-of join on version validity happens

Silver keeps type 2 history: each version of a dealer has a span during which it was true. Gold uses that span in one place, the key lookup. The dimension build copies silver's span into valid_from and valid_to on each member. The key lookup then joins each fact row to the member whose span contains the fact's event time. This is called an as-of join: the row gets the dealer as the dealer was at that moment.

src/dataplatform/adapters/spark_gold.py:191The key lookup on Spark: one left join per dimension, on the business key and the validity span.
    def add_keys(self, plan: GoldPlan, facts: DataFrame, dimensions: dict[str, DataFrame]) -> DataFrame:
        out = facts
        for i, d in enumerate(plan.dimensions):
            dim = dimensions[d.name].where(F.col(d.key) >= 0)
            names = {c: f"_d{i}_{c}" for c in (d.key, *d.business_key, "valid_from", "valid_to")}
            dim = dim.select(*[F.col(c).alias(a) for c, a in names.items()])
            t = F.col(d.as_of).cast("timestamp")
            on = [F.col(b) == F.col(names[b]) for b in d.business_key]
            on += [F.col(names["valid_from"]) <= t, t < F.col(names["valid_to"])]
            no_key = reduce(lambda a, b: a & b, [F.col(b).isNull() for b in d.business_key])
            # shiftleft: allow SL-COST-CODE-14 -- `on` is the business key equality plus the validity range (ADR-005)
            out = (out.join(dim, reduce(lambda a, b: a & b, on), "left")
                   .withColumn(d.key, F.when(no_key, F.lit(NOT_APPLICABLE))
                               .otherwise(F.coalesce(F.col(names[d.key]), F.lit(UNKNOWN))).cast("long"))
                   .drop(*names.values()))
        return out

The lines that matter, in order. Reserved members are taken out of the dimension first, so a fact can never match them by accident. The dimension's columns are renamed with a prefix so they cannot clash with the fact's. The join condition is the business key being equal, plus valid_from <= t and t < valid_to. The span is closed at the start and open at the end, so an event exactly at a change belongs to the new version and can never match two. The join is a left join, so a fact row with no match is kept. The last expression sets the key: -2 if the fact has no business key at all, the member's key if one matched, and -1 if none did.

The row ledger

A join is the easiest place to lose or multiply rows without noticing. The harness therefore counts. It counts the rows read from each input, the rows the model returned, the rows after the key lookup, and for each dimension the rows that matched a member, the rows on the unknown member and the rows marked not applicable. These counts are the row ledger, and they are written to the run log as the step gold.ledger.

src/dataplatform/gold/harness.py:375Rows in must equal rows out, or the table is not published.
def _key_lookup(ctx: Ctx, p: GoldPlan, got: _Inputs, built: Frame, dims: dict[str, Frame]) -> Frame:
    """Surrogate keys by the as-of joins (ADR-005), the rows-in = rows-out check and the row ledger (LEDG-01)."""
    keyed = ctx.engine.hold(ctx.engine.add_keys(p, built, dims))
    rows_in, rows_out = ctx.engine.count(built), ctx.engine.count(keyed)
    culprit = "" if rows_in == rows_out else _which_join(ctx, p, built, dims, rows_in)
    _step(ctx, p, "gold.keys", "succeeded" if rows_in == rows_out else "failed",
          {"rows_in": rows_in, "rows_out": rows_out}, culprit)
    _ledger(ctx, p, got, (rows_in, rows_out), keyed)
    if rows_in != rows_out:  # a fact row lost or multiplied by a join: never published
        raise CheckFailed(f"{p.name}: {rows_in} rows built, {rows_out} after the key lookup; {culprit}")
    return keyed
src/dataplatform/gold/harness.py:399The ledger. Each join's three counts must add up to the rows after the lookup.
def _ledger(ctx: Ctx, p: GoldPlan, got: _Inputs, sizes: tuple[int, int], keyed: Frame) -> dict[str, int]:
    """LEDG-01: rows read per input, rows the build gave, and per dimension join rows matched, on the unknown member
    and not applicable. Each join's three counts must add up to the rows after the lookup, else the run fails."""
    rows_in, rows_out = sizes
    counts = {f"read.{ds}": ctx.engine.count(f) for ds, f in sorted(got.frames.items()) if f is not None}
    counts.update(built=rows_in, after_keys=rows_out)
    off = []
    for key, t in ctx.engine.key_tally(p, keyed).items():
        counts.update({f"{key}.{w}": n for w, n in t.items()})
        if sum(t.values()) != rows_out:
            off.append(f"{key}: {sum(t.values())} of {rows_out}")
    balanced = not off and rows_in == rows_out
    _step(ctx, p, LEDGER_STEP, "succeeded" if balanced else "failed", counts,
          "" if balanced else f"the ledger does not balance: {'; '.join(off) or f'{rows_in} built, {rows_out} keyed'}")
    if off:
        raise CheckFailed(f"{p.name}: the ledger does not balance: {'; '.join(off)}")
    return counts

Two rules make the ledger a check and not only a report. The rows built must equal the rows keyed. And for every dimension, matched plus unknown plus not applicable must equal the rows keyed. If the total moved, _which_join reruns the lookup one dimension at a time and names the first join that changed the count, so the message says which dimension has overlapping versions.

The checks before publishing

src/dataplatform/gold/harness.py:418Three checks. Any failure raises, and the caller writes nothing.
def _checks(ctx: Ctx, p: GoldPlan, rows: Frame, built: Frame, first: str, also: set[str]) -> dict[str, int]:
    """Checks before publish (ADR-006): grain unique (KEY-01), orphan rate (LATE-02), reconcile with what the build
    gave (no row or quantity lost by the harness). A failure raises: nothing is written."""
    n = ctx.engine.count(rows)
    counts = {"rows": n}
    if p.grain_unique:
        dup = ctx.engine.duplicates(rows, p.grain)
        _step(ctx, p, "detect.KEY-01", "failed" if dup else "succeeded", {"rows": n, "duplicate_grain": dup},
              f"{dup} rows repeat the grain {list(p.grain)}" if dup else "")
        if dup:
            raise CheckFailed(f"{p.name}: {dup} rows repeat the grain")
    unknown = ctx.engine.unknown_rows(p, rows)
    orphans = max(unknown.values(), default=0)
    counts["orphan_rows"] = orphans
    if orphans:
        rate = orphans / n if n else 0.0
        over = p.orphan_rate_max is not None and rate > p.orphan_rate_max
        _step(ctx, p, "detect.LATE-02", "failed" if over else "warned",
              {"orphan_rows": orphans, "rows": n, **{f"unknown_{k}": v for k, v in unknown.items()}},
              f"{orphans} rows on the unknown member ({rate:.4%}; limit {p.orphan_rate_max}); re-keyed when the "
              f"member arrives")
        if over:
            raise CheckFailed(f"{p.name}: orphan rate {rate:.4%} above {p.orphan_rate_max}")
    if p.reconcile:
        cols = tuple(c for _, c in p.reconcile.measures)
        want = ctx.engine.totals(ctx.engine.only_windows(p, built, first, also), cols)
        have = ctx.engine.totals(rows, cols)
        bad = {c: (want[c], have[c]) for c in cols if abs(want[c] - have[c]) > p.reconcile.tolerance.get(c, 0.0)}
        _step(ctx, p, "gold.reconcile", "failed" if bad else "succeeded",
              {f"{c}_total": int(round(have[c])) for c in cols}, f"differs from the build: {bad}" if bad else "")
        if bad:
            raise CheckFailed(f"{p.name}: totals differ from the build: {bad}")
    return counts

The decision to write is made from digests. window_numbers returns, for each window, its row count, the sums of its measures and a digest, which is one number computed from every column of every row except _run_id. The harness computes this for the published table and for the new rows. A window is in changed only if the two digests differ. If the fact's manifest says hold, incomplete windows are taken out of the list. Then one call replaces exactly those windows.

src/dataplatform/adapters/spark_gold.py:360The write edge on Delta: one overwrite limited to the named windows.
    def replace_windows(self, plan: GoldPlan, rows: DataFrame, windows: list[str]) -> int:
        assert plan.window is not None
        bad = [w for w in windows if not _WINDOW.match(w)]
        if bad:
            raise ValueError(f"not window names: {bad[:3]}")
        path = self.path(plan)
        if not (path / "_delta_log").exists():
            rows.write.format("delta").mode("overwrite").save(str(path))
            return int(self.spark.read.format("delta").load(str(path)).count())
        col = _safe(plan.window.column)
        if plan.window.unit == "hour":
            values = ", ".join(f"TIMESTAMP'{w[:10]} {w[11:19]}'" for w in windows)
        else:
            values = ", ".join(f"DATE'{w}'" for w in windows)
        (rows.write.format("delta").mode("overwrite").option("replaceWhere", f"`{col}` IN ({values})")
         .save(str(path)))
        return int(rows.count())

The write is an overwrite with a condition on the window column, so rows of the named windows are removed and the new rows put in their place in one commit. Rows of other windows are not touched. A window that is named but has no new rows becomes empty, which is how an order that was deleted at the source leaves gold. The window names are checked against a strict pattern before they are placed in the condition, so no data value can ever become part of the statement.

Why a rerun writes nothing

The digest leaves out _run_id. A second run over the same silver produces the same digest for every window, so changed is empty and nothing is written. A side effect is useful: the _run_id on a row tells you which run last changed its window.

When something fails

src/dataplatform/gold/harness.py:171A failure is recorded against the table and the run carries on with the next one.
def _fail(ctx: Ctx, p: GoldPlan, step: str, exc: Exception) -> GoldTable:
    msg = f"{type(exc).__name__}: {str(exc)[:1500]}"
    ctx.store.log_error(ctx.run_id, p.schema, p.name, step, type(exc).__name__, msg)
    ctx.store.finish_dataset_run(ctx.run_id, p.schema, p.name, "failed", message=msg)
    return GoldTable(p.name, "failed", reason=msg)

A failed check is recorded under the step gold.checks, a refused plan under gold.plan, and any other error under gold.build. In all three cases nothing was written and no bookmark moved, so the next run tries the same windows again.

Rebuilding a past window from the run log

Because every fact run records its input versions and its query, src/dataplatform/gold/inspect.py can rebuild one window of a past run. It reads the two run log rows, reads each silver input as it was at that version, runs the same model and key lookup, and returns the window's numbers beside what gold publishes now. It writes nothing.

def _trace(ctx: Ctx, p: GoldPlan, got: _Inputs) -> None:
