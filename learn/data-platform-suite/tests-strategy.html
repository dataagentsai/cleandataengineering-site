The testing strategy: generated tests, the data twin, the tiers and the tools

A test can run every line of code and still prove nothing, because running a line does not mean the test would notice if the line were wrong. A hand-written list of cases is also only as complete as the person who wrote it. This page explains what we do about both, in the order we do it.

The guiding rule is to fail fast: find a wrong rule at the cheapest layer that can show it. Every bug the generated tests have found so far was found on a laptop, in seconds to minutes, before any workspace or real data was involved.

Where a test runs, from cheapest to most expensive

  1. A pure function on a laptop. Each silver step takes a table in and gives a table out, so it runs with no database and no cluster.
  2. The same step on a fast second engine. The same test tables run on DuckDB through SQLFrame, so a run takes seconds.
  3. The same step on local Spark. The engine the platform really runs on, on one machine.
  4. The simulated company, end to end. The data twin: a generated company writes into mock sources and every layer is judged against known answers. See The simulated company and The oracle.
  5. A real workspace. Real tables, real formats, real cost, a real catalog.
  6. Production. Data-quality rules, reconciliation and drift checks watching real data.

The first three layers are where most bugs can be found cheaply. The rest are needed too, because they show what a laptop cannot: format behavior, cost, scale and data nobody imagined.

What we had, and what was missing

Tests and proof describes three kinds of proof: table-driven cases, the simulated company with an oracle, and planted incidents. All three start from cases a person thought of. The review of 19 November 2026 found cases the list had missed, so we added a fourth kind: tests that generate the cases.

A worked example: how a generated test found a history bug

For history, the question is what silver must hold after a set of changes to a key arrives, in any order, possibly twice, in any number of batches. The reference model is a few lines. Order a key's changes by sequence; a new version opens when the tracked value differs from the one before; the last version is current; a version is deleted when its last change is a delete.

src/dataplatform/silver/history_model.py:32The reference model for SCD Type 2. It is not used to build silver. It is what silver is compared with.
def type2_versions(changes: Iterable[Change]) -> list[Version]:
    by_key: dict[str, list[Change]] = defaultdict(list)
    for c in _distinct(changes):
        by_key[c[0]].append(c)
    out: list[Version] = []
    for key in sorted(by_key):
        runs: list[list[Change]] = []
        for c in sorted(by_key[key], key=lambda c: c[2]):
            if runs and runs[-1][0][1] == c[1]:
                runs[-1].append(c)
            else:
                runs.append([c])
        out += [(key, r[0][1], r[0][2], i == len(runs) - 1, r[-1][3] == "D") for i, r in enumerate(runs)]
    return out

The test generates a history (changes to a few keys, delivered out of order, some twice, split into batches anywhere), builds silver from it, and compares the result with the model. It also checks the history rules: at most one current version per key, and no overlap.

tests/dataplatform/test_silver_properties.py:192The property test. One test covers every generated history.
@SETTINGS
@given(h=histories())
def test_scd2_matches_the_reference_model(spark, h):
    hypothesis.assume(not known_gap(h))
    with example_session(spark) as session:
        silver = _apply(session, plan(**SCD2), batches_of(h))
        got = rows(silver, "id", "v", "_seq_from", "_is_current", "_is_deleted")
        assert got == model_type2(h), explain(h) + difference(got, model_type2(h))

Hypothesis found a history of seven changes that made silver disagree with the model. It shrinks a failure to the smallest history that still fails. Here that is two changes: an update, then a delete that carries a newer value than the stored version. The delete arrives first, so it overwrites the stored value in place, and when the missing update arrives later the earlier history cannot be rebuilt.

What the generated tests found in SCD Type 2

#What silver doesWhy it matters
1A delete that arrives before the update it follows overwrites the stored version's value, and the earlier history is lost for good.Silent loss of history
2The same delete sent twice in one batch becomes two versions of the key.Duplicate rows
3A late change that lands inside a run of same-value changes makes the later change forgotten. (Found by review on 19 Nov, before the generated tests.)A lost change
4A key deleted and then changed back to the same value is one live version when the two arrive in separate batches, and two versions when they arrive in one batch.The result depends on how the feed was split

The SCD Type 1 property test passed every generated history. One question is still open and is a decision for the owner, not a bug: what a second delete of an already deleted key means. Silver keeps two deleted versions today and the contract does not say.

How this joins the data twin

The twin (The simulated company) is a generated company with a record of the truth. Today it judges counts, sums and digests. The new approaches plug into parts it already has: the oracle, the runner's checks, the world file's incident list, the learning loop that turns a failed run into a scenario file, and the release gate that compares a changed copy with production.

ApproachWhere it plugs into the twinWhat is new to build
The reference modelThe oracle. Today it judges counts and sums. It would also judge versions, worked out from the company's own change log.Move the model into the platform code so tests and twin share it. Done.
Invariant checks (one current version, no overlap)The runner's silver checks, every simulated day.A few checks in the existing list.
The four found gapsPlanted incident kinds in the world file, so each exists end to end.Four incident entries with their expected results.
Random seeds and shrinkingThe world's seed, and the learning loop that turns a failed run into a pending scenario file.A seed loop on the fast engine, and a bridge from the shrinker to the loop.
Reordered, split and repeated deliveryThe release gate's clone-and-compare: two copies, the same input delivered differently, silver must match.A delivery shaper.
Hostile valuesA new incident kind with parameters. The company knows exactly which rows it made unconvertible.The shaper and the expected quarantine count.
Pairwise variantsVariant copies of the slice, each of which must equal the oracle.A generator of option combinations.

None of the plug-ins is built yet except the shared model. One honest limit: a simulated company generates what its author imagines. The learning loop, and eventually real batches, are what stop the twin from only testing the author's own ideas.

Not built yet, or known gaps
  • No test proves the other tests are complete. These approaches raise confidence and show where it is weak.
  • Mutation testing has not been run, so there is no strength score for any file yet.
  • The reference model encodes the contract as read today. Where the contract is silent, the model's choice is not a ruling.
  • The generated tests cover change-feed input only. Full-copy and snapshot input, and the declarative engine, have none.
  • The data twin does not yet use any of the new approaches, apart from the shared model.
  • The test dependencies are declared in one file but not yet pinned to exact versions.
