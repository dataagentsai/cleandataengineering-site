Stage 5: time, the local time beside the instant

A timestamp in silver is an instant: one point in time, the same everywhere, held in UTC. The fifth stage leaves it that way. When a column asks for it, the stage adds a second column with the time a clock on the wall showed in a named time zone.

Both are needed. The instant is what makes two events comparable across plants. The wall-clock time is what a shift report needs, because a shift starts at six in the morning local time, not at a fixed UTC hour.

Goes inRows whose timestamp columns have been typed by stage 4.
What happensFor each timestamp column with a local_tz, the wall-clock time in that zone is worked out and written as text.
Comes outThe same rows with one more column per such timestamp, named <name>_local.

A worked example

Suppose order_ts of the sales order line has local_tz: Asia/Kolkata. The two rows show the instant and the column the stage adds. India is five and a half hours ahead of UTC.

The code

src/dataplatform/stages/clean.py:151The whole stage.
def time(df: DataFrame, ctx: StageCtx) -> Out:
    """Timestamps stay instants in UTC (the session's zone). A column with local_tz gets <name>_local beside it: the
    wall-clock time in that zone, as text (ISO, no offset)."""
    out = df
    for c in ctx.plan.kept:
        if c.logical_type == "timestamp" and c.local_tz:
            # convert_timezone from UTC (the session zone) and the text in two pieces around a literal T: the same
            # wall time on every engine (from_utc_timestamp and quoted letters in a pattern are not portable,
            # docs/DUCKDB-SPIKE.md)
            wall = F.convert_timezone(F.lit("UTC"), F.lit(c.local_tz), F.col(c.name))
            local = F.concat(F.date_format(wall, "yyyy-MM-dd"), F.lit("T"), F.date_format(wall, "HH:mm:ss"))
            out = out.withColumn(f"{c.name}_local", local)
    return Out(out)
  1. Which columns. Only kept contract columns whose type is timestamp and whose local_tz is set.
  2. Shift to the zone. convert_timezone takes the instant, read as UTC, and gives the wall-clock time in the named zone. The zone's rules for summer time are applied by the engine.
  3. Write it as text. The result is formatted in two pieces, the date and the time, joined around a literal letter T. The outcome is a text such as 2026-11-09T05:30:00, with no offset at the end.
  4. Add the column. The text goes into a new column named after the timestamp with _local added.

The local time is stored as text on purpose. If it were stored as a timestamp, every tool would treat it as an instant in UTC and shift it again when showing it. As text it means exactly what it says.

The comment in the code explains the two odd-looking choices. Another function for the same job and a pattern with a quoted letter do not behave the same on Spark and DuckDB, so the stage uses the forms that do.

The stage itself converts nothing to UTC. It relies on the session's time zone being UTC, which the local session factory sets, and on stage 4 having read the timestamps under that setting.

def test_time(spark, case, settings, want):
    p = plan(columns=[("id", "string"), ("at", "timestamp")], column_settings=[{"name": "at", **settings}])
    df = run("project", frame(spark, "id string, at timestamp", [("a", ts(0))]), p).df
    out = run("time", df, p).df
    if want is None:
        assert "at_local" not in out.columns, case
    else:
        assert rows(out, "at_local") == [(want,)], case
    assert rows(out, "at")[0][0] is not None
Not built yet, or known gaps
  • No tyre dataset declares a local_tz. The sales order line contract says the plant's local time is added beside order_ts, but the two plants are in different zones, and the plant's zone is a fact of another dataset. The design note docs/W1C-SILVER.md records that a per-row zone belongs in gold.
  • One column can have one fixed zone only.
  • The new column is not a contract column. It reaches silver among the other source columns.
  • The stage does not check that the session's time zone really is UTC.
