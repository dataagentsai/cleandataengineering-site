The declarative engine: the same stages, history by AUTO CDC

A declarative pipeline is a way of running data work where you describe the tables you want and the product works out how to build and update them. The declarative engine runs our stage functions inside such a pipeline. For history it does not use our history stage. It uses the pipeline's own change capture, called AUTO CDC and also known as apply changes.

It exists to answer a fair question: why write history code at all when the product has a managed feature for it? The answer here is to support both, from the same settings, and to hold both to the same table of cases.

Goes inThe dataset's plan from the metadata store, and its bronze table read as a stream.
What happensEleven of the thirteen stages run on the stream. Rows that pass go to a view. Rows set aside go to the quarantine table. The change capture reads the view and keeps the silver table.
Comes outA streaming silver table per dataset, and a quarantine table when a stage can set rows aside.

Why two stages cannot run in the flow

A declarative flow reads a stream. A stream hands over new rows and never the whole table. Two stages need the whole table. Stage 10 ranks rows of the same key against each other and looks into silver for repeats. Stage 12 lays the new changes beside silver's stored versions. So the recipe switches those two off and hands their work to the pipeline.

The recipe: the plan translated for the pipeline

The recipe is a small object built from the plan. It holds no product code. It says which stages run in the flow and what to ask the change capture for.

src/dataplatform/silver/declarative.py:40How a plan becomes a recipe, or is refused.
def recipe(plan: SilverPlan) -> Recipe:
    flow = replace(plan, disabled=plan.disabled | OUTSIDE_THE_FLOW)
    if plan.history in ("scd1", "scd2"):
        if not plan.keys:
            raise PlanError(f"{plan.table}: the declarative engine needs business keys for {plan.history}")
        if not plan.order_by:
            raise PlanError(f"{plan.table}: the declarative engine needs a change order (load.history_order_by) "
                            f"for {plan.history}; arrival order is not a sequence")
        if plan.delete_detect == "key_compare":
            raise PlanError(f"{plan.table}: deletes found by comparing full copies are not supported by the "
                            "declarative engine; use silver_engine 'job'")
        deletes = plan.delete_detect == "change_feed" and plan.delete_apply in ("mark_deleted", "remove")
        capture = ChangeCapture(
            keys=plan.keys,
            sequence_by=plan.order_by,
            scd_type=2 if plan.history == "scd2" else 1,
            delete_when=f"{OP_COLUMN} = 'D'" if deletes else None,
            track=plan.track,
            exclude=(OP_COLUMN,) if plan.ingest_read == "change_feed" else (),  # only a change feed carries it
        )
        return Recipe(flow, capture, ())
    if plan.history == "append":
        keys = (plan.dedup_keys or plan.keys) if plan.dedup_mode != "none" else ()
        if not keys:
            return Recipe(flow, None, ())
        if plan.event_time and plan.lookback_days is not None:
            return Recipe(flow, None, tuple(keys), (plan.event_time, plan.lookback_days))
        return Recipe(flow, None, tuple(keys), None, (f"{plan.table}: no event time and late lookback declared, so "
                                                      "streaming de-duplication keeps every key it has seen",))
    raise PlanError(f"{plan.table}: history {plan.history!r} is not supported by the declarative engine "
                    "(ADR-035); use silver_engine 'job'")
  1. The flow plan. A copy of the plan with stages 10 and 12 added to its switched-off stages. Anything the dataset already switched off stays off.
  2. Type 1 and type 2. The plan must have business keys and an order column, and must not detect deletes by comparing full copies. Then a ChangeCapture is filled in.
  3. Append. No change capture. If the dataset removes duplicates, the keys for that are passed on. When the plan has an event time and a late lookback, they bound how long keys are remembered. Otherwise a note says the keys are remembered for ever.
  4. Anything else. Snapshot and source versioned history are refused with a message that names the job engine.

realms/databricks/declarative/silver.py:38The generic pipeline definition for one dataset. It is the only place the product's functions are called.
def declare(name: str, bronze: str, r) -> None:
    table = name.replace(".", "__")

    def staged():
        return run_stages(r.flow_plan, spark.readStream.table(bronze), None, RUN_ID, AS_OF)  # noqa: F821

    dp.temporary_view(name=f"{table}__valid")(lambda: staged()[0])
    _, quarantine, _ = staged()
    if quarantine is not None:
        dp.create_streaming_table(f"{table}__quarantine")
        dp.append_flow(target=f"{table}__quarantine", name=f"{table}__quarantine_flow")(lambda: staged()[1])
    if r.capture is not None:
        c = r.capture
        dp.create_streaming_table(table)
        dp.create_auto_cdc_flow(
            target=table, source=f"{table}__valid", keys=list(c.keys), sequence_by=F.col(c.sequence_by),
            apply_as_deletes=F.expr(c.delete_when) if c.delete_when else None,
            except_column_list=list(c.exclude), stored_as_scd_type=c.scd_type,
            track_history_column_list=list(c.track) or None,
        )
    else:
        def appended():
            rows = spark.readStream.table(f"{table}__valid")  # noqa: F821
            if not r.dedupe_keys:
                return rows
            if r.dedupe_within:  # keys kept only as long as late rows may still come (the dataset's lookback)
                col, days = r.dedupe_within
                return rows.withWatermark(col, f"{days} days").dropDuplicatesWithinWatermark(list(r.dedupe_keys))
            return rows.dropDuplicates(list(r.dedupe_keys))  # unbounded; the recipe's note says so

        dp.table(name=table)(appended)

Walk through it. staged calls the same run_stages the job engine calls, with the flow plan, the bronze table as a stream, and no silver table. The rows that pass become a temporary view. If any stage can set rows aside, a quarantine table is created and an append flow feeds it.

For a type 1 or type 2 dataset the silver table is created as a streaming table and create_auto_cdc_flow is called with the six values from the table above. For an append dataset the valid rows are written as they come. With bounded keys, repeats are dropped within a watermark, which is the pipeline's limit on how late a row may still arrive. With unbounded keys every key ever seen is remembered.

How changes that arrive out of order are handled

The job engine sorts the events itself. The declarative engine passes the order column as sequence_by and the change capture does the ordering. A change with a lower sequence than one already applied is placed in history and does not become current. Arrival order is not a sequence, so the recipe refuses a type 1 or type 2 dataset that has no order column.

The spike that proved this feeds the pipeline a promised date moved twice, with the older change after the newer one.

How deletes are handled

Only one kind of delete can be expressed: a row in a change feed with operation D. The recipe turns it into the condition _op = 'D', and the change capture treats a matching row as a delete of that key at that sequence. The _op column is then left out of the stored table.

Deletes found by comparing full copies cannot be expressed. Comparing needs the whole silver table, and the flow never has it. Such a dataset is refused.

Both apply rules, mark_deleted and remove, become the same condition. The declarative engine has no way to tell them apart.

Because of the third row, the two outputs cannot be compared column by column. The shared contract compares meaning instead. A helper reads the declarative table and says: the last version of a key is current, and it is deleted when it has an end.

src/dataplatform/silver/history_contract.py:53Turning a table that closes deleted keys into the contract's five values per version.
def normalise_closed(rows: Iterable[Mapping[str, Any]], key: str, value: str, start: str, end: str) -> list[Version]:
    """An engine that closes a deleted key's last version (end set, nothing after it): the last version of a key is
    'current'; it is 'deleted' when it is closed."""
    by_key: dict[Any, list[Mapping[str, Any]]] = {}
    for r in rows:
        by_key.setdefault(r[key], []).append(r)
    out: list[Version] = []
    for k in sorted(by_key):
        vs = sorted(by_key[k], key=lambda r: int(r[start]))
        for i, r in enumerate(vs):
            last = i == len(vs) - 1
            out.append((str(k), int(r[value]), int(r[start]), last, last and r[end] is not None))
    return out

Not built yet, or known gaps
  • Three of the nine tyre datasets cannot run here: materials and presses, which find deletes by comparing full copies, and dealer sell-out, which is a snapshot.
  • A critical quality rule cannot hold the batch. The broken rows go to the quarantine table and the rest of the batch is written.
  • The pipeline definition writes nothing to our run log. It prints the recipe's notes. The pipeline's own event log is the record.
  • The stored table lacks _is_current, _is_deleted, _valid_from and _row_key. Nothing in the repository adds them back, so a reader written for the job engine's columns cannot read a declarative table as it is.
  • When a type 2 dataset lists no tracked columns, the call passes no list and the change capture tracks every column of the view. The job engine tracks only the kept contract columns. All four type 2 tyre datasets list their tracked columns, so the difference does not arise there. It was not tested.
  • Of the three append tyre datasets, only press readings has both an event time and a late lookback. Lab inspection results and production records get unbounded removal of repeats, with the recipe's note. This is read from the manifests and the code and was not run.
  • What the change capture does with a delete on a type 1 table is not shown anywhere in the repository. The spike and the contract cover type 2 only.
  • No recorded output of the eight contract cases on the pipeline is in the repository. The runner is there. Its result could not be checked for this page.
