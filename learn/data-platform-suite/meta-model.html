The config data model: every table and every column

The config schema is the platform's description of what it must load. It has nine tables. Every pipeline decision that differs between datasets is read from them.

The model is small on purpose. A dataset is one row with a handful of typed columns for the facts every pipeline needs, a key and value table for the many optional settings, and the whole manifest kept as a JSON document for everything else.

Goes in, what happens, comes out

Goes inOne document per domain and one per dataset, built by the loader from the YAML manifest and the data contract.
What happensThe functions config.load_domain and config.load_dataset check the document and replace the dataset's rows whole, in one transaction.
Comes outRows in the nine tables, read back only through functions such as config.dataset_view.

A worked example: the materials dataset as rows

The tyre company's material master comes from the manifest file data-platform-catalog/slices/02-tyre/manifest/datasets/erp.material.yaml. After the loader runs, the store holds these rows for it. The first column is the table, the second is how many rows, the third is what they say.

The tables, one at a time

config.setting_def: the dictionary of allowed settings

One row per setting that a manifest may use. Settings and the merge explains it in full. Its primary key is (scope, key), so the same key can exist at two scopes.

ColumnType and ruleWhat it is for
scopeText. One of platform, source, dataset.The level the setting belongs to.
keyText.The setting's name, for example retry_count.
value_typeText.The kind of value, for example int, bool, enum.
default_valueText, may be empty.The value used when nothing sets the key.
allowedArray of text, may be empty.The list of permitted values for an enum.
descriptionText.A sentence for people.
statusText. registered or proposed.Whether the key is settled or still a proposal from the specifications.

config.domain: one row per domain

config.domain_setting: defaults for a whole domain

ColumnType and ruleWhat it is for

config.business_key: which columns identify a row

    dataset_id BIGINT NOT NULL,
    key_kind TEXT NOT NULL CHECK (key_kind IN ('primary', 'dedup')),

    column_name TEXT NOT NULL,

The code that writes a dataset

src/dataplatform/adapters/sql/postgres_meta.sql:397The second half of config.load_dataset. The dataset's child rows are deleted and written again in the same transaction.
    -- the dataset's settings, columns and keys are replaced whole, in this transaction
    DELETE FROM config.business_key WHERE dataset_id = ds;
    DELETE FROM config.dataset_column WHERE dataset_id = ds;
    DELETE FROM config.dataset_setting WHERE dataset_id = ds;
    FOR k, v IN SELECT * FROM jsonb_each_text(COALESCE(p_doc -> 'settings', '{}')) LOOP
        INSERT INTO config.dataset_setting (dataset_id, key, value) VALUES (ds, k, v);
    END LOOP;
    INSERT INTO config.dataset_column (dataset_id, ordinal, column_name, logical_type, is_required,
                                       primary_key_position, description, classification)
    SELECT ds, c.ord, c.x ->> 'name', c.x ->> 'logical_type', COALESCE((c.x ->> 'required')::BOOLEAN, FALSE),
           (c.x ->> 'primary_key_position')::INT, COALESCE(c.x ->> 'description', ''),
           COALESCE(c.x ->> 'classification', '')
    FROM jsonb_array_elements(COALESCE(p_doc -> 'columns', '[]')) WITH ORDINALITY AS c (x, ord);
    FOR kind, cols IN SELECT * FROM jsonb_each(COALESCE(p_doc -> 'business_keys', '{}')) LOOP
        i := 0;
        FOR k IN SELECT jsonb_array_elements_text(cols) LOOP
            i := i + 1;
            INSERT INTO config.business_key (dataset_id, key_kind, ordinal, column_name) VALUES (ds, kind, i, k);
        END LOOP;
    END LOOP;
    RETURN ds;

Walk through it. The three deletes clear the dataset's keys, columns and settings. The order matters: keys go first because they point at columns. The settings are inserted one row per key. The columns are inserted in one statement, and WITH ORDINALITY numbers them in the order the document lists them, which is the contract's order. The keys are inserted last with a counter per kind. Because the function is one transaction, a reader never sees a dataset with half its columns.

How it is tested

The contract table in tests/dataplatform/test_meta_store.py has cases for the model: columns come back in contract order, keys come back in position order, a business key that names a missing column is refused, and loading a dataset again leaves one row and replaces its settings whole.

tests/dataplatform/test_meta_store.py:190Two real cases. After a reload with fewer settings, the dropped key falls back to its default.

Not built yet, or known gaps
  • A source name is unique across the whole store, not within a domain. If a second domain loaded a dataset under a source name that already exists, the existing source row would be reused and would keep the first domain. Only one domain is loaded today, so this has not happened.
  • A dataset that is removed from the manifest is not removed from the store. The loader reports it and leaves the rows. There is no function that deletes a dataset.
  • config.business_key and config.dq_rule do not cascade from the dataset in the same way as the other child tables. Since no function deletes a dataset, nothing depends on it yet.
  • Gold tables are stored as datasets under a source named gold_ plus the gold manifest's domain, for example gold_sales. The word source is stretched to cover them.
  • The store does not check a value against the dictionary's type or allowed list. The loader does, and only as a warning. See Settings and the merge.
