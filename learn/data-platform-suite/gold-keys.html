Stable integer keys, and why gold needs them

Every dimension member has one integer key, and every fact row carries the key of the member it belongs to. The key is not a counter. It is computed from the member's own data, so rebuilding a table from nothing gives every member the same key it had before.

Without this, a rebuild would renumber the members, and every fact row and every saved report that holds a key would point at the wrong dealer.

Why not use silver's hashes

Silver already has two hashes. _key_hash is a hash of the business key, and _row_key identifies one version. Both are SHA-256 values kept as 64 characters of text. Gold computes its own key for four reasons.

ReasonWhat silver's hash givesWhat gold needs
One key per version_key_hash is the same for every version of a dealer.A fact row must point at one version, the one that was true at the event.
A whole number64 characters of text.A single whole-number column. It is smaller in every fact row, and joins and group-bys on it are cheaper.
Reserved membersA hash has no value that means nothing was found.Two keys that are never produced by the recipe: -1 for a member that has not arrived, -2 for a row that has no business key.
A recipe anyone can repeatThe hash is computed inside the silver stages.A recipe written as plain text, so Python, Spark and DuckDB all compute the same number and a test can prove it.

The recipe

def canonical_time(t: datetime) -> str:
    """A version start as the recipe writes it (a naive time is taken as UTC)."""
    aware = t if t.tzinfo else t.replace(tzinfo=UTC)
    return aware.astimezone(UTC).strftime(TS_FORMAT)
src/dataplatform/gold/keys.py:32The text, then the key.
def key_text(dataset: str, business_key: tuple[object, ...], version_start: datetime | None = None) -> str:
    parts = [dataset, *("" if v is None else str(v) for v in business_key)]
    if version_start is not None:
        parts.append(canonical_time(version_start))
    # shiftleft: allow SL-COST-CODE-14 -- a string join (str.join), not a dataframe join
    return SEP.join(parts)


def surrogate_key(dataset: str, business_key: tuple[object, ...], version_start: datetime | None = None) -> int:
    """The member's key; the same inputs always give the same number."""
    digest = hashlib.sha256(key_text(dataset, business_key, version_start).encode()).hexdigest()
    return int(digest[:HEX_DIGITS], 16)

Walk through it. key_text makes a list that starts with the input's name, then each business key value as text with a missing value written as empty, then the version's start. The parts are joined with a bar. surrogate_key hashes that text with SHA-256, keeps the first 15 hex digits, and reads them as a number in base 16.

Fifteen hex digits are 60 bits. That is why 15 was chosen: the number is always positive and always fits in a 64-bit integer, whatever engine stores it. The input's name is part of the text so that a material M1 from one system and a material M1 from another never share a key.

The same recipe inside each engine

The dimension has millions of rows on a real system, so the key is computed by the engine, not row by row in Python. Each engine adapter repeats the recipe in its own functions.

src/dataplatform/adapters/spark_gold.py:59On Spark: the same text, the same hash, the same 15 digits, converted from base 16 to base 10.
def key_text(dataset: str, key: list[Column], version_start: Column | None) -> Column:
    """keys.key_text in the engine: the same text the Python recipe hashes."""
    parts = [F.lit(dataset), *[F.coalesce(c.cast("string"), F.lit("")) for c in key]]
    if version_start is not None:
        parts.append(as_text(version_start, TS_PIECES))
    return F.concat_ws(SEP, *parts)


def surrogate(dataset: str, key: list[Column], version_start: Column | None) -> Column:
    """keys.surrogate_key in Spark: the same text, the same SHA-256, the first 15 hex digits."""
    text = key_text(dataset, key, version_start)
    return F.conv(F.substring(F.sha2(text, 256), 1, HEX_DIGITS), 16, 10).cast("long")
src/dataplatform/adapters/duckdb_gold.py:32On DuckDB there is no base conversion function, so the 15 digits are added up one by one.
def surrogate(dataset: str, key: list[Column], version_start: Column | None) -> Column:
    """keys.surrogate_key: the first 15 hex digits of SHA-256(key text) as a whole number, digit by digit (a hex
    digit's value from its character code: 0-9 are 48-57, a-f are 97-102)."""
    digest = F.sha2(key_text(dataset, key, version_start), 256)
    codes = [F.ascii(F.substring(digest, i + 1, 1)) for i in range(HEX_DIGITS)]
    digits = [F.when(c < 58, c - 48).otherwise(c - 87).cast("long") * F.lit(16 ** (HEX_DIGITS - 1 - i))
              for i, c in enumerate(codes)]
    return reduce(lambda a, b: a + b, digits).cast("long")

The DuckDB version looks different but does the same sum. It takes each of the 15 characters, turns the character into its value from 0 to 15 using its character code, multiplies by the right power of 16, and adds the 15 results.

The reserved members

src/dataplatform/gold/keys.py:46The rule for the key a fact row points at.
def member(business_key: tuple[object, ...], found: int | None) -> int:
    """The key a fact row points at: not applicable without a business key, unknown when no member matched."""
    if not business_key or all(v is None for v in business_key):
        return NOT_APPLICABLE
    return UNKNOWN if found is None else found
SituationKeyWhat happens next
The fact row's dealer matched a memberThe member's keyNothing. This is the normal case.
The fact row has a dealer code, but no member matched-1, unknownThe row is published and counted as an orphan. Its window is rebuilt on every later run until the member arrives, whatever the lookback.
The fact row has no dealer code at all-2, not applicableThe row is published. There is nothing to wait for.

In the engines this rule is written as an expression inside the key lookup, which The harness shows. The published windows that still hold a -1 are found by windows_with_unknown and added to the range of every run.

src/dataplatform/adapters/spark_gold.py:281Published windows that still hold a row on the unknown member.
    def windows_with_unknown(self, plan: GoldPlan, facts: DataFrame | None) -> set[str]:
        if facts is None or not plan.dimensions:
            return set()
        hit = reduce(lambda a, b: a | b, [F.col(d.key) == UNKNOWN for d in plan.dimensions])
        return {str(r[0]) for r in facts.where(hit).select(self.window_text(plan)).distinct().collect()}

Collisions

Two different texts can in principle give the same 15 digits. The recipe does not prevent that. The harness detects it: after shaping a dimension it counts duplicate keys, and if there is even one, the dimension is not written and the step detect.KEY-01 is recorded as failed.

Not built yet, or known gaps
  • A collision is detected, not resolved. If one ever happens the dimension stops being written until someone changes the recipe.
  • The Python function member states the rule and is tested, but the engines do not call it. They repeat the rule as an engine expression.
  • The manifest's keys.unknown_member and keys.not_applicable values are not used by the engine. The reserved keys are always -1 and -2.
  • The specification does not say how an event before a member's first version should join. Joining the first version is a decision taken in the code.
