Ingestion brings data from the systems that produce it into bronze, the first layer of the platform. Bronze holds every batch exactly as the source sent it, with a few columns added that say where each row came from.

Sources differ a great deal. One sends files, one must be asked, one never stops talking. If each had its own loading code, each would have its own idea of a duplicate, of a broken file and of what to record. Here the sources differ only in how a batch is found. Once a batch is in hand, the same checks run for all of them.

Three words used on every page

WordMeaning
Landing zoneA storage folder that holds delivered files exactly as they arrived, each with a small manifest file beside it. A delivery is written once and never changed.
LanderOur code that takes a batch, checks it and writes it to bronze. It is the same code whether the batch came from landing, from a database or from a stream.
BronzeOne table per dataset that keeps every accepted batch as delivered. Nothing is cleaned or merged here.

Push, pull and stream

Way inWho starts itWhere a batch comes fromWhy it exists
PushThe source side. A mover, which is a service outside our code, copies files into landing.A delivery in landing.Change capture services and file transfers already exist as products. The platform only asks that they write each delivery once with a manifest.
PullOur run. It asks the source.Rows read from a database copy or from pages of an interface. There is no landing hop.Some sources only answer questions.
StreamOur run. It reads each part of the stream from where it stopped to the end, then stops.Records from a stream. The stream itself plays the part of landing.Sensor readings arrive all day. Reading them in scheduled runs keeps one loading model for everything.

The design decisions

DecisionWhat it meansWhy
One set of entry steps for every way inA pushed file, a pulled copy, a page and a stream chunk all go through the same function.A rule such as the duplicate check is written and tested once.
A batch is identified by its contentThe batch key is a hash of the batch's bytes. The file name and the arrival time are not part of it.A file that is sent again under a new name is still recognised.
A held batch is never a successA batch that fails a check is not written. Its dataset run is recorded as failed, with the reason.A broken delivery must be seen by a person, not skipped quietly.
Positions live in the metadata storeHow far a dataset has been read is kept in the store and moves only when the dataset run succeeds.A failed run is taken again from the same place.
Bronze is written once per dataset per runThe new batches of a run are written in one commit, and only then recorded as loaded.The record never says loaded before the rows are there.

How we know it works

tests/dataplatform/test_ingest_world.py runs the simulated tyre company for 14 days at a small scale through ingestion with local adapters. For every day, the number of rows that reached bronze per dataset must equal the simulated company's own count. The company also plants eleven incidents, one on each of days 3 to 13, and each must get the verdict ingestion owes it.

tests/dataplatform/test_ingest_world.py:86The planted incidents: name, day, the rule it tests, and the verdict expected from ingestion.

A verdict of handled means ingestion did what the rule asks, such as skipping a file sent twice. Flagged means ingestion counted the problem and left the fix to silver. Deferred means the problem is not ingestion's to catch. Tests and proof explains the simulated company.

Not built yet, or known gaps
  • The connectors to real source systems are thin. Most adapters behind the source ports are local stand-ins built for the simulated company. Sources and movers says which is which.
  • Datasets are run one after another inside a run. There is no parallel loading.
  • Streams are read in scheduled runs that stop when they reach the end. There is no continuously running reader.
  • A source discovery helper exists and is tested, but no runner calls it.
