Planted incidents: eleven faults the platform must catch

A planted incident is a fault put into the simulated company's data on purpose, on a known day. A dealer's file arrives four days late. A file is sent twice. The lab renames a column. Each one is something real sources do.

Clean data proves that the platform works when nothing goes wrong. Incidents prove the part that matters more: that it notices when something does, handles it at the right layer, and stays quiet on a clean day.

How an incident is declared

Every incident is one entry in the world file's calendar. The entry names the day, the dataset, the exact values, the detector expected to fire, and the oracle: one sentence that says what a correct platform must hold afterwards. A detector here is the id of a rule in the specification catalog, such as DEL-01 for deletes at the source.

data-platform-catalog/slices/02-tyre/world.yaml:117One calendar entry in full.
  - id: sellout-file-late
    day: 5
    story: late_data
    kind: late_delivery
    dataset: partner.dealer_sellout
    does: Dealer D-0042's October file, due on day 1, arrives on day 5.
    params: {dealer: D-0042, month: "2026-10", due_day: 1}
    expect:
      detector: LATE-01
      handled_by: [DPC-0080, DPC-0059, DPC-0079]
      oracle: October for D-0042 is published flagged incomplete until day 5, then rebuilt, marked complete and logged as a restatement

The generator reads the values from the params block and keeps no table of its own. When the plain sentence and the block disagree, the block wins.

The four verdicts

VerdictMeaning
handledThe layer did what the rule asks.
flaggedThe layer noticed the condition and recorded it. A later layer applies it.
deferredNot this layer's rule. The layer only loads the rows.
missedThe layer should have caught it and did not. This fails the test.

Two things the recorded runs do not show

First, neither design note records a verdict for change-feed-drops-rows. The code that judges it exists in the silver day-by-day module, and the comparison it relies on has its own unit test, but I found no recorded run that shows the seven keys being named.

Second, neither note records a run on the compressed calendar. The compressed days in the table above come from the world file. A test proves that the compressed calendar loads, moves every incident into three days and keeps day 1 clean. It does not run the platform on it.

How a verdict is reached

src/dataplatform/ingest/daybyday.py:70Ingestion's judge: one verdict per incident, from the dataset's run report.
def judge(day: int, finding: dict[str, Any], d: DatasetReport | None) -> Verdict:
    det, ds = finding["detector"], finding["dataset"]
    c, noticed = (d.counts, d.noticed) if d else ({}, {})

    def v(verdict: str, evidence: str) -> Verdict:
        return Verdict(day, finding["incident"], det, ds, verdict, evidence)

    if det == "DUP-01":
        ok = c.get("skipped_duplicate", 0) > 0
        return v("handled" if ok else "missed", f"{c.get('skipped_duplicate', 0)} batch(es) skipped as duplicates")
    if det == "SCH-02":
        col = str(finding["detail"].get("missing_column", ""))
        named = d is not None and any(col in r for r in d.reasons)
        return v(
            "handled" if c.get("rejected_contract", 0) and named else "missed",
            f"{c.get('rejected_contract', 0)} file(s) stopped naming {col}; others loaded ({c.get('loaded', 0)})",
        )
    if det == "DEL-04":
        return v(
            "handled" if c.get("held_mass_delete", 0) else "missed", "; ".join(d.reasons) if d else "dataset not run"
        )
    if det in NOTICED:
        return v("flagged" if noticed.get(det, 0) else "missed", f"{noticed.get(det, 0)} {NOTICED[det]}")
    if det in DEFERRED:
        return v("deferred", DEFERRED[det])
    return v("missed", "no ingestion rule for this detector")

Walk through it. For a duplicate, the verdict is handled when at least one batch was skipped as a duplicate. For a renamed column, it is handled when a file was rejected and the reason names the missing column. For a short copy, it is handled when a batch was held as a mass delete. For the four detectors ingestion only notices, the verdict is flagged when the count it noticed is above zero. For the four that belong to later layers, the verdict is deferred, with a sentence saying who owns it. Anything else is missed.

src/dataplatform/silver/daybyday.py:93Silver's judge reads what the silver table holds. The delete case is shown.
def judge(
    n: int, finding: dict[str, Any], tables: SilverTables, ps: dict[str, SilverPlan], day: SilverDay
) -> Verdict | None:
    det, ds = finding["detector"], finding["dataset"]
    if det not in SILVER_DETECTORS or ds not in ps:
        return None
    plan, detail = ps[ds], finding["detail"]

    def v(ok: bool, evidence: str) -> Verdict:
        return Verdict(n, finding["incident"], det, ds, "handled" if ok else "missed", evidence)

    if det == "DEL-01":
        rows = [tables.versions(plan, dict(zip(plan.keys, k, strict=True))) for k in detail["keys"]]
        marked = sum(1 for r in rows if r and any(x["_is_current"] and x["_is_deleted"] for x in r))
        return v(marked == len(rows), f"{marked} of {len(rows)} deleted keys kept in silver and marked deleted")

Silver's judge does not read counts from a log. For the deleted lines it asks silver for the versions of each deleted key and checks that a current version is marked deleted. The gold judge works the same way, with queries on published gold.

No alarm on a clean day

Catching every incident is half the promise. The other half is that nothing fires when nothing happened. One test walks every day's findings and fails if an incident shows up on a day the calendar did not give it. It also checks that days 1, 2 and 14 are clean.

tests/dataplatform/test_world_tyre.py:232Each incident on its own day and no other.
def test_detectors_fire_only_on_their_days(run):
    """SIM-01: each incident shows up on its calendar day (a late dimension also on the day after) and no other."""
    allowed = {e["id"]: {e["day"]} for e in run["dwd"].world["calendar"]}
    allowed["new-dealer-late"] = {11, 12}
    for day, r in run["reports"].items():
        for f in r["findings"]:
            assert day in allowed[f["incident"]], f"{f['incident']} fired on day {day}"
    assert [d for d, r in run["reports"].items() if r["clean_day"]] == [1, 2, 14]

Not built yet, or known gaps
  • The silent loss of seven delivery rows has no recorded verdict, and neither slow test passes the live source reader that the check needs. Only the run script does.
  • No recorded run uses the compressed calendar.
  • Silver does not write detector rows to the run log for the incidents it handles, so operations cannot alert on them from the engine's run log yet.
  • The late dealer file is listed by the world file as a finding only on day 5, when the file arrives. The lateness is visible from day 1. The operations notes record this as a gap in the specification.
  • Checks for the data expectation services layer are pending in every scenario.
