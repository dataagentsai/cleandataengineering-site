One day, end to end: what happens to a day of data

The fastest way to understand the platform is to follow one day through it. This page walks the day in order. Each step links to the page that explains it in full.

The day, in order

  1. Before the first day. The dataset manifests are checked and loaded into the metadata store. From this moment the store is the only place the code reads settings from. See Loader.
  2. 1 The sources change. Orders are placed, tyres are made, a dealer changes region. In the runs shown on these pages a simulated company does this, so the true totals for the day are known. See The simulated company.
  3. 2 Data reaches landing. Sources that push send change-feed files and plain files to the landing zone. Sources that are pulled are read by the platform. See Sources and movers.
  4. 3 One ingestion run takes everything new to bronze. The runner loops over the enabled datasets. For each it picks one of five pipelines, passes the batch through the entry steps, and the lander writes it to bronze. Bronze row counts are compared with the truth.
  5. 4 One silver run. For each dataset the reader picks the bronze batches loaded since silver last ran. They go through the thirteen stages, the history stage decides versions and deletes, and the writer applies it in one merge. Silver is compared with the truth.
  6. 5 One gold run for the business date. The harness builds the dimensions and the facts for the day's window. Gold is compared with the truth.
  7. 6 The semantic layer. After the last day the metrics are asked questions whose answers are known. See Semantic layer.
  8. Throughout. Every run, dataset and step is recorded. Freshness, alerts and the operations page are read from that record. See Operations.

The same thing in the code

One script runs the simulated company and the platform together, day by day, on a laptop. Its opening comment is the most compact description of a day that exists.

the manifest is loaded into it first (PostgreSQL database DP_RUN_META_DSN, default dbname=dp_meta_run, recreated
each run; or in memory). Silver (W1c): after each day's ingestion, one silver run on a local Spark (local[2], 1 GB
driver) takes the new bronze batches through the thirteen stages into Delta tables under build/run/silver/, and
silver is compared with the oracle's silver totals for the day; DEL-01, SCD-02, LATE-03 and DUP-04 are judged on what
silver holds. The mass-delete guard compares each full copy with silver's current keys. Gold (W1d): after silver,
one gold run for the day's business date builds the dimensions and the facts (models/tyre/gold/) into Delta tables
under build/run/gold/, and gold is compared with the oracle's gold for the day; LATE-01, LATE-02, HIST-05, DEL-01 and
DUP-01 are judged on gold. After the last day the metric views' known answers are asked of gold
(build/run/gold_metrics.json, the DP_GOLD_METRICS file W5's tests read). Report: build/run/report.json.

What is checked on a day

LayerCompared with the truthIncidents judged here
BronzeRows per dataset for the dayA file sent twice, a column renamed, a full copy that is far too short
SilverCurrent rows, versions, deletes marked, and each dataset's own measuresDeletes, a change arriving out of order, late readings, a replayed stream
GoldEach fact's measuresLate facts, history, deletes and duplicates seen from gold
SemanticKnown answersNone

An incident is a fault planted in the data on purpose on a known day. Planted incidents lists them all, with the rule that detects each one and the layer that handles it.
