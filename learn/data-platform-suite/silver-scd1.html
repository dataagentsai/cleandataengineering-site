Type 1 history: the latest state of a key wins

Type 1 history keeps one row per business key: its latest state. A change replaces the row. The past is not kept.

It is the default for transactions, such as the tyre company's deliveries. A delivery is updated as it moves, and reports only need where it stands now. The risk is the same as for type 2. If the latest arrival won, a late older change would overwrite newer data. So the latest change by the source's order wins.

Goes inThe new changes, and the stored row of every key they touch.
What happensThe events of a key are ranked by the order column, highest first. Rank 1 is kept.
Comes outOne row per touched key, with the key hash as its row key.

A worked example

Delivery D-7 was changed twice at the source. The second change, with sequence 2, reached silver first. The first change, with sequence 1, arrived in a later batch.

The code

src/dataplatform/stages/history.py:171The whole of type 1.
def scd1(inc: DataFrame, cur: DataFrame | None, plan: SilverPlan) -> DataFrame:
    o = plan.order_by
    events, rows = _events(_incoming(inc, plan).withColumn("_pos", F.col(o)), cur, plan)
    latest = Window.partitionBy("_key_hash").orderBy(F.col(o).desc_nulls_last(), F.col("_existing").asc_nulls_first(),
                                                     *arrival_desc(events))
    deleted = F.col("_op") == "D"
    out = events.withColumn("_rn", F.row_number().over(latest)).where("_rn = 1").withColumns({
        "_valid_from": F.col("_ts"),
        "_valid_to": F.lit(None).cast("timestamp"),
        "_is_current": F.lit(True),
        "_is_deleted": deleted,
        "_deleted_at": F.when(deleted, F.col("_ts")),
        "_seq_from": F.col(o),
        "_row_key": F.col("_key_hash"),
    })
    return _finish(out, _stale(rows, out), plan)

The first lines are the same as type 2. The new rows become events, and the stored rows of the touched keys are added. The hub page explains those helpers.

The window latest ranks the events of a key. The highest order value comes first. At a tie a new change comes before the stored row, and after that the newest arrival wins. Rank 1 is kept and the rest are dropped.

The history columns are simple. The row is always current. There is no end of validity. _valid_from is the effective time of the change that won. _seq_from is its order value. The row key is the key hash, so the merge finds the one stored row of the key and overwrites it.

A delete is one more event. If the delete has the highest order value, the row that survives is the delete row, and it is flagged deleted with the delete's time. The row is not removed unless the dataset's rule is remove. If a newer change for the key arrives later, that change wins and the flag is gone.

Not built yet, or known gaps
  • Type 1 keeps no past. If a report later needs the earlier values of a delivery, the dataset has to move to type 2 and be rebuilt from bronze.
  • Stage 10 already keeps only the latest change per key inside a batch for this kind of dataset, so the ranking here mostly decides between the batch and the stored row.
