Two engines for silver: the job engine and the declarative engine

Bronze to silver can be run by two engines. The job engine is our own runner: it calls the thirteen stages and writes with one merge. The declarative engine runs the stages inside a declarative pipeline and lets the pipeline's change capture keep the history. A dataset picks one with a single setting.

Two engines are only safe if two things hold. A dataset must never be run by an engine that cannot do what its manifest asks. And both engines must mean the same thing by history. This page shows how each of the two is enforced, and how far each has been checked.

Picking the engine

What each engine can do, written as data

src/dataplatform/silver/engines.py:27The capabilities of each engine: the history types it writes and the table formats it writes natively.
CAPS: dict[str, EngineCaps] = {
    "job": EngineCaps(frozenset({"scd1", "scd2", "append", "snapshot", "source_versioned"}), None),
    # Spike 13-14 Nov: managed change capture keeps SCD Type 1 and 2; the bound declarative product writes its own
    # format natively and the open format only as added metadata, so a native open-format contract stays on `job`.
    "declarative": EngineCaps(frozenset({"scd1", "scd2", "append"}), frozenset({"delta"})),
}

The job engine writes all five history types, in any format, because it writes through the table port. The declarative engine writes type 1, type 2 and append, and only Delta natively. The comment records why. In the spike, the pipeline's tables were Delta tables that other engines can read as Iceberg through added metadata. They were not native Iceberg tables.

Because the capabilities are data, a deployment can pass its own table to engine_problems and widen or narrow an engine without changing this file.

The refusals, and why each exists

src/dataplatform/silver/engines.py:46Every reason a dataset cannot run on its chosen engine. An empty list means it can.
def engine_problems(name: str, manifest: Mapping[str, object], settings: Mapping[str, str],
                    platform: Mapping[str, str], caps: Mapping[str, EngineCaps] | None = None) -> list[str]:
    """Why this dataset cannot run on its chosen engine; empty when it can."""
    caps = CAPS if caps is None else caps
    engine = engine_of(settings, platform)
    if engine not in caps:
        return [f"{name}: silver_engine '{engine}' is not one of {sorted(caps)}"]
    c, out = caps[engine], []
    hist = history_type(manifest)
    if hist and hist not in c.history:
        out.append(f"{name}: history '{hist}' is not supported by silver_engine '{engine}' "
                   f"(supports {sorted(c.history)}); use silver_engine 'job'")
    load = manifest.get("load")
    deletes = load.get("deletes") if isinstance(load, Mapping) else None
    if engine == "declarative" and isinstance(deletes, Mapping) and deletes.get("detect") == "key_compare":
        out.append(f"{name}: deletes found by comparing full copies are not supported by silver_engine "
                   f"'{engine}'; use silver_engine 'job'")
    fmt = str(settings.get("table_format") or platform.get("table_format") or "")
    if c.formats is not None and fmt and fmt not in c.formats:
        out.append(f"{name}: table_format '{fmt}' is not written natively by silver_engine '{engine}' "
                   f"(writes {sorted(c.formats)}); a contract that needs native '{fmt}' stays on silver_engine 'job'")
    return out

The history contract both engines must pass

The contract is eight cases written as plain data. Each case gives batches of changes in arrival order, and what silver must mean afterwards as one line per version: key, value, the sequence the version starts at, whether it is current, whether it is deleted.

CaseWhat it pins down
1A first load gives one current version per key.
2A tracked change opens a version.
3A change that is not tracked updates the version in place.
4Several changes in one batch become versions in sequence order.

The type 2 page works through all eight with before and after tables.

The engines store a deleted key differently, so their tables are first brought to the contract's shape. The job engine needs no help: its columns are the contract's values. For an engine that closes the deleted version there is a helper. The file's description calls this step normalise. The function it provides is normalise_closed.

src/dataplatform/silver/history_contract.py:53For an engine that closes a deleted key: the last version is current, and it is deleted when it has an end.
def normalise_closed(rows: Iterable[Mapping[str, Any]], key: str, value: str, start: str, end: str) -> list[Version]:
    """An engine that closes a deleted key's last version (end set, nothing after it): the last version of a key is
    'current'; it is 'deleted' when it is closed."""
    by_key: dict[Any, list[Mapping[str, Any]]] = {}
    for r in rows:
        by_key.setdefault(r[key], []).append(r)
    out: list[Version] = []
    for k in sorted(by_key):
        vs = sorted(by_key[k], key=lambda r: int(r[start]))
        for i, r in enumerate(vs):
            last = i == len(vs) - 1
            out.append((str(k), int(r[value]), int(r[start]), last, last and r[end] is not None))
    return out

When to choose which

If the datasetChooseBecause
Is a full copy that can lose rowsJobOnly the job engine finds deletes by comparison.
Is a snapshot or keeps its own versions at the sourceJobThe declarative engine refuses both.
Has a critical rule that must stop the batchJobOnly the job engine can hold a batch.
Must be in a native open format other than DeltaJobThe declarative engine writes Delta natively.
Must appear in the platform's run log, stage by stageJobThe pipeline does not write it.
Is read downstream by its _is_current and _is_deleted columnsJobThe declarative table does not have them.
Is a change feed or an event stream, and the team wants the product to manage the writesDeclarativeType 1, type 2 and append are what it supports, from the same manifest.
Is anything else, or you are unsureJobIt is the default and takes every dataset.

The declarative engine's tables equal the job engine's on the six datasetsNot verified. A comparison script is in the repository beside the pipeline. It compares live rows, version counts and business columns for those six datasets. It needs a deployed workspace, and no output of it is recorded in the repository. The public snapshot's design notes do not mention the declarative engine at all.
Not built yet, or known gaps
  • No test runs the two engines on the same data in one place. The contract is shared, but each engine runs it in its own harness.
  • The contract covers type 2 only. Type 1 and append on the declarative engine have recipe tests and no shared cases.
  • The comparison of the two engines' tables looks at live rows. It does not compare how a deleted key is stored, which is the known difference.
  • The capability table lists what the declarative engine supports. It does not list what it lacks at run time: the hold on a critical rule and the run log are not refusals, so a dataset that needs them can still be moved to the declarative engine without a warning.
