Every function in the store, grouped by purpose

The functions are the store's whole public surface. This page lists every one. The main file src/dataplatform/adapters/sql/postgres_meta.sql defines 38. The operations file src/dataplatform/adapters/sql/postgres_obs.sql adds one more.

Reading them as a list is the fastest way to learn what the platform can and cannot do with its metadata. If an action has no function, no pipeline can perform it.

What every function has in common

src/dataplatform/adapters/sql/postgres_meta.sql:300The helper nearly every function starts with. It turns a source and dataset name into an id, or refuses with DPM02.
CREATE OR REPLACE FUNCTION config._dataset_id(p_source TEXT, p_dataset TEXT) RETURNS BIGINT
LANGUAGE plpgsql STABLE SECURITY DEFINER SET search_path = pg_catalog, pg_temp AS $$
DECLARE v BIGINT;
BEGIN
    SELECT d.dataset_id INTO v FROM config.dataset d JOIN config.source s USING (source_id)
    WHERE s.source_name = p_source AND d.dataset_name = p_dataset;
    IF v IS NULL THEN
        RAISE EXCEPTION 'dataset %.% is not loaded', p_source, p_dataset USING ERRCODE = 'DPM02';
    END IF;
    RETURN v;
END $$;

Three things in the second line apply to all of them. SECURITY DEFINER makes the function run with its owner's rights, which is how a caller with no right on any table can still read and write through it. SET search_path pins the schema search to the system catalogue, so a caller cannot make the function pick up a table of the caller's own. Functions that only read are marked STABLE.

src/dataplatform/adapters/sql/postgres_meta.sql:694How a run's status follows its datasets: none failed is succeeded, all failed is failed, anything between is partial, and a run with no dataset is failed.
CREATE OR REPLACE FUNCTION runtime.finish_run(p_run_id TEXT) RETURNS TEXT
LANGUAGE plpgsql SECURITY DEFINER SET search_path = pg_catalog, pg_temp AS $$
DECLARE st TEXT; n INT; failed INT; running INT; final TEXT;
BEGIN
    PERFORM runtime._check_run(p_run_id);
    SELECT status INTO st FROM runtime.run WHERE run_id = p_run_id FOR UPDATE;
    IF st <> 'running' THEN
        RAISE EXCEPTION 'run % is already %', p_run_id, st USING ERRCODE = 'DPM04';
    END IF;
    SELECT count(*), count(*) FILTER (WHERE status = 'failed'), count(*) FILTER (WHERE status = 'running')
    INTO n, failed, running FROM runtime.dataset_run WHERE run_id = p_run_id;
    IF running > 0 THEN
        RAISE EXCEPTION 'run % still has datasets running', p_run_id USING ERRCODE = 'DPM04';
    END IF;
    final := CASE WHEN n = 0 THEN 'failed' WHEN failed = 0 THEN 'succeeded' WHEN failed = n THEN 'failed'
                  ELSE 'partial' END;
    UPDATE runtime.run SET status = final, ended_at = now() WHERE run_id = p_run_id;
    RETURN final;
END $$;

src/dataplatform/adapters/sql/postgres_meta.sql:615A void wins over whatever the file log says. Otherwise the newest file log row of the batch key decides.
CREATE OR REPLACE FUNCTION runtime.batch_status(p_source TEXT, p_dataset TEXT, p_batch_key TEXT) RETURNS TEXT
LANGUAGE plpgsql STABLE SECURITY DEFINER SET search_path = pg_catalog, pg_temp AS $$
DECLARE ds BIGINT := config._dataset_id(p_source, p_dataset);
BEGIN
    IF EXISTS (SELECT 1 FROM runtime.batch_void v WHERE v.dataset_id = ds AND v.batch_key = p_batch_key) THEN
        RETURN 'void';
    END IF;
    RETURN (SELECT f.status FROM runtime.file_log f WHERE f.dataset_id = ds AND f.batch_key = p_batch_key
            ORDER BY f.file_id DESC LIMIT 1);
END $$;

The adapter: one method per function

src/dataplatform/adapters/postgres_meta.py:175A typical method. It holds no table name and no rule. It passes its arguments to the function.
    def finish_dataset_run(self, run_id: str, source: str, dataset: str, status: str,
                           counts: dict[str, int] | None = None, watermark: str | None = None,
                           bookmarks: dict[str, str] | None = None, message: str = "") -> None:
        self._call("SELECT runtime.finish_dataset_run(%s, %s, %s, %s, %s::jsonb, %s, %s::jsonb, %s)",
                   (run_id, source, dataset, status, self._json(counts or {}), watermark,
                    self._json(bookmarks or {}), message))

The connection is set to commit each statement on its own, so one function call is one transaction. That is what makes a function such as finish_dataset_run all or nothing.

The settings these functions read

The functions read no setting. Their limits are constants in the SQL: a reason must have at least 10 characters, a stored message is cut at 4000 characters, and a lease needs a positive time limit. The same constants are in src/dataplatform/meta/port.py so the in-memory adapter behaves the same way.

How it is tested

Each function has cases in the contract table of tests/dataplatform/test_meta_store.py, both for what it returns and for each refusal. The same cases run against the in-memory adapter, which is how the two are kept in step.

Not built yet, or known gaps
  • Three functions have no caller in the platform code that I could find: runtime.reset_watermark, runtime.log_dq_results and runtime.dq_results. They are tested but not yet used by a pipeline or a tool. The table runtime.dq_result therefore stays empty in a normal run.
  • There is no function to reset or delete a bookmark, to delete a dataset, or to read the domain row.
  • There is no function that lists runs for a pipeline to inspect. The only reader across runs is runtime.ops_run_log in the operations file.
  • My list of callers comes from searching the source for each method name. A caller that reaches the store through a wrapper with a different name could be missing from it.
