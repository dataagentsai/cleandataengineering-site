Landing to bronze: the lander, the bronze columns and the formats

This page is about the two ends of the lander: what a delivery in landing looks like, and what a row in bronze looks like once the lander has written it.

Both ends are built so that a mistake can be undone. Landing keeps the bytes as they arrived, so a bad read can be done again. Bronze keeps the batch key on every row, so a batch can be found, replaced or removed as a unit.

Two landers in the code

The repository has two. src/dataplatform/lander.py is the first one, written for the first slice of the platform with a single dataset. It still runs in that slice's test. The lander that loads the nine tyre datasets is the function enter in src/dataplatform/ingest/steps.py, described in Entry steps. The two share ideas and differ in details, which the table lists.

def land(cfg: dict[str, Any], contract: dict[str, Any], landing: LandingStore, meta: MetadataStore,
         writer: TableWriter, runlog: RunLog, run_id: str, day: int) -> list[LandOutcome]:
    source, dataset = cfg["source_name"], cfg["dataset_name"]
    allowed_extra = {c for c, _ in CHANGE_COLUMNS}
    columns = odcs.columns(contract) + CHANGE_COLUMNS + LOAD_COLUMNS
    band = cfg.get("volume", {}).get("expected_rows_per_delivery", {})
    outcomes: list[LandOutcome] = []

    for d in sorted(landing.deliveries(source, dataset), key=lambda d: (d.window, d.name)):
        key = batch_key(d.window, d.checksum)
        file_id = f"file:{d.window}/{d.name}"
        if meta.batch_status(file_id) is not None:      # this file was handled by an earlier run
            continue
        if meta.batch_status(key) == "loaded":          # new file name, same window and bytes: a resend
            reason = f"same window and bytes as batch {key}"
            meta.record_batch(file_id, d, "skipped_duplicate", run_id, reason)
            outcomes.append(LandOutcome(d, key, "skipped_duplicate", 0, reason))
            continue
        rows = landing.read(d)
        observed = set().union(*(r.keys() for r in rows)) if rows else set()
        verdict = odcs.check_columns(contract, observed, allowed_extra)
        outcome = _decide(d, key, rows, verdict, band)
        if outcome.status == "loaded":
            stamped = [{**r, "_batch_key": key, "_run_id": run_id, "_source_file": d.name, "_window": d.window}
                       for r in rows]
            writer.append(cfg["bronze_table"], stamped, columns)
        if outcome.status == "loaded":
            meta.record_batch(key, d, "loaded", run_id)
        meta.record_batch(file_id, d, outcome.status, run_id, outcome.reason)
        outcomes.append(outcome)

Landing: a delivery is written once

        window: str,
        name: str,
        data: bytes,
        rows: int,

    ) -> Delivery:
        """Store a delivery and then its manifest. Raises DeliveryExists if (window, name) was landed before."""

    def deliveries(self, source: str, dataset: str) -> list[Delivery]:
        """Deliveries that have a manifest, in window then name order."""

    def read_bytes(self, delivery: Delivery) -> bytes: ...

    def manifest(self, delivery: Delivery) -> dict[str, Any]:
        """The manifest the mover wrote, including any extra fields (feed positions, arrival time)."""
src/dataplatform/adapters/files.py:44Landing on a plain folder. The data file is written first and its manifest last.
    def put(self, source: str, dataset: str, window: str, name: str, data: bytes, rows: int,
            extra: dict[str, Any] | None = None) -> Delivery:
        if "/" in name or name.startswith(".") or "/" in window:
            raise ValueError(f"not a plain delivery name: {window}/{name}")
        folder = self._dir(source, dataset) / window
        manifest_path = folder / f"{name}.manifest.json"
        if manifest_path.exists():
            raise DeliveryExists(f"{source}.{dataset} {window}/{name} is already landed; landing is written once")
        folder.mkdir(parents=True, exist_ok=True)
        (folder / name).write_bytes(data)
        manifest = {**(extra or {}), "source": source, "dataset": dataset, "window": window, "rows": rows,
                    "file": name}
        manifest_path.write_text(json.dumps(manifest, sort_keys=True))
        return Delivery(source, dataset, window, name, checksum(data), rows)

The layout is one folder per source, dataset and business date. A delivery is two files: the data exactly as delivered, and a small JSON manifest beside it with the row count and anything the mover wants to add. Two rules make landing safe. The manifest is written last, and a data file without a manifest is not a delivery, so a half-written file is never picked up. A second write of the same date and name is refused, so a replay always reads the bytes the first run read.

New columns are held in _extra

When a source starts sending a column the contract does not have, and the manifest allows it, the batch still loads. The contract columns go to their own bronze columns. The new ones are written together as one JSON text in _extra. Nothing is lost and the bronze table's shape does not change. The outcome carries a note naming the new columns, which reaches the file log as the reason. Promoting such a column into the contract is a change to the contract file.

The bronze writer and why a rerun changes nothing

src/dataplatform/ingest/ports.py:54The port. The first two methods write. The last two answer questions for reconciliation and the mass-delete guard.
class BronzeWriter(Protocol):
    """table_writer for bronze: append-only as delivered, idempotent by batch key."""

    def write(self, table: str, batch_key: str, rows: list[Row], columns: Columns, replace: bool = False) -> int:
        """Write one batch in one transaction, replacing whatever the table holds for this batch key: the same batch
        written twice leaves the table unchanged (DUP-01, DPC-0024) and a failed write leaves no trace (ORCH-03).
        `replace` is the lander saying "this batch may be in the table already" (a reload): a writer that appends new
        batches cheaply must then replace. Returns the rows written."""

    def write_many(self, table: str, batches: list[tuple[str, list[Row]]], columns: Columns) -> int:
        """Write several new batches of one table in one transaction (one commit instead of one per batch); all or
        nothing. The lander logs them as loaded only after this returns. Returns the rows written."""

    def fingerprint(
        self, table: str, where: dict[str, str] | None = None, sums: tuple[str, ...] = ()
    ) -> dict[str, float]:
        """{"row_count": n, <column>: total, ...} for the table, or for the rows where every column equals its value.
        A table never written has row_count 0."""

    def keys(self, table: str, columns: tuple[str, ...], where: dict[str, str]) -> set[tuple[Any, ...]]:
        """The distinct values of `columns` in the rows matching `where` (the mass-delete guard's comparison)."""

A write that can be repeated safely is called idempotent. The port states it as a rule: a write replaces whatever the table holds for its batch key. Since the batch key is a hash of the content, the same content written twice replaces itself with itself.

src/dataplatform/adapters/delta_bronze.py:56Bronze on Delta tables in a folder, without a cluster. One commit that overwrites only the rows of this batch key.
    def write(self, table: str, batch_key: str, rows: list[Row], columns: Columns, replace: bool = False) -> int:
        import pyarrow as pa
        from deltalake import write_deltalake

        check_batch_key(batch_key)  # it goes into the overwrite predicate
        schema = pa.schema([(c, _arrow_type(t)) for c, t in columns])
        data = pa.Table.from_pylist([{c: r.get(c) for c, _ in columns} for r in rows], schema=schema)
        handle = self._handle(table)
        write_deltalake(
            handle if handle is not None else str(self.path(table)),
            data,
            mode="overwrite",
            predicate=f"_batch_key = '{batch_key}'",
        )
        return int(data.num_rows)
src/dataplatform/adapters/delta_bronze.py:72Several new batches in one commit. The overwrite names exactly these batch keys.
    def write_many(self, table: str, batches: list[tuple[str, list[Row]]], columns: Columns) -> int:
        """New batches in one Delta commit; the lander logs them only after it returns."""
        import pyarrow as pa
        from deltalake import write_deltalake

        if not batches:
            return 0
        for k, _ in batches:
            check_batch_key(k)
        schema = pa.schema([(c, _arrow_type(t)) for c, t in columns])
        data = pa.Table.from_pylist([{c: r.get(c) for c, _ in columns} for _, part in batches for r in part],
                                    schema=schema)
        handle = self._handle(table)
        keys = ", ".join(f"'{k}'" for k, _ in batches)  # each checked by check_batch_key above
        # one commit that replaces exactly these batch keys: idempotent if a crash came between commit and file log
        write_deltalake(handle if handle is not None else str(self.path(table)), data, mode="overwrite",
                        predicate=f"_batch_key IN ({keys})")
        return int(data.num_rows)
src/dataplatform/ingest/ports.py:16A batch key ends up inside a filter text, so every writer checks its shape first.
SAFE_BATCH_KEY = re.compile(r"^[A-Za-z0-9_:.-]{1,128}$")  # batch keys reach a write predicate: every writer checks


def check_batch_key(key: str) -> str:
    if not SAFE_BATCH_KEY.match(key):
        raise ValueError(f"not a safe batch key: {key!r}")
    return key

src/dataplatform/adapters/table_store.py:601The engine's writer. A new batch is appended with a write mark. Only a reload takes the replace path.
    def write(self, table: str, batch_key: str, rows: list[dict[str, Any]], columns: list[tuple[str, str]],
              replace: bool = False) -> int:
        from dataplatform.ingest.ports import check_batch_key  # noqa: PLC0415 -- no ingest import at load

        check_batch_key(batch_key)  # it goes into the replace predicate
        ddl = ", ".join(f"{quoted(c)} {self.TYPES[t]}" for c, t in columns)
        df = self.store.spark.createDataFrame([tuple(r.get(c) for c, _ in columns) for r in rows], ddl)
        name = self._table(table)
        # A new batch is appended (cheap; the batch key is the write's idempotency mark). Only a batch written before,
        # a reload, takes the replace path, which rewrites the rows of that batch key in one commit. Replacing on
        # every write scanned the whole bronze table per batch (13 Nov: most of a 3-day run's time).
        # Delta's write mark must rise, so Delta always takes its native replace (cheap and idempotent there)
        delta = self.store.format == "delta"
        if delta or replace or not self.store.append("bronze", name, df, f"bronze:{name}", batch_key):
            self.store.replace_where("bronze", name, df, f"_batch_key = '{batch_key}'")
        return len(rows)

The comment in this method records a measured lesson: replacing on every write scanned the whole bronze table per batch and took most of a run's time. So on one table format a new batch is appended, and the format's own write mark, made of an application name and the batch key, stops the same batch from being appended twice.

The file log entry

src/dataplatform/ingest/steps.py:379The record of a batch. It is written after the bronze commit.
def _record(ctx: Ctx, o: Outcome) -> Outcome:
    s = ctx.spec
    ctx.store.log_file(
        FileRecord(
            ctx.run_id,
            s.source,
            s.dataset,
            o.batch_key,
            o.batch.name,
            o.batch.window,
            hashlib.sha256(o.batch.data).hexdigest(),
            o.batch.declared_rows,
            o.rows,
            o.status,
            o.reason,
            "full" if s.read == "full_copy" else "incremental",  # a full copy is a rebase point (B8)
        )
    )
    return o

The file log is what the rest of the platform trusts. Silver decides what to read from it. A reload finds a window's batches in it. Reader: picking batches and Runtime tables show both.

Not built yet, or known gaps
  • SparkBronzeWriter.write_many appends without a replace and without a write mark. If a process died after that commit and before the file log was written, the next run would append the same batches again. The other three writers guard against this. I found this writer used only by the contract test.
  • The folder landing adapter reads every delivery's bytes to compute its checksum each time it lists the deliveries of a dataset. The cost grows with the number of files kept in landing.
  • The load column names are written in two modules that must be kept in step by hand.
  • A value in _extra is text inside JSON. It is not typed and silver does not read it.
  • Compressed and archive files are recognised by the discovery helper and cannot be parsed by the lander.
  • The first lander is still in the repository beside the current one. It is not on the path of the nine tyre datasets.
