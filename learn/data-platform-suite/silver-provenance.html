Stage 13: provenance, where each row came from

The last stage finishes the row. It records which silver run handled it and when, keeps the facts about the bronze batch it came from, adds a hash of its business values, and puts the columns in one fixed order.

Provenance means the record of where something came from. When a number in a report looks wrong, these columns are how you walk back from the silver row to the run, the batch and the file. The stage before this one is stage 12, history, which has its own pages.

Goes inThe rows history produced, the run id and the load time from the context.
What happensOne column is renamed, three are added, and the columns are put in order.
Comes outThe rows exactly as the write edge will write them.

The settings that drive it

The stage reads no dataset setting. It uses the plan's list of kept columns, the run id and the load time from the context, and three fixed lists of column names in the plan module. It has no switch.

The code

src/dataplatform/stages/rows.py:72The whole stage.
def provenance(df: DataFrame, ctx: StageCtx) -> Out:
    """Where each row came from and when silver took it: batch, file, bronze window and run, silver run, load time,
    and a record hash over the business columns. Columns come out in a fixed order: contract, other source columns,
    then load, transport and silver columns."""
    plan = ctx.plan
    business = [c.name for c in plan.kept]
    out = df.withColumnRenamed("_run_id", "_bronze_run_id") if "_run_id" in df.columns else df
    out = (
        out.withColumn("_record_hash", F.sha2(F.to_json(F.struct(*[F.col(c) for c in business])), 256))
        .withColumn("_silver_run_id", F.lit(ctx.run_id))
        .withColumn("_silver_loaded_at", F.lit(ctx.loaded_at).cast("timestamp"))
    )
    fixed = [*LOAD_COLUMNS, *TRANSPORT_COLUMNS, *SILVER_COLUMNS, "_action"]
    known = set(business) | set(fixed)
    extra = sorted(c for c in out.columns if c not in known)
    order = business + extra + [c for c in fixed if c in out.columns and c != "_run_id"]
    return Out(out.select(*order))
  1. The business columns. business is the names of the kept contract columns, in contract order.
  2. Rename the bronze run. Bronze calls the run that loaded the row _run_id. In silver there are two runs to tell apart, so the column becomes _bronze_run_id.
  3. The record hash. The business columns are packed into one structure, written as JSON text, and hashed with SHA-256. More on this below.
  4. The silver run. _silver_run_id is the run id from the context, the same on every row of the run.
  5. The load time. _silver_loaded_at is the load time from the context, as a timestamp. The stage does not read the clock. If no load time was passed, the column is null.
  6. The fixed columns. fixed is the load columns, then the transport columns, then silver's own columns, then _action.
  7. Everything else. extra is every column that is neither a business column nor a fixed one, sorted by name. These are the source columns the contract does not list, and columns added on the way such as a local time.
  8. Reorder. The final order is business, then extra, then the fixed columns that the frame actually has. _run_id is left out because it was renamed.

The fixed order matters more than it looks. Rows from two batches are stacked by column name elsewhere, but a table whose columns come in a stable, predictable order is easier to read, to compare and to test. The test for this stage checks that the first three columns are the contract's.

How the record hash is computed

Take the test's row: id is a, v is 1, seq is 2. The three steps are these.

StepResult
F.struct(...) packs the business columns, in contract orderone value with three named fields
F.to_json(...) writes it as text{"id":"a","v":1,"seq":2}
F.sha2(..., 256) hashes the texta54293011ea10149452d63d0aecefc4d8b15607ca6493bc30910599c25022f31

JSON is used and not a plain join of the values, because JSON carries the column names and the types. The number 1 and the text "1" are written differently, and a value cannot slide from one column into the next. So the key hash needs a separator and the record hash does not.

The hash covers the kept contract columns only. It does not cover other source columns, _extra, or any underscore column. Two rows with the same business values from two different batches have the same record hash.

One difference between engines is recorded in the tests. Spark leaves a missing field out of the JSON. DuckDB writes it as null. The texts differ, so the hashes differ. A record hash must therefore be compared only with hashes made by the same engine.

Not built yet, or known gaps
  • Nothing in the stages reads _record_hash back. The history stage drops it when it takes silver's rows into its working shape, and this stage computes it again. Type 2 history decides whether a version changed from its own fingerprint of the tracked columns. The record hash is there for people and for later checks, not for the engine's decisions.
  • The record hash differs between Spark and DuckDB for a row with a missing business value.
  • A rerun of the same batch gives the same business values and the same row key, but a new silver run id and a new load time. So a rerun's merge rewrites these two columns on the rows it touches. This is my reading of the merge, which sets every column of a matched row.
  • The settings registry has a key processor_groups.provenance. No code reads it. The stage cannot be switched off.
  • The load time is one value for the whole run, not the moment each row was written.
