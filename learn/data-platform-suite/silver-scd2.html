Type 2 history: keep every version of a key

Type 2 history keeps one row for every version of a business key. When a tracked value changes, the old version is closed and a new one is opened. Nothing is overwritten, so silver can answer what was true on any past day.

The tyre company needs this for its sales order lines. On-time delivery is judged against the date that was first promised to the dealer. If silver kept only the latest promised date, a line whose date was moved would always look on time.

The hard part is not opening a version. The hard part is that changes do not arrive in order. A change made at ten o'clock can reach silver after a change made at eleven. If silver trusted the order of arrival, the older value would become the current one. So the function on this page never looks at arrival order to decide history. It uses the order the source gave.

  1. Collect the events. The new changes of this batch and the versions silver already holds for the same keys become one list of events. Each event has a position in the source's order.
  2. Open versions. Walking each key's events in that order, an event opens a new version when its tracked values differ from the tracked values before it.
  3. Pick one row per version. A version may contain several events. The one with the highest order value gives the version its values.
  4. Date, flag and key the versions. Each version gets its validity times, its current flag, its deleted flag and a row key built from the key and the version's start. Stored rows that the new history no longer contains are marked for removal.

The plan adds one more thing the function needs: the effective time. It is the time a change took effect, and it becomes the validity dates of versions. For a change feed it is the commit time the feed carries, in the column _committed_at. For other sources it is the order column, when that column is a timestamp. Materials and presses are full copies ordered by extracted_at, a timestamp, so their versions are dated by the time the copy was taken.

The code, step by step

Step 1: put stored versions and new changes in one list, in the source's order

src/dataplatform/stages/history.py:137The first lines of scd2(): the events, and the order they are walked in.
def scd2(inc: DataFrame, cur: DataFrame | None, plan: SilverPlan) -> DataFrame:
    o = plan.order_by
    new = _incoming(inc, plan).withColumn("_pos", F.col(o))
    events, rows = _events(new, cur, plan)
    # nulls placed explicitly in every window order (Spark's default, NULLS FIRST ascending): SQLFrame's window
    # orders leave it to the engine, and DuckDB puts nulls last (docs/DUCKDB-SPIKE.md)
    by_pos = Window.partitionBy("_key_hash").orderBy(F.col("_pos").asc_nulls_first(), F.col(o).asc_nulls_first(),
                                                     F.col("_existing").desc_nulls_last())

Line by line. o is the name of the order column, change_seq for the order lines. _incoming turns the new rows into events, and each new event gets a position _pos equal to its order value. _events adds the stored versions of the same keys. Both helpers are explained on the hub page. A stored version arrives with _pos equal to its _seq_from, the order value at which it started.

by_pos is the heart of the function. It is a window, which means a rule for walking rows group by group. The group is one business key. Inside a key the rows are walked by position, then by the order column, and at a tie the stored version comes before a new change. Arrival order is not in this rule at all. That one fact is why a late change lands in its proper place.

The comment about nulls matters for portability. Spark and DuckDB disagree about where an empty value sorts unless the code says so. Every window on this page states it, so the same history comes out on both engines.

Step 2: decide which events open a version

src/dataplatform/stages/history.py:130Which columns are tracked.
def _tracked(plan: SilverPlan, columns: list[str]) -> list[str]:
    if plan.track:
        return list(plan.track)
    skip = set(plan.keys) | {plan.order_by}
    return [c.name for c in plan.kept if c.name not in skip and c.name in columns]

If the manifest lists tracked columns, those are used. If it lists none, every contract column that silver keeps is tracked, except the key columns and the order column. The order column must be left out, because it changes with every change and would open a version every time.

src/dataplatform/stages/history.py:145The tracked hash, the value before, and the two columns that mark versions.
    tracked = F.sha2(text_parts(_tracked(plan, events.columns)), 256)
    # last_value(..., ignoreNulls) rather than last(ignorenulls=True): the same window function, and the form every
    # engine the stages run on keeps the null skipping of (docs/DUCKDB-SPIKE.md)
    before = F.last_value("_t", F.lit(True)).over(by_pos.rowsBetween(Window.unboundedPreceding, -1))
    events = (
        # a delete event never opens a version (it marks the one it falls in); a stored version keeps its values
        events.withColumn("_t", F.when((F.col("_op") == "D") & ~F.col("_existing"), F.lit(None)).otherwise(tracked))
        .withColumn("_new", F.when(before.isNull(), True).when(F.col("_t").isNull(), False)
                    .otherwise(F.col("_t") != before))
        .withColumn("_ver", F.sum(F.col("_new").cast("int")).over(
            by_pos.rowsBetween(Window.unboundedPreceding, Window.currentRow)))
    )
ColumnWhat it holdsWhy
_tA hash of the event's tracked values. A hash is a short fingerprint: two rows with the same tracked values have the same hash. A new delete event has no hash.Comparing one fingerprint is simpler than comparing every tracked column. A delete says the row is gone, not that a value changed, so it must not look like a change.
beforeThe most recent hash among the earlier events of the same key, skipping events that have none.Skipping empty hashes means a delete does not break the chain. The event after a delete is compared with the values before the delete.
_newTrue when this event opens a version.See the three rules below.
_verA running count of the true values of _new within the key.Events with the same count belong to the same version.

The three rules for _new are read in order. If there is no hash before this event, it is the first event of the key and it opens the first version. Otherwise, if this event has no hash, it is a delete and it opens nothing. Otherwise it opens a version exactly when its hash differs from the hash before it.

Step 3: one row per version

src/dataplatform/stages/history.py:157From events to versions: the start, the earliest time, and the row that represents the version.
    group = Window.partitionBy("_key_hash", "_ver")
    latest = group.orderBy(F.col(o).desc_nulls_last(), F.col("_existing").asc_nulls_first(), *arrival_desc(events))
    versions = events.withColumns({
        "_start": F.min("_pos").over(group),
        "_gts": F.min("_ts").over(group),
        "_rn": F.row_number().over(latest),
    }).where("_rn = 1")

A version can hold more than one event. A change to a column that is not tracked falls into the version that is open at that point. Three values are computed over the events of a version.

ColumnWhat it is
_startThe lowest position in the version. This is where the version begins in the source's order.
_gtsThe earliest effective time in the version.
_rnA rank. Rank 1 is the event with the highest order value. At a tie a new change beats a stored version, and after that the newest arrival wins.

Only rank 1 is kept. So a version takes its start from its earliest event and its values from its latest event. The tie rules make a resent change harmless: the same change delivered twice has the same order value, and the newest delivery simply replaces the older one.

Step 4: validity dates, flags and the row key

src/dataplatform/stages/history.py:164The last lines of scd2(): the columns silver stores for each version.
    per_key = Window.partitionBy("_key_hash").orderBy(F.col("_start").asc_nulls_first())
    deleted = F.col("_op") == "D"
    out = versions.withColumns({
        "_valid_from": F.min("_gts").over(per_key.rowsBetween(Window.currentRow, Window.unboundedFollowing)),
        "_is_current": F.lead("_start").over(per_key).isNull(),
        "_is_deleted": deleted,
        "_deleted_at": F.when(deleted, F.col("_dts")),
        "_seq_from": F.col("_start"),
        "_row_key": F.sha2(F.concat_ws("|", F.col("_key_hash"), F.col("_start").cast("string")), 256),
    }).withColumn("_valid_to", F.lead("_valid_from").over(per_key))
    return _finish(out, _stale(rows, out), plan)
ColumnHow it is computedWhat to notice
_valid_fromThe lowest effective time among this version and every later version of the key.Looking at later versions too keeps the dates in step with the source's order. A version can never start after a version that follows it.
_valid_toThe _valid_from of the next version. Empty for the last version.The end of one version is exactly the start of the next. There are no gaps and no overlaps.
_is_currentTrue when no version follows.At most one version per key is current.
_is_deletedTrue when the row that represents the version is a delete.A delete marks the version it falls in. It does not close it.
_deleted_atThe effective time of that delete.
_seq_fromThe version's start in the source's order.The next run reads it back as the stored version's position.
_row_keyA hash of the key hash, a bar character and the version's start.This is what makes each version its own row in the merge.

The rule for _valid_from deserves an example. In case 5 below, the late change was committed at 01:05, an hour after the newer change was committed at 00:05. Dated by its own commit time, the middle version would start after the version that follows it. The rule gives it the lowest time among itself and the later version, which is 00:05. Its validity then runs from 00:05 to 00:05. It has zero length. The version is in history and can be read, but a lookup for the value that was true at some moment never lands on it.

The last line calls _stale and _finish. A stored row of a touched key whose row key is not among the new rows gets the action delete. Case 6 below shows why that is needed. Every other row gets upsert. The writer then applies them in one merge on _row_key.

Why running the same batch again changes nothing

Nothing in the function depends on when it runs or how often. Positions come from the order column. Versions come from the tracked hash. The row key comes from the key and the version's start. A second run of the same batch adds events that have the same order value as events already folded into the stored versions. They fall into the same versions, the same row wins rank 1 with the same values, and every row key is one silver already has. The merge updates each row to what it already is. Case 8 proves it. One stage earlier, stage 10 has already dropped a change that appears twice inside one batch.

How it is tested

The history section of tests/dataplatform/test_silver_stages.py runs all thirteen stages for each batch and keeps silver in memory, applying the row keys and actions the way the merge would.

tests/dataplatform/test_silver_stages.py:349The test's stand-in for the merge: rows whose key is not in the new output are kept, upserts are added.
def _apply(spark, p, batches, ddl=FEED):
    """Run every stage for each batch and keep silver as a frame (a merge on _row_key done in memory)."""
    current = None
    for n, data in enumerate(batches, 1):
        df = frame(spark, ddl, data, batch=f"b{n}", window=f"2026-11-{8 + n:02d}")
        out, _, _ = run_stages(p, df, current, f"silver-{n}", f"2026-11-{8 + n:02d}", hold=stage_hold(df))
        out = hold(out)
        keep = [] if current is None else (
            current.join(out.select("_row_key"), "_row_key", "left_anti").select(*current.columns).collect())
        new = out.where("_action = 'upsert'").drop("_action")
        current = new if not keep else new.unionByName(spark.createDataFrame(keep, current.schema))
        current = hold(current)
    return current

What the recorded run shows

In the recorded 14-day run of the tyre company at full scale (4 November 2026, local Spark), a promised date was changed out of order on day 8. The design note records the verdict: three versions, the late change with sequence 87216 in history and not current, and the current promised date 2026-11-20. On day 14 silver held 113,457 current order lines in 121,322 versions, equal to the oracle. The numbers are quoted from docs/W1C-SILVER.md. The run was not repeated for this page.

Not built yet, or known gaps
  • A stored version remembers its start and its latest values, not every change that fell into it. If a tracked value changes and later changes back, and the middle change arrives after the last one was already folded into the stored version, the middle change is placed after that version and becomes current. Checked by running it: value 1 at sequence 1, a note change at sequence 3, then a late value 2 at sequence 2 leaves value 2 current. The source's true latest value is 1. A test case named late-after-flip-back in test_silver_stages.py states the right answer and is marked as a known failure, so the bug stays visible and the case turns red the day it is fixed.
  • When the order column is not a timestamp and the source is not a change feed, there is no effective time, so _valid_from and _valid_to stay empty. The versions are still right. The full copy test cases run this way.
  • Every version of a touched key is written again in the merge, not only the versions that changed.
