Silver to gold: the harness that builds facts and dimensions

Gold data modelling said what to build: facts and dimensions. This page is how to build them from silver every night, without losing, doubling or silently changing a number, and without the cost growing with history. It starts from zero with one small worked example, then covers the six kinds of fact and whether this layer can be a Databricks declarative pipeline, and ends with the full rulebook.

In one paragraph. One harness builds every gold table the same way. It reads only what changed in silver since its watermark, works out which windows of the fact (days, months, hours) those changes touch, rebuilds just those windows with a small pure build per fact, looks up keys as of each event, checks everything before writing, replaces the windows, logs any number that changed after it was published, and moves the watermark last. Because the build is pure, it is tested on a laptop with small tables and with a whole synthetic company that plants problems on purpose.

Words you will meet

WordWhat it means here
SilverClean copies of the source tables, still shaped like the source (an orders table, a deliveries table).
GoldTables shaped for questions: facts and dimensions. What dashboards, metric views and AI agents read.
FactA table of things that happened or were measured, with numbers (tyres ordered, tyres delivered).
DimensionA table that describes the who, what and where of a fact (the dealer, its name, its region).
GrainWhat one row of a fact means, in one sentence. Here: one row per order line.
Surrogate keyA number gold gives each dimension row (dealer_key 2), instead of the source's own id. It lets one dealer have several versions.
SCD Type 2Keeping history in a dimension: when a dealer moves region, the old row is closed and a new row opens. Both stay.
WindowA slice of the fact rebuilt as one piece. Here: one day of promised date.
Watermark (bookmark)The last change number this table has already used. The next run starts after it.
High markThe newest change number when a run starts. The run reads up to it and no further.
LookbackHow old a window may be and still be rebuilt automatically (35 days here). Older fixes need a correction plan.
CompletenessA window is complete when every feed that owes data for it has sent it.
RestatementA number that was already published and has now changed. Logged with old value, new value and reason.
IdempotentRunning it twice gives the same result as running it once.
Pure functionCode that only turns inputs into outputs: it reads no tables, writes nothing and never asks the time.
HarnessThe shared code that runs every gold table the same way. Only the business rule is written per table.

Part A · 1

The story: a tyre company and one question

A tyre maker sells to dealers. A sales director asks one question every morning: what percent of order lines did we deliver on time and in full (OTIF), per region, per day? "On time" means the last delivery came on or before the promised date. "In full" means all the tyres ordered were delivered. A line counts towards OTIF only if both are true.

Silver already holds clean data from three sources. Gold must turn it into a fact and a dimension that answer the question. A program called the harness does that every night.

Part A · 3

Night 1 (run r1, 13 Nov), step by step

Steps 1 and 2: where did I stop, and what changed since?

The metadata store says the last run used order lines up to change 1001 and deliveries up to change 2101. Those are the watermarks. At the start, the run notes the newest change numbers that exist right now, 1046 and 2205. Those are the high marks, and they do not move during the run. The run reads only the rows in between.

Read a closed range: after the watermark, up to the high mark. Anything newer waits.

inputwatermark (from last run)high mark (fixed at start)rows read
order_lines10011046L1 to L6 (6 rows)
deliveries21012205X1 to X5 (5 rows)

Why change numbers and not times? Two rows can have the same time, and clocks on different servers disagree. A change number only goes up and never repeats, so nothing is skipped or read twice.

Step 3: which windows do the changes touch?

The fact is rebuilt one day of promised date at a time. Each changed row points at one day. A delivery has no promised date of its own, so it points at the day of its order line.

Changes become a short list of days. Only those days are rebuilt.

Result: run r1 rebuilds 10 Nov, 11 Nov, 13 Nov. The 5 Nov window is never read again. That is why the run's cost follows the number of changes, not the size of history. With years of history, a night still rebuilds only a few days.

The run then reads every silver row of those three days, not just the changed ones. A day is rebuilt whole, so it must be built from the full set of its rows.

Step 4: the build (processor)

The build is the only code written for this fact. It gets the order lines and deliveries for the three days and returns one row per line with the OTIF flags. Note the first thing it does: add up deliveries per line before joining. Section 6 below shows what happens without that.

def build_otif(lines: DataFrame, deliveries: DataFrame, params: dict) -> DataFrame:
    per_line = (deliveries.groupBy("line_id")                                       # one row per line FIRST,
                .agg(F.sum("qty").alias("qty_delivered"),                           # so the join below can
                     F.max("delivered_date").alias("last_delivered")))              # never multiply lines
    j = lines.join(per_line, "line_id", "left")
    qty_del = F.coalesce("qty_delivered", F.lit(0))
    on_time = F.coalesce(F.col("last_delivered") <= F.col("promised_date"), F.lit(False)).cast("int")
    in_full = (qty_del >= F.col("qty_ordered")).cast("int")
    return j.select("line_id", "dealer_id", "promised_date", "qty_ordered",
                    qty_del.alias("qty_delivered"), on_time.alias("on_time"), in_full.alias("in_full"),
                    (on_time * in_full).alias("otif"))

Step 5: keys as of the event date

Dealer D7 moved from North to West on 12 Nov. Which region should L3 count under? The region that was true on the line's date. L3 was promised on 11 Nov, when D7 was North. The harness finds the dimension version whose valid_from to valid_to range holds the promised date and takes its key.

Each line gets the dealer version that was true on its own date.

The wrong way is to join each line to the dealer's current row. These rows come from the run. Compare the last two columns:

L110 Nov1NorthNorth
L210 Nov0NorthNorth
L311 Nov0NorthWest

With the right lookup, North's OTIF on these lines is 1 of 3 and West's is 1 of 1. With the wrong one, L3 jumps to West: North becomes 1 of 2 and West 1 of 2. Every past report would change each time a dealer moves. That is exactly what SCD Type 2 and as-of lookups prevent.

L5's dealer, D9, is not in the dimension at all. The line still goes into gold, but with key -1 ("unknown dealer"), and it is counted. It is not dropped: dropping it would quietly lose 6 tyres from every total. The code:

def lookup_keys(fact: DataFrame, dim: DataFrame, bk: str, key: str, as_of: str) -> DataFrame:
    """Find the dimension version that was true ON THE EVENT DATE. Missing member -> -1 (unknown)."""
    d = dim.select(F.col(bk).alias("_bk"), key, "valid_from", "valid_to")
    on = (F.col(bk) == F.col("_bk")) & (F.col(as_of) >= F.col("valid_from")) & (F.col(as_of) < F.col("valid_to"))
    out = fact.join(F.broadcast(d), on, "left").drop("_bk", "valid_from", "valid_to")
    return out.withColumn(key, F.coalesce(F.col(key), F.lit(-1)))

Step 6: complete or not, check, and count

Both warehouses owe a delivery file every day. On the night of 13 Nov, WH-B's file for 13 Nov has not come. So the 13 Nov window is written with _is_complete = false. Readers and dashboards can show "not final yet" instead of a number that will change. 10 and 11 Nov have both files, so they are complete.

Before writing anything, the harness counts rows at each step (the row ledger) and checks: one row per line, the ledger balances, the join added and lost nothing, and unknown dealers stay under their limit.

Every row is accounted for. A missing or extra row stops the run before it writes.

Step 7: replace the windows, then move the bookmark

The writer replaces the three days whole. It does not add rows on top: run it twice and you get the same table. Only after the write succeeds does the run log its work and move the watermarks to 1046 and 2205. If anything fails before that, the bookmark stays put and the next run simply does the work again.

def replace_windows(spark, df: DataFrame, path: str, window_col: str, windows: list):
    """Replace whole windows. Running it twice gives the same table; rows deleted at source simply vanish."""
    if not DeltaTable.isDeltaTable(spark, path):
        df.write.format("delta").save(path)
        return
    cond = f"{window_col} IN ({', '.join(repr(str(w)) for w in windows)})"
    df.write.format("delta").mode("overwrite").option("replaceWhere", cond).save(path)

Part A · 5

What if the machine dies halfway?

We made run r2 crash on purpose, after it had written gold but before it moved the bookmark ("machine lost"). Then we ran it again.

Bookmark last, windows replaced whole: a crash means repeated work, never lost or doubled numbers.

Result: the table after the rerun is identical to the table the crashed run wrote: yes. Both restatements are logged once. Final watermarks: order_lines 1046, deliveries 2206.

A real lesson from writing this example: our first version planned the rerun by looking at gold as the crashed run had left it. The crashed run had already fixed L5's key and the 13 Nov flag, so the rerun thought 13 Nov needed nothing. It rebuilt only 11 Nov and lost the 13 Nov restatement. The fix: a run always plans and compares against the last committed version of gold (the version recorded when the bookmark last moved), never against whatever is in the table now. Delta and Iceberg keep old versions, which makes this one line.

Part A · 6

What if someone writes a careless join?

We swapped the build for a careless one that joins every delivery row straight onto the order lines. L3 has two deliveries now, so it became two rows.

One line with two deliveries becomes two rows unless deliveries are added up first.

The harness refused to write. The exact message from the run:

['grain not unique: 1 keys appear more than once', "ledger does not balance: {'read': 7, 'filtered': 1, 'after_join': 7, 'rejected': 0, 'unknown_keys': 0, 'written': 7}", 'a lookup join changed the row count: 6 in, 7 out']

Wrote anything? No. Three separate checks caught it: the grain (L3 twice), the ledger balance, and the join row count. In a notebook without these checks, the dashboard would have shown 8 extra tyres ordered, and nobody would have known why.

The whole run, as tested (harness.py, run_fact)
def run_fact(spark, meta: dict, store: Meta, silver: dict, gold_path: str, build, run_id: str, run_date, files: DataFrame):
    name, wcol, dm = meta["name"], meta["window_col"], meta["dimension"]
    driver = silver[meta["driver"]]

    # 1-2 READER: watermarks, fixed high marks, changed rows only
    marks = {i: store.watermark(name, i) for i in meta["inputs"]}
    highs = {i: high_mark(silver[i], c["bookmark"]) for i, c in meta["inputs"].items()}
    changed = {i: read_changes(silver[i], c["bookmark"], marks[i], highs[i]) for i, c in meta["inputs"].items()}

    # 3 changed rows -> windows (a child row, like a delivery, belongs to the window of its driver row)
    w = changed[meta["driver"]].select(wcol)
    for i, c in meta["inputs"].items():
        if "window_via" in c:
            w = w.union(changed[i].join(driver, c["window_via"]).select(wcol))
    v = store.data.get("versions", {}).get(name)          # plan from the last COMMITTED version, never from a
    if v is not None:                                       # crashed run's half-done write
        g = spark.read.format("delta").option("versionAsOf", v).load(gold_path)
        # also: windows holding unknown members who have now arrived, and windows not yet complete
        w = w.union(g.where(f"{dm['key']} = -1").join(silver[dm["table"]], dm["business_key"], "left_semi").select(wcol))
        w = w.union(g.where("NOT _is_complete").select(wcol))
    windows = sorted({r[0] for r in w.distinct().collect()})
    too_old = [d for d in windows if (run_date - d).days > meta["lookback_days"]]
    windows = [d for d in windows if d not in too_old]          # older changes need a correction plan
    if not windows:
        return {"run": run_id, "windows": [], "note": "nothing changed"}

    # 4 read ALL current silver rows for those windows (not just the changed ones), then the declared filters
    inputs = {meta["driver"]: driver.where(F.col(wcol).isin(windows))}
    for i, c in meta["inputs"].items():
        if "window_via" in c:
            inputs[i] = silver[i].join(inputs[meta["driver"]].select(c["window_via"]), c["window_via"], "left_semi")
    n_read = inputs[meta["driver"]].count()
    for rule in meta["filters"].values():
        inputs[meta["driver"]] = inputs[meta["driver"]].where(rule)
    n_kept = inputs[meta["driver"]].count()

    # 5 PROCESSOR: the pure build
    built = build(*inputs.values(), meta["params"])

    # 6 keys as of the event
    out = lookup_keys(built, silver[dm["table"]], dm["business_key"], dm["key"], dm["as_of"])

    # 7 completeness: every owed feed has sent its file for the window's day
    got = files.groupBy("file_date").agg(F.collect_set("warehouse").alias("got"))
    owed = F.array(*[F.lit(x) for x in meta["owed_feeds"]])
    out = (out.join(got, out[wcol] == got["file_date"], "left")
              .withColumn("_is_complete", F.coalesce(F.size(F.array_except(owed, F.col("got"))) == 0, F.lit(False)))
              .drop("file_date", "got").withColumn("_run_id", F.lit(run_id)))

    # 8 CHECKS with the row ledger
    ledger = {"read": n_read, "filtered": n_read - n_kept, "after_join": built.count(), "rejected": 0,
              "unknown_keys": out.where(f"{dm['key']} = -1").count(), "written": out.count()}
    problems = check(out, ledger, meta)
    if problems:
        raise RuntimeError(f"{run_id} stopped before writing: {problems}")   # nothing written, watermark unchanged

    # 9 restatements: compare with the last COMMITTED version (a crashed run's half-done write does not count)
    new_s = window_summary(out, meta)
    old_s = window_summary(g.where(F.col(wcol).isin(windows)), meta) if v is not None else {}
    rest = [{"run": run_id, "window": k, "old": old_s[k], "new": v} for k, v in new_s.items() if k in old_s and old_s[k] != v]

    # 10 WRITER: replace only those windows
    replace_windows(spark, out, gold_path, wcol, windows)
    version = DeltaTable.forPath(spark, gold_path).history(1).first()["version"]

    # 11 run log, then move the watermarks LAST
    run = {"run": run_id, "read_from": marks, "read_to": highs, "windows": [str(d) for d in windows],
           "refused_too_old": [str(d) for d in too_old], "ledger": ledger, "restatements": rest, "gold_version": version}
    store.commit(name, highs, run)
    return run

class Meta:
    def __init__(self, path: Path):
        self.path = path
        self.data = json.loads(path.read_text()) if path.exists() else {"watermarks": {}, "runs": [], "restatements": []}

    def watermark(self, fact, inp):
        return self.data["watermarks"].get(f"{fact}.{inp}", 0)

    def commit(self, fact, high_marks, run):
        """Called LAST, only after the write and the checks succeeded."""
        for inp, hm in high_marks.items():
            self.data["watermarks"][f"{fact}.{inp}"] = hm
        self.data.setdefault("versions", {})[fact] = run["gold_version"]   # the last version readers may trust
        self.data["runs"].append(run)
        self.data["restatements"] += run["restatements"]
        self.path.write_text(json.dumps(self.data, indent=1, default=str))


def high_mark(df: DataFrame, col: str) -> int:
    """Fixed once at the start of the run: changes arriving later wait for the next run."""
    return df.agg(F.max(col)).first()[0] or 0


def read_changes(df: DataFrame, col: str, low: int, high: int) -> DataFrame:
    """Only the rows changed after the watermark, up to the high mark: a closed range."""
    return df.where((F.col(col) > low) & (F.col(col) <= high))


def assign_keys(history: DataFrame, keymap: DataFrame, bk: str, key: str) -> DataFrame:
    """Stable surrogate keys: existing versions keep their key; new versions get the next numbers."""
    known = history.join(keymap, [bk, "valid_from"], "left")
    start = keymap.agg(F.coalesce(F.max(key), F.lit(0))).first()[0]
    rows = sorted(known.where(F.col(key).isNull()).select(bk, "valid_from").collect())
    add = [(r[0], r[1], start + i + 1) for i, r in enumerate(rows)]
    added = history.sparkSession.createDataFrame(add, f"{bk} string, valid_from date, {key} int")
    return keymap.unionByName(added)

def window_summary(df: DataFrame, meta: dict) -> dict:
    """Per window: row count, total of each measure, unknown keys. Used for restatements."""
    key, cols = meta["dimension"]["key"], ["rows"] + meta["measures"] + ["unknown_keys"]
    aggs = [F.count("*").alias("rows")] + [F.sum(m).alias(m) for m in meta["measures"]]
    aggs.append(F.sum((F.col(key) == -1).cast("int")).alias("unknown_keys"))
    s = df.groupBy(meta["window_col"]).agg(*aggs)
    return {str(r[0]): {c: r[c] for c in cols} for r in s.collect()}


def check(out: DataFrame, ledger: dict, meta: dict) -> list:
    problems = []
    dupes = out.groupBy(*meta["grain"]).count().where("count > 1").count()
    if dupes:
        problems.append(f"grain not unique: {dupes} keys appear more than once")
    if ledger["read"] != ledger["filtered"] + ledger["rejected"] + ledger["written"]:
        problems.append(f"ledger does not balance: {ledger}")
    if ledger["after_join"] != ledger["read"] - ledger["filtered"]:
        problems.append(f"a lookup join changed the row count: {ledger['read'] - ledger['filtered']} in, {ledger['after_join']} out")
    if ledger["written"] and ledger["unknown_keys"] / ledger["written"] > meta["max_unknown_rate"]:
        problems.append("too many unknown dealers")
    return problems

Part B · 1

Why are there so many kinds of fact?

Because business questions come in a few different shapes, and each shape needs rows that behave differently over time. "What happened?" needs a row per event that never changes. "How much is in stock?" needs a row per day even on quiet days. "How far along is each order?" needs one row that keeps changing. Put the wrong shape in the wrong kind of table and the numbers come out wrong, or the queries crawl.

So the kind is not decoration. It decides how the reader finds the windows and how the writer writes. That is why the harness asks for it in the settings file, and why one harness can build all six: it knows six ways to read and two ways to write, and the business rule stays in the small build.

Part B · 2

Reader, processor, writer: the three parts of every build

Reader and writer are shared; the processor is the business rule.

Reader. Its job is to answer: what changed since my bookmark, and which windows does that touch? Then it reads every row of those windows, plus small dimension tables. It never decides business meaning. It is generic: the settings say which inputs, which bookmark column and which window column.

Processor. A pure function, build(inputs, params). It gets DataFrames and returns DataFrames. It holds the one thing only your business knows: what "on time" means, how stock carries forward, how a plan meets actuals. Because it reads and writes nothing, you can test it with three rows on a laptop. In our examples the six builds are 4 to 15 lines each.

Writer. Its job is to put the rows into gold safely. For five kinds that means replacing whole windows, which is idempotent: twice is the same as once. For the accumulating snapshot it means a MERGE by key that never blanks a known milestone. Only after a successful write does the bookmark move.

Around all three, the harness adds what no single build should have to remember: keys as of the date, completeness, checks, the row ledger, restatements and the run log.

def build_daily_stock(movements: DataFrame, days: DataFrame, params: dict) -> DataFrame:
    pairs = movements.select("warehouse", "product").distinct()
    grid = pairs.crossJoin(days.select(F.col("day").alias("snapshot_date")))       # a row per pair per day
    m = movements.select("warehouse", "product", "move_date", "qty")
    j = grid.join(m, ["warehouse", "product"], "left")
    upto = F.when(F.col("move_date") <= F.col("snapshot_date"), F.col("qty")).otherwise(0)   # count, never drop, the day
    return (j.groupBy("warehouse", "product", "snapshot_date")
             .agg(F.sum(upto).cast("int").alias("stock_on_hand")))

Traps: never add stock up across days (100 on Monday plus 100 on Tuesday is not 200 tyres): it adds up across warehouses, not across time. Use the last day or the average instead. The bug our test caught lived here: a day before the first movement was dropped instead of showing 0.

def merge_by_key(spark, df: DataFrame, path: str, key: str, cols: list):
    """Only for accumulating snapshots: update the row for a key, never blank out a milestone already known."""
    if not DeltaTable.isDeltaTable(spark, path):
        df.write.format("delta").save(path)
        return
    t = DeltaTable.forPath(spark, path)
    sets = {c: F.coalesce(F.col(f"s.{c}"), F.col(f"t.{c}")) for c in cols}
    (t.alias("t").merge(df.alias("s"), f"t.{key} = s.{key}")
      .whenMatchedUpdate(set=sets).whenNotMatchedInsertAll().execute())

Traps: this is the only fact kind where rows change after they are written, so every update is effectively a restatement; and a line that never reaches 'delivered' needs an 'open' flag, or averages hide it.

Part C · 1

Can silver to gold be a Databricks declarative pipeline?

Short answer. Yes, it can run as a Lakeflow Spark Declarative Pipeline. Dimensions, aggregates and simple facts fit very well. What a declarative pipeline does not give you is the bookkeeping: choosing which windows to rebuild, logging restatements, correction plans, a full row ledger, and checks across rows. Our recommendation is the hybrid: Lakeflow for dimensions and aggregates, the harness for facts that need that bookkeeping, both in one Databricks job. Go fully declarative only for small, simple marts where no one audits past numbers.

First, what "declarative" means: you say what each table is ("fact_otif is build_otif over these silver tables"), and the engine works out how: order, what is new, retries, refresh. The harness is the opposite. You (well, the shared code) say exactly how each night runs. More on the idea itself: Declarative or not.

Part D. The full rulebook, in plain words

Everything below is reference: the rules the harness follows, in tables. If a word is new, it is in the list under Start here, and Part A shows it happening.

Silver is clean, but shaped like the sources: an orders table, a deliveries table, a dealers table with history. Gold is shaped for questions: a fact of order lines with on-time flags, a monthly sales fact, dimensions with keys. The silver-to-gold hop is the factory between them. A good factory does the same steps for every product, checks every product before it leaves, and only remakes what changed.

Same steps for every gold table; only the build in the middle is written per fact.

1. The harness

The harness, step by step

Metadata (one file per gold table) declares the kind (fact or dimension), the grain, the inputs and how each is bookmarked, the window column and lookback, the dimensions and how to look them up, and the checks. The harness reads it and runs these steps:

  1. Read each input's watermark from the metadata store and fix a high mark for this run. Changes that arrive during the run wait for the next one.
  2. Read only the silver changes between the watermark and the high mark (change sequence, file list, or commit version, per input).
  3. Turn changed rows into changed windows: the window column of each changed row (promised date, sale month, cure hour), widened by the lookback the fact declares.
  4. Overlay any correction plan due today (records from a corrections table, never edits in the source).
  5. Run the fact's build for those windows: a small SQL file or PySpark function, pure, reading only the frames it is given.
  6. Look up surrogate keys as of each row's event time; a missing member gets the unknown key (-1) and is counted.
  7. Mark each window complete or not: every input has loaded past the window's end, and every feed that owes data has sent it.
  8. Check before writing: grain unique, rows in equal rows out, totals reconcile with silver, unknown-key rate under its limit. A failure stops here; nothing is written.
  9. Replace only the windows whose numbers changed. A window published before and now different is logged as a restatement.
  10. Write the run log and move each watermark to its high mark. Last, and only on success.

1b. One harness for every fact?

Can one harness build every kind of fact?

Yes, for the mechanics: reading changes, windows, keys, completeness, checks, writing, logging. Each fact kind is a declared mode the harness knows. What one harness cannot do is decide business logic: how OTIF is defined, how a header discount is shared out over lines. That stays in a small build per fact, and it should.

Is gold too business-specific to generalise?

Partly, and that is the point of the split. Gold is the first layer where business logic cannot be avoided: silver is almost entirely generic (13 standard stages driven by metadata), while gold must know what "on time" means. But the business part is small. In our build the three facts' business logic is 116 lines in total (about 35 to 45 each), the shared harness is about 1,400 lines written once, and the six gold tables' metadata is 140 lines of YAML. So: generalise the mechanics, declare the shape, hand-write only the business rule. Never per-dataset code for the mechanics; that is where every notebook-per-table platform goes wrong.

2. Incremental loading

How incremental loading works

Incremental means a run does work in proportion to what changed, not to how much history there is. In gold that takes two moves: find the changed rows, then turn them into the windows they touch.

Read a closed range of changes, map them to windows, rebuild only those windows.

Watermarks

TopicRule
What it isA bookmark per gold table and per input: the last change this table has already used. Stored in the metadata store's run log, never in a notebook or a file.
What it is measured inA value that only goes up and never ties: a change sequence from the source, a table commit version, an ordered file list, an API cursor. Timestamps tie and go backwards with clock skew; use them only when nothing better exists, with an overlap and a dedupe.

Never past unsaved dataIf a window was held back (incomplete, failed check), the watermark does not pass it.

4. Grain and windows

Grain and windows

The fact's grain (one row per order line) says what a row is. The window says how the fact is rebuilt: by the time part of that grain. Declaring both is what lets the harness rebuild a day without touching the rest.

TopicRule
Window columnThe date that decides where a row belongs in gold: promised date for OTIF, sale month for sales, cure hour for scrap.
Window sizeThe grain of time the fact is rebuilt in: day, month or hour. Usually the time part of the fact's grain.
LookbackHow far back a late or changed row may still land (35 days for OTIF, 3 months for sales, 48 hours for scrap). Changes older than that go through a correction plan.
Replace, not mergeThe whole window is recomputed and replaced. Running it twice gives the same table; a deleted source row disappears without a delete rule.
On incompletePublish the window flagged incomplete (readers see it is not final), or hold it until complete. Declared per fact.
RestatementA window that was published and later changes is recorded with its old and new numbers, the reason (late data or a correction plan) and the run.

5. Completeness

Completeness and restatements

A number shown before all its data arrived is a promise that will change. The harness says so on the row (_is_complete) and records the change when it comes.

A month owed files by many dealers is complete only when the last owed file is in.

A real lesson from our tests: our test oracle once expected October to complete on the day the late dealer's file arrived. The harness kept October open, because other dealers' files were still owed that day, and it was right. Completeness is "every owed feed has delivered", not "the late one arrived".

10b. Reuse first

Has the industry solved this layer?

Partly. The common mechanics (incremental by time window, SCD2 dimensions, tests, safe releases) are well solved by open tools. What no tool we know gives out of the box is the gold-specific part: keys looked up as of the event with late members, a window being complete only when every owed feed has delivered, a logged restatement when a published number changes, correction plans, and a row ledger. Our recommendation is to build only that part, and to put it on top of an open tool where a team already uses one, not to rebuild what dbt or SQLMesh already do well.

FAQ

Questions people ask

How does incremental loading from silver to gold work?

Each gold table keeps a watermark per input. A run fixes a high mark, reads only the changes between the two, turns the changed rows into the windows they touch (plus a lookback), rebuilds only those windows from silver, checks them, replaces them in gold, and moves the watermark last.

What is a watermark in data engineering?

A bookmark of the last change a table has already processed, stored per table and per input in a metadata store. It should be a value that only goes up and never ties, such as a change sequence or a commit version, and it moves only after a run has written and checked its output.

Why rebuild whole windows instead of merging rows?

A window (a day, a month, an hour) recomputed and replaced whole is idempotent, removes deleted rows without delete rules, and is cheap because only changed windows are touched. Row-level MERGE is kept for accumulating snapshots that update by key.

How do I test a silver-to-gold pipeline locally?

Keep each fact's build a pure function of its input frames, put reading and writing in adapters, and test the build with small tables in and expected rows out. Then run the whole hop on a synthetic world with planted incidents, comparing gold with the world's own truth after every day, on a laptop with DuckDB or local Spark.

How does gold handle late-arriving data?

Late facts inside the lookback rebuild their window and are logged as restatements; older ones go through a correction plan. A window owed data by several feeds stays flagged incomplete until all have arrived. Facts whose dimension member is missing get the unknown key and are re-keyed when it appears.

Why are there so many types of fact table?

Because business questions come in different shapes. Events that happened once need a row per event (transaction). Levels like stock need a row per period even on quiet days (periodic snapshot). Processes with several steps need one row updated as it moves (accumulating snapshot). Events with nothing to measure need rows without numbers (factless). Busy questions need a summary (aggregate), and comparing sources needs one shared grain (consolidated). The kind decides how a pipeline reads changes and how it writes.

Can the silver to gold layer be built as a Databricks declarative pipeline?

Yes. AUTO CDC builds SCD Type 2 dimensions and materialized views build facts and aggregates, with expectations for quality. What it does not give is control over which windows are rebuilt, a restatement log, correction plans, a full row ledger or checks across rows. A hybrid works best: Lakeflow for dimensions and aggregates, a harness for facts that need that bookkeeping.

What are reader, processor and writer in a data pipeline?

The reader finds what changed since the last run and reads the rows of the windows it touches. The processor is a pure function holding the business rule, which takes data in and returns data out. The writer puts the result into the target safely, by replacing whole windows or merging by key, and only then is the bookmark moved.
