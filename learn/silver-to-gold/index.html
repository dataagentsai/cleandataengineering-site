Silver to gold: the harness that builds facts and dimensions

Gold data modelling said what to build: facts at a declared grain, conformed dimensions, surrogate keys. This page is how to build it from silver, every day, without losing, doubling or silently changing a number, and without the cost growing with history. It describes the harness as we built and run it, and links to the gold harness spec for the full requirements.

In one paragraph. One harness builds every gold table the same way. It reads only what changed in silver since its watermark, works out which windows of the fact (days, months, hours) those changes touch, rebuilds just those windows with a small pure build per fact, looks up keys as of each event, checks everything before writing, replaces the windows, logs any number that changed after it was published, and moves the watermark last. Because the build is pure, it is tested on a laptop with small tables and with a whole synthetic company that plants problems on purpose.

Lesson first

In plain words

Silver is clean, but shaped like the sources: an orders table, a deliveries table, a dealers table with history. Gold is shaped for questions: a fact of order lines with on-time flags, a monthly sales fact, dimensions with keys. The silver-to-gold hop is the factory between them. A good factory does the same steps for every product, checks every product before it leaves, and only remakes what changed.

Same steps for every gold table; only the build in the middle is written per fact.

1. The harness

The harness, step by step

Metadata (one file per gold table) declares the kind (fact or dimension), the grain, the inputs and how each is bookmarked, the window column and lookback, the dimensions and how to look them up, and the checks. The harness reads it and runs these steps:

  1. Read each input's watermark from the metadata store and fix a high mark for this run. Changes that arrive during the run wait for the next one.
  2. Read only the silver changes between the watermark and the high mark (change sequence, file list, or commit version, per input).
  3. Turn changed rows into changed windows: the window column of each changed row (promised date, sale month, cure hour), widened by the lookback the fact declares.
  4. Overlay any correction plan due today (records from a corrections table, never edits in the source).
  5. Run the fact's build for those windows: a small SQL file or PySpark function, pure, reading only the frames it is given.
  6. Look up surrogate keys as of each row's event time; a missing member gets the unknown key (-1) and is counted.
  7. Mark each window complete or not: every input has loaded past the window's end, and every feed that owes data has sent it.
  8. Check before writing: grain unique, rows in equal rows out, totals reconcile with silver, unknown-key rate under its limit. A failure stops here; nothing is written.
  9. Replace only the windows whose numbers changed. A window published before and now different is logged as a restatement.
  10. Write the run log and move each watermark to its high mark. Last, and only on success.

1b. One harness for every fact?

Can one harness build every kind of fact?

Yes, for the mechanics: reading changes, windows, keys, completeness, checks, writing, logging. Each fact kind is a declared mode the harness knows. What one harness cannot do is decide business logic: how OTIF is defined, how a header discount is shared out over lines. That stays in a small build per fact, and it should.

Fact kindHow the harness builds itIn our build
Transaction factReplace changed windows of the event dateBuilt (order lines, scrap)
Periodic snapshotRebuild the open period; closed periods frozen; completeness per periodBuilt (monthly sales)
Accumulating snapshotUpsert by grain key as milestones arrive (the one mode that MERGEs rows)Owed: a declared fact mode
Factless factSame as transaction, with no measuresSame code path
Aggregate factRebuild the windows its source fact changedSame code path, input is a gold fact
Consolidated fact (plan vs actual)Each input added up to the common grain in the buildSame code path
DimensionsOne shared dimension pipeline, no code per dimensionBuilt
Bridge tables with weightsBuilt with their dimension; weights checked to add to 1Owed

Is gold too business-specific to generalise?

Partly, and that is the point of the split. Gold is the first layer where business logic cannot be avoided: silver is almost entirely generic (13 standard stages driven by metadata), while gold must know what "on time" means. But the business part is small. In our build the three facts' business logic is 116 lines in total (about 35 to 45 each), the shared harness is about 1,400 lines written once, and the six gold tables' metadata is 140 lines of YAML. So: generalise the mechanics, declare the shape, hand-write only the business rule. Never per-dataset code for the mechanics; that is where every notebook-per-table platform goes wrong.

PartGeneric or per factWhere it lives

How to keep the common and the specific apart

The build: SQL or PySpark DataFrames?

Both, chosen per fact, behind the same build interface. Default to SQL; use PySpark when the logic is genuinely complex. In our build the two sales facts are SQL and the scrap fact (hours, shifts, plant time zones) is PySpark.

1c. Developer friendly

Troubleshooting: seeing the intermediate results

People can fix only what they can see. A harness that hides its steps is worse than a notebook. So every step must be visible: what was read, what each step produced, and where rows came and went.

FeatureWhat the developer getsState
Each SQL build is a file of named steps (CTEs)Run any step alone in a SQL editor against the same inputsBuilt: fact_otif.sql, fact_sales.sql
The harness logs the exact SQL it ran, with the window values filled inCopy, paste, runProposed
Inspect mode for one run and a few windowsEvery step's output saved to a scratch schema keyed by run id: changed rows, windows, build output before and after key lookup, rows rejected, check resultsProposed: off by default, sampled, auto-dropped after a few days
Replay one window locallyThe run log holds the input ranges; a command rebuilds that window on a laptop from a copy of those inputsProposed
Row counts per step in the run logSee where rows were added or lost without rerunningBuilt for silver stages and gold totals; per-join counts proposed
Checks name their rowsA failed check lists sample keys, not just a countPartly built

Where exactly records drop: the row ledger

Every run keeps a ledger of rows per step. When totals are wrong, the ledger shows the step where they changed, without rerunning anything.

Ledger lineWhat is countedStep
Rows read per inputRows in the changed range of each inputReading
FilteredRows removed by a declared filter (cancelled, test dealers), counted per filter nameBuild
After each joinRows out against rows in, per join; a lookup join must never add rows and never lose rowsBuild
Unknown keysRows given -1 because the member is missing, per dimensionKey lookup
RejectedRows that broke a rule, with the reason, in a rejects tableChecks
WrittenRows in the replaced windowsWrite
The balanceRows read = filtered + rejected + written (or the aggregate's declared rule); totals of each measure equal silver's for the same windowsBefore publish

Catching many-to-many joins

A join that silently matches several rows multiplies totals. The harness checks for it at four points:

WhereCheckWhat it catches
Before the joinCheck the dimension side is unique on the join key (one row per surrogate key, or per business key and version range)Stops the run and names the duplicate keys
At the joinCount rows out against rows in; for a lookup join they must be equalFails the build step that grew
SCD2 rangesNo overlapping valid_from / valid_to for a member, checked every runAn overlap would match two versions
Real many-to-manyModel it with a bridge table and weights that add to 1Totals stay right when an order line has two sales reps
Grain after the buildThe fact is unique on its grain columnsCatches anything that slipped through

2. Incremental loading

How incremental loading works

Incremental means a run does work in proportion to what changed, not to how much history there is. In gold that takes two moves: find the changed rows, then turn them into the windows they touch.

Read a closed range of changes, map them to windows, rebuild only those windows.

Table kindIncremental patternWhy
FactsRebuild changed windows from silverA window is small (a day, a month, an hour), rebuilt whole, so the write is idempotent and needs no row-by-row MERGE
Dimensions (SCD Type 2)Through one shared dimension pipeline; replace the dimension when it changedDimensions are small; history comes from silver's SCD2 rows, keys from the key map stay stable
Very large dimensionsMERGE only changed membersWorth it above tens of millions of members
Aggregate tablesRebuild the windows the atomic fact changedSame windows, same checks
Full rebuildOnly on a declared backfill, with its own run id and the same checksNever as the daily default: cost grows with history, not with change

What gold reads from silver incrementally, and what in full

Silver inputHow gold reads itNote
Transactional tables with a change feed (order lines, deliveries, production)Incremental: rows changed since the watermark, by change sequenceThen the whole changed windows are recomputed from silver's current rows
Event streams (sensor readings)Incremental: by arrival or commit, mapped to event-time windows with a lookbackLate events inside the lookback rebuild their window
File-per-period feeds (a dealer's monthly file)Incremental per feed: each feed's newest file is a mark; a window waits until every owed feed has deliveredRe-sent copies are refused before silver
Small dimensions' sources (dealers, materials, presses)Full read of silver's current and history rows: small, so a full read is cheaper than tracking changesSwitch to incremental above tens of millions of members
Dimension slices during a fact buildOnly the members whose keys appear in the changed rows, as of their event timesBroadcast when small
Full daily copies from the source (a materials copy)Silver turns the copy into changes; gold reads silver like any other tableA short copy is held in bronze, never passed on (mass-delete guard)
Gold facts read by aggregatesIncremental: the windows the atomic fact changed in this runNever the whole fact
Backfill, history load, rule changeFull for a declared date range, through the same harnessLogged, checked, compared before release

3. Watermarks

Watermarks

TopicRule
What it isA bookmark per gold table and per input: the last change this table has already used. Stored in the metadata store's run log, never in a notebook or a file.
What it is measured inA value that only goes up and never ties: a change sequence from the source, a table commit version, an ordered file list, an API cursor. Timestamps tie and go backwards with clock skew; use them only when nothing better exists, with an overlap and a dedupe.
Fixed high markFixed at the start of the run, so the run reads a closed range and a rerun reads the same range.
Moves lastOnly after the write and the checks succeed. A crash before that repeats work; it never leaves a gap.
Never past unsaved dataIf a window was held back (incomplete, failed check), the watermark does not pass it.
Second job: completenessAn input's watermark says how far its data is loaded. A window is complete when every input's watermark is past the window's end.
Reset is an eventMoving a watermark back (to reload) is a logged action with a reason, never a silent edit.

4. Grain and windows

Grain and windows

The fact's grain (one row per order line) says what a row is. The window says how the fact is rebuilt: by the time part of that grain. Declaring both is what lets the harness rebuild a day without touching the rest.

TopicRule
Window columnThe date that decides where a row belongs in gold: promised date for OTIF, sale month for sales, cure hour for scrap.
Window sizeThe grain of time the fact is rebuilt in: day, month or hour. Usually the time part of the fact's grain.
LookbackHow far back a late or changed row may still land (35 days for OTIF, 3 months for sales, 48 hours for scrap). Changes older than that go through a correction plan.
Replace, not mergeThe whole window is recomputed and replaced. Running it twice gives the same table; a deleted source row disappears without a delete rule.
On incompletePublish the window flagged incomplete (readers see it is not final), or hold it until complete. Declared per fact.
RestatementA window that was published and later changes is recorded with its old and new numbers, the reason (late data or a correction plan) and the run.

5. Completeness

Completeness and restatements

A number shown before all its data arrived is a promise that will change. The harness says so on the row (_is_complete) and records the change when it comes.

A month owed files by many dealers is complete only when the last owed file is in.

A real lesson from our tests: our test oracle once expected October to complete on the day the late dealer's file arrived. The harness kept October open, because other dealers' files were still owed that day, and it was right. Completeness is "every owed feed has delivered", not "the late one arrived".

6. Late data

Late facts and late dimensions

CaseWhat the harness doesExample
Late fact inside the lookbackIts window is rebuilt; the change is a restatement if the window was already publishedLate sensor readings, a delivery recorded a day late
Late fact outside the lookbackGoes through a correction plan with the windows it may touch, approved and datedA promised date corrected after the month closed
Late feed (a file per dealer)The window stays incomplete until every feed that owes data has sent it, then completes and restatesOne dealer's October file arrives late
Re-sent fileRefused at landing as a duplicate; gold does not change and nothing is restatedThe same file sent twice under a new name
Dimension member arrives after its factsFacts get the unknown key (-1) and are counted as orphans; re-keyed in the run where the member appearsOrders for a new dealer before the dealer list has it
Source deletesSilver marks the row deleted; the window rebuild leaves it out of goldCancelled order lines hard-deleted at source

Inferred members (a placeholder dimension row with a real key, filled in later) are the alternative to the unknown key; both are compared on the gold harness spec.

6b. Loads that are not daily

History load, reloads and hiding a bad batch

The history load

The first load of years of history is just a long backfill: the same harness, period by period, oldest first, with the same checks. What is special is the order, the size and the handover to daily runs.

StepHowWhy
Load silver's history firstYears of source history land in bronze and silver once (snapshots, history tables or a full extract); SCD2 dimensions are built from it with their real valid_from datesFacts can only look up versions that exist
Build gold with the same harness, period by periodA backfill run per month (or quarter), oldest first, with its own run id, the same build and the same checksNo special one-off scripts that skip the rules
Dimensions before factsEvery dimension holds its full history before any fact is looked up against itAs-of lookups land on the right version
Size compute for the load, then shrinkA bigger cluster or more parallel periods only for the history loadHistory is a one-time cost; do not keep paying it
Reconcile with the old systemPer period: counts and totals against the legacy warehouse or finance closeProves the history before anyone reports on it
Quiet the alarmsRestatement and freshness alerts off for backfill runs (still logged)A history load is not an incident
Freeze closed periodsMark periods already closed by finance as frozen once reconciledLater loads cannot move them by accident
Hand over to incrementalSet each input's watermark to the point the history load read up to, in the same logged step, then start the daily runsNo gap and no overlap between history and daily loads (our harness owes a written rule for this step)

Reloads: reload from the nearest correct copy

Pick the reload by where the fault entered, and start from the nearest copy that is still right. Most reloads are small: a few windows rebuilt from silver.

Where the fault enteredReloadReload from
Gold build was wrong (a rule or a bug)Fix the build; backfill the affected windows from silverSilver
Silver was wrong (a stage or a setting)Rebuild silver from bronze for the affected batches, then rebuild the gold windows they touchBronze
A file was landed wrongRe-land it from the landing archive, then silver and goldLanding archive
The source sent wrong dataAsk the source to resend (or re-extract); the new delivery flows through normallySource
Rules for every reloadA logged backfill run with a reason; watermarks moved back only as a logged event; restatements logged; a data diff against current gold before the swap-

Hiding a bad batch

A bad batch that reached readers must disappear from their numbers quickly, and leave a record of why.

OptionHowState or verdict
Stop it before readers see itChecks run before publish: a failing batch writes nothing and the watermark staysBest: built
Void the batchMark the batch void in the metadata store; every row carries its batch key, so silver is rebuilt from bronze without itBuilt in silver (void plus rebuild)
Rebuild the gold windows it touchedLineage from batch to windows says which; the harness rebuilds just those and logs the restatementOwed: the gold rerun after a silver rebuild
Hide it at once, while the rebuild runsViews and metric views filter out rows of void batches, or the windows are flagged 'under review' so readers see the number is not finalProposed
Roll the table back (time travel restore)Fast, but it also undoes every good batch after the bad onePursue with care: emergencies only
Delete the rows by handNo record of why; the next run may bring them backDrop

7. Testing

Pure functions, and testing locally with synthetic data

Keep every decision in a pure build; keep reading and writing in adapters; then the build can be tested anywhere.

PracticeWhat it means
The build is a functionbuild(inputs, params) takes the input frames and returns the fact's rows. It reads nothing, writes nothing, never asks the clock or a random source.
I/O lives in adaptersReading silver and writing gold windows sit behind ports (reader, table writer, metadata store). Swapping Delta for Iceberg or Spark for DuckDB is a new adapter, not new logic.
Same code, several enginesThe same stage and build tests run on Spark and on DuckDB (through SQLFrame): DuckDB on every push in about two minutes with no Java, Spark nightly and on Databricks.
Table-driven testsEach case is a few input rows and the expected output rows: new member, late fact, deleted line, duplicate, window straddling a month.
A synthetic worldA seeded generator plays a whole company (orders, deliveries, dealer files, presses, lab results) and keeps its own truth (the oracle): what gold must hold on each day.
Planted incidentsThe world plants problems on a calendar: late files, re-sent files, deletes, a dealer that appears late, an out-of-order change, a backdated correction. Each names the check that must catch it.
Compressed calendarFor the daily loop, every incident is moved into three days, so a short run meets all of them.
Compare layer by layerAfter each simulated day, bronze, silver and gold are compared with the oracle; a difference fails the run and names the layer.

More on testing data code without a cluster: Shift left. The synthetic world idea: DataTwin.

Regression: proving a change broke nothing

A change to one build, one setting or the harness itself can move numbers far away. Regression testing is layered, from seconds to a full simulated run, and the slowest layer is the one that catches the surprises.

LayerWhat it comparesWhenState
Unit tests on each buildTable-driven cases: small tables in, expected rows out, on Spark and DuckDBEvery commitBuilt
Generated files unchanged unless meantMetric views, dashboards, bundle files are generated and compared with the committed copies; any drift failsEvery commitBuilt
Known answersFixed questions (OTIF for one region and month) asked of the metric views; the answer must equal the expected numberEvery runBuilt
The synthetic world, every incidentThree compressed days with eleven planted incidents; every layer must equal the world's truthEvery change to the harness or a build; daily on the platformBuilt
Side-by-side data diffRun the new version on the same inputs into a scratch schema; compare with today's gold per window: row counts, keys, measure totals; any difference must be explained before releaseBefore every release that touches a build or metadataProposed
Speed and costStep times and rows per step from the run log, compared with the last runs; a step twice as slow is flaggedEvery runPartly built (timings logged; comparison proposed)
Release gateA change ships only when all of the above pass; a planted bad change must be blockedEvery releaseBuilt for the observability gate; extend to gold builds

PracticeHowWhat it prevents

FAQ

Questions people ask

How does incremental loading from silver to gold work?

Each gold table keeps a watermark per input. A run fixes a high mark, reads only the changes between the two, turns the changed rows into the windows they touch (plus a lookback), rebuilds only those windows from silver, checks them, replaces them in gold, and moves the watermark last.

What is a watermark in data engineering?

A bookmark of the last change a table has already processed, stored per table and per input in a metadata store. It should be a value that only goes up and never ties, such as a change sequence or a commit version, and it moves only after a run has written and checked its output.

Why rebuild whole windows instead of merging rows?

A window (a day, a month, an hour) recomputed and replaced whole is idempotent, removes deleted rows without delete rules, and is cheap because only changed windows are touched. Row-level MERGE is kept for accumulating snapshots that update by key.

How do I test a silver-to-gold pipeline locally?

Keep each fact's build a pure function of its input frames, put reading and writing in adapters, and test the build with small tables in and expected rows out. Then run the whole hop on a synthetic world with planted incidents, comparing gold with the world's own truth after every day, on a laptop with DuckDB or local Spark.

How does gold handle late-arriving data?

Late facts inside the lookback rebuild their window and are logged as restatements; older ones go through a correction plan. A window owed data by several feeds stays flagged incomplete until all have arrived. Facts whose dimension member is missing get the unknown key and are re-keyed when it appears.
