The harness rulebook 3: testing, reliability, cost, decisions and FAQ

The last third of the rulebook: testing without a cluster, reliability and cost, what exists already, what is built, the decisions, and the questions people ask. This is one page of Silver to gold.

7. Testing

Pure functions, and testing locally with synthetic data

Keep every decision in a pure build; keep reading and writing in adapters; then the build can be tested anywhere.

PracticeWhat it means
The build is a functionbuild(inputs, params) takes the input frames and returns the fact's rows. It reads nothing, writes nothing, never asks the clock or a random source.
I/O lives in adaptersReading silver and writing gold windows sit behind ports (reader, table writer, metadata store). Swapping Delta for Iceberg or Spark for DuckDB is a new adapter, not new logic.
Same code, several enginesThe same stage and build tests run on Spark and on DuckDB (through SQLFrame): DuckDB on every push in about two minutes with no Java, Spark nightly and on Databricks.
Table-driven testsEach case is a few input rows and the expected output rows: new member, late fact, deleted line, duplicate, window straddling a month.
A synthetic worldA seeded generator plays a whole company (orders, deliveries, dealer files, presses, lab results) and keeps its own truth (the oracle): what gold must hold on each day.
Planted incidentsThe world plants problems on a calendar: late files, re-sent files, deletes, a dealer that appears late, an out-of-order change, a backdated correction. Each names the check that must catch it.
Compressed calendarFor the daily loop, every incident is moved into three days, so a short run meets all of them.
Compare layer by layerAfter each simulated day, bronze, silver and gold are compared with the oracle; a difference fails the run and names the layer.

More on testing data code without a cluster: Shift left. The synthetic world idea: DataTwin.

Regression: proving a change broke nothing

A change to one build, one setting or the harness itself can move numbers far away. Regression testing is layered, from seconds to a full simulated run, and the slowest layer is the one that catches the surprises.

LayerWhat it comparesWhenState
Unit tests on each buildTable-driven cases: small tables in, expected rows out, on Spark and DuckDBEvery commitBuilt
Generated files unchanged unless meantMetric views, dashboards, bundle files are generated and compared with the committed copies; any drift failsEvery commitBuilt
Known answersFixed questions (OTIF for one region and month) asked of the metric views; the answer must equal the expected numberEvery runBuilt
The synthetic world, every incidentThree compressed days with eleven planted incidents; every layer must equal the world's truthEvery change to the harness or a build; daily on the platformBuilt
Side-by-side data diffRun the new version on the same inputs into a scratch schema; compare with today's gold per window: row counts, keys, measure totals; any difference must be explained before releaseBefore every release that touches a build or metadataProposed
Speed and costStep times and rows per step from the run log, compared with the last runs; a step twice as slow is flaggedEvery runPartly built (timings logged; comparison proposed)
Release gateA change ships only when all of the above pass; a planted bad change must be blockedEvery releaseBuilt for the observability gate; extend to gold builds

10b. Reuse first

Has the industry solved this layer?

Partly. The common mechanics (incremental by time window, SCD2 dimensions, tests, safe releases) are well solved by open tools. What no tool we know gives out of the box is the gold-specific part: keys looked up as of the event with late members, a window being complete only when every owed feed has delivered, a logged restatement when a published number changes, correction plans, and a row ledger. Our recommendation is to build only that part, and to put it on top of an open tool where a team already uses one, not to rebuild what dbt or SQLMesh already do well.

FAQ

Questions people ask

How does incremental loading from silver to gold work?

Each gold table keeps a watermark per input. A run fixes a high mark, reads only the changes between the two, turns the changed rows into the windows they touch (plus a lookback), rebuilds only those windows from silver, checks them, replaces them in gold, and moves the watermark last.

What is a watermark in data engineering?

A bookmark of the last change a table has already processed, stored per table and per input in a metadata store. It should be a value that only goes up and never ties, such as a change sequence or a commit version, and it moves only after a run has written and checked its output.

Why rebuild whole windows instead of merging rows?

A window (a day, a month, an hour) recomputed and replaced whole is idempotent, removes deleted rows without delete rules, and is cheap because only changed windows are touched. Row-level MERGE is kept for accumulating snapshots that update by key.

How do I test a silver-to-gold pipeline locally?

Keep each fact's build a pure function of its input frames, put reading and writing in adapters, and test the build with small tables in and expected rows out. Then run the whole hop on a synthetic world with planted incidents, comparing gold with the world's own truth after every day, on a laptop with DuckDB or local Spark.

How does gold handle late-arriving data?

Late facts inside the lookback rebuild their window and are logged as restatements; older ones go through a correction plan. A window owed data by several feeds stays flagged incomplete until all have arrived. Facts whose dimension member is missing get the unknown key and are re-keyed when it appears.

Why are there so many types of fact table?

Because business questions come in different shapes. Events that happened once need a row per event (transaction). Levels like stock need a row per period even on quiet days (periodic snapshot). Processes with several steps need one row updated as it moves (accumulating snapshot). Events with nothing to measure need rows without numbers (factless). Busy questions need a summary (aggregate), and comparing sources needs one shared grain (consolidated). The kind decides how a pipeline reads changes and how it writes.

Can the silver to gold layer be built as a Databricks declarative pipeline?

It can: AUTO CDC builds SCD Type 2 dimensions, and materialized views build facts and aggregates, with expectations for quality. But it does not give control over which days are rebuilt, a restatement log, correction plans, a full row ledger, checks across rows or stable integer keys. We recommend a harness for gold, run as a Databricks job, with materialized views only as an option for some aggregates.

What are reader, processor and writer in a data pipeline?

The reader finds what changed since the last run and reads the rows of the windows it touches. The processor is a pure function holding the business rule, which takes data in and returns data out. The writer puts the result into the target safely, by replacing whole windows or merging by key, and only then is the bookmark moved.

Can a fact table be written in SQL?

Yes. The business rule of a fact is usually a few CTEs: add child rows up per parent, apply the rule, select the grain. The harness or dbt does the rest: picks the days, looks up keys, checks and writes. Our SQL and PySpark builds return the same rows.

How does a custom gold harness compare with dbt?

For the business rule they are equal: the same SQL. dbt is better at lineage, docs, adapters and community. A harness is better at choosing which days to rebuild, checking before writing (dbt's data tests run after the table is written), completeness, restatements and stable integer keys. Teams on dbt can add those as macros and a write-audit-publish step.

Is a delivery a fact or a dimension?

A fact: it is an event with numbers. It can be an input to another fact (order lines with OTIF flags) or its own fact at one row per delivery. Dimensions describe what you filter and group by, such as dealer, warehouse and product.

What is a versioned fact table?

A fact that keeps every version of a row, dated by when it was recorded, like SCD Type 2 on the fact's grain. It answers 'what did we report on that day?'. The alternatives are current-state facts with a restatement log, or append-only adjustment rows.

What are the types of fact tables?

Six: transaction (a row per event), periodic snapshot (a row per thing per period, quiet periods included), accumulating snapshot (one row per process, updated as it moves), factless (rows with no numbers, counted), aggregate (a summary built from another fact) and consolidated (two sources brought to one grain to compare).

What is the difference between a periodic and an accumulating snapshot?

A periodic snapshot adds a new row for every thing every period, like a daily account balance; old rows never change. An accumulating snapshot keeps one row per process, like a loan application, and updates it as each step happens.

Can incremental loading from silver to gold miss records?

Yes, if gold bookmarks by a column the writers fill in: a number set only on insert misses updates; a source change number misses hard deletes, full overwrites and out-of-order commits; even a silver batch number misses deletes and out-of-order commits. Reading the table's own change log (Delta change data feed or Iceberg changelog), bookmarked by commit version, caught every case in our test.

What happens to Delta change data feed on a full overwrite?

Every old row is recorded as a delete and every new row as an insert, so a downstream reader sees the whole table as changed. It misses nothing but rebuilds everything. Writing only the differences with a MERGE keeps the change feed small.
