Dimension table examples in SQL: eleven kinds, each run and checked

Eleven dimension tables written as plain SQL on tiny tables: overwrite, history, previous value, date, junk, bridge and more. Every result is from a real run. This is one page of Silver to gold.

  • How to read and run these
  • The eleven examples at a glance
  • Type 1: overwrite the old value
  • Type 2: keep history, one row per version
  • Type 3: current value plus the one before
  • Mini-dimension: fast-changing attributes in their own small table
  • Date dimension: generated, never changes
  • Role-playing: one date table, used as promised date and delivered date
  • Junk dimension: a handful of flags in one small table
  • Degenerate dimension: the order number stays in the fact
  • Bridge table: a dealer offers several services
  • Hierarchy: city, state and region in one row
  • Late dealer: the unknown row and the inferred row

Before you start

How to read and run these

Every example is plain SQL on tiny tables: silver in, SQL, gold out. The tables you see are the real results of running the SQL, in DuckDB 1.4, from _guides/code/silver_to_gold/ (run_sql.py runs all 19 examples; a table-driven test checks 60 claims such as "the shares add up to the freight"). Each Setup SQL box creates the silver table, so you can paste an example into any DuckDB and run it.

The tyre company is the one from the worked example. These pages show the business rule of each table, which is the part you write. Finding changed rows, picking windows and moving the bookmark is the harness's job, shown on the other pages.

Which one?

The eleven examples at a glance

Start with Type 1 and Type 2: they cover most dimensions. The others solve one specific problem each; reach for one only when you have that problem.

ExampleThe question it answersVerdict
Type 1: overwriteWhat is this product called today? (Nobody needs to know what it was called last year.)Pursue: The default for names, codes, descriptions
Type 2: keep historyWhich region was this dealer in on the day the order was promised?Pursue: Whenever the past matters for grouping
Type 3: previous valueShow each dealer's region now, and the region they were in before, side by side.Pursue with care: Only for 'moved from X to Y' or a transition period

Role-playing dateWhich weekday was the delivery made on, and how many days after the promised day?Pursue: No second date table, ever
Junk dimensionCount orders by rush, payment mode and gift wrap, without three more columns of text on a huge fact.Pursue with care: Only when several small flags crowd a big fact
Degenerate dimensionShow me everything on order O1.Pursue: Free: keep the number in the fact

1. SCD Type 1

Type 1: overwrite the old value

The question: What is this product called today? (Nobody needs to know what it was called last year.)

The dimension keeps one row per product. When the source changes a name, the row is rewritten. The product keeps its key, so every old fact still points at it and now shows the new name.

1. Night 1: build the dimension. The key is a number gold hands out; the source's own id stays as a column.

CREATE TABLE dim_product AS
SELECT row_number() OVER (ORDER BY product_id) AS product_key,
       product_id, product_name, brand, size
FROM silver_products;

Result

1P1Highway PlusApex205/55R16
2P2City GripApex185/65R15

2. Night 2, first half: rewrite rows whose attributes changed. The key does not move.

UPDATE dim_product d
SET product_name = s.product_name, brand = s.brand, size = s.size
FROM silver_products_day2 s
WHERE d.product_id = s.product_id
  AND (d.product_name IS DISTINCT FROM s.product_name
    OR d.brand        IS DISTINCT FROM s.brand
    OR d.size         IS DISTINCT FROM s.size);

3. Night 2, second half: add products gold has never seen, with the next free keys.

INSERT INTO dim_product
SELECT (SELECT COALESCE(max(product_key), 0) FROM dim_product)
         + row_number() OVER (ORDER BY s.product_id),
       s.product_id, s.product_name, s.brand, s.size
FROM silver_products_day2 s
WHERE NOT EXISTS (SELECT 1 FROM dim_product d WHERE d.product_id = s.product_id);

Use it whenNames, descriptions and codes where a correction should show everywhere, and history has no business value.
The trapHistory is gone on purpose. If someone later asks 'what was it called when we sold it?', Type 1 cannot answer. Also never re-number: the key must stay the same on every run, or old facts point at the wrong product.

2. SCD Type 2

Type 2: keep history, one row per version

The question: Which region was this dealer in on the day the order was promised?

When a dealer moves region, the old row is closed (it gets an end date) and a new row opens. Both stay. Each version has its own key, and a fact picks the version that was true on the event date.

1. Drop rows where nothing changed (the re-sent 8 Nov row), by comparing each row with the one before it.

CREATE TABLE dealer_changes_clean AS
SELECT *
FROM (SELECT *,
             concat_ws('|', name, region, tier) AS sig,
             lag(concat_ws('|', name, region, tier))
               OVER (PARTITION BY dealer_id ORDER BY changed_on) AS prev_sig
      FROM silver_dealer_changes)
WHERE prev_sig IS NULL OR sig <> prev_sig;

2. Each version ends where the next one starts. The last version stays open (a far-future end date, so range joins need no NULL handling).

CREATE TABLE dim_dealer AS
SELECT row_number() OVER (ORDER BY dealer_id, changed_on) AS dealer_key,
       dealer_id, name, region, tier,
       changed_on AS valid_from,
       COALESCE(lead(changed_on) OVER (PARTITION BY dealer_id ORDER BY changed_on),
                DATE '9999-12-31')                          AS valid_to,
       lead(changed_on) OVER (PARTITION BY dealer_id ORDER BY changed_on) IS NULL AS is_current
FROM dealer_changes_clean;

SELECT o.line_id, o.dealer_id, o.promised_date,
       d.dealer_key, d.region, d.tier
FROM silver_order_lines o
LEFT JOIN dim_dealer d
  ON d.dealer_id = o.dealer_id

 AND o.promised_date <  d.valid_to
ORDER BY o.line_id;

The trapLooking up the dealer's current row instead of the row true on the date silently moves old orders to the new region. Also check that versions of one dealer never overlap: an overlap makes a fact match two rows and doubles its numbers.

3. SCD Type 3

Type 3: current value plus the one before

The question: Show each dealer's region now, and the region they were in before, side by side.

One row per dealer, with two columns: region now and region before. Only one step back is kept. Useful for a 'moved from X to Y' report, and for a transition period when a reorganisation happens.

silver_dealer_regions

CREATE TABLE silver_dealer_regions (dealer_id VARCHAR, name VARCHAR, region VARCHAR, from_date DATE);
INSERT INTO silver_dealer_regions VALUES
  ('D1','Sharma Tyres','North',DATE '2026-11-01'),
  ('D7','Patel Motors','North',DATE '2026-11-01'),
  ('D7','Patel Motors','West', DATE '2026-11-12');

1. Take each dealer's newest row, and bring in the region from the row before it.

CREATE TABLE dim_dealer_t3 AS
SELECT row_number() OVER (ORDER BY dealer_id) AS dealer_key,
       dealer_id, name,
       region          AS current_region,
       prev_region     AS previous_region,
       from_date       AS current_region_since
FROM (SELECT *,
             lag(region) OVER (PARTITION BY dealer_id ORDER BY from_date) AS prev_region,
             row_number() OVER (PARTITION BY dealer_id ORDER BY from_date DESC) AS rn
      FROM silver_dealer_regions)
WHERE rn = 1;

The trapTwo moves in a row lose the first region. If that matters, you wanted Type 2.

4. Mini-dimension

Mini-dimension: fast-changing attributes in their own small table

The question: Report orders by the dealer's volume band and risk band, as they were that month, without a new dealer row every month.

Volume band and risk band change often. Making a Type 2 version of the dealer each time would explode the dealer table. Instead the few possible band combinations go in a tiny table of their own, and the fact carries both keys.

5. Type 0 (fixed), generated

Date dimension: generated, never changes

The question: Group by fiscal quarter, weekday or weekend without writing date maths in every report.

No source table at all. You generate one row per day for as many years as you need. Rows never change (Type 0), and every fact points at a date by a whole-number key like 20261113.

1. One row per day for an Indian financial year (April to March). In Spark or Databricks, replace the generator with explode(sequence(DATE'2026-04-01', DATE'2027-03-31', INTERVAL 1 DAY)).

CREATE TABLE dim_date AS
SELECT CAST(strftime(d, '%Y%m%d') AS INTEGER)                    AS date_key,
       d                                                          AS date,
       dayname(d)                                                 AS day_name,
       isodow(d) >= 6                                             AS is_weekend,
       strftime(d, '%Y-%m')                                       AS year_month,
       'FY' || (year(d) + CASE WHEN month(d) >= 4 THEN 0 ELSE -1 END)
            || '-' || right(CAST(year(d) + CASE WHEN month(d) >= 4 THEN 1 ELSE 0 END AS VARCHAR), 2) AS fiscal_year,
       'Q' || CAST(((month(d) + 8) % 12) // 3 + 1 AS INTEGER)       AS fiscal_quarter
FROM (SELECT CAST(unnest(generate_series(DATE '2026-04-01', DATE '2027-03-31', INTERVAL 1 DAY)) AS DATE) AS d);

6. Role-playing

Role-playing: one date table, used as promised date and delivered date

The question: Which weekday was the delivery made on, and how many days after the promised day?

A fact often has several dates. You do not build a second date table. The same date dimension plays two roles, and gets a different name each time you join it. (This example uses the dim_date built in the previous one.)

  ('L1', 20261110, 20261110), ('L2', 20261110, 20261111), ('L3', 20261111, 20261112), ('L7', 20261113, NULL);

1. Give each role its own view, so report tools show 'Promised date' and 'Delivered date' as separate pickers.

CREATE VIEW dim_promised_date  AS SELECT date_key AS promised_date_key,  date AS promised_date,  day_name AS promised_day  FROM dim_date;
CREATE VIEW dim_delivered_date AS SELECT date_key AS delivered_date_key, date AS delivered_date, day_name AS delivered_day FROM dim_date;

2. Join both roles to the same fact. A LEFT JOIN on the second keeps L7, which has not been delivered yet.

SELECT f.line_id, p.promised_day, d.delivered_day,
       date_diff('day', p.promised_date, d.delivered_date) AS days_after_promise
FROM fact_order_line_dates f
JOIN dim_promised_date p USING (promised_date_key)
LEFT JOIN dim_delivered_date d USING (delivered_date_key)
ORDER BY f.line_id;

Use it whenAny fact with more than one date, or more than one dealer, warehouse or employee role (ship-from and ship-to).
The trapAn INNER JOIN on the second role quietly drops every row that has no value yet, such as lines not yet delivered. Use LEFT JOIN, or point the key at the unknown row.

Junk dimension: a handful of flags in one small table

The question: Count orders by rush, payment mode and gift wrap, without three more columns of text on a huge fact.

9. Bridge table

Bridge table: a dealer offers several services

The question: Revenue by service, when one dealer offers fitting, balancing and alignment, without counting the same money three times.

One dealer, many services: a join would repeat the dealer's revenue once per service. A bridge table sits between them and gives each pair a weight. Weights for one dealer add up to 1, so the totals still add up.

1. The bridge: one row per dealer and service, weight = 1 divided by how many services the dealer offers.

       1.0 / count(*) OVER (PARTITION BY dealer_id) AS weight

Hierarchy: city, state and region in one row

The question: Group orders by region, state or city, with no recursive queries in the report.

1. A fixed three-level tree is just two self-joins. (A tree of unknown depth needs a recursive query; do it once here, never in reports.)

CREATE TABLE dim_geography AS
SELECT row_number() OVER (ORDER BY c.geo_id) AS geography_key,
       c.name AS city, s.name AS state, r.name AS region
FROM silver_geography c
JOIN silver_geography s ON s.geo_id = c.parent_id AND s.level = 'state'
JOIN silver_geography r ON r.geo_id = s.parent_id AND r.level = 'region'
WHERE c.level = 'city';

11. Late-arriving member

Late dealer: the unknown row and the inferred row

The question: An order arrives for dealer D9 before D9 is in the dealer list. What does the fact point at?
