Silver to gold · Examples in SQL · 19 min read

Fact table examples in SQL: eight kinds, each run and checked

Eight fact tables written as plain SQL on tiny tables. Each shows the silver in, the SQL, the gold out, when to use it and the trap that catches people. Every result is from a real run. This is one page of Silver to gold.

  • How to read and run these
  • The eight examples at a glance
  • Transaction fact: one row per order line, with an on-time-in-full flag
  • Periodic snapshot: stock level per warehouse, per product, per day
  • Accumulating snapshot: one row per order line, filled in as it moves
  • Factless fact: visits (an event) and promo coverage (what could have happened)
  • Aggregate fact: OTIF by region and day, built from the fact above
  • Consolidated fact: plan next to actual, at one shared grain
  • Spreading an order-level amount (freight) over its lines
  • Adjustment rows: corrections as new rows, never edits

Before you start

How to read and run these

Every example is plain SQL on tiny tables: silver in, SQL, gold out. The tables you see are the real results of running the SQL, in DuckDB 1.4, from _guides/code/silver_to_gold/ (run_sql.py runs all 19 examples; a table-driven test checks 60 claims such as "the shares add up to the freight"). Each Setup SQL box creates the silver table, so you can paste an example into any DuckDB and run it.

The tyre company is the one from the worked example. These pages show the business rule of each table, which is the part you write. Finding changed rows, picking windows and moving the bookmark is the harness's job, shown on the other pages.

Which one?

The eight examples at a glance

Read them in order: the first builds fact_order_line, and the aggregate and plan-against-actual examples read it. The kind is chosen by the shape of the question, not by the data.

ExampleThe question it answersVerdict
TransactionDid each order line arrive on time and in full? And how many tyres did we promise by region?Pursue: The default
Periodic snapshotHow many tyres did each warehouse hold at the end of each day, including quiet days when nothing moved?Pursue: For levels and balances
Accumulating snapshotHow many days does a line take from order to shipment, and which lines are still open?Pursue: For multi-step processes
FactlessHow many times did our reps visit each dealer? And which dealers were offered the November promo but never ordered?Pursue: For coverage and 'who did not' questions
AggregateShow OTIF by region on a dashboard that must open instantly.Pursue with care: Only where a question is slow and frequent
ConsolidatedPer region and month: what did we plan, what did we deliver, and what is the gap?Pursue: For plan against actual
Allocated header amountFreight is charged per order, but profit is reported per product. How is it shared out without a cent going missing?Pursue: Whenever a header amount must reach lines
Adjustment rowsWhat is line L1 worth now, and what did we report for it on 15 November?Pursue: For finance-grade numbers that must not silently change

1. Transaction fact

Transaction fact: one row per order line, with an on-time-in-full flag

The question: Did each order line arrive on time and in full? And how many tyres did we promise by region?

One row means: One row per order line.

The workhorse. Something happened once (a line was ordered), so it gets one row, with the numbers that belong to it. Here the rule is: a line is OTIF when everything ordered was delivered, and the last delivery was on or before the promised date.

1. The build. Add the child rows (deliveries) up to one row per line first, then join. Then look up the dealer version true on the promised date, with -1 for a dealer silver has not got yet.

CREATE TABLE fact_order_line AS
WITH delivered AS (                       -- one row per line, BEFORE joining
  SELECT line_id, sum(qty) AS qty_delivered, max(delivered_date) AS last_delivered
  FROM silver_deliveries GROUP BY line_id)
SELECT o.line_id,
       o.order_id,                                            -- degenerate dimension
       COALESCE(d.dealer_key, -1)                AS dealer_key,
       CAST(strftime(o.promised_date, '%Y%m%d') AS INTEGER) AS promised_date_key,
       o.qty_ordered,
       COALESCE(x.qty_delivered, 0)              AS qty_delivered,
       o.qty_ordered * o.unit_price              AS line_amount,
       COALESCE(x.qty_delivered, 0) >= o.qty_ordered
         AND x.last_delivered <= o.promised_date AS is_otif
FROM silver_order_lines o
LEFT JOIN delivered x ON x.line_id = o.line_id
LEFT JOIN dim_dealer d
  ON d.dealer_id = o.dealer_id
 AND o.promised_date >= d.valid_from AND o.promised_date < d.valid_to
WHERE o.dealer_id NOT LIKE 'TEST%';

2. Periodic snapshot

Periodic snapshot: stock level per warehouse, per product, per day

The question: How many tyres did each warehouse hold at the end of each day, including quiet days when nothing moved?

One row means: One row per warehouse, per product, per day, from the first day it had stock.

Stock is a level, not an event. Nothing 'happens' on a quiet day, but the question 'how much on Wednesday?' still has an answer. So we write a row for every day, carrying the level forward.

1. Build a row for every day from each pair's first movement, then add up movements to date. Days with no movement get net 0 and keep the level. (In Spark or Databricks, replace the day generator with explode(sequence(...)).)

CREATE TABLE fact_stock_daily AS
WITH pairs AS (
  SELECT warehouse, product_id, min(movement_date) AS first_day
  FROM silver_stock_movements GROUP BY warehouse, product_id),
days AS (
  SELECT CAST(unnest(generate_series(DATE '2026-11-10', DATE '2026-11-14', INTERVAL 1 DAY)) AS DATE) AS day),
spine AS (
  SELECT p.warehouse, p.product_id, d.day
  FROM pairs p JOIN days d ON d.day >= p.first_day),
moved AS (
  SELECT warehouse, product_id, movement_date AS day, sum(qty_change) AS net
  FROM silver_stock_movements GROUP BY warehouse, product_id, movement_date)
SELECT s.warehouse, s.product_id, s.day,
       COALESCE(m.net, 0) AS net_movement,
       sum(COALESCE(m.net, 0)) OVER (PARTITION BY s.warehouse, s.product_id
                                     ORDER BY s.day) AS closing_qty
FROM spine s
LEFT JOIN moved m USING (warehouse, product_id, day);

2. What you may add up. Across warehouses on one day: fine. Across days: never. Compare the three answers for product P1.

SELECT
  (SELECT sum(closing_qty) FROM fact_stock_daily
    WHERE product_id = 'P1' AND day = DATE '2026-11-14')                AS right_latest_day_all_warehouses,
  (SELECT sum(closing_qty) FROM fact_stock_daily WHERE product_id = 'P1') AS wrong_added_over_days,
  (SELECT round(avg(t), 1) FROM (SELECT day, sum(closing_qty) AS t
     FROM fact_stock_daily WHERE product_id = 'P1' GROUP BY day))        AS right_average_stock;

Use it whenLevels and balances: stock, bank balance, headcount, open orders at the end of each day.
The trapNever add a level across days: 100 on Monday plus 100 on Tuesday is not 200 tyres. Add across warehouses, then take the last day or the average over days. And a day before the first movement should show 0 or no row by design, not a surprise gap.

3. Accumulating snapshot

Accumulating snapshot: one row per order line, filled in as it moves

The question: How many days does a line take from order to shipment, and which lines are still open?

One row means: One row per order line, for its whole life.

A line goes through steps: ordered, picked, shipped, delivered. Instead of four rows, there is one row with four date columns. Empty at first, filled in as each step happens. This is the one fact kind whose rows change after they are written.

1. The processor, as a view: turn milestone events into one row per line. It is pure: events in, rows out.

CREATE VIEW v_line_pipeline AS
SELECT line_id,
       max(CASE WHEN event = 'ordered'   THEN event_date END) AS ordered_date,
       max(CASE WHEN event = 'picked'    THEN event_date END) AS picked_date,
       max(CASE WHEN event = 'shipped'   THEN event_date END) AS shipped_date,
       max(CASE WHEN event = 'delivered' THEN event_date END) AS delivered_date
FROM silver_line_events GROUP BY line_id;

2. Night 1: build the table, with the measures worked out from the dates. Empty steps stay empty. An 'is_open' flag stops open lines hiding inside averages.

CREATE TABLE fact_line_pipeline AS
SELECT line_id, ordered_date, picked_date, shipped_date, delivered_date,
       date_diff('day', ordered_date, shipped_date)  AS days_order_to_ship,
       delivered_date IS NULL                        AS is_open
FROM v_line_pipeline;

4. Night 2, the writer: MERGE by line. Rows that exist are updated, new lines are inserted. Run it twice and nothing changes.

MERGE INTO fact_line_pipeline t
USING (SELECT line_id, ordered_date, picked_date, shipped_date, delivered_date,
              date_diff('day', ordered_date, shipped_date) AS days_order_to_ship,
              delivered_date IS NULL                       AS is_open
       FROM v_line_pipeline) s
ON t.line_id = s.line_id
WHEN MATCHED THEN UPDATE SET
     ordered_date = s.ordered_date, picked_date = s.picked_date,
     shipped_date = s.shipped_date, delivered_date = s.delivered_date,
     days_order_to_ship = s.days_order_to_ship, is_open = s.is_open
WHEN NOT MATCHED THEN INSERT VALUES
     (s.line_id, s.ordered_date, s.picked_date, s.shipped_date, s.delivered_date,
      s.days_order_to_ship, s.is_open);

       count(*) FILTER (WHERE is_open)   AS open_lines,

4. Factless fact

Factless fact: visits (an event) and promo coverage (what could have happened)

The question: How many times did our reps visit each dealer? And which dealers were offered the November promo but never ordered?

One row means: Visits: one row per visit. Coverage: one row per promo per eligible dealer.

Some facts have nothing to add up. A rep visited a dealer: that is the whole fact. You count rows. A second kind records what was possible (who was offered a promo) so you can later ask what did not happen.

5. Aggregate fact

Aggregate fact: OTIF by region and day, built from the fact above

The question: Show OTIF by region on a dashboard that must open instantly.

One row means: One row per region per promised date.

A summary of another gold fact, kept because a busy dashboard asks the same question all day. Built from the transaction fact, never from silver, so the two always agree. Store the counts, not just the percent.

Reads fact_order_line and dim_dealer, built in the first example.

1. Group the transaction fact. Keep lines and otif_lines as counts.

CREATE TABLE fact_otif_region_day AS
SELECT d.region,
       CAST(strptime(CAST(f.promised_date_key AS VARCHAR), '%Y%m%d') AS DATE) AS promised_date,
       count(*)                                  AS lines,
       sum(CASE WHEN f.is_otif THEN 1 ELSE 0 END) AS otif_lines,
       sum(f.qty_ordered)                        AS qty_ordered
FROM fact_order_line f
JOIN dim_dealer d USING (dealer_key)
GROUP BY d.region, f.promised_date_key;

SELECT region,
       round(avg(100.0 * otif_lines / lines), 1)       AS wrong_avg_of_percents,

6. Consolidated fact

Consolidated fact: plan next to actual, at one shared grain

The question: Per region and month: what did we plan, what did we deliver, and what is the gap?

One row means: One row per region per month.

Plan comes from finance, actuals from our own fact. They arrive at different grains. Bring both to region and month first, then put them side by side with a FULL OUTER JOIN, so a region with only a plan, or only actuals, still shows.

Reads fact_order_line and dim_dealer from the first example, and finance's plan below.

1. Two inputs brought to the same grain, then combined. COALESCE turns a missing side into 0 and gap shows what is missing.

CREATE TABLE fact_plan_vs_actual AS
WITH actual AS (
  SELECT d.region,
         strftime(CAST(strptime(CAST(f.promised_date_key AS VARCHAR), '%Y%m%d') AS DATE), '%Y-%m') AS month,
         sum(f.qty_ordered) AS actual_qty
  FROM fact_order_line f JOIN dim_dealer d USING (dealer_key)
  GROUP BY 1, 2)
SELECT COALESCE(p.region, a.region) AS region,
       COALESCE(p.month,  a.month)  AS month,
       COALESCE(p.planned_qty, 0)   AS planned_qty,
       COALESCE(a.actual_qty,  0)   AS actual_qty,
       COALESCE(a.actual_qty, 0) - COALESCE(p.planned_qty, 0) AS gap
FROM silver_sales_plan p
FULL OUTER JOIN actual a ON a.region = p.region AND a.month = p.month;

The trapAn INNER or LEFT join silently drops the region that exists on only one side, which is exactly the row someone must look at. Use FULL OUTER JOIN, and reconcile both totals to their sources.

7. Transaction fact with allocation

Spreading an order-level amount (freight) over its lines

The question: Freight is charged per order, but profit is reported per product. How is it shared out without a cent going missing?

One row means: One row per order line, with its share of the order's freight.

The amount belongs to the order (the header), but the fact is at line level. Share it in proportion to line value. Naive rounding loses or invents cents, so the share is worked out on a running total and each line gets the difference.

1. The wrong way: round each line's share. Three equal lines each get 33.33, and 100.00 becomes 99.99.

SELECT order_id, freight, sum(share) AS allocated_naive
FROM (SELECT l.order_id, f.freight,
             round(f.freight * l.line_amount / sum(l.line_amount) OVER (PARTITION BY l.order_id), 2) AS share
      FROM silver_alloc_lines l JOIN silver_order_freight f USING (order_id))
GROUP BY order_id, freight ORDER BY order_id;

Result

order_idfreightallocated_naive

2. The right way: each line gets (rounded running share) minus (rounded running share of the line before it). The pieces add up to exactly the freight.

CREATE TABLE fact_line_freight AS
WITH running AS (
  SELECT l.order_id, l.line_id, l.line_amount, f.freight,
         sum(l.line_amount) OVER (PARTITION BY l.order_id ORDER BY l.line_id) AS cum_amount,
         sum(l.line_amount) OVER (PARTITION BY l.order_id)                   AS total_amount
  FROM silver_alloc_lines l JOIN silver_order_freight f USING (order_id)),
shares AS (
  SELECT *, round(freight * cum_amount / total_amount, 2) AS cum_share FROM running)
SELECT order_id, line_id, line_amount,
       cum_share - COALESCE(lag(cum_share) OVER (PARTITION BY order_id ORDER BY line_id), 0) AS freight_share
FROM shares;

3. The check every allocation needs: the shares add back to the header, order by order. This returns no rows when it is right.

SELECT f.order_id, f.freight, sum(a.freight_share) AS allocated
FROM silver_order_freight f JOIN fact_line_freight a USING (order_id)
GROUP BY f.order_id, f.freight
HAVING sum(a.freight_share) <> f.freight;

Result

(no rows: that is the right answer here)

Use it whenFreight, discounts, taxes and fees recorded per order or invoice but analysed per line, product or customer.
The trapChoose the share rule (by value, by quantity, equally) once, with the business, and write it down. Changing the rule later restates history.

8. Fact with adjustment rows

Adjustment rows: corrections as new rows, never edits

The question: What is line L1 worth now, and what did we report for it on 15 November?

One row means: One row per amount entry (the original, then each correction).

When a number is corrected, don't change the old row. Add a new row with the difference, dated by when it was recorded. Add them all up for today's truth; add up to a date for what was known then.
