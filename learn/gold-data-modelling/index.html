Gold data modelling: grain, keys, facts and dimensions done right

Gold is where people, dashboards and AI read their answers. If gold is shaped well, every number agrees everywhere and new questions are easy. If it is shaped badly, totals double count, history breaks and every tool invents its own definition. This page teaches the shape from zero, then gives the rules and the decisions. How gold gets built from silver is the next page: Silver to gold.

In one paragraph. One fact table per business process, at a grain you can say in one sentence. Dimensions around it describe who, what, where and when, and are shared by every fact (conformed). Facts link to dimensions with surrogate keys, never with the source's own keys. History is kept (SCD Type 2) only where reports need it. Ratios are stored as their two parts. A semantic layer (metric views) on top defines each measure once. Aggregates and materialized views are added later, only for questions that are slow, at one step above the atomic grain.

Lesson first

In plain words

Think of a shop's receipt. The receipt line (2 tyres, ₹9,000) is a fact: it happened, and it has numbers. The shop, the tyre type, the day and the customer are dimensions: they describe the fact, and you slice the numbers by them ("sales by region by month"). Put the fact in the middle and the dimensions around it, and you get a star.

A star schema. The fact holds numbers; each dimension holds descriptions. The date dimension appears three times, once for each date on the order line.

Why this shape? Because almost every business question is "a number, sliced by some descriptions, over time". A star answers that with one join per description, it is easy for people and AI tools to read, and the same dimension can serve many facts, so sales and deliveries can be compared on the same dealer list.

WordWhat it means here
GoldThe layer people and tools read answers from. Shaped for questions, not for the source system.
Dimensional modelTables arranged as facts (what happened, with numbers) and dimensions (who, what, where, when). Also called a star schema, because one fact with its dimensions looks like a star.
Business processOne thing the business does that makes events: taking an order, delivering, curing a tyre. One fact table per process.
GrainWhat exactly one row of a fact means, in one sentence: "one row per order line". The most important decision in gold.
MeasureA number on a fact row that people add up or average: quantity, value, minutes late.
Business keyThe key the source uses for a thing: dealer code D-0042, material code M-1188. Meaningful to people, can be reused or changed by the source.
Primary keyWhatever makes a row unique in its table. In a dimension it is the surrogate key; in a fact it is usually the grain columns.
Surrogate key (sk)A meaningless number the warehouse gives each dimension row. Facts point to dimensions with it, never with the business key.
Durable keyOne number per real-world member (dealer 42) that stays the same across all its history versions.
Conformed dimensionA dimension shared, unchanged, by several facts, so their numbers can be compared side by side.

Degenerate dimensionA business key kept on the fact with no table of its own, such as an order number.

Method

Where Kimball helps, and where not

Ralph Kimball's dimensional modelling is the method this page follows: start from business processes, declare the grain, build conformed dimensions, plan with a bus matrix. On a lakehouse it still fits gold, because storage got cheaper but people, BI tools and AI still need clear, small, joinable tables. It is not the tool for every layer.

NeedWhyVerdict
Shaping data for questions people askBusiness processes, grain, facts and dimensions map straight to how people askPursue: this is Kimball's home ground
Many facts that must agreeConformed dimensions and the bus matrix make sales, deliveries and returns comparablePursue
History of descriptionsSCD types give a named, tested choice per attributePursue
BI tools, semantic layers and AI answersStars are what metric views, Power BI and text-to-SQL tools read best: few joins, clear names, one grain per tablePursue
Integrating many messy sourcesKimball assumes clean, conformed input; matching, deduplicating and keeping source history is silver's job (or a data vault)Pursue with care: not the tool for this layer
Sub-second or streaming answersA star is batch or micro-batch; a live lane needs a store built for itDrop for the live lane
Machine learning featuresModels want one wide row per entity per time; build it from the starPursue with care: derive, don't replace
Exploring unknown dataModelling first slows people who don't know the questions yetDrop for exploration: let them read silver

1. The first decision

Start with the grain

The grain is what one row of a fact means. Say it in one sentence before anything else: one row per order line, one row per press per hour, one row per dealer per material per month. Most broken gold models broke here: two grains mixed in one table, so totals double count.

  • Atomic first. Choose the lowest level the source gives. You can always add up later; you can never split a total back into its lines.
  • Every dimension must be true at the grain. If "delivery driver" is not known for an order line, it does not belong on the order-line fact.
  • The grain is the primary key. order_id plus line_no; checked for uniqueness on every run, not just in tests.
  • One grain per table. Order headers and order lines are two facts, or header values are shared out onto lines.

Coarser grains are built by adding up the atomic one. Ratios are the exception: add up their parts, then divide.

2. Keys

Business key, primary key, surrogate key

Three kinds of key are easy to mix up. The business key is the source's name for a thing (dealer D-0042). The primary key is whatever makes a row unique in its own table. The surrogate key is a meaningless number the warehouse gives each dimension row, and it is the only thing a fact uses to point at a dimension.

The source's code is kept as a column, but facts link through warehouse keys, so history and source changes never break them.

KeyWhat it isExampleRule
Business key (natural key)Comes from the source; identifies the thing in the source's worlddealer_code D-0042Keep it as a column on the dimension, never as the link from facts
Durable keyOne per real-world member, assigned once by a key map, never changesdealer 42Store on facts that need today's values (current view)
Surrogate (version) keyOne per dimension row; with SCD2, one per versionsk 701 (Pune), sk 702 (Delhi)Store on facts that need the values true on the fact's date (as-of view)
Dimension primary keyThe surrogate keydealer_skUnique, not null, never reused
Fact primary keyThe grain columns (often business keys plus dates), or a hash of themorder_id + line_noDeclare it and check it every run; a surrogate row id adds nothing
Reserved keys-1 unknown (the fact had no value), -2 not applicable (the dimension does not apply)dealer_sk = -1One row each in every dimension, so joins never drop facts

3. Joining

Join on the surrogate key or the business key?

Short answer: business keys are for building gold, surrogate keys are for reading it. The build looks up each fact's business key (as of its event time) and stores the surrogate key. Every reader then joins fact to dimension on the surrogate key with a plain equality join.

The most common gold bug: a business-key join against a history dimension multiplies every total.

JoinOnWhat happensVerdict
Fact to dimensionSurrogate keyExactly one dimension row per fact row, by constructionPursue
Fact to dimension on the business keyBusiness keyWith SCD2, one fact row matches every version: totals multiply (fan-out)Drop
Business key plus is_currentBusiness keyGives today's view, but silently drops facts whose member is no longer current or not yet loadedPursue with care: prefer the durable key
Fact to fact (drill across)Neither: never join two facts row to rowDifferent grains multiply rows (chasm trap)Drop: add each up to the common grain on conformed dimensions, then join the results
Silver to gold, while buildingBusiness key, as of the event dateThis is the lookup that turns business keys into surrogate keysPursue: business keys belong to the build, surrogate keys to the readers
Gold to an outside systemBusiness keyOther systems do not know your surrogate keysPursue: always keep the business key as a column on the dimension

4. History joins

SCD Type 2 joins, done right

TopicRule
Where the as-of join happensOnce, in the build (silver to gold): business key plus event time finds the version, the fact stores its surrogate key. Readers then join on that key with a plain equality join.
The rulevalid_from <= event_time < valid_to: start included, end excluded. The current row has valid_to = 9999-12-31 (or null treated as open), never a gap between versions.
Which timeThe business event time in the business time zone (order time), not the load time. A late fact must land on the version valid when it happened.
Event before the member's first versionPick a rule and write it down: the first version (most common) or the unknown member. Never drop the row.
Member not loaded yetUnknown member now, re-keyed when it arrives, or an inferred member with a real key filled in later. Both are on the harness page.
Backdated dimension changeA version inserted in the past changes which facts belong to it: re-key only the facts of that member in that date range.
Checks every runOne current row per member, no overlapping ranges, no gaps, every fact key exists in the dimension. Broken ranges cause fan-out or lost rows.
PerformanceLook up only the members in the batch; broadcast small dimensions; use a range-join hint or bin by date for large ones; cluster the dimension by business key.

Meaning first

How a business ontology helps

An ontology is a written map of the business: its concepts (dealer, material, order line), what identifies each one, how they relate, what words mean, and what can change. A good gold model is that map made into tables. Write the ontology (even a light one: a glossary with keys and relationships) and much of the model follows from it; skip it, and each team's gold invents its own meaning of "customer".

In the ontologyBecomes in goldWhat it buys
Business concepts (Dealer, Material, Plant, Order line, Delivery)Dimensions for things, facts for eventsGold names come from the business, not from source tables
Identity of a concept (what makes a dealer one dealer)Business keys and the key mapTwo sources that say 'customer' resolve to one member, or are told apart on purpose
Relationships (a dealer places order lines; a press cures tyres)Fact-to-dimension links and the grainWhich dimensions are true at a fact's grain is read off the ontology
Concepts shared across departmentsConformed dimensions and the bus matrixSales and manufacturing mean the same 'material'
Definitions and synonyms (OTIF, on-time delivery, delivery performance)Metric views: descriptions, synonyms, certified measuresPeople and AI tools ask in their words and get one definition
Rules and constraints (an order line belongs to one order; a delivery cannot precede its order)Grain checks, quality rules, as-of rulesChecks come from business facts, not from guesses
Change over time (a dealer can change region)SCD type per attributeHistory is kept where the business says the concept changes

Verdict. Pursue a light ontology (a glossary of concepts, keys, relationships and definitions kept in Git, feeding the catalog's glossary and the metric views' descriptions). Pursue with care a full ontology platform: worth it when many domains and AI agents must agree on meaning; not as the first step.

5. Dimensions

Dimensions, and how they change

A dimension is a list of things with their descriptions: one row per dealer, with name, region and segment. When a description changes (a dealer moves region), you must choose what the warehouse remembers. That choice is the SCD type.

TypeWhat it keepsExampleVerdict
Type 0: keep the originalThe value never changes after first loadDate of birth, first order datePursue where true
Type 1: overwriteOnly today's value; history lostCorrected spellings, contact emailPursue for attributes nobody reports on over time
Type 2: new row per changeFull history with valid_from, valid_to, is_currentDealer region, material class, price bandPursue for attributes reports slice history by
Type 3: previous value columnCurrent plus one previous valueOld and new sales territory during a reorganisationPursue with care: one step of history only
Type 4 / mini-dimensionFast-changing attributes split into their own small dimensionCustomer credit band changing monthlyPursue when Type 2 would explode the row count
Type 6: 1 + 2 + 3Version rows plus a current-value column on every versionReport history by the region of the day and also by today's regionPursue when both views are asked for often
Type 2 on every columnHistory for everything-Drop: rows multiply, nobody asks for most of it

Kinds of dimension

KindWhat it isVerdict

As of then, or as of today? With Type 2, a fact can show the dealer's region on the order date (store the version key) or today's region (store the durable key). Ask which the reports need; many need both, and storing both keys costs little. See SCD Type 2: AUTO CDC or own PySpark and time travel as SCD2.

6. Facts

The kinds of fact table

Facts differ by how their rows behave over time. Pick the kind from the business process, not from the source table.

Transaction facts collect events, periodic snapshots take a picture every period, accumulating snapshots follow one thing through its milestones.

KindOne row isExampleHow rows changeWhen
Transaction factOne eventOne row per order line, payment, sensor readingAppended; corrected only by a declared correction ruleMost common; start here
Periodic snapshotThe state of a thing at the end of each periodStock per material per day; account balance per monthRebuilt for the open period; closed periods frozenFor levels and balances
Accumulating snapshotOne thing's whole life, with a date per milestoneOne row per order line with ordered, promised, shipped, delivered dates and lagsUpdated in place as milestones arriveFor processes with a start and an end
Factless factAn event or coverage with no numberDealer attended a training; product on promotion in a store on a dayAppendedFor 'what did not happen' questions
Aggregate factA coarser grain of another factDealer x material x day salesRebuilt for changed days onlyOnly when the atomic fact is too slow for a named question
Consolidated factTwo processes at the same grain side by sidePlan vs actual per dealer per monthRebuilt per periodOnly on conformed dimensions

Measures: what adds up

KindMeaningExamplesRule
AdditiveAdds up across every dimensionQuantity, net value, scrap kilogramsStore as is
Semi-additiveAdds up across some dimensions but not timeStock on hand, account balance (add across materials, not across days)Store; use last value or average over time

7. Inside a fact

What goes in a fact: only IDs?

Mostly keys and numbers, but not only IDs. A fact holds the keys that place a row (who, what, when), the business keys that name the event itself, the numbers, and a few columns that let the platform prove where the row came from. Descriptions never.

Column kindExampleIn the fact?
Surrogate keys to each dimensiondealer_sk, material_sk, order_date_key, promised_date_keyYes: the links, small integers, never null (-1, -2)
Durable keys, where today's view is neededdealer_dkWhen reports need both as-it-was and as-it-is
Degenerate dimensionsorder_id, line_no, invoice_noYes: business keys with no table of their own; also the grain
Measuresqty_ordered, qty_delivered, net_value_inr, on_time_in_full (0/1)Yes: the reason the fact exists
Event timestamps at their natural precisionorder_ts, delivered_tsYes, when lags or hours are asked; the date key covers day-level slicing
Lag and duration measures (accumulating snapshots)days_order_to_deliveryYes: computed once in the build, not in every report
Small flagsis_rush, is_cancelledA few are fine; many go into a junk dimension
Audit columns_run_id, _is_complete, _source_batchYes: lineage, completeness, reruns
Descriptive textdealer_name, material_description, regionNo: lives in dimensions; copied text means rewriting facts on every rename
Business keys of dimensionsdealer_codeNo as a link; at most kept for traceability on very large facts, never joined on

8. A common confusion

Is a fact "Type 1" or "Type 2"?

SCD types belong to dimensions, not facts. When people say "a Type 2 fact" they usually mean one of two different things: which dimension key the fact stores (the version true at the time, or today's), or how the fact's own rows change when the source corrects them (overwritten, versioned, or reversed). Separate the two questions, and each requirement maps to a clear design:

RequirementExample askDesignNote
Show values as they were on the fact's dateSales by the dealer's region at the time of saleFact stores the dimension's version key (as-of lookup)Often called a 'Type 2 fact', but the history lives in the dimension
Show today's values for all historyAll past sales under today's regions after a reorganisationFact stores the durable key; join to the current versionOften called a 'Type 1 fact'
Both viewsFinance wants as-it-was, sales wants as-it-isStore both keys on the fact; the metric view exposes bothCheap: two integer columns
The fact's own numbers get corrected, latest is enoughA delivery quantity fixed next dayUpsert by grain key: the row is overwrittenThe fact behaves like Type 1
The fact's corrections must be auditableProve what the report showed last monthVersioned fact: new row per change with valid_from and valid_to on the grain keyThe fact behaves like Type 2; expensive, use only when required
Corrections must never change a posted rowLedgers, invoicesReversal rows: a minus row and a plus rowTotals stay additive; history is the rows themselves
Show what the report said on a past dayAudit of a published monthTime travel or snapshots of the gold table, or a versioned factTime travel retention is short; keep a snapshot if the period matters

9. Designing a fact

How to design a fact properly: ten steps

  1. Name the business process and its owner (taking orders, sales team).
  2. Write the grain in one sentence, at the lowest level the source gives (one row per order line). Atomic grain first; aggregates come later.
  3. List the dimensions that are true at that grain (date, dealer, material, plant). A dimension that is not true for one row means the grain is wrong.
  4. List the measures that are true at that grain, and mark each additive, semi-additive or non-additive.
  5. Pick the fact kind (transaction, periodic snapshot, accumulating snapshot) from how rows change over time.
  6. Decide per dimension: as-of (version key) or current (durable key), or both.
  7. Declare the primary key (the grain columns) and check it is unique on every run.
  8. Declare how late data and corrections arrive: lookback window, correction rule, what happens when a dimension member is missing.
  9. Declare the window column (order date, promised date, cure hour) the harness rebuilds by, and when a window is complete.
  10. Write the contract: columns, types, owner, quality rules, freshness target. Only then write the build.
The test of a good fact: you can say its grain in one sentence, every column is either a key, a measure or a degenerate dimension, every measure says whether it adds up, and the harness can rebuild any day of it without touching the others.

12. Beyond facts and dimensions

What else lives in gold

Gold tables hold the truth; metric views define the numbers; materialized views keep popular answers ready.

15. Pre-aggregation

Pre-aggregate or not, and at what grain

Pre-aggregation trades storage and refresh compute for faster, cheaper reads. It pays only when the same coarse answer is read many times. When not: the atomic fact is small or well clustered, reads are spread over many slices, or nobody can name the question it speeds up. The rules:

RuleWhat it means
Look at what is askedTake the top dashboards and AI questions; write down the grain each one reads (dealer x month, region x week). Query history tells you.
Keep the atomic factNever replace it: drill-down, reconciliation and new questions need it.
Aggregate one step up firstdealer x material x day usually serves most tiles and cuts rows 10 to 100 times. Go coarser only for a named slow question.
Only additive measuresPre-aggregate sums and counts. For ratios, pre-aggregate the numerator and denominator; divide in the metric view.
Same dimensions, same keysAn aggregate uses the conformed dimensions (or their rolled-up versions, such as month instead of date), so it joins like the atomic fact.
Refresh by changed windowRecompute only the days or months the atomic fact changed; never the whole table.
Prove it paysCompare query time and compute cost before and after. An aggregate nobody reads is pure cost: drop it.

FAQ

Questions people ask

What is the right way to model the gold layer?

Model gold dimensionally: one fact table per business process at a declared atomic grain, conformed dimensions with surrogate keys shared by every fact, SCD Type 2 only where reports need history, ratios stored as numerator and denominator, and a semantic layer (metric views) on top so every tool reads one definition per measure.

What is the difference between a business key, a primary key and a surrogate key?

A business key comes from the source (dealer code D-0042). A primary key is whatever makes a row unique in its table. A surrogate key is a meaningless number the warehouse assigns to each dimension row; it is the dimension's primary key, and facts link to dimensions with it, never with the business key.

What are the kinds of fact table?

Transaction facts (one row per event), periodic snapshots (one row per thing per period), accumulating snapshots (one row per thing updated at each milestone), factless facts (events with no number), aggregate facts (a coarser grain of another fact) and consolidated facts (two processes at the same grain).

How do I define the grain of a fact table?

Write one sentence that says what one row means, at the lowest level the source provides, such as one row per order line. Every dimension and measure must be true at that grain, and the grain columns become the fact's primary key, checked for uniqueness on every run.

At what level should I pre-aggregate?

Keep the atomic fact, then pre-aggregate one step up (for example dealer by material by day) only for named slow questions, using additive measures only (numerator and denominator for ratios), refreshed by changed window, and drop any aggregate nobody reads.

Should I use materialized views or aggregate tables in gold?

Use a materialized view when the aggregate is a plain SQL query over gold that is read many times and can be refreshed by the platform; use an aggregate table built by your own harness when it needs the same windows, completeness flags and checks as the atomic fact.
