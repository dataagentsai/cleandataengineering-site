AgentTwin, explained

How do you know an AI agent is ready to talk to real customers? AgentTwin puts the real agent in a pretend world (pretend customers, pretend systems, pretend data, things going wrong) and then checks what actually changed in that world, not just what the agent said. This page explains it from zero, lets you play it on a tiny agent, scales it up, and then is honest about what is built, what is not, and who else does this.

Part 1 · The explainer

What it is, in plain words, before any detail.

What problem does it solve?

A flight simulator for AI agents

Pilots don't learn engine failure on a real plane with passengers. They sit in a simulator: the cockpit is real, everything outside it is pretend, and an instructor can make an engine fail, the weather turn, or the radio go silent. Afterwards nobody asks the pilot "did you feel confident?". They look at where the plane ended up.

AgentTwin does the same for an AI agent, such as a customer-support or insurance-claims assistant. The agent is the real one, unchanged. Everything it talks to is pretend: the customer, the order system, the database rows, the manager who approves refunds, the clock, and the faults (a slow system, a lost reply). After each test, judges look at what changed in the pretend world. Did a refund really get issued? Was something promised and never done? Did the agent read another customer's data?

That last point is the heart of it. An agent can say "your refund is on its way" when no refund exists. A judge reading the chat would pass that. A judge reading the world would not.

Is it a digital twin?

AgentTwin vs a digital twin

The name borrows from "digital twin", but it points the other way. A digital twin copies a real thing (a jet engine, a factory) so you can watch it and predict it. AgentTwin keeps the thing real (the agent) and copies the world around it, so you can test it.

Digital twinAgentTwin
What is copiedThe thing itself: an engine, a plant, a cityThe world around the agent: customers, systems, data, people, faults, time
What stays realThe world. The thing runs for realThe agent. Its code, prompts and model are unchanged
Where data flowsFrom the real thing into the copy (sensors)From the spec into the world; nothing comes from production
When it is usedIn operation, for the thing's whole lifeBefore release and on every change; nightly once live
The questionWhat is this machine doing, and what will it do?Will this agent do the right thing in every situation it must face?
How close to realAs close as possible, everywhereExact only where a test needs it; each world states what it is faithful about
What comes outPredictions, alerts, what-ifsPass or fail per scenario, evidence, a coverage map, a ship-or-block verdict

What goes in, what happens, what comes out?

Input, processing, output

Agent's owner

Writes the agent spec (called an AOAS): its tools, the rule behind each tool, the states things move through, and what it owes customers.

Tester

Fills the world with a few rows on each rule's edge and writes or generates scenarios: who says what, what goes wrong, what must be true at the end.

The Assurance Catalog

118 public checks an AI application may owe. The agent's shape picks which ones it owes.

Agent's team

Writes one binding function: how to start the agent and point it at the pretend tools.

Part 2 · How it works

From set-up to a verdict, then a tiny agent you can play, then a big one.

What has to exist before any agent is tested?

How the system is set up

Four open repositories, set up once and shared by every agent:

AgentTwin

The library and command line: world format, stand-ins, actors, faults, clock, judges, run, scaffold, coverage.

AI Assurance Catalog

What must be true: 118 checks, 36 owed by every AI app, the rest by shape.

AI Harness Catalog

What must exist around the model call: the harness parts each shape needs.

Clean AI Engineering

The spec formats and the four gates, plus one "yardstick" file per agent that the agent's own team cannot edit.

The yardstick living outside the agent's repository matters: an agent that could bring its own tests could bring easy ones.

I have a new agent. What do I do?

What you do for each agent

  1. Write the agent's spec (AOAS). Its entities, tools, the rule behind each tool, the states and the promises it owes (for example: a refund is owed when a return is received). The agent's owner writes it; it is the single source of the rules.
  2. Say what shape it is. One or more of ten archetypes (a tool-using agent is A6; a deterministic router in front of it adds A5). The shape decides which Assurance Catalog checks it owes.
  3. Run agenttwin scaffold on the spec. It writes a world file, a starter scenario for each tool and rule, a binding stub and a gates file. Most of the work after this is data, not code: the electronics version of the shop agent is a 70-line world file.
  4. Fill the world with rows. A few members, orders or claims that sit on each rule's edge: 7 days late and 8 days late, inside and outside a window. The loader refuses impossible rows (a returned book that is still overdue).
  5. Write the binding. One function that starts the agent and points it at the world's tools: (live, *, wrap, clock, model) -> Subject. The agent never imports AgentTwin; the build fails if it tries.
  6. Run agenttwin coverage, then top up. It lists which combinations of intent, state, persona and fault, and which state changes, no scenario covers yet. scaffold --pairwise writes skeletons for the missing ones.
  7. Run the four gates. tools/gates.py runs the scenarios, checks every owed statement is proved or knowingly accepted, checks the build's structure and the harness parts. One command, one verdict, a route for every failure.

For a given agent, how do we know these are the tests it needs?

How we know which tests a given agent needs

This is the most important question on the page. The answer: nobody picks the tests by taste. The agent's test list is whatever it takes to prove everything the agent owes, and what it owes is written down, item by item, each with an id.

Where each owed item comes from:

  • The agent's own spec. Every tool gets a test that it works inside its rule and is refused outside it. Every rule gets tests on its edges (7 days late passes, 8 fails; the spec's own numbers say which values matter). Every state change in the spec's state machines gets a path. Every promise ("a refund is owed once the return is received") gets a test that it is kept.
  • The Assurance Catalog, by shape. A tool-using agent owes checks a plain chatbot doesn't, such as "hard termination under every condition". The shape picks them.
  • The Harness Catalog, by shape. The harness parts the shape needs (approval gates, idempotency, kill switch) each need a test.
  • Attack corpora. Injections are generated from PyRIT, AgentDojo and built-in templates into every field the spec marks untrusted.
  • Combinations. agenttwin coverage crosses intent × state × persona × fault and keeps a small set that covers every pair (pairwise testing), so you don't need thousands of cases.
  • Production misses. When something slips through in the wild, it becomes a scenario, so it can't slip through twice.

Every test then says which items it proves (discharges: [AAC-0047, op:renew]). The gate builds a map: each owed item is proved, an accepted gap (with a reason, an owner and a review date), not applicable (with a reason), or not exercised. Any "not exercised" item fails the gate, with its name. So the answer to "are these the right tests?" is checkable: the right tests are the ones that leave nothing unaccounted for.

The honest catch. This proves the tests are complete against what is written down. If a rule is missing from the spec, nothing asks for its test. Three things push against that: generation runs (build an agent from the spec alone and route every surprise back into the spec), a model-played customer who says things nobody scripted, and production misses becoming cases.

Writing the world and scenarios is a lot for a tester. How do we stop them missing things?

How we help the tester not miss

The tester should never start from a blank page, and should never have to remember the common cases. Six layers of help, from what the spec gives for free to what only production can teach:

2 · What's missingcoverage lists uncovered pairs of intent, state, customer type (6 built in) and fault (8 kinds), and state changes never walked; --pairwise writes starters for thembuilt
3 · The common packScenarios every agent needs whatever its business: the same message twice, a long chat that should fetch a person, an approver who never answers, the kill switch, the model provider down, never quoting a figure no tool gave. Hasn't AI already solved this? The calculator question

"If I want to test a calculator API, can't I generate all the test cases automatically and cover 100%?" Partly. Three different things hide inside "100%":

"100%" of…For a calculator
Every line of code run (code coverage)easy Tools like Pynguin (Python) and EvoSuite (Java), and AI coding assistants, generate tests that run every line. But a test can run every line of a buggy divide and still pass.
Every possible inputimpossible Two 64-bit numbers make about 3.4 × 1038 pairs. At a billion tests a second that is about 1022 years; the universe is about 1010 years old.
The right answer for each inputthe hard part Generated tests often just record what the code does today, bugs included. Someone must say what is right. Testers call this the oracle problem.

A calculator is the easy case, because maths gives an oracle for free: compare with a trusted library, or check rules that must always hold (a + b = b + a; (a + b) − b = a). Pick inputs smartly (zero, negatives, huge numbers, the edges) and a machine can test a calculator very well, without trying every input.

An agent has no free oracle. Whether "refund this order" is right depends on the shop's rules, the order's state, who is asking and what was promised. AI can generate endless conversations, but it can't know which outcome is correct unless the rules are written down. That is why AgentTwin starts from the agent's spec: the spec is the oracle, and the four judges apply it to the world's state.

How the software world handles it

Nobody has fully solved "complete tests". Mature teams combine six habits, and each has an AgentTwin counterpart:

How LangWatch handles it

In LangWatch Scenario, developers write scenarios in code: a model plays the user, a model judge scores the chat against criteria. An autopilot mode lets the simulated user improvise towards a goal, and LangWatch describes generating multi-step scenarios from a list of business policies, including where two policies overlap. Its answer is breadth: let a model write many scenarios. What it doesn't publish is a count of what's missing. AgentTwin's difference is that it counts the gaps; the idea worth borrowing is drafting scenarios where two rules meet.

What PyRIT-style tools add

PyRIT, Microsoft's red-teaming kit, is built from four parts: seeds (attack goals), converters (rewrite one attack many ways), attacker models (read the reply and try again, turn by turn) and scorers. Two of those ideas reach beyond security. Converters become "one scenario, many wordings, languages and moods", which takes the phrasing work off the tester. The attacker model becomes the adversarial customer in layer 5. PyRIT knows nothing of your business rules, so AgentTwin supplies the goals from the spec and does the scoring with its judges.

How are the pretend systems made?

How the pretend systems are made

Not by writing mocks by hand, and not by asking a model to play the system. AgentTwin reads the agent's spec and projects each system as a stand-in that holds state and enforces the spec's rules. Ask it to cancel a shipped order and it refuses, the way the real system would.

A canned mock that answers "OK" to everything is not enough: it would cancel the shipped order, the agent's test would pass, and it would prove nothing. A model playing the system is not enough either: it can be talked into allowing what the real system refuses.

Kind of thing the agent talks toHow AgentTwin treats it
A data storeThe world's state, shown as rows
An API with a contractAnswers from the declared contract
A tool server (MCP)Tool results: the cleanest seam there is
The customerAn actor (scripted, state machine, or model-played), not a system
A person who approvesAn actor plus a queue, acting between turns on a clock
A plain calculationRun it for real. Mocking it adds risk and removes nothing

Each world also says what it is faithful about and what it is not. The clothing shop's world is exact about order status, the return window and which actions can't be undone, and openly not faithful about prices, stock or carriers. A test may only check things inside that list.

Where does each test's data come from?

How test data is made, per case

  • A small declared set of rows in the world file, chosen to sit on each rule's edge. Seeded, so every run is the same.
  • Edge values are read off the rules: a rule that says "at most 30 days" makes 0, 30 and 31 the interesting values. Hypothesis adds more around them.
  • Per-scenario changes: a scenario can plant a value (an injection in an order note) or set the clock forward. Planting is only allowed in fields the spec marks untrusted; the runner refuses otherwise, because it would test a threat nobody faces.
  • A population for long runs: Faker generates customers and orders in the AgentTwin Lab, and the loader checks them against the same rules as hand-written rows. SDV for realistic volumes is planned.
  • Impossible data is refused. A returned book that is still overdue, or a loan for a member who doesn't exist, stops the load with a reason.

    Can we really reach 100%?
    Is 100% coverage achievable?
    

    It depends on what the 100% is of.
    

    100% of…Achievable?Why

    What limits are we facing?
    Our limits today
    

    1. The tests are only as complete as the spec. If a rule is missing from the spec, no scenario will look for it. Five 'generation runs' (build an agent from the spec alone, see what goes wrong) keep finding spec gaps: run 5 found 7 missing statements and 1 contradiction. A model-played customer found one too: a customer said 'my jacket is lost', the rule only matched 'lost in transit', and nobody was fetched.
    2. Stand-ins are hand-faithful, not proven faithful. Every world declares what it is faithful about, but none has been checked against a real system yet (shadow mode is designed, not running).
    3. Scenarios run once, with a scripted model. Live models are random; one pass proves little. pass^k (the same scenario k times, all must pass) runs in the lab only; nightly live runs are designed.
    4. MCP agents only. An agent that calls REST APIs or a database directly cannot be tested yet. The fixes (DNS interception; a real database per run) are designed.
    5. Worlds are small and clean. A handful of rows on each rule's edge. Messy, high-volume data (SDV) is planned.
    6. Soft qualities are not judged. Tone, helpfulness and completeness need model graders (DeepEval or Inspect); not plugged in yet. AgentTwin judges what changed, not how nice it sounded.
    7. No platform. No UI, dashboards or managed runs. It is a library, a command line and CI. Fine for engineers; a gap for a buyer who wants a product.
    8. One builder, two reference agents. Proved on a shop agent, a motor-claims agent and three τ²-bench agents we did not build. Not yet used by an outside team.

    FAQ
    Questions people ask
    Is AgentTwin a digital twin?
    Not in the usual sense. A digital twin copies a real machine to watch and predict it. AgentTwin copies the world around an AI agent (customers, systems, data, approvers, faults, time) and keeps the agent itself real, so it can be tested before it meets real people.
    Does AgentTwin test the model?
    No. It tests the whole agent as built: model, prompts, harness, checks and tools. The model can be fooled in a test and the test can still pass, if nothing harmful reached the world.
    Why judge the world's state instead of the conversation?
    Because agents can say the right thing and do the wrong thing, or the reverse. 'Your refund is on its way' is only true if a refund exists. The world knows; the transcript does not.
    Can I use it on my agent?
    If your agent calls its tools over MCP and you can write its spec, yes: scaffold the world from the spec, write one binding function, run the gates. It is open source under Apache 2.0.
    Does it replace LangWatch, promptfoo or DeepEval?
    No. It uses them. LangWatch Scenario plays the customer, PyRIT and AgentDojo supply attacks, and DeepEval or Inspect are planned for soft grading. AgentTwin adds the spec-driven world and the judges that read it.
    Can't AI just generate every test case, like for a calculator?
    It can generate inputs and run every line of code. It can't try every input (two 64-bit numbers alone make 3.4 × 10^38 pairs), and it can't know the right answer unless something states it. Maths states it for a calculator; for an agent, the written spec has to, which is why AgentTwin starts there.
    Is 100% coverage possible?
    100% of what an agent owes can be accounted for: each check proved by a test or signed off as a known gap. 100% of everything that could happen cannot, and nobody can promise that. See the section on coverage.
