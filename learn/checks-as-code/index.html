Checks as code, and the Ops gate

A checklist in a document tells people what should be true. A check as code states it precisely, attaches evidence, and can be run the same way on every project. This page explains the idea, shows how discovery, architecture and operations gates can all be built from it, and gives a detailed Ops gate checklist, in categories, so a project knows what it will be tested on before it starts.

Teach first

A document says. A check proves.

Every project has a checklist somewhere: a sheet of things to confirm before go-live. Most are written once, copied from the last project, ticked by whoever is in a hurry, and never read again. The idea of a check as code is to write the same expectations in a precise, structured form, keep them with the project, and attach evidence to each.

The same expectations, written two ways. Only the second can be run, counted and trusted.

A document checklistA check as code
Where it livesA Word, Excel or PDF file, copied aroundIn a repository, next to the code
When it is writtenOnce, at the startContinuously, with history
Who reads itThe author, at the endEveryone, at every change
What counts as evidenceA tick by a personEvidence attached; some checks run themselves
DriftCopies diverge and old versions circulateOne source; differences are visible
Same for every projectEach project edits its own copyOne spec; 'applies when' rules trim it
RepeatabilityDepends on who runs itSame inputs, same result
CoverageUnknownCounted: passed, failed, not yet known
Cost of checkingManual every timeAutomatable for the checkable part
WeaknessIgnored once the deadline nearsNeeds upfront work; can be gamed; not everything is checkable
In one line: checks as code do not remove judgement. They make each judgement explicit, owned, evidenced and repeatable.

Spec-driven

The spec comes first. The checks follow.

In spec-driven development, a specification says what must be true, and everything else is derived from it. The same works for gates. The spec of a good discovery, a good design or a ready-to-run system is written once. The checks come from it. A gate runs the checks against evidence, and reports what is proven, failed and not yet known.

One spec, many gates. A gate is a view of the spec, not a new document.

The wider idea is on the spec-driven development pages, and for data platforms in spec-driven data platforms.

Anatomy

What one check looks like

The project review that this site already publishes works this way: 198 checks, each a small structured record, filterable by stage and role (see the checks and the open repository). The Ops gate uses the same fields.

id: OPS-REC-02
title: A restore has been tested, and the time measured
question: >
  Has someone restored the data and configuration from backup into a clean
  environment, with the time measured and compared with the agreed target?
why: >
  The backups ran for a year. The first real restore failed because the keys
  were not backed up. Recovery took three days instead of three hours.
applies:
  kind: [any]
  components: [storage, platform]
owner: operations
also: [tech-anchor]
evidence:
  docs: [recovery-document, restore-test-record]
  looks_like: A dated test record with the measured time and who ran it.
severity: blocker
due: 8            # lifecycle stage
fail_fast: Ask in discovery where backups live and who has ever restored one.
verify: drill
FieldWhat it holds
idA stable name, such as OPS-REC-02.
titleThe check in one sentence.
questionThe question a reviewer asks.
whyWhat goes wrong without it, in one story.
appliesWhen it applies: kind of project, components, patterns, such as 'AI in scope'.
ownerThe role accountable for passing it.
evidenceWhat must be shown: documents and what 'good' looks like.
severityBlocker, major, minor.
dueThe lifecycle stage by which it should be ready.
fail_fastThe cheapest early test to know if it will pass.

Four levels of verification

LevelWhat it meansExample
ManualA person looks at evidence and decides.Is the runbook usable? Are the definitions owned?
Semi-automatedA script collects the evidence; a person judges it.List all accounts that run production jobs; a person decides if each is allowed.
AutomatedThe check runs and returns pass or fail.Did the last 30 loads alert on a deliberate failure? Is any secret in the code?
DrillA rehearsal proves it works under stress.Restore from backup. Roll back a release. Run the runbook cold.

How a gate runs

No surprises at the gate

  1. Pre-flight. Run the checks yourself, weeks before the gate. The gate holds no surprises.
  2. Evidence pack. Gather the evidence for each check in one place, named by check ID.
  3. Gate review. Reviewers go through the report, not the whole pack. Open items only.
  4. Decision. Pass, conditional pass, or not yet. Written, with names and dates.
  5. After. Conditions tracked to closure. Lessons feed back into the spec.

Three outcomes

DecisionWhenWhat happens
PassNo open blockers. Every category has a named owner who has signed. Majors are fixed or accepted in writing with dates.Go to production.
Conditional passNo open blockers. A short list of majors, each with an owner and a date before or soon after go-live.Go, with conditions tracked weekly.
Not yetAny open blocker, or a category with no owner.Do not go. Fix, then re-run only the failed checks.

The Ops gate

The final gate before production: 101 checks in 14 categories

The question: can operations run this at 3 a.m. without the builders? Operations meet the project once, at the end. If the project knows what they will test, it can prepare for months. Start with the categories. Open the checks only where you are weak.

Prepare

Do the work early. The gate is the last check, not the first

WhenPrepare
Stage 3 to 4Classify sensitive data. Record lawful basis. Agree budget and owner. Agree the old-report switch-off date. Run the Responsible AI review if AI is in scope.
Stage 5Name the owner and the support model. Agree release route. Release from a pipeline from day one. Name consumers.
Stage 6Make jobs safe to rerun. Move secrets to a store. Switch on data quality checks. Tag resources. Document schedules and dependencies.
Stage 7Alerts for failure, freshness and quality. Reconciliation signed. Load and performance tests. Security review. Role tests. Test acceptance.

FAQ

Questions people ask

What is the difference between a checklist and checks as code?

A checklist is a document that people read and tick. Checks as code are written in a structured, versioned form, so they can be applied the same way every time, reported on, and partly automated. The thinking is the same. The discipline is higher.

Do all checks need to be automated?

No. Many are judgements. The point of 'as code' is that each check is stated precisely, has evidence, an owner and a severity, and lives with the project, whether a person or a script verifies it.

Why one Ops gate instead of many?

Operations meet the project once, at the end, and decide whether to take it. A single published gate means they know what they will test, and the project knows what to prepare, months ahead.

Is 105 checks too many?

Not as a menu. Each category has a few checks and an owner, and the 'applies when' rules remove many. Use the categories to see where you stand, and open the checks only where you are weak.

How does this connect to spec-driven development?

A spec says what must be true. Checks are derived from the spec, and run against evidence. When the spec changes, the checks change with it, and the gate report shows which parts of the spec are proven.
