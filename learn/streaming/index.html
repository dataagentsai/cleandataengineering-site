Streaming architecture on AWS and Databricks

IoT and ordinary sources, seconds and minutes, AWS alone or with Databricks: the architecture as roles first, then the options for every part with pros, cons and a verdict.

How live data gets from factory machines (and from databases, apps and files) to screens, alerts and reports. The guide starts with the architecture as roles with no product names, then gives options on AWS alone and on AWS with Databricks for every role, each with pros, cons and a verdict. A tyre maker is the worked example throughout.

Try it: the streaming simulator animates this design for each binding and route, and three lanes together runs the fast, near-real-time and batch lanes over a simulated day. Building the fast lane inside Databricks instead: real-time mode.

The worked example

A tyre maker with five plants. Curing presses, mixers and extruders report temperature, pressure and cycle state every few seconds. Supervisors want alerts and live boards within seconds. Planners and quality teams want hourly numbers they can trust. SAP, MES, a lab system (LIMS) and a dealer portal also produce data that has to join with the sensor data.

Design rules used throughout

  • One event stream feeds two lanes: a live lane (seconds, for acting now) and a platform lane (minutes, the number of record).
  • The platform lane does not run continuously: streaming tables run once every 15 minutes and stop.
  • The live lane never writes gold. Gold is the number of record.
  • One contract per stream: Avro in a schema registry; key = press_id; every record carries reading_id and event time. The stream keeps 7 days.
  • Gold facts are built by recomputing changed time windows, with as-of joins to history dimensions, not by joining inside the stream.

What a stream is, in plain words

A batch is a box of data delivered at a time: "here are yesterday's orders". A stream is a conveyor belt: small messages keep arriving, one after another, and never "finish". Streaming is a way of delivering data, not a kind of data. The same orders can arrive as a nightly file or as one message per order.

Three things make streams harder than batches:

  1. Time has two clocks. Event time is when it happened at the press. Arrival time is when the message reached us. A gateway that was offline for 20 minutes delivers old readings late, so reports must group by event time.
  2. Nothing ever "ends". To say "the 10:00–11:00 average is final", you need a rule for how long to wait for stragglers. That rule is a watermark, for example "wait 10 minutes after the hour".
  3. Messages can arrive twice. Senders retry when unsure. Every reading carries a unique reading_id so duplicates can be removed and totals never double.

Where a tyre company gets streams from

Machines (IoT)

Curing presses, mixers and extruders report temperature, pressure and cycle state every few seconds.

Connected tyres (IoT, maybe later)

Sensors inside tyres on fleet vehicles report pressure and temperature. Millions of small senders.

Database changes

SAP orders and MES production records. These are not events by nature; change capture (CDC) turns every insert or update into an event.

App events

Dealer portal clicks, warranty-claim app submissions.

Webhooks

Salesforce or a payment provider calls our URL when something changes.

Files and logs

LIMS lab results, partner files, application logs. Files arrive in bursts but can be read "as a stream" of files.

The key question for every source is the same: who must act on this data, and how fast? If a supervisor must stop a press within a minute, it needs the live lane. If a planner reads it tomorrow, a 15-minute or daily load is cheaper and simpler.

Measure two ways. Report delay from event time (what the user feels) and from arrival time (what the platform controls). A gateway that was offline for an hour makes event-time delay look terrible, but that is a plant network problem, not a platform breach. The SLA report keeps both and says which one broke.

Three speeds, two lanes: where they meet

There are three speeds: seconds (1–5 s), near real time (15–75 min) and batch (daily). There are only two lanes. Near real time and batch are the same pipeline (same code, same tables) run at a different cadence. The seconds lane is a separate, light, disposable lane.

(1) One raw stream, read separately by each lane. (2) Reference data is copied from the platform lane into the seconds lane on a schedule. (3) Near real time and batch meet in gold. (4) The screen shows live and final numbers side by side, labelled.

Kappa, Lambda, and where we sit

Lambda: two paths, one answer, merged. Kappa: one path, history rebuilt by replay. Ours: Kappa where bronze plays the long log; the live lane is a different product.

How Kappa fits, in four points

  1. Kappa's idea: everything is a stream, there is one code path, and to fix or change logic you replay the log from the start. No separate batch code.
  2. The catch: Kappa needs a log that keeps everything. Kinesis can keep up to 365 days and Kafka can keep forever with tiered storage, but paying a log to hold years of readings is expensive and awkward to query.
  3. Our answer: the log keeps 7 days (for outages); bronze keeps everything forever on S3, cheaply. Bronze is Kappa's long log. Spark reads bronze with the same code as a stream or as a full replay, so there is still one code path.
  4. Why our two lanes are not Lambda: Lambda computes the same number twice and merges. Our live lane computes "act now" signals that are never reported as the number of record; gold comes only from the platform lane. So the two lanes never disagree about a reported number.

Where SCD type 1 and type 2 happen

  • In silver. The dataset kind sets the history type. Master data is SCD2, transactions are SCD1, events are append-only, and snapshots are kept as snapshots. Only the listed tracked columns open a new version.
  • Sensor readings get no SCD. They are facts that never change. A "correction" is a new reading, and deduplication keeps the first.
  • Gold does not redo SCD. It builds dimensions from silver's SCD2 history, adds surrogate keys, and joins facts as of event time.
  • The streaming catch for SCD2: changes can arrive out of order, and a late change must be slotted into the middle of history. Two ways to do it:
    • DLT's AUTO CDC (formerly APPLY CHANGES) handles this with a sequence column.
    • Plain Spark needs our own MERGE in foreachBatch that re-cuts the valid-from and valid-to dates. This is one reason to consider DLT for CDC tables (see Databricks choices).
  • Changing a table from type 1 to type 2 is a replay from bronze, which still holds every change, so the past gets history too.

Joining data in a stream

In batch, a join sees both tables complete. In a stream, one or both sides are still arriving, so every join has to answer: how long do I remember the other side, and what if it is late? Memory held between messages is called state. State costs RAM, and lost state means a wrong answer.

Example: link each curing cycle to the tyre serial scanned at the press. The processor keeps unmatched cycles until the watermark passes, then gives up and routes them to an "unmatched" output.

The join rule: join inside the stream only when the answer is needed in seconds and the other side is small or time-bounded. Otherwise land both sides in bronze and silver, and join in gold by window recompute. This keeps state small and makes corrections automatic.

Five join hazards and what handles each

  • Late dimension (a new press appears in readings before it appears in the master table): keep the reading with an unknown key (−1). Window recompute fixes it when the master row lands.
  • Fan-out (duplicate key on the "one" side multiplies rows): count duplicate keys on the one side separately; one net count hides mistakes that cancel out.
  • Clock skew (a press clock that is 3 minutes wrong): the gateway stamps its own time too; when the two differ by more than a limit, the reading is flagged.
  • State loss (a processor restart without its checkpoint): checkpoints on S3; the live lane can rebuild from 2 days of Kinesis.
  • Re-emitted results: sinks are idempotent (MERGE on key, or upsert by press and minute), so a retry never double counts.

Databricks choices: DLT or not, Spark Streaming, Auto Loader, file arrival

Is Spark Structured Streaming worth it when we only run every 15 minutes?

Yes, for the platform lane. Even when it runs once and stops (trigger "available now"), a Spark streaming read gives us the bookkeeping for free: which Kinesis records or which files are already done (the checkpoint), exactly-once writes into Delta, and catch-up after a missed run. Doing the same with plain batch reads means writing our own "where did I stop" logic for every source.

DLT (Lakeflow Declarative Pipelines) or not?

DLT means you declare tables (streaming tables, materialized views) and their rules, and Databricks runs them: checkpoints, retries, ordering, data quality expectations, and AUTO CDC for SCD. The alternative ("non-DLT") is our own PySpark code using Structured Streaming inside Lakeflow Jobs. The reference ETL on this site is built that way: the 13 silver stages as pure PySpark functions, testable on a laptop.

Auto Loader, in plain words

Auto Loader is a Spark streaming source for files. You point it at an S3 folder; it finds new files, remembers which ones it has read (in its checkpoint), handles schema changes, and puts unexpected fields in a rescue column. It finds new files in one of two ways:

  • Listing the folder. Fine for small folders, but slow and costly for big ones.
  • File events. S3 tells Databricks about each new file through queue notifications that Databricks sets up on the Unity Catalog external location. This is recommended.

Kinesis is for records; S3 events are for files. The sensor stream comes through Kinesis. DMS change files, LIMS results and partner files come through S3 and Auto Loader.

Answer: do not hand a single file to DLT. Trigger the pipeline (F2), or run it on a schedule (F1), and let Auto Loader find every new file. That way a missed event never loses a file, and ten files arriving together cost one run, not ten.

Can S3 be used?

Yes, in four of the five roles below, but not as the conveyor belt itself. S3 is a warehouse, not a belt: it holds objects, it does not push them to readers, and every object written is a paid request.

The number that settles it: at production scale (300 readings a second), one S3 object per reading is about 778 million PUT requests a month. At about $0.005 per 1,000 PUTs, that is roughly $3,900 a month in requests alone. Readers would also have to list or be notified about each object, and then the platform lane reads millions of tiny files. Buffering readings into one file a minute fixes all three, at the cost of a minute of delay.

Five performance rules

  1. Batch at the edge. Bundling readings per gateway per second cuts messages, requests and cost by 10–100 times.
  2. Key by press. Order is kept per press; the many presses spread across shards. Never key by plant: one hot shard.
  3. Give each lane its own reader (enhanced fan-out) so the 15-minute catch-up run cannot slow the live lane.
  4. Emit changes, not every reading, into the live store and to screens; at stretch scale this is the difference between $50 and $5,000 a month in DynamoDB writes.
  5. Bronze files sized well: 15-minute runs write fewer, larger files; liquid clustering and predictive optimization keep them tidy.

What drives the bill

  1. Per-message prices (IoT Core, S3 PUTs, DynamoDB writes) dominate at scale: batch at the edge and emit only changes.
  2. Always-on compute (Flink): keep the live lane to what someone acts on within minutes.
  3. The 15-minute cadence sets the Databricks part: 30 minutes roughly halves it; 5 minutes roughly triples it.
  4. Retention on the belt: 7 days is cheap; history belongs in bronze.

Replays

A replay is reading old data again on purpose: after a fault, a bug fix or a logic change. Because Kinesis keeps 7 days and bronze keeps everything, every layer can be rebuilt. Rules: every replay is a logged run with a reason; replays use separate compute so live service levels are not hurt; replays never re-send alerts.

The end-to-end SLA report

One report answers four questions every day: did we keep the promises, where did the time go, did anything get lost, and what went wrong.

Timestamps every reading carries

StampSet byMeaning
t0 event_timeMachineWhen it happened
t1 gateway_timePlant gatewayWhen the plant sent it (also catches clock skew)
t2 kinesis_arrivalKinesisWhen it reached AWS
t3 live_emitted_atFlinkWhen the live lane pushed it (alerts and windows)
t4 bronze_at + run idLanderWhen it landed in bronze
t5 silver_at + run idSilver builderWhen it became clean data
t6 gold_complete_atGold builderWhen its press-hour was marked complete

How it is built

  • Flink writes a one-minute summary per plant: counts, p50/p95/p99 of t3 − t0 and t3 − t2, late and bad counts. The summary goes through Firehose into an ops table.
  • Each 15-minute run records counts and delay percentiles per hop through the run recorder.
  • Two ops tables hold the result:
    • ops.stream_sla_minute: stream, plant, minute, hop, count, p50, p95, p99, late, duplicate and quarantined counts.
    • ops.gold_hour_completeness: press-hour, complete at, inputs late, restated.
  • Metric views sit on top, feeding an AI/BI dashboard. Ops agents read them through tools, never through raw queries.

The five pages of the report

1 · Scorecard

Each promise with % met for yesterday, 7 days and 30 days, plus breach count. Example: "Alerts ≤5 s: 99.6% (target 99%)".

2 · Where the time goes

A waterfall of p95 delay per hop (machine → gateway → Kinesis → live, and → bronze → silver → gold) by plant.

3 · Nothing lost

Counts per hop side by side: gateway sent, Kinesis received, bronze, silver (+ duplicates + quarantined), gold minutes covered. The difference must be zero or explained.

4 · Errors and lateness

Quarantine by reason, late readings by bucket (<5 min, <1 h, <1 day, older), restated gold hours.

5 · Incidents

Silent plants, missed runs, lag alarms and replays, each with start, end, cause and which promise it broke (event-time vs arrival-time).

Made-up numbers to show the shape: most delay is waiting for the next run, which is a cadence choice, not a performance problem.

FAQ

Questions people ask

Should a 1 to 5 second streaming lane call Databricks?

No. Keep it light and inside the streaming layer: validate, deduplicate, limit checks, one-minute windows, and small reference data copied in on a schedule. Databricks reads the raw stream separately and builds the numbers of record.

Where do SCD type 1 and type 2 happen in a streaming lakehouse?

In silver, by dataset kind: master data as SCD type 2, transactions as type 1, sensor events append only. Gold builds dimensions from silver's history and joins facts as of event time.

DLT or plain Structured Streaming?

Plain Structured Streaming in jobs as the default, because it is portable and fully testable; DLT's AUTO CDC is worth it for tables built from database changes, where out-of-order SCD2 is hardest to write by hand.

Can S3 be used as the stream?

Not as the belt itself: one object per event is slow and costs a request each. S3 works well as minute-level landing for Auto Loader and as the long-term history that makes Kappa replays possible.

Should I trigger a DLT pipeline for each file that lands in S3?

No. Use a file arrival trigger or a schedule and let Auto Loader pick up every new file, so a missed event never loses a file and ten files cost one run.
