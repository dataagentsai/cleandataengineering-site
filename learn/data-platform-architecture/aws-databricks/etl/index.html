The ETL, end to end

How the core actually runs: which parts there are, what starts each one, how one load moves from a source system to a metric, the ids and log rows that tie it together, what happens when something breaks, and how we watch it. The concept pages say what each layer does; this page says how it runs.

Start here

Six rules the whole runtime follows

Everything below follows from these. If a design choice ever conflicts with one of them, the rule wins.

1
Movers never write to bronze; the lander never talks to a source. AWS services bring data to S3 landing; our one lander takes it from there. So every source, whatever its type, enters the platform the same way, and a source outage never touches Databricks.
2
Everything is a run, and every run leaves the same rows. A file load, a pipeline update and a 15-minute slice of a stream all get a run id and the same log rows, so one dashboard and one set of alerts cover all of them.
3
Every step can run twice. Re-running a step after a crash gives the same tables as running it once. That is what makes retries, re-runs and backfills safe without a person checking.
4
Jobs are generated, never hand-built. The run controller's jobs and pipelines are generated from the metadata and deployed with Asset Bundles. Adding a dataset changes YAML, not a job.
5
One orchestrator per path. Lakeflow Jobs owns everything from landing onwards. AWS only starts movers. Two schedulers for one pipeline is how runs overlap or never start.
6
Log before you work, close after you commit. A run that cannot write its start row does not start. A run is marked succeeded, and its bookmark moved, only after its data is committed.

Sources and ingestion tech

What we load, and what brings each one in

Nine kinds of source cover a tyre maker: databases that change all day, small reference tables, SAP, SaaS apps, APIs, partner files, machines, historian history, and the spreadsheets people keep. Five technologies bring them in. Four are AWS services (DMS, AppFlow, Transfer Family, Kinesis with SiteWise); the fifth is our own puller, built from the framework's existing connectors. All five deliver to the same landing area, which is why one lander can take it from there.

How to pick, in order

For a new source, ask these questions in order and stop at the first yes.

1
Is it machine data? Kinesis, through SiteWise or IoT Core.
2
Is it SAP? AppFlow with the SAP OData connector. If SAP Datasphere or Business Data Cloud is licensed, the SAP team may choose those instead; the landing contract stays the same.
3
Is it a database with many changes a day, or are deletes needed? AWS DMS with change capture.
4
Is it a small table, a reference list, or a database where CDC is not allowed? Our puller, full or by watermark.
5
Is it a SaaS application? AppFlow if it has a connector; otherwise our puller's REST connector.
6
Is it files from someone outside? Transfer Family SFTP, one folder and one login per partner.
7
None of the above? Ask how it can become a file in landing. If it cannot, it is a design discussion, not a quick add.

The landing contract: what every mover must deliver

The movers differ; what they hand over does not. This contract is what lets the lander treat every source the same way.

1
One place. landing/<source>/<dataset>/<batch or date>/, in the landing bucket of the environment. Personal-data sources use the personal-data landing bucket.
2
Never overwrite, never edit. A mover only adds files; a re-sent batch gets the same batch id, so it replaces only itself.
3
Complete or invisible. A file appears only when it is complete (S3 writes are all-or-nothing; SFTP uploads go to a temporary name first).
4
Say how many. Where the mover can, it states the row count: a manifest from our puller, the flow-run event from AppFlow, a control file from partners who agree one. DMS cannot, so DMS loads are checked against CloudWatch table statistics instead.
5
Say what was deleted. DMS marks deletes in its operation column; full copies are compared with the last copy in silver; partners send either full snapshots or a delete file. SAP deletes depend on the extractor (check current status per object).
6
No transforming. Movers change the format at most (to Parquet). Every rule about content lives in the lander and after.

Ten parts, three bands

One run, step by step

A quarter-hour of MES data, from database to gold

Follow one load: changes to the press events table in the plant's MES database, picked up at 00:15 and in gold by 00:20. Times are illustrative.

1
00:00:00 The mover keeps landing files. AWS DMS reads the MES database's change log continuously and writes a file of changes to landing/mes/press_event/ every few minutes, each with an operation flag and a commit time. DMS writes no manifest, so its loads are checked against its own table statistics.
2
00:15:00 The run controller starts a job run. The lander job for MES has a 15-minute schedule and a file-arrival trigger, whichever comes first. Lakeflow gives it a job run id.
3
00:15:02 First task: open the master run. It writes one master_run_log row (RUNNING), reads dataset_view for every enabled MES dataset, stores the merged settings once in config_snapshot by their fingerprint, and lists which datasets have new files.
4
00:15:05 One task per dataset, eight at a time. A for-each task runs the lander for each due dataset. Each opens its own run_log row (STARTED) with the master run id, the job's task run id and the window it will load.
5
00:15:06 The lander loads. Auto Loader reads only files it has not seen. The lander checks each batch against its row count where the mover gives one, tokenises personal columns, drops undeclared ones for personal-data sources, adds the ingest columns and appends to bronze. Each part is a step_log row with rows in and out.
6
00:15:40 The run closes after the commit. Only after the Delta commit: run_log becomes SUCCEEDED with rows read, written and rejected, and the newest commit time it loaded is stored as the watermark, in one database transaction.
7
00:15:45 The master run closes. SUCCEEDED if every dataset succeeded, PARTIAL if some failed (they get their own error_log rows), FAILED if none did. The next stage does not wait for the slowest dataset; it is started by the bronze tables themselves.
8
00:16:00 Bronze changes start silver. The silver pipeline for the manufacturing domain has a table-update trigger on its bronze tables, at most once every 15 minutes. A wrapper task opens a run_log row for the pipeline update and stores its update id.
9
00:16:05 The silver pipeline runs. Contract check, then the eleven bronze-to-silver steps; expectations park bad rows in quarantine; AUTO CDC applies changes and history. The integrator's materialized views refresh incrementally.
10
00:19:30 The wrapper reads the pipeline's event log. Rows per table, expectation results and errors are copied into run_log, step_log and dq_result, so a pipeline update looks like any other run.
11
00:20:00 Gold. Simple facts refresh as materialized views in the same pipeline. Multi-input facts (production per press-hour) run in the window-recompute job, which works out which hours changed in any input and rebuilds those hours whole.
12
00:30:00 The ops builder sees it. Its 15-minute run copies the new runtime rows into prod_ops, joins the job runs and their cost from system tables, and updates freshness: the MES-fed tables are green.

Jobs and triggers

What starts what

Lakeflow Jobs can start a job on a clock, when a file arrives, or when a table it reads has changed. We use all three, each where it fits, so data flows as soon as it can and nothing polls for no reason.

ScheduleBatch sources with a fixed rhythm (SAP every 30 minutes in plant hours, full nightly)The lander job of that source
File arrivalSources that drop files at unknown times (dealer sell-out, warranty files)The lander job of that source (check current status for limits on watched paths)
Table updateSilver and gold: run when their inputs changed, not on a clockThe pipeline of a domain, with a minimum gap between runs (check current status)
ContinuousSensor streamsThe streaming pipeline, always on
Manual or APIRe-runs, backfills, the heartbeat testAny job, with a run type that says why it ran

One generated job, as an example. It is produced from the metadata for every source; people change the YAML in the metadata, never this file.

# Generated from dataset_view by the framework's generator; never edited by hand.
# (Asset Bundle job syntax: check current status)
resources:
  jobs:
    lander_mes:
      name: lander_mes
      trigger:
        file_arrival: { url: "s3://landing-prod/mes/" }
      schedule: { quartz_cron_expression: "0 0/15 * * * ?", timezone_id: "UTC" }
      max_concurrent_runs: 1                 # a run never overlaps the previous one
      tasks:
        - task_key: open_master_run
          python_wheel_task: { package_name: lake_ingest, entry_point: open_master_run,
                               parameters: ["--source", "mes"] }
        - task_key: load_each_dataset
          depends_on: [ { task_key: open_master_run } ]
          for_each_task:
            inputs: "{{tasks.open_master_run.values.due_datasets}}"
            concurrency: 8
            task:
              task_key: land_one
              python_wheel_task: { package_name: lake_ingest, entry_point: land,
                                   parameters: ["--dataset", "{{input}}"] }
              max_retries: 2                 # only for errors classed as transient
        - task_key: close_master_run
          depends_on: [ { task_key: load_each_dataset } ]
          run_if: ALL_DONE                   # closes the master run even after failures
          python_wheel_task: { package_name: lake_ingest, entry_point: close_master_run }

The lander job for the MES source, generated as an Asset Bundle resource.

These are the framework's existing run tables, in the runtime schema of the metadata database.

The run recorder: six calls

Every part logs through one small library, so the rows are always complete and always the same shape.

1
open_master_run(source, trigger) Writes the master run row; returns its id. Fails the job if it cannot write: no work without a record.
2
open_run(dataset, stage, window) Writes the run row with all ids it can see (job run, task run, update id).
3
step(name, rows_in, rows_out) One step row; used as a context manager so the time is measured for you.
4
error(exc) Classifies the error, scrubs the message of data values, writes error_log, and says whether a retry makes sense.
5
quality(results) Writes dq_result rows from DQX or the pipeline's expectations.
6
close_run(status, counts, new_watermark) Marks the run and moves the watermark in one transaction, only when status is SUCCEEDED.

Streaming

Sensors fit the same model

A stream never ends, so it has no runs of its own. These five rules make it look like everything else to on-call and to the dashboard.

1
There are no runs, so we cut windows. Every 15 minutes the ops builder writes one run_log row per stream per window, from the pipeline's event log and streaming progress: rows in, rows out, how far behind (lag), errors.
2
The bookmark is not ours. The stream's checkpoint and Kinesis' sequence numbers are the watermark. We record where the checkpoint lives and the last sequence per shard, not a second bookmark.
3
Freshness is event time. A stream is fresh when the newest reading in silver is recent, not when the job is running. A running job that reads nothing is the silent failure we look for.
4
Gold from streams is hourly. The hourly gold materialized view refreshes after each hour closes, plus late readings within 2 hours; later ones are picked up by the window recompute.
5
Silent machines are checked separately. One press going quiet does not move a stream's totals, so a per-press check (no reading for 30 minutes in a planned shift) runs in the ops builder.

When something breaks

Each failure has one place it is caught

For each kind of failure: where it is caught, what the platform does by itself, and the one thing a person needs to do. Retries happen only for errors classed as passing (a network blip, a busy cluster), never for bad data or bugs, because retrying those just fails again.

What goes wrongCaught byWhat happens by itselfWhat a person does
Source down or slowMover: CloudWatch alarm on DMS lag or AppFlow failureAWS retries; the lander finds no new files and ends as skippedFreshness alert at the promised time; incident for the source owner
A file is empty, unreadable or does not match its manifestLander, file checkThat dataset's run fails; the file moves to landing/_rejected; other datasets carry on (master run PARTIAL)The source owner re-sends; the next run picks it up
Columns removed, renamed or retypedSilver, contract checkThat table's flow fails; its silver stays as it was; bronze still has everythingNew contract version and mapping; then replay from bronze
Bad rowsSilver, quality rulesRows parked in quarantine with the reason; the rest carry on; stop only past the bad-share limitSteward reviews weekly; fixed rows are released and re-merged
Job or cluster dies halfwayLakeflow task failureTask retried (transient errors only, up to 2 times); nothing was committed, or the commit is replayed safelyNothing, unless retries run out
Same file sent twiceLanderAuto Loader skips a file it has seen; the same rows in a new file are removed by silver's duplicate stepNothing
Data arrives lateLander and goldLands normally; gold recomputes the windows it changes and logs a restatementNothing; dashboards show the restatement note
The metadata database is unreachableRun recorder, at open_master_runThe job fails before doing any work; nothing half-donePlatform on-call: the alert comes from Databricks job failure, which does not need our database
A bug in our codeAny stageFails; error class 'our bug'; no retryFix, release, then re-run the failed runs

Re-runs, replays and backfills

Four ways to run again, each safe

KindWhenHow
Re-run failedOnly the datasets that failed in a master run, with the same windowA new master run with run type rerun and retry_of_master_run_id set; the watermark never moved, so the window is the same
Replay from bronzeRebuild one silver table after a logic or contract fixA full refresh of that one table in its pipeline; bronze is the source of truth, so nothing is fetched from the source again
BackfillLoad or rebuild a past window on purposeA plan in Git with dataset, window, reason and cost; runs as its own run type and never moves the normal watermark; gold windows rebuilt and a restatement logged
Re-extractFetch from the source againOnly for sources that can resend a window. Never for SAP, which moves its own delta token: we replay from landing or bronze instead

-- prod_ops.v_dataset_health: one row per dataset, the first thing on-call opens
SELECT d.dataset_name, d.tier, d.owner,
       r.status                          AS last_status,
       r.ended_at                        AS last_success_at,
       f.promised_by, f.minutes_late,    -- freshness against the target in dataset_config
       r.rows_written,
       b.rows_low, b.rows_high,          -- the usual band for this weekday
       q.rules_failed, q.rows_quarantined,
       c.cost_today_usd
FROM ops.dim_dataset d
LEFT JOIN ops.last_run r         USING (dataset_id)
LEFT JOIN ops.fct_freshness f    ON f.dataset_id = d.dataset_id AND f.day = current_date()

Questions

Questions engineers ask

Why not one big job from source to gold?

Because sources arrive at different times. A job per source loads what has arrived; pipelines per domain run when their inputs change. Nothing waits for the slowest source, and a failure in one source does not block the others.

Why does a Declarative Pipeline need a wrapper task?

The pipeline has its own event log and its own ids. The wrapper opens and closes our run row around each update and copies the counts and expectation results across, so on-call sees one kind of run everywhere.

What if the logging database is down?

Jobs fail at their first task, before any work, so nothing is left half-done. The failure itself is visible in Databricks job alerts and system tables, which do not depend on our database.

How is this different from Azure Data Factory designs?

In an ADF design the orchestrator also moves data. Here the AWS movers only move, Lakeflow Jobs only orchestrates, and our lander and pipelines only transform. The framework's contracts (master run, run, step, segment, watermark) are the same.
