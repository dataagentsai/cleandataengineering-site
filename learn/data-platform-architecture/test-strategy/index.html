Data platform architecture · testing

Test strategy for a data platform

What we test, when each test runs, and what blocks a release: seventeen kinds of test on a reference build, with what is proven so far and how each one works.

Part one · crisp

The strategy on one page

Aim. A wrong number never reaches a dashboard without someone being told, and a bad change never reaches production. Tests run before the merge, at release, and inside every production run.

Five principles

Test against known answers. A simulated company produces the source data and also knows the correct total at every layer for every day. The platform's output must equal those totals.

Plant every fault you claim to handle. Duplicates, late files, renamed columns and mass deletes are put into the data on purpose. Each one must be caught at the layer that is supposed to catch it.

Compare versions on the same input. A change runs beside the current version on copies of production tables. Any difference nobody declared blocks the release.

Production runs test themselves. Contract rules, reconciliation and row counts run on every load, so a problem in real data is caught the same way as a planted one.

Every rule has a test or a written waiver. A rule catalog lists what must be true of the platform. Coverage is counted, not assumed.

Four questions the tests answer

QuestionTest kinds that answer itWhen
A. Is the code right?Static checks, unit tests, contract tests, engine conformance, spec and infrastructure testsEvery commit and pull request
B. Is the data right?World against known answers, planted faults, metric known answers, checks inside every runEvery merge, every deploy, every production run
C. Is this change safe?Release gate with a data comparison, version comparisons, integration run in devBefore every release to production
D. Does it hold up in operation?Scenario tests, recovery tests, performance and scale, security and privacy, a long unattended runOn a schedule and before go-live

GateBlocks whenWho can override

MergeThe three-day world differs from the known answers at any layer, or a planted fault is not handledNobody

Part two · how

How each kind works

A. Is the code right?

1. Static checks partly no secret scan yet

What. Checks that read the code without running it.

How. A linter for style and common mistakes, strict type checks on the cloud adapters, and the shift-left checks for PySpark and SQL anti-patterns. The shift-left scan compares with a baseline: old findings are listed there, and any new finding blocks the pull request.

Left to do. Add a secret scan. Widen strict typing from the cloud adapters to the whole core.

2. Unit tests done 1,269 pass

What. Each pure function is tested with a list of cases: a name, the input and the expected output.

How. The cases sit in a table at the top of the test file and one test runs them all, so a new case is one new row. Logic is kept in pure functions so most of it is tested with no cluster and no database. The whole set runs in under a minute.

3. Contract tests done

What. Every outside system sits behind an interface (a port). A contract test is one table of cases per port that every implementation (adapter) must pass.

How. The same cases run against the in-memory adapter, the real one, and a simulator of the cloud service. Examples: 64 cases for the metadata store on memory and PostgreSQL; 23 for the table store on Delta and Iceberg; 8 history cases that both silver engines pass. Moving to another cloud means writing new adapters and passing the same tables.

4. Engine conformance done 143 cases

What. The silver steps and the gold builds give identical results on Spark and on DuckDB.

How. The same test tables run once per engine in separate processes, and hashed keys must be equal on both. The first run found 20 differences, 6 of them silent wrong values.

5. Spec and infrastructure tests done

What. The things that drive the platform are valid before anything runs.

How. Every rule, capability and decision record is linted. Data contracts are validated against the open data contract standard. The generated jobs must equal what the manifest would generate now. Infrastructure code is formatted, validated and planned against mocked providers for each environment.

B. Is the data right?

6. World against known answers done laptop and a free Databricks workspace

What. The end-to-end test. A simulated company writes a day of data into mock source systems, the platform loads it, and each layer is compared with the totals the world knows are right.

How. For each day: bronze row counts per dataset, silver measures per dataset (some per hour) and gold measures per table. A day passes only when every number is equal. It runs with every hop in one process, and also with ingestion, silver and gold as separate processes, the shape deployed jobs have.

Left to do. Run it in CI on every merge. Run it at full scale for 14 days.

7. Planted faults done 11 of 11

What. Eleven kinds of fault are put into the world's data on set days. Each names the check that must catch it.

How. After each day the run gives a verdict per fault: handled, flagged or missed. A missed fault fails the run. A compressed calendar puts all eleven on days 2 and 3, so a three-day run covers them. The faults: a file sent twice, a file sent late, rows deleted at the source, a column renamed, readings out of order, a full copy that is 40% short, a correction to past data, a new dealer whose record arrives after its orders, a change feed that drops rows, a stream replayed, and a promised date changed out of order. A 14-day fixture also checks that nothing fires on a clean day.

8. Metric known answers done 8 of 8

What. The number a business user sees equals gold and equals the world's truth.

How. After each run the certified metrics are recreated and asked fixed questions, for example order lines in November. Each answer is compared with gold and with the world. The plain-language question interface is checked the same way: its answer must equal the metric.

9. Checks inside every run done

What. Tests that run on real data in production, as part of the load.

How. Contract rules by severity: a broken critical rule holds the whole batch, a major one sends the row to quarantine, a minor one flags it. A second copy of a delivery is refused, and a full copy that would delete too much is held. The live source is compared with silver every day, naming the exact missing keys and the hop that lost them. In gold, rows in must equal rows out at every join, and the join that changes the count is named. Every check writes a step in the run log, which feeds the dashboards and the alerts.

C. Is this change safe?

10. Release gate with data comparison partly built; not yet run against a production environment

What. The data form of A/B testing. The new version and the current version run on the same data, and the outputs are compared.

How. Each production table the change touches is shallow-cloned, which copies only the table's file list and so costs almost nothing. The change runs against the clones. Row counts, measure totals and key sets are compared with production, in total and per window, for example per day. A difference blocks unless the change declared it and someone wrote the explanation. The clones are dropped whatever happens.

Left to do. Run it from CI against a real production environment. Today it blocks two planted bad changes in tests.

11. Version comparisons partly four built; format benchmark not built

What. Where the platform offers two ways to do one job, both must agree.

How. Spark against DuckDB. The job silver engine against the declarative one: equal rows on six datasets. Delta against Iceberg: the same 23 cases. One process against separate processes: every layer equal, with the same fault verdicts.

Left to do. A format benchmark: Iceberg, Delta and Hudi on the same world, measured for speed and cost.

12. Integration run in dev not yet written; waits for a paid cloud workspace

What. After a deploy to dev, one world day goes through cloud storage and every generated job runs once. Any failed check fails the pipeline.

How. The deploy pipeline calls it straight after the deploy, so a job that deploys but does not run is caught the same day.

Left to do. Run it. It needs the job generator updated for the current engine and a cloud account.

D. Does it hold up in operation?

13. Scenario tests done laptop

What. Eleven written stories of something going wrong in operation, each with the alert and the state expected afterwards.

How. Each scenario is a small file: the situation, the fault, and what must be true after. One engine plays it against the platform with a simulated clock. Noise rules are tested too: one alert per incident, none on clean days, and snoozes expire.

Left to do. Send alerts to a live channel and play the scenarios against the deployed platform.

14. Recovery tests partly withdraw not yet proven on the real platform

What. Proof that the platform can get back from a bad state.

How. Loading the same day twice adds no rows and changes no window. Withdrawing a batch voids it, rebuilds silver from bronze, and recomputes gold, replacing only the changed windows and logging each as a restatement. After old bronze batches are removed, silver rebuilt from what is left has the same current rows. A second run on a table already being written skips with a reason. A past window rebuilt from its run log equals what was published.

Left to do. Prove the withdraw path on the real platform.

15. Performance and scale not yet

What. It finishes in time at real volume.

How. Every hop stamps its time, and a report gives the delay per hop and names any breach. One day at one tenth scale takes about 5.8 minutes against a target of 6.

Left to do. Full scale for 14 days. Hop times and gold-ready-by-morning measured on the real platform. Cost per daily load, which needs a billed workspace.

16. Security and privacy partly scan and access check not running

What. Secrets, personal data and access stay as declared.

How. Error messages are redacted before they reach the run log. Personal values are replaced by tokens at landing. Column masks and grants are generated from one access model, with a check that compares the model with what the catalog holds.

Left to do. A scan of every layer for clear personal values, with planted ones to prove the scan works. A secret scan in CI. The access check on a workspace with account-level groups. Right to be forgotten.

17. Long unattended run not yet

What. Thirty days on a schedule with nobody watching, and at the end the dashboard equals the world.

How. It comes last because it needs everything else in place: deployed jobs, live alerts and a billed workspace.

Source of test dataUsed byWhy

The simulated world runs at any scale: one tenth for the daily loop on a laptop, full scale on the real platform. Personal data in it is made up, so no real personal data is used in a test.

Adding a dataset

What a new dataset gets without anyone writing a test

Most tests come from the dataset's entry in the manifest and its data contract, so adding a dataset adds its tests.

Where the tests come fromWhat the dataset gets
From the data contractColumn, type and row rules run in every load, with quarantine by severity
From the manifest entryDuplicate-delivery refusal, the mass-delete guard for full copies, freshness, and the live source comparison for database sources
From the gold definitionThe row ledger at each join, completeness per window, and the per-window comparison at the release gate
What the author addsThe dataset in the simulated world with its known answers, and a planted fault if it has a failure mode the existing eleven do not cover

Words used

Words used on this page

WordMeaning
Known answersThe correct totals the simulated world works out for itself at every layer, used to judge the platform's output. Often called the oracle.
Table-driven testOne test that runs a list of cases, each a name, an input and an expected output.
Port and adapterA port is the interface the platform's logic talks to. An adapter is one implementation of it, for example PostgreSQL or object storage.
Shallow cloneA copy of a table that shares the original's data files, so it is quick and nearly free.
WindowThe slice of a table a run rebuilds, usually one business day.
RestatementA logged change to a number that was already published.
HopOne move of data between layers: landing to bronze, bronze to silver, silver to gold.
Shift leftCatching a problem earlier, at commit or pull request, instead of in production.

Questions

Questions people ask

How do you do A/B testing on a data platform?

Not in the classic sense of splitting live users between two versions, because a pipeline has no user behaviour to measure. The equivalent is to run the new version and the current version on the same data and compare the outputs. That is the release gate: the change runs on shallow clones of production tables, and any undeclared difference in a measure, a key set or a window blocks the release. True A/B testing belongs to user-facing AI, where two versions answer real questions and the answers are scored.

How is this page different from the test architecture page?

The test architecture page is the design: nine kinds of test and why each exists, with no platform named. This page is the strategy as it is practised on a reference build: seventeen kinds grouped by the question they answer, when each runs, what blocks a release, and what is proven so far.

Why simulate a company instead of using sample data?

Sample data has no right answer attached. A simulated company with a fixed seed produces the same data every time and also knows the correct total at every layer, so the test is a comparison of numbers and not a judgement.

Which test would you add first to an existing platform?

The checks inside every run: contract rules with quarantine, and a daily comparison of the live source with silver. They need no simulator and they catch real problems from the first day.

What does a new dataset need before it can go live?

Its contract and manifest entry give it most of its tests. The author adds the dataset to the simulated world with its known answers, and a planted fault if it has a failure mode the existing ones do not cover.
