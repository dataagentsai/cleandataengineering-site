Data platform architecture · testing

Test architecture for a data platform

How to know the numbers are right before anyone sees them: nine kinds of test, from reading the code to comparing a new version with production on real data, and one release report that decides.

The one-minute version

Cheap tests catch most problems; real-data tests catch the rest

Push logic into pure functions. Then fast unit tests on a laptop cover most of the logic, and slow tests only need to prove the plumbing.

Test each hop on its own. Source to bronze, bronze to silver, silver to gold, gold to metrics: a failure points at one place.

Use simulation and real data, not one or the other. DataTwin plants known faults; a pre-production run on real data, compared with production, catches what nobody imagined.

Release on evidence. Every test writes its result to one record; the release report is generated from it, never ticked by hand.

Design for testing

Logic in the middle, input and output at the edges

A pure function gives the same output for the same input and touches nothing else: it reads no table, writes no file, calls no service and does not look at the clock. For data code that means DataFrame in, DataFrame out. Everything else is impure.

Static analysis enforces it: the shift-left bundle marks every function pure, impure or unknown, shows where an impure function could be pure, and fails a pull request that adds impure functions to a transformation module.

Integration

One integration test per hop

Each hop between layers has its own integration test, with a fixed input and a known expected output, run on the real platform in the dev environment on a fresh schema. When one fails, you know which hop broke.

HopFixed inputThe test passes when
Source → bronzeSample files and change records in the landing folderEvery row lands once; arrival details added; the same file again changes nothing; unexpected new columns kept; run log and watermark right
Bronze → silverA bronze table with duplicates, late rows, a schema change, a delete, and a record changed twice in a dayTypes and standardisation right; the contract check stops the schema change; duplicates removed; SCD2 versions and dates right; bad rows quarantined with a reason; a re-run changes nothing; rows in = rows out + quarantined
Silver → goldSilver tables including a missing dimension row and a late-arriving contributing factThe fact's level of detail is right; no row dropped (reconciliation); an inferred member is created, then filled when the dimension arrives; changed windows recomputed; totals match silver
Gold → metricsGold tables with known answersEach metric returns the expected number (for example scrap rate for plant A on day 3 = 2.4%); joins and filters right; masked columns stay masked

Simulation and real data

DataTwin is not the whole story

DataTwin runs the platform in a simulated business and plants faults on purpose, so the bad days happen on schedule. But a simulation only contains what someone thought of. Real data has formats, values and volumes nobody wrote down. So before release the new version also runs end to end on real data in pre-production, using zero-copy clones of production tables: instant, cheap, and production is never touched. Personal data stays masked and restricted data is left out.

TestProvesCatchesCannot catch
DataTwin (simulation)Faults we know about, on purpose, every nightLate files, duplicates, schema changes, a job dying halfway, clock changesCannot know this company's real formats and odd values
End to end on real dataThis company's real data, before releaseOdd values, real volumes, real edge cases nobody wrote downOnly the faults that happen to be in the data that week
Parallel runThat nothing changed that should not haveA fix that also moves a number it should notNeeds a production version to compare with

Old version against new

Parallel run, canary, and what A/B testing means here

For any change to logic that already runs in production, the old and new versions run side by side on the same real input and the outputs are compared: row by row on keys, counts and sums per key, and the result of every metric. "Scrap rate per plant per day matches to 0.01%, except plant B, where the bug fix moved it as intended" is release evidence.

NameWhat it isUse it forVerdict
Parallel run (shadow run, data diff)Old and new pipeline on the same data; outputs comparedPipelines: every change to existing logicPursue
Canary releaseThe new version switched on for one plant or one business unit first, watched, then rolled outRisky pipeline changesPursue for risky changes
A/B testing (true sense)Users split between two versions; their behaviour measuredThe conversation UI and Genie: two ways of answering, measured on accuracy and ratingsOnly for user-facing AI, not pipelines

Evidence

Profiles, checks and one release report

Every test run in the dev and pre-production environments also profiles its outputs and compares them with the last good run, and runs every quality rule and reconciliation. All results go to one test-run record, and the release report is generated from it.

EvidencePasses when
Static analysisNo must-fix finding; impure functions in transformation modules did not grow
Unit tests and coverageAll pass; branch coverage on pure modules at or above target; mutation score on critical logic
Contract testsAll contracts valid; no unapproved breaking change
Integration, per hopAll four hops pass, including the re-run test
DataTwinEvery planted fault caught and held; dashboard matches the simulated truth
Real-data run and compareDifferences from production are zero, or each is explained and approved
Profile comparisonRow counts, empty rates, distinct counts and ranges within tolerance of the last good run
Quality rules and reconciliationAll stop-level rules pass; source totals = gold totals; rows in = rows out + quarantined

Questions

Questions people ask

Why not just test on production data and look at the dashboard?

Because by then the wrong number has already been seen. Most problems are cheaper to catch in seconds on a laptop than in hours on a cluster, and the ones that only show on real data are caught in pre-production, before release.

Is DataTwin enough for end-to-end testing?

No. DataTwin proves the platform survives the faults we know about. A run on real data in pre-production, compared with production, proves it works on this company's actual data. We need both.

Which one is A/B testing?

In data pipelines, what people usually mean is a parallel run: old and new versions on the same data, outputs compared. True A/B testing splits users between two versions and belongs to user-facing AI like a conversation UI.

Why insist on pure functions?

A pure function can be tested with a small table in seconds, without a cluster. If most logic is pure, unit tests cover most of it, and the slow integration tests only need to prove the plumbing.

Who owns the test strategy?

The test strategy lead in the centre of excellence writes it into the specs; data engineers write the unit and integration tests; the release gate reads the evidence.
