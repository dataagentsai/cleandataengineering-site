In plain words

Think of a factory

The production line moves raw material through stations until it becomes a finished product; that is the row of layers in the middle, the medallion. The planning office decides what each station does, from written instructions, and keeps a log of every shift; that is the control plane. Advisors walk the floor and suggest improvements, but they cannot touch the machines; that is the agent plane. And some jobs happen at every station: inspection, safety, costing, record-keeping; those are the cross-cutting concerns. A good factory builds those in from day one, instead of adding an inspector after the first recall.

Control plane

Written instructions in, pipelines out

People (and agents, by pull request) describe each source and table in a short YAML file, the platform manifest: where it comes from, how it is loaded, its key, how history is kept, its contract, its quality checks, who owns it, its budget. Nothing else is hand-written.

  1. Validate. A validator checks every key against a registry of allowed keys and types.
  2. Load the metadata DB. A loader writes the manifest into a metadata database: master tables for sources and datasets, key-value config tables, and one stable view that every pipeline reads. One database per environment (dev, test, prod), same schema. The design is described in Metadata DB Design for Data Engineering Platforms.
  3. Generate. Generators turn the metadata into pipelines for the chosen platform, using that platform's binding file.
  4. Run and record. The orchestrator runs them; every run is logged with a fingerprint of the exact config it used, so any replay or backfill can prove what it ran with.

Runtime state (watermarks, run logs, quality results) is kept apart from configuration, so changing a setting never rewrites history.

Services

Three services, three owners

ServiceCoversIts jobTypical owner
A · Acquiresources → landing → bronze → silverGet every source in, faithfully and safely, and make one clean, trusted row per real thing.Platform / ingestion team
B · Modelgold → semanticShape data for the business: facts, dimensions, marts, data products and metric definitions.Analytics engineers with the business
C · ServeexperiencesPut it in front of people and programs: dashboards, conversation UIs, APIs, sharing, ML features, documents for AI.Product and BI teams

Splitting them means each can change at its own pace, and a failure in one doesn't silently corrupt another: Serve only ever reads from Model, and Model only from Acquire's silver.

Streaming

One medallion, two speeds

Streaming does not need a second architecture. Hot tables flow through the same layers continuously: event stream → bronze stream → silver streaming tables → gold incremental views. The contracts, quality checks, lineage and rules are the same; only the speed changes. Late events are handled with watermarks, and every step must still be safe to run twice.

Agent plane

Agents that may only suggest

Agents help with two jobs: writing metadata, and handling incidents. Neither lets an agent change production. This is deterministic first: code that can decide something decides it, and an agent only comes in where judgement is really needed.

The self-healing loop: detect → triage → fix in dev → validate → gate → pull request → deploy → verify it held → roll back if not.

Simulation: a pretend shop produces data on its own clock, and incidents are planted on purpose (a renamed column, a day sent twice, a source going dark). The platform must catch each one before production does.

Rules

Nine design rules

Each rule says what it forbids and can be checked by a machine.

1
The design names no product and no business. A bank and a clothing shop read the same architecture. Product names live only in the binding file for each platform.
2
Everything is declared in the manifest. No pipeline, table or check exists that the manifest didn't ask for. What runs is compared with what is declared.
3
Generators write pipelines; people and agents write the manifest. Generated code is never edited by hand; CI regenerates it and fails on a difference.
4
Every vendor sits behind a port. No 'if cloud == …' branches. Changing platform means a new adapter and a new binding file, never a redesign.
5
Cross-cutting jobs are on by default. Turning one off for a table needs a written waiver with a reason, an approver and an expiry date.
6
Agents propose, gates decide. Agents can only open pull requests against the manifest. Contracts and metric definitions are protected files.
7
Nothing passes by absence. A check that looked at 0 rows is an error, never a pass.
8
Data flows one way. Gold never reads bronze; a dashboard never reads silver. Lineage is checked against the allowed paths.
9
Every kind of incident has a planted test. If the simulated world can produce it, a detector must have been seen to catch it.

FAQ

Questions people ask

What is a data platform architecture?

The overall design of how data gets from the systems that create it to the people, dashboards and AI that use it: the layers it passes through, the services that move it, the control plane that configures it, and the jobs such as quality, lineage, security and cost that apply everywhere.

What is the difference between the control plane and the data plane?

The data plane is where data actually moves: the layers from sources to experiences. The control plane decides what should move and how: it reads the manifest and metadata, generates the pipelines, schedules them and records every run.

Is medallion architecture the same as a data platform architecture?

No. The medallion (bronze, silver, gold) is the middle row: the layers data moves through. A full platform architecture also has the control plane above, the cross-cutting jobs below, the services that own each part, and a plan for streaming.

Why a metadata-driven platform?

Because then a new source is a few lines of YAML, not a new notebook. The manifest switches on quality, lineage, cost and access for each table, so nothing is forgotten, and every platform is built the same way.

Should AI agents be allowed to change pipelines?

Not directly. Here agents can only propose changes as pull requests against the manifest; tests and people decide. Contracts and metric definitions are protected, so an agent can never loosen a rule to make a problem disappear.

Lambda, Kappa or one medallion for streaming?

Most platforms do well with one medallion run at two speeds: the same layers and the same contracts, with hot tables flowing continuously. Kappa (everything as a stream) fits when the sources are streams to begin with.
