Technical checks (81)

What has to be true of the data and the platform: the things that make numbers wrong, loads fail or go-lives slip.

Same data arriving or being processed twice (4)

DUP-01Same batch or file arriving twicehighTechnical anchor
Question
How is a file, batch or extract that arrives a second time prevented from doubling the numbers?
Why it matters
After an outage the source resent yesterday's file, the pipeline loaded it again as new, and revenue on the dashboard doubled for a day before anyone noticed.
Applies to
any · components: ingestion · patterns: batch, file, api, database
Owner
Technical anchor · also Developers, Test lead
Evidence
in: architecture, test-strategy
looks like: A business key or file fingerprint, a record of what has already been loaded, and a test that loads the same input twice.
How the gap shows
  • The architecture describes loads as appends with no key, fingerprint or load register.
  • The test strategy has no test that resends an input.
Due by
planstage 3: Discovery
designedstage 5: MVP starts
evidencedstage 7: Test
provenstage 9: Production sign-off
Fail fast
Load the same file twice in a test environment; row counts and key totals in every layer must not change after the second load.
Related
DUP-02, DUP-03, REC-01
On DatabricksIngest files with Auto Loader or COPY INTO, which both remember files already loaded. Write to silver with MERGE on the business key, not append.
Check it: Re-drop the same file and rerun; DESCRIBE HISTORY on the target shows no rows inserted (operationMetrics numTargetRowsInserted = 0).
Trap: A file renamed or rewritten by the source counts as new to Auto Loader. Its checkpoint is the memory: deleting or moving it reloads everything.
DUP-02Rerunning a job changes the resulthighTechnical anchor
Question
If a job is run again for the same period, does it produce exactly the same result (is every step idempotent)?
Why it matters
Operations reran a failed nightly job, but its first half had already appended rows, so the fact table held two copies of the night's orders until month-end reconciliation found them.
Applies to
any · components: ingestion, transformation, modelling · patterns: any
Owner
Technical anchor · also Developers, Operations and support
Evidence
in: architecture, test-strategy, runbook
looks like: Each write described as merge on a key, or replace of a whole partition or period, never a blind append; a rerun test per pipeline; the runbook says reruns are safe.
How the gap shows
  • Writes are described as "insert" or "append" with no key or partition overwrite.
  • The runbook warns operators not to rerun, or says to clean up by hand before rerunning.
Due by
planstage 3: Discovery
designedstage 5: MVP starts
evidencedstage 7: Test
provenstage 9: Production sign-off
Fail fast
Run the pipeline twice in a row for the same day in test and compare a fingerprint of every output table (counts, sums of key measures); they must be identical.
Related
DUP-01, ORCH-03, TEST-05
On DatabricksUse MERGE on a key, or INSERT OVERWRITE / replaceWhere for a whole date range, for every write a rerun could repeat.
Check it: Run the job twice for the same period; compare counts and DESCRIBE HISTORY metrics between runs.
Trap: Repairing a failed Lakeflow Jobs run reruns failed tasks from the start; a task that appended before failing will append again.
DUP-03Duplicates already inside the sourcehighBusiness analyst
Question
Does each source have a reliable unique key, and what is the rule when the source itself sends two rows for the same thing?
Why it matters
The source table had no primary key and sent the same customer twice with different spellings; joins to it multiplied order rows and inflated sales by eight percent.
Applies to
any · components: ingestion, transformation · patterns: any
Owner
Business analyst · also Technical anchor, Source system owners
Evidence
in: discovery, data-model
looks like: A profile showing key uniqueness per source table, the chosen business key, and an agreed rule for duplicates (keep latest, keep all, reject), signed by the data owner.
How the gap shows
  • The data model lists tables without a key, or says "key to be confirmed".
  • No profiling results for key uniqueness are recorded.
Due by
planstage 3: Discovery
designedstage 4: Discovery sign-off
evidencedstage 7: Test
Fail fast
Count rows per proposed key in a real extract of every source table; any key with more than one row needs a written rule before design continues.
Related
DQ-05, DES-04, SCD-03
On DatabricksProfile key uniqueness with a GROUP BY key HAVING count(*) > 1 query; deduplicate in silver with a window (row_number over key ordered by a change timestamp) before MERGE.
Check it: A uniqueness expectation or test on the silver key runs on every load.
Trap: MERGE fails when several source rows match one target row; deduplicate the source batch first. PRIMARY KEY constraints in Unity Catalog are informational and are not enforced.
DUP-04Replayed events in a streamhighTechnical anchor
Question
When the stream redelivers events after a restart or failure (at-least-once delivery), how does the target avoid counting them twice?
Why it matters
A consumer restarted from an older position and replayed two hours of events; the counts sink appended them again and the real-time dashboard overstated traffic for the day.
Applies to
any · components: ingestion, transformation · patterns: streaming, cdc
Owner
Technical anchor · also Developers
Evidence
in: architecture, test-strategy
looks like: An event id or key plus sequence used to deduplicate, a stated delivery guarantee end to end, and an idempotent or transactional write to the sink.
How the gap shows
  • The design assumes "exactly once" without saying which component provides it.
Due by
planstage 3: Discovery
designedstage 5: MVP starts
evidencedstage 7: Test
provenstage 9: Production sign-off
Fail fast
In test, stop the stream mid-flow, rewind its position by a known number of events, restart, and confirm output counts match the input exactly.
Related
DUP-02, ORCH-06, LATE-03
On DatabricksIn Structured Streaming use dropDuplicatesWithinWatermark on an event id, and idempotent writes in foreachBatch (MERGE, or txnAppId plus txnVersion options).
Check it: Restart a stream from an older checkpoint copy in test and compare counts.
Trap: dropDuplicates without a watermark keeps state forever and grows until the job slows or fails.

Initial load, history, backfill (4)

HIST-01History load scope and approachhighTechnical anchor
Question
How much history will be loaded, from where, and by what approach (one go, in phases, or from archive), and who checks the old numbers?
Why it matters
The plan assumed history would come from the same feed as daily loads, but the source only kept ninety days; five years had to come from an archive in another format, adding six weeks.
Applies to
any · components: ingestion · patterns: any
Owner
Technical anchor · also Business owner and sponsor, Source system owners
Evidence
in: discovery, architecture, deployment
looks like: The number of years in scope, where each year comes from, the load approach and order, the expected volume, and who signs off that historical numbers are right.
How the gap shows
  • History is not mentioned, or "history to be loaded" appears with no years or source.
  • The plan has no task or time for the history load.
Due by
planstage 3: Discovery
designedstage 5: MVP starts
evidencedstage 7: Test
provenstage 9: Production sign-off
Fail fast
Ask the source owner how far back the source really holds data, and pull one month of the oldest year in scope through the pipeline.
Related
HIST-02, HIST-03, REC-02
On DatabricksLoad history into the same bronze tables as daily loads, by date chunk, from archive files or a source extract; record the chunks in a control table.
Check it: Reconcile each historical year against the source or finance before switching on daily loads.
HIST-02Source can bear the history extractmediumTechnical anchor
Question
Can the source system take the load of the history extract, and is the extract split into chunks that can each be retried?
Why it matters
A single five-year query against the source database ran for nine hours, hit an undo limit and failed at ninety percent; it failed again the next night and slowed the source for its users.
Applies to
any · components: ingestion · patterns: database, cdc, api, history load
Owner
Technical anchor · also Source system owners
Evidence
in: architecture, deployment, raid
looks like: An extract split by date or key range, an agreed extract window with the source owner, and an estimate of run time per chunk from a real trial.
How the gap shows
  • The history load is one step with no chunking or restart point.
  • Source owners are not listed as reviewers of the extract approach.
Due by
planstage 3: Discovery
designedstage 5: MVP starts
evidencedstage 7: Test
Fail fast
Time the extract of one realistic chunk against the real source in its normal busy window and multiply out; agree the result with the source owner.
Related
HIST-01, PERF-01
On DatabricksFor JDBC reads, set partitionColumn, lowerBound, upperBound and numPartitions and keep parallel connections within what the source owner agreed; or land extracts as files instead.
Check it: Time one chunk against the source in its busy window.
Trap: Too many partitions in a JDBC read opens that many connections at once against the source.

Question
How does the switch from the history or full load to incremental loads avoid both a gap and an overlap in the data?
Why it matters
The full snapshot finished at 10:00 but incremental capture was started at 11:00; an hour of changes was never loaded and the totals were quietly short for months.
Applies to
any · components: ingestion · patterns: cdc, database, streaming, history load
Owner
Technical anchor · also Developers
Evidence
in: architecture, deployment
looks like: A defined high-water mark or change position taken before the snapshot starts, incremental capture starting from it, and overlapping rows absorbed by a merge on key.
Due by
planstage 3: Discovery
designedstage 5: MVP starts
evidencedstage 7: Test
provenstage 9: Production sign-off
Fail fast
In test, change rows in the source while the full load runs, then start incremental; every changed row must appear once with its latest value.
Related
HIST-01, DUP-01, REC-01
On DatabricksWith Lakeflow pipelines, AUTO CDC with SEQUENCE BY absorbs overlap between the snapshot and the change feed; otherwise MERGE with a sequence column so older changes never overwrite newer.
Check it: Change rows during the snapshot in test and check each ends with its latest value once.

Question
Can a single past period (a day, a month) be reloaded or backfilled on demand without touching other periods or rebuilding everything?
Why it matters
A source bug corrupted three days in March; the only way to fix them was a full rebuild that took the platform down for a weekend.
Applies to
any · components: ingestion, transformation, modelling · patterns: batch, cdc, file, database, api
Owner
Technical anchor · also Operations and support, Developers
Evidence
in: architecture, runbook
looks like: Pipelines parameterised by period, writes that replace exactly that period, a runbook step for reloading a period, and a note on which downstream tables must also be rebuilt.
How the gap shows

  • Jobs read "today" from the clock instead of taking the period as a parameter.
Due by
planstage 4: Discovery sign-off
designedstage 5: MVP starts
evidencedstage 7: Test

In test, reload one day from three days ago with a parameter and check that only that day's rows and its downstream aggregates changed.
Related
DUP-02, LATE-01, HAND-01
On DatabricksPass the period as a job parameter and write with replaceWhere on the date column; keep a separate backfill job or bundle target for large reloads.
Check it: Reload one past day in test; DESCRIBE HISTORY shows only that day's files were rewritten.
Trap: A full refresh of a Lakeflow pipeline streaming table re-reads all source data and clears the table first; check source retention before pressing it.

Question
When rows arrive late or yesterday's figures are corrected next week, which periods are rebuilt, and how far back can corrections reach?
Why it matters
Returns were booked against sales from three weeks earlier, but the pipeline only rebuilt the last two days, so monthly net revenue never matched the finance ledger.
Applies to
any · components: ingestion, transformation, modelling · patterns: any
Owner
Technical anchor · also Business analyst, Source system owners
Evidence
in: discovery, architecture
looks like: A profile of how late data really arrives, an agreed correction window, and a design that reprocesses affected periods by business date rather than load date.
How the gap shows

  • Nothing in the discovery document says how late source data can arrive.
Due by
planstage 3: Discovery
designedstage 5: MVP starts
evidencedstage 7: Test

On DatabricksRebuild aggregates for affected business dates with MERGE or replaceWhere driven by the dates present in the incoming batch; Change Data Feed on silver can tell gold which keys changed.
Check it: Insert a row with an old business date in test and check the gold total for that date changes.

Technical anchor · also Developers

in: architecture, data-model
looks like: An "unknown" or placeholder member, or a quarantine with automatic reprocessing, and a step that re-points facts once the reference record arrives.

Due by

designedstage 5: MVP starts

Related
LATE-01, DQ-02, REC-01
On DatabricksInsert an unknown-member row in each dimension and left join facts to it; or quarantine misses to a table and reprocess it in a scheduled task.
Check it: An expectation or test counts facts pointing at the unknown member over time.

Question
Do streaming aggregations use event time, how long do they wait for late events (the watermark), and what happens to events later than that?
Why it matters
The window waited ten minutes, but mobile clients uploaded events hours later after going offline; those events were silently discarded and daily active users were understated.
Applies to
any · components: transformation, modelling · patterns: streaming
Owner
Technical anchor · also Developers, Data consumers
Evidence
in: architecture, requirements
looks like: The lateness of real events measured, a watermark chosen from that, and a stated home for events beyond it (a correction batch or a side table) agreed with consumers.
Due by
planstage 3: Discovery
designedstage 5: MVP starts
evidencedstage 7: Test
provenstage 9: Production sign-off
Fail fast
Measure the gap between event time and arrival time in a day of real events and see what share falls beyond the proposed watermark.
Related
LATE-01, DUP-04, PERF-02
On DatabricksSet withWatermark on the event-time column from measured lateness; route later events to a side table.

LATE-04Time zones and business datesmediumBusiness analyst
Question
Which time zone does each source use, how are timestamps stored, and which time zone defines a business day?
Why it matters
One source sent local time and another sent universal time; orders placed late in the evening fell into the next day and daily sales never matched the stores' own reports.
Applies to
any · components: ingestion, transformation, modelling · patterns: any
Owner
Business analyst · also Technical anchor
Evidence
in: data-model, discovery
looks like: The time zone of every source timestamp, a single storage convention, a defined business-day time zone, and a rule for daylight-saving changes.
How the gap shows
  • The data dictionary lists timestamps without a time zone.
Due by
planstage 3: Discovery
designedstage 5: MVP starts
evidencedstage 7: Test
Fail fast
Pick ten real transactions near midnight and check that their business date matches what the source application shows.
Related
DES-04, REC-02
On DatabricksStore timestamps as TIMESTAMP (universal time) and convert with from_utc_timestamp for the business-day time zone; set the session time zone deliberately rather than relying on defaults.
Check it: Compare business dates of near-midnight rows with the source application.
Trap: TIMESTAMP_NTZ has no time zone; mixing it with TIMESTAMP across sources shifts hours.

DEL-01Detecting hard deletes at the sourcehighTechnical anchor
Question
When a record is physically deleted in the source, how does the platform find out?
Why it matters
Cancelled orders were deleted in the source, but the incremental extract only picked up new and changed rows, so the cancelled orders stayed in the warehouse and inflated sales.
Applies to
any · components: ingestion · patterns: batch, database, api, file, cdc
Owner
Technical anchor · also Source system owners
Evidence
in: discovery, architecture
looks like: For each source, whether deletes happen and how they are captured: change capture with delete events, a periodic full key comparison, or a delete feed from the source.
How the gap shows
  • Incremental loads use a modified-date filter and deletes are not mentioned.
Due by
planstage 3: Discovery
designedstage 5: MVP starts
evidencedstage 7: Test
Fail fast
Ask the source owner whether rows are ever deleted, then delete a test row in a source test system and run the load; the platform must reflect it.
Related
DEL-02, DEL-03, REC-01

Trap: WHEN NOT MATCHED BY SOURCE against a partial extract deletes everything not in that extract.

Applies to
any · components: modelling, transformation · patterns: any
Owner
Developers · also Technical anchor, Test lead

in: architecture, test-strategy

Trap: Sequencing by ingestion time instead of a source sequence breaks history when changes arrive out of order.
