Learning the joins between datasets

Every join we build is declared, already used, or proven on the data, and confirmed by the owner.

How to find out how datasets join when nobody can tell you: read what's declared, harvest the joins already in use, propose candidates, measure them on the data, and get the owner to confirm.

For leaders

  • Wrong joins are the quietest way to get wrong numbers: they multiply or drop rows and still look like correct output.
  • Most sources don't declare their relationships, especially SaaS apps and older systems.
  • Learn the joins cheapest first: declared keys and the vendor's model, then joins already used in reports and code, then candidates measured on the data.
  • AI can propose joins; only measurements and the owner can confirm them.

In plain words

A family tree from old letters

Building a family tree, you start with what's written down: birth certificates and marriage records. Then the family's own stories. Then guesses from shared surnames and towns, which you check against dates before you write them in. A shared surname proves nothing on its own. Finding joins between datasets works the same way: written-down keys first, then the joins people already use, then guesses, and every guess checked against the data.

Smartly, cheapest first

Six steps to learn the joins

StepWhat we doWhat it givesEffort
1 · Read what is declaredForeign keys in the database catalog; the vendor's published data model (Salesforce object relationships, SAP check tables)Exact, when presentCheap
2 · Read how people already joinViews, stored procedures, ETL code, report SQL, and the database's query historyThe joins the business really uses, including the rules inside themCheap to medium
3 · Propose candidatesMatching names and types (customer_id to customers.id); an AI model reading names, comments and sample valuesMany candidates, some wrongCheap
4 · Measure on the dataFor each candidate: is the parent side unique, what share of child values exist in the parent, how many rows match on each side, how many orphansEvidence for or against each joinMedium; use samples and compact value sketches on big tables
5 · Confirm with the ownerShow the map with the measurements; the owner accepts, rejects or correctsAgreed joinsA meeting
6 · Write it down and test itRelationships in the data contract (ODCS supports them since 3.1), tested on every loadJoins that stay trueAutomatic after setup

Evidence

How much each signal is worth

SignalStrengthFalse-match risk
Declared foreign keyStrongLow, but the key may be declared and not enforced
Used in existing views, reports or query historyStrongLow; check the join conditions, not just the tables
Same name and type (order_id in both)MediumMedium: generic names (id, code, type) match everything
Most child values found in a unique parent columnStrongHigh for small numbers: ids 1 to 100 overlap with almost anything
AI model's suggestionWeak until measuredMedium: plausible-sounding joins that the data doesn't support

The measurement in step 4 is what turns a guess into a join. For big tables it runs on samples and compact summaries of each column's values, inside the source's environment, so only the measurements leave it. See question L2 on the Upstreams page.

Why it matters

Two ways a wrong join hurts

A join assumed to match one row that sometimes matches two multiplies numbers. A join to a parent that's missing drops rows from an inner join. Both look like correct output. The relationship questions I1 to I7 on the Upstreams page cover how many rows match on each side, orphans, timing and joins as of a past date.

FAQ

Questions people ask

How do you find relationships between tables when there are no foreign keys?

Read how people already join them (views, report SQL, ETL code, query history), propose candidates from names and types, then measure each on the data: the parent side must be unique, most child values must exist in it, and orphans must be few. The data owner confirms the result, and it is recorded in the data contract and tested every load.

Can AI find the joins between tables?

It is good at proposing candidates from names, comments and sample values, and poor at proving them. Treat its suggestions as candidates and accept only those the data measurements and the owner confirm.
