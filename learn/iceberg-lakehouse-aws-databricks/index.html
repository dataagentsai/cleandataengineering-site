Iceberg lakehouse on AWS with Databricks: who should own the catalog?

You want an open lakehouse on AWS, with Apache Iceberg as the table format and Databricks in the picture. AWS offers S3 Tables, Glue, Lake Formation and the SageMaker lakehouse; Databricks offers Unity Catalog. The names spin heads, but there is one decision underneath: which catalog owns the tables. This page draws the whole platform first, then the two physical designs, then compares them concern by concern and picks a winner.

Short answer: if Databricks does most of the work, let Unity Catalog own the tables (Architecture A): managed Iceberg in your own S3 bucket, Predictive Optimization doing the chores, and Athena, Redshift and QuickSight reading gold in place through Glue federation. If AWS engines do most of the work and Databricks is a light guest, let AWS own them (Architecture B): S3 Tables with Glue and Lake Formation. Never let both own the same table.

Step 1 · the conceptual big picture

The whole data platform, with every concern

Before any product name, here is the platform as jobs. Data comes from sources on the left, moves along one line (ingest, bronze, silver, gold, semantic) and reaches consumers on the right. Under the line sit five layers every table needs. Along the bottom are the 24 concerns that cut across every hop; each is explained on the data platform page.

Look at the thick box. Storage, the table format and compute are easy to agree on. Who owns the catalog decides who can write, who sets permissions, who sees lineage and who cleans the tables.

Why the catalog matters so much: an Iceberg write only becomes real when the catalog swaps its pointer to the new metadata file. Whoever holds that pointer controls writes, permissions and clean-up. Every other engine is a guest. See Who maintains your tables for the picture.

Step 2 · the AWS names, decoded

Six names, three jobs

Several of these are layers of the same thing, which is why they confuse. Storage is S3 Tables. Catalog and permissions are Glue plus Lake Formation, sold together as the SageMaker lakehouse. Unity Catalog does both catalog and permissions on the Databricks side.

Step 3 · physical design B

Architecture B: AWS owns the catalog, Databricks is a guest

Iceberg tables live in an S3 table bucket. The Glue Data Catalog holds each table's pointer and Lake Formation holds the permissions. S3 Tables compacts, expires snapshots and removes unreferenced files by itself. AWS engines write and read natively.

Owners on the left write through Glue. AWS readers on the right read through Glue. Databricks, dashed, is a guest.

Can Databricks do bronze to silver to gold here?

Step 4 · physical design A

Architecture A: Unity Catalog owns the catalog, AWS engines are guests

Iceberg tables live in your own S3 bucket as Unity Catalog managed Iceberg tables. Unity Catalog holds the pointer, the grants, the lineage and the audit. Predictive Optimization does the chores. Databricks writes every layer on serverless compute.

Step 5 · the asymmetry

Who can write where

This grid is the heart of the decision. Unity Catalog lets outside Iceberg engines write managed tables through its REST catalog, under its own grants. Glue lets Databricks write only around Unity Catalog. So A keeps the door open both ways; B closes Databricks' governed door.

Green: full, governed. Butter: works with a limit. Rose: read-only, or writes that skip governance.

Step 7 · what each one restricts

What you accept with each

If you go with A (Unity Catalog owns)

  • Athena, Redshift and QuickSight read gold through Glue federation and cannot write. EMR, Glue Spark or Trino can write managed Iceberg through Unity Catalog's Iceberg REST, but those writes are missing from Unity Catalog lineage.
  • Lake Formation still appears, but only at the read door for AWS engines, on curated gold tables. Expose tables without row filters or masks there, or pre-filtered gold tables.
  • Managed Iceberg today gives up row filters, column masks and informational keys; change data feed works only on Iceberg v3 and only for Databricks readers; Lakeflow streaming tables and materialized views are Delta. Keep those tables in Delta with Iceberg reads (UniForm), or use dynamic views.
  • Check that managed Iceberg is generally available for your region and runtime before production; parts were still marked preview in the docs we checked.
  • Firehose and DMS cannot write straight into Unity Catalog tables: they land files, and Auto Loader loads them.
  • Databricks is the main bill. Predictive Optimization runs on serverless and shows up as DBUs.
  • Unity Catalog picks the paths of managed tables. Leaving later means re-registering or rewriting tables.

If you go with B (AWS owns)

  • Databricks sees AWS tables as foreign Iceberg tables: read-only, no partition evolution, and views defined on one side are not visible on the other.
  • Databricks can do bronze to silver to gold only from classic clusters with the open-source Iceberg library pointed at the Glue REST endpoint: no serverless, no Lakeflow pipelines, no Unity Catalog permissions, lineage or audit on those writes.
  • No Predictive Optimization, liquid clustering control, table-update triggers or Unity Catalog masks on these tables; Genie and metric views can only sit over read-only foreign tables.
  • Permissions live in two systems: Lake Formation for AWS engines and Unity Catalog for Databricks readers. Tables with Lake Formation row or cell filters are generally not readable by outside engines.
  • Lineage is fragmented: nothing automatic on the AWS side, and Databricks writes through the Glue endpoint are invisible to Unity Catalog.
  • Two bills, two toolchains (CloudFormation or CDK and Databricks bundles), two monitoring places.
  • AWS only. Moving to Azure, Fabric or Google Cloud later means a new catalog and new permissions.

Step 8 · evidence

Case studies: from a bad design to a good one

We found clear public write-ups of Architecture A (United Airlines, with Delta tables read as Iceberg) and of Architecture B without Databricks (Razor Group). We found no public case of B with Databricks as the main writer, which is itself a finding. Numbers come from the companies' or vendors' own blogs and are not audited.

United AirlinesArchitecture A, with Delta + Iceberg reads

Before. Before: petabytes in bronze, silver and gold, catalogued in Unity Catalog. Redshift could not see them, so tables were copied into Redshift storage with sync pipelines and a manually synced catalog, which AWS's write-up calls operationally expensive and prone to drift.

After. After: Databricks does all processing and owns the tables (Delta with UniForm). A Glue federated catalog fetches metadata from Unity Catalog's Iceberg REST endpoint, Lake Formation vends scoped credentials, and Redshift Serverless reads the files in place. About $30K a month of duplicate ETL removed; 30 tables in production, 70 rolling out, hundreds planned.

Lesson. Grant Lake Formation SELECT on the target tables, not on the resource link; roll out the busiest tables first; name external schemas so readers know the data is federated.

Read the write-up

Razor GroupArchitecture B, without Databricks

Before. Before: more than 1,000 SQL models on always-on Redshift clusters, 98% of compute spent on batch ETL, data 4 to 6 hours old, workloads fighting for one cluster.

After. After: S3 Tables (Iceberg) in bronze, silver and gold, Glue and Lake Formation as catalog and permissions, Spark on EC2 Spot for ETL, Athena for ad-hoc SQL, Redshift Serverless only for Tableau. About 40% of compute removed by moving ingestion alone, data fresh in minutes, Iceberg time travel saved over 35 Redshift hours a week.

Lesson. About 30% of SQL models needed a person to convert; running old and new side by side with row-by-row comparison avoided downtime; S3 Tables removed compaction and snapshot chores.

Read the write-up

HelloFreshArchitecture A, Unity Catalog as the Iceberg REST catalog for many engines

Before. A decentralised mix of tools needed one table format and one catalog.

After. Iceberg as the format, Unity Catalog serving as the Iceberg REST catalog for Spark, Flink and Snowflake.

Lesson. A conference talk: design, not audited numbers.

Read the write-up

RiskifiedArchitecture A, native Iceberg in Unity Catalog

Before. Wanted tables any engine could read, without tying the data to Databricks.

After. Writes Iceberg tables through Unity Catalog that any Iceberg client can read, which the team describes as future-proofing the architecture.

Lesson. A press-release quote: direction, not detail.

Read the write-up

Grab and InsiderStorage step only: Hive tables to Iceberg, on either architecture

Before. Parquet under a Hive-style Glue catalog: too many small files, unsafe concurrent writes, slow file listing.

After. Iceberg tables; Insider reports about 90% lower S3 costs.

Lesson. An in-place migration carries small files over, so rewrite or compact as you migrate; expect lock contention, timestamp mismatches and a temporary S3 cost spike (Grab).

Read the write-up

Step 9 · the market

Who chose A, who chose B, and what the benchmarks really say

We looked for every public team running Iceberg on AWS that says which catalog owns its tables. The picture is very clean. Teams with Databricks at the centre chose A. Teams that chose B do not use Databricks at all. We found no public team running B with Databricks as a real writer, and the public moves between the two that keep Databricks (Decathlon, Outreach) all went from B to A.

Where A wins and loses in practice

  • Wins: copy pipelines into Redshift disappear (United, about $30K a month); one catalog stays the truth for many engines (Mastercard, HelloFresh); it survived scale where Glue strained (Decathlon).
  • Loses: AWS readers are read-only; only Iceberg or UniForm tables cross the door; Lake Formation grants have gotchas; almost none of these teams publish numbers, so A's case rests on design talks more than measurements.

Where B wins and loses in practice

  • Wins: big, measured cost and speed gains (Razor 40% compute, Pendulum 40% cost and 6x jobs, Tubular merges 6 to 8 hours down to under 2, Comcast 38% cost).
  • Loses: those gains are mostly against a bad before state (no maintenance, raw Parquet, an always-on warehouse), not against A; Lake Formation sharing and logging are the hard parts (Indeed; one team lost a month to cross-account sharing); none of them run Databricks.

Has anyone moved from one to the other, and did it pay?

Moves are rare and almost never measured. Every B-to-A move we found was a Databricks-centred team leaving the Glue catalog; the only A-to-B-like move left Databricks entirely, for reasons about ML operations rather than the catalog. Nobody published a before-and-after cost or speed number for a pure catalog move in either direction.

The clear story the numbers do tell: the big wins on both sides come from two things, giving the tables one owner of the chores (S3 Tables or Predictive Optimization) and deleting copies. That is why Databricks-centred teams land on A and AWS-only teams land on B.

Step 10 · synthesis

Who wins

Winner for an AWS platform where Databricks does most of the work: Architecture A. One owner for every table, every Databricks feature working on it, automatic lineage and audit, serverless everywhere, AWS engines reading gold in place, and Iceberg engines still able to write through Unity Catalog's REST catalog. It is also the design that moves to Azure, Fabric or Google Cloud with the fewest changes.

Architecture B wins only when AWS is the real home: Glue, EMR, Athena, Redshift, Firehose and Flink do the work, and Databricks is a light guest or absent. Then S3 Tables, Glue and Lake Formation are native, cheaper and simpler, as Razor Group shows.

FAQ

Questions people ask

Can Databricks write bronze to silver to gold when AWS owns the catalog?

Only from classic clusters, using the open-source Iceberg library pointed at the Glue Iceberg REST endpoint with Lake Formation credentials. It works, but those writes skip Unity Catalog permissions, lineage and audit, cannot use serverless or Lakeflow pipelines, and you maintain library versions. Through Unity Catalog itself, AWS-owned tables are read-only foreign tables.

Can AWS engines write when Unity Catalog owns the catalog?

Spark on EMR or Glue, Trino and Snowflake can write managed Iceberg tables through Unity Catalog's Iceberg REST catalog with a Databricks service principal, governed by Unity Catalog grants. Athena, Redshift and QuickSight read gold through Glue federation and do not write. Firehose and DMS land files that Auto Loader loads.

Are Glue with Lake Formation and the SageMaker lakehouse the same thing?

Mostly. Glue Data Catalog is the catalog, Lake Formation is the permissions on it, and the SageMaker lakehouse is AWS's umbrella name for the two, reaching across S3, S3 Tables, Redshift storage and federated catalogs. SageMaker Catalog (formerly DataZone) is a different, business-facing layer.

Where does Redshift fit?

As one more reader of the same Iceberg tables, through federation, if the client already uses it. Loading data into Redshift's own storage creates a second copy with its own permissions, which is the pattern the case studies moved away from.

Why not let both catalogs own tables?

Two writers on one table means two pointers, conflicting commits and clean-ups that delete each other's files. Split by domain only if teams force it, and even then every table has exactly one owner.

Is Iceberg the right format on Databricks?

It is a sound choice for openness. Inside Databricks, Delta still has features managed Iceberg lacks today (row filters, column masks, keys, Lakeflow streaming tables). Delta with Iceberg reads (UniForm) gives AWS engines Iceberg without giving those up, so many teams mix the two.
