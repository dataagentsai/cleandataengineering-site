AI engineering · cloud binding

The agent harness on AWS

The same harness, the same specs and the same tests as on Azure. Only the binding changes: each box gets an AWS service, an open-source tool, or our own code.

The one-minute version. An agent that talks to dealers, customers and staff needs much more than a model: sign-in, guardrails, memory, tools, approvals, logging, cost limits, tests. We call that the harness, and we split it into 22 concerns.

The concerns never name a product. For each cloud we write a binding: which service does each job. This page is the AWS binding, with a tyre manufacturer as the example. On average, by our judgement, about a third of each concern comes from AWS (36%), nearly half is shared code we write once (45%), and about a fifth is what each agent team writes (19%).

Already seen the Azure version? Compare the harness on Azure and the Azure tech stack, concern by concern. Why we work from specs: spec-driven development.

22 concernsin five families: think, act, control, see, change
6 agentsfor dealers, plants, quality and fleets, on one shared platform, each with its own autonomy level
12 horizontal assetsbuilt once on AWS, reused by every agent
India + EUMumbai and Hyderabad for India, Frankfurt or Ireland for European plants; personal data stays in its region

The big picture

One request, top to bottom, on AWS

Read it as one request: a dealer or an engineer asks, through a channel, past the front door, to one vertical agent, which uses the shared assets to reach the company's systems. The left rail is the life of every agent; the right rail is governance.

BandWhat it does on AWS
End usersDealers, fleet customers and consumers sign in through Cognito or the existing dealer portal; plant, quality, sales and service staff through IAM Identity Center.
ChannelsWeb and app chat, WhatsApp and SMS through AWS End User Messaging, email through SES, and the contact centre through Amazon Connect.
Front doorCloudFront and WAF at the edge; Bedrock Guardrails for hidden instructions; Comprehend to find personal data; our router rules; API Gateway limits.
OrchestrationOur router picks one agent; agents hand work to each other over A2A; a registry in Git names the owner and version of each.
Vertical agentsOne ECS service per business job. Each has an autonomy level: answers, suggests, drafts for a person, or acts after checks.
Horizontal assetsTwelve shared parts every agent reuses (next sections).
Systems of recordSAP S/4HANA, the dealer management system, MES, the plant historian and IoT SiteWise, quality and LIMS, warranty, CRM and the supplier portal, reached only through MCP tools with the user's own rights.

The 22 concerns, one table

For each concern: what AWS offers and whether we use it, the open-source options, and what we code once for every agent, and why.

Think · how the agent decides
L1 · Context assembly
What the model sees each turn, built in one place, within a budget.
  • not usedBedrock Prompt Management stores prompts, does not assemble a turn
  • useJinja templates fixed replies only
Our assembler: cache-friendly order, fencing, trimming from the middle, transcript check; prompts in Git
No product on any cloud assembles a turn the way a regulated agent needs, so we code it once.
L2 · Model invocation
Every model call goes through one door.
  • useAmazon Bedrock, Converse API Claude, Llama, Mistral, Nova behind one API
  • useCross-region inference profiles keep inside the India geography where offered; check per model
  • not usedBedrock Intelligent Prompt Routing picks the model per prompt; not deterministic
  • plannedBedrock AgentCore Gateway (inference endpoint) AWS's managed AI gateway: one door to models, tools and agents; fallback + circuit breaker (Oct 2026); token rate limits
  • useBedrock application inference profiles one per agent, tagged, so cost and quota are per agent
  • consideredLiteLLM proxy on ECS Fargate fallback gateway if AgentCore Gateway lacks a rule we need, or for non-AWS models
  • usePydantic AI model layer only
Our gateway policy: allow-list per job, token budget, one retry budget, token metric per agent
AgentCore Gateway is AWS's AI gateway, the same job APIM's AI gateway does on Azure: one governed door with identity, rate and token limits, fallback and logging. Our policy (allow-list per job, budgets) sits on top as config. Check region availability and token-limit features before go-live. The agent never holds a provider key.
L4 · Control loop
Plan, act, check, with step and no-progress limits.
  • not usedBedrock Agents the platform would own the loop
  • consideredBedrock AgentCore Runtime could host our own loop; check current status
  • not usedStrands Agents AWS's open SDK; fine for simple agents
  • not usedLangGraph workflow-shaped agents only
  • not usedClaude Agent SDK Claude-only, loop hidden
Hand-written loop, about 400 lines; budgets of 12 steps, 60 s and a cost cap per turn
Agents that touch orders, warranties and money need every step testable and checks at exact positions. Our own loop runs on any model and any cloud.
L5 · State & memory
What is kept, for how long, and for whom.
  • useAurora PostgreSQL Serverless v2 HA, backups, IAM login, scales to near zero in dev
  • consideredDynamoDB not picked
  • consideredElastiCache for Valkey caches only
  • consideredAgentCore Memory check current status
  • usepsycopg + pool driver
5 agent tables + DBOS state in the same database; retention and erase per person
One managed store that also holds the approval engine and, later, pgvector: no extra infrastructure.
18 · Knowledge & retrieval
Finds sourced passages, filtered by what this user may see.
  • plannedpgvector on the same Aurora chosen
  • consideredBedrock Knowledge Bases managed RAG; less control of filters
  • consideredOpenSearch Serverless if the corpus outgrows pgvector
  • consideredS3 Vectors cheap cold vectors; check current status
  • plannedpgvector chosen
  • consideredQdrant on ECS alternative
Entitlement filter as SQL: a plant engineer sees machine manuals, a dealer sees only their own orders and price lists
One store, one backup, one access model; the entitlement check is just a SQL filter.
Act · how it reaches people and systems
CH · Channels & human desk
How dealers, customers and staff reach the agent, and how a person takes over with the full history.
  • plannedAWS End User Messaging SMS and WhatsApp
  • plannedAmazon SES email
  • plannedAmazon Connect contact centre, chat and hand-off to a person
  • consideredAPI Gateway WebSocket push replies to the window
  • plannedChatwoot web chat + desk if there is no contact centre
  • consideredA Next.js window alone six more things to build
Our chat page and desk API; one conversation id across channels
If the company already runs a contact centre, hand off into it (Connect). Otherwise Chatwoot gives the desk without building one.
L3 · Tool layer
Actions through typed tools, checked before they run.
  • useMCP servers on ECS Fargate or Lambda one server per system of record
  • plannedBedrock AgentCore Gateway the same gateway fronts our MCP tool servers: one door for tools and models
  • useMCP Python SDK client + servers
  • consideredFastMCP
Gating before every call, idempotency keys, size caps, argument checks with jsonschema
The tool protocol is open (MCP), so the servers move clouds unchanged. The gating that protects orders, prices and warranties is ours.
L6 · I/O contracts
Typed inputs and outputs at every edge.
  • plannedAPI Gateway request validation reject bad shapes at the edge
  • usePydantic
  • useJSON Schema
  • plannedSAP OData / BAPI shapes typed at the ERP adapter
Frozen Pydantic models everywhere; MCP structured output
Contracts are code, not cloud. SAP and dealer-system shapes are typed once at their adapters.
L8 · Concurrency & flow
Who gets served first when load spikes.
  • plannedAmazon SQS FIFO one message group per conversation keeps order
  • useAPI Gateway usage plans rate limits per client
  • useBedrock quotas tokens per minute, the real ceiling
  • consideredOwn semaphores
  • consideredLiteLLM limits only if LiteLLM is the gateway
One turn per conversation (ledger row), priority classes (plant breakdowns before marketing), honest shedding
AWS gives the queue and the limits. Which request waits, and what we tell the person, is ours.
17 · Agent-to-agent
Agents hand work to agents through typed, bounded, traced hand-offs.
  • plannedA2A over HTTPS behind API Gateway
  • consideredAgentCore A2A support check current status
  • plannedA2A SDK
  • consideredBackstage registry
Registry in Git: who, which version, owner, autonomy level
A2A is an open protocol, so hand-offs work across clouds. The registry stays a file we own.
PS · Performance & scalability
Fast enough at the 95th percentile; more servers when load rises; the model quota is the real limit.
  • useECS Fargate service auto scaling
  • useBedrock prompt caching cheaper, faster repeated context
  • plannedDistributed Load Testing on AWS AWS solution
  • consideredBedrock provisioned throughput only at steady high volume
  • consideredk6 / Locust
Per-turn time budget (60 s), cache-friendly context order
Servers are stateless and scale out; the model quota is what to plan and load-test.
Control · what keeps it safe
L16 · Identity & authz
Who is asking, and whose authority the agent acts with.
  • plannedAmazon Cognito dealer, fleet and consumer sign-in, or federate the dealer portal
  • useIAM Identity Center staff sign-in
  • useIAM roles for tasks no keys in code
  • useSecrets Manager + KMS
  • consideredAmazon Verified Permissions Cedar policies for fine-grained rules
  • usePyJWT local token check
  • consideredKeycloak
Principal → dealer, customer or staff identity; on-behalf-of: the agent acts with the user's rights, never its own
Checking a token is local and cloud-neutral. Ports make leaving Cognito a configuration change.
PV · Privacy & data protection
Personal data of dealers, fleet drivers and consumers used only for this case, kept in its region (India or EU), masked, and forgotten on request.
  • plannedComprehend PII names, phone, ids in text
  • plannedAmazon Macie finds personal data in S3
  • useMumbai, Hyderabad; Frankfurt, Ireland India data in India, EU data in the EU
  • useKMS, PrivateLink
  • consideredPresidio Aadhaar, PAN, GSTIN and vehicle numbers need custom recognisers anyway
redact() in telemetry (Aadhaar, PAN, phone, vehicle number), no_pii_echo rule, forget() + retention per the DPDP Act and GDPR
Residency and encryption come from AWS. Which data a turn may use, masking and erasure are domain rules we code once.
L7 · Policy enforcement
Guardrails on the way in and on the way out.
  • useBedrock Guardrails prompt attacks, harmful content, denied topics, PII
  • useApplyGuardrail API the same checks on any model and on tool results
  • plannedContextual grounding check answers must stay on the sources
  • consideredAutomated Reasoning checks check current status
  • plannedLlama Prompt Guard 2 small local classifier
  • not usedNeMo Guardrails wants to own the loop
  • not usedLlama Guard an LLM, too slow
Our positioned rules (30 checks): no price or warranty promised outside policy, no order changed without OK, a dealer's own records only
We own every position and every rule; every check that protects money or a customer is ours. AWS supplies detectors behind one port.
L10 · Failure handling
Typed failures, fallbacks, undo paths, honest messages.
  • useCross-region inference spreads load when a region is busy
  • useALB / ECS health checks
  • consideredtenacity
  • useOwn resilience wrapper one retry budget per turn
Typed failures, ledger abandon-and-retry, an honest message instead of a guess
Retries without a budget hide outages. One retry budget per turn is ours on any cloud.
L14 · Human-in-the-loop
Approvals and hand-offs the agent cannot grant itself.
  • consideredStep Functions task tokens a managed wait; one more service to run
  • plannedAmazon Connect hand-off to a person with history
  • useDBOS durable waits in our own Aurora
  • consideredTemporal
Approval and escalation tables, desk API, approval cards to staff
A warranty or order approval must survive restarts. DBOS keeps it in the database we already run, so it moves clouds unchanged.
AV · Availability & disaster recovery
A lost server or zone goes unnoticed; a lost region is rebuilt from code and backups.
  • plannedMulti-AZ ECS + Aurora Multi-AZ
  • consideredAurora Global Database Mumbai ↔ Hyderabad; EU pair for Europe
  • plannedRoute 53 health checks
  • plannedAWS Backup
  • useTerraform or AWS CDK infrastructure as code
Stateless servers + durable state; a rebuild drill
Two Indian regions make a DR pair without data leaving the country; European data pairs inside the EU.
See · what we can see and prove
L11 · Observability
Traces, metrics and alerts for every step.
  • useCloudWatch + Application Signals via the ADOT collector
  • useAWS X-Ray traces
  • useBedrock model invocation logging to S3, for evidence
  • consideredCloudWatch generative AI observability check current status
  • plannedManaged Prometheus + Grafana
  • useOpenTelemetry behind one helper
  • consideredLangfuse
Spans per step with GenAI attributes, personal data redacted before export, alert rules as code
OpenTelemetry keeps the code cloud-neutral; only the exporter changes.
L9 · Determinism & replay
A past decision can be re-run and explained.
  • considered(nothing on AWS) invocation logs help, but do not replay
  • consideredVCR.py
  • useOwn recorder
Run record + cassettes + config fingerprint
"Why did the agent say that to this dealer?" needs a replay. No cloud offers it, so it is ours.
L13 · Cost accounting
Spend measured per unit of business work.
  • useBedrock application inference profiles one tagged profile per agent = cost per agent
  • useAWS Budgets
  • useCost Explorer
  • plannedCUR 2.0 data exports
  • consideredLangfuse cost
  • useOwn meter
Meter per turn and per case (cost per warranty claim triaged), hard budget stop
AWS tells you cost per agent; only we know cost per warranty claim or per dealer order.
Change · how it changes safely
L12 · Eval harness
Golden sets and graders that gate every release.
  • plannedBedrock model evaluation LLM-as-judge and human review
  • plannedBedrock RAG evaluation
  • consideredAgentCore Evaluations check current status
  • useAgentTwin, pytest, pydantic-evals
  • plannedpromptfoo, PyRIT red team
Golden sets owned by quality, warranty and dealer-service leads, hard graders, 4 CI gates, model selection run
The pretend dealer network and plant (AgentTwin) and the hard graders are the same on any cloud; AWS judges are one plug-in.
L15 · Release & config
Prompt, model and policy versioned and rolled back together.
  • useAWS AppConfig kill switch, limits, model per job
  • useECS blue/green deployments
  • useAmazon ECR
  • consideredCodePipeline or GitHub Actions + OIDC
  • useGitHub Actions + OIDC
  • consideredOpenFeature
One release bundle: prompt + model + policy + config fingerprint
AppConfig is a close match for App Configuration; the bundle and rollback rule are ours.

Services marked "check current status" are newer AWS offerings; confirm their availability in the Mumbai, Hyderabad, Frankfurt and Ireland regions before relying on them.

Who builds what

What AWS gives, what we build, what each agent writes

For each concern, how much does AWS give us, how much do we code once for every agent, and how much does each agent team still write? AWS gives the plumbing. The parts that make an agent safe for dealers and customers stay in our code.

The rule that keeps this healthy: when two agents write the same code, it moves into the shared middle (blue). When AWS catches up, it moves to the left (grey).

What does not change: specs, tests and agent code.

  • The 22 concerns and the specs (AI Harness Catalog, AI Assurance Catalog, agent specs)
  • The agent code: router, loop, context assembler, tools, approval flows
  • The tests: AgentTwin worlds, golden sets, hard graders, the four CI gates
  • The rules: every guardrail position and every check that protects money or a customer
  • The ports: each AWS service sits behind the same interface the Azure one did

That is the point of binding through ports: moving from Azure to AWS is a new binding file and a set of adapters, not a rebuild.
