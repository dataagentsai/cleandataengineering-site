The tools that do log-based CDC, by source database, are on their own page: change capture tools.

Step 4, closer

A queue is not a log

RabbitMQ and SQS are queues: a message disappears once it has been read, so nothing can replay it. Kafka, Event Hubs, Kinesis and Pulsar are logs: they keep events for a set time, and any number of consumers can read, and re-read, at their own pace. Kappa needs a log.

Step 5, closer

Three kinds of receiver

  1. A stream processor (Flink and similar) reads raw topics, transforms them and writes curated topics.
  2. A sink connector (Kafka Connect, ClickPipes, Pinot's real-time ingestion) copies a topic as it is into a store.
  3. A lakehouse writer (Flink, Spark, or Confluent Tableflow) writes Iceberg or Delta tables.

The processor's output is another topic with its own contract, so the same pattern repeats: producer, topic, consumer. See contracts and bindings.

FAQ

Questions people ask

What are the components of a real-time analytics architecture?

A transaction system and database, change capture, an event log such as Kafka, optional stream processing, curated topics, a fast serving store such as ClickHouse, a lakehouse for history, an API layer, a push gateway and the screen.

Who creates the events in a streaming pipeline?

Usually a change data capture tool that reads the database's change log, or the app itself through the outbox pattern. Browser SDKs, IoT devices, log shippers and webhooks create events too.

Can I use RabbitMQ or SQS instead of Kafka?

Not for analytics that need replay. Queues delete a message once it is read; Kafka-style logs keep events so any consumer can re-read them.
