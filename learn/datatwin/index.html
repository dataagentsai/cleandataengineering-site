DataTwin, explained

How do you know a data platform shows the right number, every day, whatever its sources do? DataTwin keeps the platform real and puts it in a pretend business: a shop that keeps selling, source systems that send its data, and a calendar of things going wrong. Every simulated night it asks one question: do the dashboard, the conversation UI and the world agree? This is the data-engineering sibling of AgentTwin.

Where it stands (31 Oct 2026). The DataTwin Studio, where you learn by watching real Spark and Delta runs, is built and live. DataTwin as a testing tool for your own platform is designed, not built: it is phases 6 to 8 of the plan, early 2027. This page explains the design and marks every feature as built, partly built, or to build.

Part 1 · The explainer

What it is, in plain words, before any detail.

What problem does it solve?

A fire drill for a data platform

Most data platforms are tested the same way: run the jobs, see them finish green, look at the dashboard and decide the numbers "look about right". Then one morning a source team renames a column, the pipeline carries on happily, and revenue shows zero. Or a file arrives twice and revenue doubles. Every job was green both times.

The trouble is that nobody knows what the right number is. Production can't tell you; it only has the data it has.

DataTwin fixes that by inventing the business. A pretend clothing shop sells, takes returns and pays refunds on its own clock, and it remembers every sale. Its source systems send that data to your platform exactly as real ones would: database changes, daily files, an API. The platform is the real one, unchanged. Then, like a fire drill, DataTwin sets things off on purpose from a calendar: day 3 arrives twice, day 4 has a renamed column, day 7 the source goes dark for six hours.

Because the shop made every sale, it knows the true total. So at the end of each simulated day, the check is simple and strict: does the number on the dashboard equal the number the world knows? Not "does it look normal", but "is it right".

Is it a digital twin?

DataTwin vs a digital twin

The name borrows from "digital twin", but it points the other way. A digital twin copies a real thing so you can watch and predict it. DataTwin keeps the thing real (your platform) and copies the world that feeds it, so you can test it.

Part 2 · How it works

From set-up to a verdict, then a tiny platform you can play, then a real one.

What has to exist before any platform is tested?

How the system is set up

Five specs, shared by every platform. Three name no product and no business, so a bank and a clothing shop read the same document:

DPC · must exist

The Data Platform Catalog: each stage of the spine (sources, landing, bronze, silver, gold, semantic, experiences), the 22 cross-cutting concerns and the port each is reached through.

DAC · must be true

The Data Assurance Catalog: checkable obligations, citing DAMA and ODCS rather than restating them.

DWD · must be faced

The Data World Description: source systems, the change feed, the clock and the incident calendar. Extends AgentTwin's world format.

DPM · must do

The Platform Manifest: one per company, universal format. What this platform does.

DBS · which product

The Binding: for each port, the adapter on one stack. databricks.yaml first.

DataTwin itself is not a separate repository. It is AgentTwin extended with a data world, because the clock, the faults, the run modes and the "nothing passes by absence" runner are the same.

I have a data platform. What do I do?

What you do for each platform

  1. Write the platform manifest (DPM). Every source, entity and table, each table's contract (written in ODCS, the open data contract standard), each metric, each freshness promise. The platform team writes it; it is the single source of what the platform does, and the generators read it to build the pipelines.
  2. Say which kinds of pipeline it has. Ten pipeline kinds are planned: file drop, database replication (CDC), API pull, event stream, analytical mart, ML features, documents for AI, reverse ETL, data sharing, regulatory report. The kinds decide which checks it owes.
  3. Describe the world (DWD). A business that trades on its own clock (our example is a clothing shop: orders, returns, refunds), its source systems, and the incident calendar: which day a column is renamed, which day arrives twice. The plan is to scaffold most of this from the manifest, as AgentTwin scaffolds a world from an agent's spec.
  4. Choose the binding (DBS). Which stack the platform runs on: Databricks first, then Microsoft, AWS and GCP. The world never changes when the stack does.
  5. Point the platform at the world's sources. Each source has the mode switch from AgentTwin: mock (the world makes the rows), replay (recorded real extracts), real (a real store started for the run), shadow (real and simulated side by side, compared). The platform doesn't know which one it is reading.
  6. Run N simulated days. One day, seven days, or thirty, unattended. Every night the world's truth is compared with the dashboard and the conversation UI.
  7. Read the verdicts and the evidence. Per day: pass or fail, and why. Per incident: caught by which detector, how fast, fixed how, did it hold, did a person have to decide. Per platform: which incident kinds and owed checks are still unproved.

For a given platform, how do we know these are the tests it needs?

How we know which tests a platform needs

The same answer as for agents: nobody picks the tests by taste. The platform's test list is whatever it takes to prove what it declares and what its kinds of pipeline owe.

  • The manifest. Every source gets the incidents its kind can suffer: a database replication source can replay a day, a file source can send a file twice or half a file, an API can throttle. Every contract rule gets an edge row on each side. Every metric gets "the dashboard equals the world". Every freshness promise gets a dark source that breaks it.
  • The Data Assurance Catalog, by pipeline kind. A regulatory report owes checks a marketing mart doesn't.
  • The Data Platform Catalog's 22 concerns. Quality, reconciliation, lineage, freshness, cost, privacy and the rest are on by default (rule R5). Turning one off needs a waiver with a reason, an approver and an expiry, so a missing check is a decision someone signed, never an accident.
  • The Problem Lab. 19 problems every platform meets sooner or later: duplicates, re-runs that double a day, history that can't be true, late data, failure halfway, a poison row, schema drift, deletes nobody sees. Each one becomes an incident kind.
  • Production incidents. Anything that slips through in the wild becomes a planted incident, so it can't slip through twice.

Then rule R9 joins the two lists: every incident kind in the world's calendar must be matched to a detector that has been seen to fire on it. An unmatched kind is a named gap. A detector nobody has ever seen fire is treated as untested, however good it looks.

The honest catch. As with agents, this proves the tests are complete against what is written down. A source missing from the manifest gets no incidents. Replay of real extracts, and every production miss becoming a planted incident, push against that.

From the world's state, not by hand. The shop keeps its own tables; each source system shows those tables the way it really would.

Where does each day's data come from, and how is the right answer known?

The data, and how the truth is known

On the AgentTwin page we met the oracle problem: generating tests is easy; knowing the right answer for each is hard. Data platforms have the same problem, and usually dodge it. Quality tools check rows against rules ("amount is never negative"); observability tools check today against history ("volume is 3× normal"). Neither knows what the revenue should be.

A simulated world does. It generated every order, so the true total for every day, every product and every customer is known before the platform sees a row. That is DataTwin's oracle.

  • Rows that obey the contract by default, from Faker, then SDV for realistic shapes and volumes. Seeded, so every run is the same.
  • Bad rows only where planted. A negative refund appears because the calendar says so, and the world counts it, so "quarantine count equals planted count" can be checked exactly.
  • Edge rows on each rule: amount 0 and −1, a timestamp one second before midnight.
  • Volume on demand for performance stories: the same day at 1,000 rows or 10 million.
  • Impossible worlds are refused. A refund for an order that never existed stops the load, unless it is a planted incident.

    What limits are we facing?
    Our limits today
    

    1. It isn't built yet. The biggest limit. The design is written and the learning studio is real, but the data world, the pretend sources, the checks and the 30-day run are phases 6 to 8. Everything in Part 2 past the Studio is how it will work, not how it works today.
    2. Pretend data is cleaner than real data. Real sources send odd encodings, half-written files, duplicate keys with different values, time zones that change in March. Faker and even SDV only make what they are told to. Replay mode (recorded real extracts) and shadow mode are the answer, and both are planned.
    3. The tests are only as complete as the manifest. If a source or rule is not declared, no incident will be planted for it. The same is true of AgentTwin and its spec, and the same answer applies: every production incident becomes a planted one.
    4. Laptop scale hides some problems. A lesson from building the Studio: at small volumes, some before-and-after numbers don't move. Skew, spill and cost only show at size. Those stories must be rescaled or labelled illustrative, never passed off as measured.
    5. Some managed-platform behaviour can't run locally. Serverless compute, Photon and Unity Catalog grants are Databricks-only. The engine internals are recorded on open-source Spark and Delta; the Databricks binding has to be tested on Databricks Free Edition, which has quotas.
    6. Dashboards are judged by their numbers. DataTwin checks that the tile and the conversation UI give the world's number. It does not judge whether a chart is clear, or whether the metric is the right one for the business.
    7. One domain so far. The clothing shop. A second domain is planned to prove the specs don't secretly assume retail.

    FAQ
    Questions people ask
    Is DataTwin a digital twin?
    Not in the usual sense. A digital twin copies a real machine to watch and predict it. DataTwin keeps your data platform real and copies the business and source systems that feed it, so you can break the platform on purpose before real data does.
    How is it different from AgentTwin?
    Same idea, different subject. AgentTwin keeps an AI agent real and simulates its customers and tools. DataTwin keeps a data platform real and simulates its sources and their incidents. DataTwin extends AgentTwin's world format rather than starting a new one, so the clock, faults and run modes are shared.
    Is it built?
    Partly. The DataTwin Studio, where you learn by watching real Spark and Delta runs, is built and live. DataTwin as a testing tool for your platform is designed and planned for early 2027. This page marks every feature as built, partly built, or to build.
    Why not just use Great Expectations or Monte Carlo?
    Keep them: they are what DataTwin tests. Rule tools check rows against rules you wrote; observability tools check today against history. Neither knows the right answer. DataTwin's world made the data, so it knows the true total, and it checks that your rules and monitors actually fire when an incident is planted.
    Can't I test on a copy of production instead?
    Yes, and you should, for changes. But production only contains the incidents that already happened. DataTwin lets you plant the ones that haven't happened yet (a renamed column, a duplicate day, a dark source), on a calendar, as often as you like.
    Is 100% coverage possible?
    100% of what a platform owes can be accounted for: every declared incident kind planted and caught, every owed check proved or signed off. 100% of everything real data can do cannot. See the section on coverage.
    Does it work only on Databricks?
    No. The world and the checks name no product. Databricks is the first binding; Microsoft, AWS, GCP and an open-source binding are planned.
