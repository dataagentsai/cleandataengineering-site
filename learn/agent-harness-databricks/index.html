The agent harness on Databricks

The same agent harness as on Azure and AWS: the same 22 concerns, in the same families, with only the binding changed. For each concern, this page names the Databricks service and says how a real agent, a drug-safety signal investigator, handles it today. For what each Databricks AI service is and which ones we do not use, see Build an agent on Databricks.

5 concerns work on Databricks7 built and tested offline8 planned2 not used

Status as of 19 November 2026, from what we ran on a Databricks Free Edition workspace. The code is not public yet. Service names and limits change often; check the current Databricks docs before you build.

The agent in one paragraph

A drug-safety scientist asks whether a drug and an adverse event form a signal. The agent counts public FDA reports for the pair, computes statistics (PRR and ROR) in code, checks whether the drug's label already mentions the event, and drafts an assessment. A person approves, edits or rejects every draft. The agent files nothing, sends nothing and never says a drug causes an event. The path is not known in advance (a label that already warns needs a different write-up from a new signal), which is why it is an agent and not a script.

One request, end to end

  1. A safety scientist asksIs there a signal for lisinopril and angioedema?Databricks Apps (planned); today a script
  2. A job run startsOne run per request, under the agent's own login.Lakeflow Jobs, Unity Catalog service principal (planned)
  3. The model chooses a toolIt sees three tool descriptions and picks report counts first.Foundation Model APIs (works)
  4. The tool runsCounts, then statistics and the signal screen, then the label check.Unity Catalog functions on a serverless SQL warehouse, over Delta tables (works)
  5. The model draftsAn assessment with numbers from the tools, uncertainty and a recommendation.Foundation Model APIs (works)
  6. Checks runOutput contract, then grounding: every number equals a tool result. A failure goes to a person.Our harness code (built)
  7. The draft is saved and shownA row with status drafted.Delta table, Databricks Apps (planned)
  8. A person decidesApprove, edit or reject; the decision is final.Databricks Apps, Delta decision table (planned)
  9. Everything is traced and scoredEach step is a trace; the eval harness answers the ops questions; cost comes from billing tables.MLflow tracing, system tables, eval harness (planned)

What Databricks gives, and what stays ours

  • Databricks gives: governed data and permissions (Unity Catalog), tables with history (Delta), SQL compute, registered tools (Unity Catalog functions), hosted models (Foundation Model APIs), run tracking (MLflow), scheduled runs (Lakeflow Jobs), a place for a review screen (Databricks Apps), and usage records (system tables).
  • Stays ours, on every cloud: the loop and its limits, the tool contract, the policy rules and the grounding check, the approval rule, the cost limit, the evaluation sets and the specification. These are what make the same agent testable on Azure and on Databricks.
  • A finding: the harness assumes a durable-wait library for approvals. A Databricks job has none, so a wait is a run that ends and a new run that starts on the decision. The specification should state the contract (state survives, the decision is a message, resume is safe to repeat) without naming a library.
