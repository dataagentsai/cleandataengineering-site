Concept and physical

A concept is the job and its rules. A physical thing is a product doing that job somewhere. Sorting is a concept; writing it in Java or Python is physical. Evaluation is a concept; doing it in LangSmith or DeepEval is physical.

The same idea, for a whole system

The agent harness is a concept too: a loop, context, tools, state, checks, durable waits and tracing around a model call. It can be built on any platform. We built it twice, the same concerns both times; only the bindings changed.

Why this matters when you learn

When you learn……you can
the concept (what the job is, what can go wrong)judge any product that claims to do it, in an hour
only a productuse that one product, until it changes or you move platform
the concept, then one product properlyswitch to the next product by mapping, not relearning

Five kinds of physical thing

KindWhat it isExamples
Implementationdoes one concept's jobLangfuse does tracing; vLLM serves models; pgvector stores embeddings
Bundle / platformpackages many concepts under one nameMicrosoft Foundry, Bedrock AgentCore, Databricks
Protocol / standardan agreed way for two concepts to talkMCP (agent ↔ tools), A2A (agent ↔ agent), OpenTelemetry (anything ↔ tracing)
Wrappera convenience layer over another implementationLiteLLM over provider APIs; a chat app over a model
Modelthe trained weights themselvesClaude, GPT, Gemini, Llama, Qwen, gpt-oss
Patterna way of combining concepts, not a productRAG, ReAct, human-in-the-loop
