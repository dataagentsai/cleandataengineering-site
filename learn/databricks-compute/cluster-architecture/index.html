Databricks cluster architecture: planes, driver, workers, memory and machine types

The control plane and compute plane, the driver and worker anatomy of every cluster, all-purpose and job clusters and pools, what lives in RAM and on local disk, and the five machine families.

Cluster architecture

Two planes: where the machines live

Databricks splits itself into a control plane (the brain: web app, job scheduler, notebooks, cluster manager, Unity Catalog) and a compute plane (the muscle: the virtual machines that run Spark). Your data stays in your own cloud storage the whole time.

Rule of thumb. Classic means you pick machine types, versions and network details, and you wait for VMs to boot. Serverless means you pick almost nothing, Databricks tunes it, and it starts fast. You trade control for convenience.

Cluster architecture

Anatomy of one Spark cluster

Every cluster, whatever its name, is the same shape: one driver that plans and coordinates, and many workers that do the real work. A worker runs an executor, and an executor has one slot for each CPU core. A slot runs one task (one small piece of your query) at a time.

Cluster architecture

Classic clusters in detail

All-purpose (interactive) cluster

The one you create from the Compute page and attach notebooks to. Several people can share it. It stays on until it hits the auto-terminate timer, so it is the easiest compute to forget and overpay for. It costs more per hour than a job cluster for the same machines.

  • Access mode decides sharing and security: standard (shared by users, isolated) or dedicated (one user or group, full feature set).
  • Runtime is a version of Databricks Runtime (DBR). It bundles a Spark version, Delta, Python and libraries. You choose it and you must upgrade it.
  • Autoscaling adds workers between your minimum and maximum. Scaling up needs VM boot time, so it reacts in minutes.
  • Spot instances use cheap interruptible VMs for workers, with fallback to on-demand. The driver should stay on-demand.
  • Init scripts, custom libraries, Spark configs are all yours to change. This freedom is what serverless takes away.

Job cluster

The cluster is created when a job starts and deleted when it ends. Nobody shares it, nothing is left running, and the hourly rate is lower than all-purpose. This is the default choice for production pipelines on classic compute.

Pools

A pool keeps a set of already-booted idle VMs. A cluster that asks for machines from a pool skips the cloud's VM boot step, so it starts in seconds instead of minutes. You pay the cloud provider for idle pool VMs, but not Databricks DBUs for them.

Machine types: compute, memory, storage, general, GPU

On classic compute you pick the VM family. Serverless picks for you. The names differ by cloud, but the five families are the same idea everywhere.

A useful sentence to remember: compute optimized is about CPU, memory optimized is about RAM, storage optimized is about local disk. Photon plus disk cache loves the storage optimized family because scans hit the local SSD instead of cloud storage.

FAQ

Questions people ask

What is the difference between the driver and a worker?

The driver plans the query, cuts it into tasks and collects small results. Workers run an executor that executes the tasks, one task per CPU core at a time. A driver that runs out of memory kills the whole application.

Which machine family should I pick?

General purpose when unsure, memory optimized when the Spark UI shows spill, storage optimized for read-heavy and interactive work that benefits from the SSD disk cache, compute optimized for CPU-bound jobs, GPU only for model training.

Why does a pool start clusters faster?

A pool keeps booted idle VMs, so a cluster skips the cloud's VM boot step. You still pay the cloud for idle pool VMs, but no Databricks DBUs for them.
