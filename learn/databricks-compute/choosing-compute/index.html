Choosing Databricks compute: classic, serverless, SQL warehouses, users, batch and live access, settings and mistakes

Start here

How many kinds of serverless are there?

"Serverless" is not one thing. Databricks uses the word for several separate products, and each has different settings. For your own code and SQL there are four. Other serverless features are billed and configured separately.

KindWhat it runsWho uses it
1. Serverless SQL warehouseSQL queries from the SQL editor, dashboards, Power BI and other BI toolsAnalysts, BI tools, apps that send SQL
2. Serverless notebooksPython and SQL in an interactive notebookEngineers and data scientists developing
3. Serverless jobsScheduled or triggered tasks in Lakeflow JobsProduction batch pipelines
4. Serverless pipelinesLakeflow Spark Declarative PipelinesDeclarative bronze, silver and gold
Other serverless featuresModel Serving, Predictive Optimization, and others, each with its own endpoint or billing lineSpecific features. Check each one's page and price.

The first four share one idea: you do not pick machines, and Databricks runs the compute in its own account. Notebooks, jobs and pipelines all run on the same kind of serverless engine. A SQL warehouse is a separate product with its own sizing.

Enabling serverless for SQL warehouses is a separate step from enabling it for notebooks, jobs and pipelines, and availability depends on cloud and region. If a choice is greyed out in your workspace, ask your account admin before assuming it does not exist.

Configuration

What you can configure on each kind

KindYou can setYou cannot set
Serverless SQL warehouseCluster size (T-shirt size), the minimum and maximum number of clusters, auto-stop (5 minutes at the lowest in the UI, 1 minute through the API), tags, permissions, and a statement timeout at session or workspace levelMachine type, Photon on or off (it is always on), spot, init scripts, which VPC it runs in
Serverless notebookEnvironment version, base environment and libraries, and memory (standard is 16 GB, high is 32 GB, with a higher DBU rate for high memory)Machine type, number of workers, most Spark settings, compute policies
Serverless jobPerformance mode (performance optimized or standard), environment and libraries, job timeout, retries, notifications, tags and a budget policyMachine type, number of workers, autoscaling limits, Photon on or off, init scripts, custom images
Serverless pipelineServerless on or off, triggered or continuous mode, performance mode, and a budget policyMachines and worker counts

The pattern is simple: on serverless you set behaviour and limits (mode, timeout, memory, libraries, tags), and you give up machine-level control (node type, worker count, spot, init scripts, Photon). Only warehouses give you a sizing knob, because a warehouse is sized by T-shirt size and cluster count.

Two settings are worth knowing exactly: serverless jobs in Standard mode use fewer DBUs but typically take 4 to 6 minutes to start, and auto-stop on pro and classic warehouses defaults to 45 minutes with a 10-minute minimum, while serverless defaults to 10 minutes. The page on cost-saving hacks lists the rest.

Factors

The factors that decide the choice

FactorAskLeans toward
Workload shapeScheduled batch, interactive, live BI queries, or always-on streaming?Batch: jobs compute or serverless jobs. Interactive: serverless notebook. BI: SQL warehouse. Always-on streaming: classic job cluster.
ConcurrencyHow many queries run at the same moment, not how many people exist?Many concurrent queries: a warehouse with more clusters
LatencyDoes a user wait for the first result? Is a start-up of minutes acceptable?Seconds: serverless. Minutes fine: classic, or serverless Standard mode.
PredictabilitySteady 24 hours a day, or bursty?Bursty: serverless, because idle time is cheap. Steady and heavy: classic on spot or committed VMs can win.
Language and APIScala, R, RDD code, continuous streaming triggers?Classic or dedicated compute. Serverless restricts these.
Libraries and customisationCustom images, init scripts, special drivers?Classic
NetworkingMust the compute sit inside your private network, for example to reach a database that only has a private IP, or a firewall that allows only your own IP ranges?Serverless runs in Databricks' network, not yours. It can reach private resources only through a network connectivity configuration (private endpoints, stable IP ranges, outbound policies), which has limits: for example, firewall enablement is not supported for S3 or DynamoDB. If you cannot or may not set that up, use a pro warehouse or classic compute.
Run lengthCould a run exceed 7 days?Classic. Serverless stops runs after 7 days.
Cost attributionDo you need to trace each VM on the cloud bill?Classic, where tags reach the VMs. Serverless uses budget policies.
Team skillIs anyone available to tune clusters?No one: serverless
AvailabilityIs serverless enabled in your cloud and region?If not, pro warehouses and classic compute

Sizing

Number of users, concurrency and performance

Count concurrent queries, not users. Ten users can mean two queries or two hundred. A dashboard with twelve tiles sends twelve queries each time it opens or refreshes.

Problem you seeWhat it meansFix
One query is slow, or spills to diskThe cluster is too small for that queryIncrease the size
Many queries wait in a queueToo few clusters for the concurrencyRaise the maximum number of clusters
Cost is too high, queries are fastThe warehouse is bigger than it needs to beStep down one size, as long as nothing spills or slows noticeably
  • On classic and pro warehouses, the planning rule is about 10 concurrent queries per cluster. Autoscaling adds clusters based on the estimated time to clear running and queued queries, and a query queued for 5 minutes triggers scale-up.
  • Serverless warehouses scale on the time needed to process running, queued and expected incoming queries (looking about two minutes ahead), and scale down after 15 minutes of low load while keeping enough clusters for the last 15 minutes' peak.
  • Queries queue when every cluster is full or the warehouse is starting. A queue holds up to 1,000 queries.
  • Watch the Peak Queued Queries metric on the warehouse monitoring page. A value that is consistently above zero means more size or more clusters.
  • Databricks suggests starting a serverless warehouse larger than you think you need and sizing down as you test.
  • Pro and classic warehouses take several minutes to start (typically about 4). Serverless starts in seconds. Serverless also has Intelligent Workload Management, which pro and classic lack, and pro adds Predictive IO but classic has Photon only.

Treat the 10-per-cluster figure as a planning rule, not a hard limit, and load test with your real dashboards.

Watch out

What to watch out for

  • Start-up time. Serverless in default mode starts quickly. Standard mode, pro and classic take minutes. Do not put a slow start in front of a user.
  • Serverless limits. Only Spark Connect APIs, no RDD access, no global temporary views, 7-day maximum runs. The full list is on the limitations section of the comparison page.
  • Quotas. Serverless usage is limited in DBUs per hour, so a big backfill can hit a quota.
  • Opaque cost. You see DBUs, not machines. Use system tables and budget policies for attribution.
  • Availability. Check that serverless is enabled for your cloud, region and each product kind.
  • Environment versions. They change what libraries and behaviour you get. Pin and test.
  • Dev and prod. Keep separate warehouses and workspaces so a dev experiment cannot slow production dashboards.

Quick chooser

Six questions, in order

  1. Is it SQL from a BI tool or editor? Use a serverless SQL warehouse. Use pro or classic only for custom networking or when serverless is unavailable.
  2. Is it interactive development? Use a serverless notebook, or standard all-purpose compute. Use dedicated for GPU, RDD or R.
  3. Is it a scheduled job? Use serverless jobs unless a limit blocks it. Use Standard mode if it can wait.
  4. Does it need Scala, RDD code, custom images, special networking, always-on streaming, or runs over 7 days? Use a classic job cluster.
  5. Is it large, steady and heavy? Price a classic cluster on spot against serverless for your real usage.
  6. Is it a declarative pipeline? Use serverless pipelines in triggered mode.

Worked decision

A shared dev setup for data engineers and data scientists, available any time

"Anytime they can query" does not mean "a cluster running 24 hours a day". It means a user can start work whenever they want and not wait long. Compute that starts in seconds, or restarts on demand, gives the same availability without paying for the empty hours.

OptionHow it worksIllustrative monthly costVerdict
A. One big shared cluster running 24 hours a day8 machines (16 DBU per hour) on all-purpose compute, always on730 h × 16 = 11,680 DBU × $0.55 = $6,424, plus VMs $2,243 = $8,667Drop. Most of those hours are empty.
B. One shared cluster that starts on demand and stops when idleStandard access mode, autoscaling from 2 to 8 machines, auto-terminate after 30 to 60 minutes. Users reconnect and it restarts.Active 12 h a day for 22 days at an average of 4 machines: 264 h × 8 DBU × $0.55 = $1,162, plus VMs $406 = $1,567Pursue when many users run light work and need Scala, RDD or libraries
C. Serverless notebooks, one per personNo cluster to wait for or share. Each person's session is isolated.You pay only while a session is active. At an assumed 2 DBU per active hour, 88 hours a month is 176 DBU × $0.75 = $132 per personPursue as the default for DE and DS
D. One small serverless SQL warehouse per team2X-Small (4 DBU per hour), starts in seconds, short auto-stop. Anyone can run SQL at any time.6 busy hours a day for 22 days: 132 h × 4 = 528 DBU × $0.70 = $370Pursue for ad-hoc SQL

The cheapest effective setup

  1. Serverless notebooks for most DE and DS work (option C), because nothing runs, or bills, when nobody is working.
  2. One small serverless SQL warehouse per team (option D) for anyone who just wants to query.
  3. Personal single-node classic clusters or a shared standard cluster (E or B) only for what serverless cannot do: Scala or RDD code, custom images, GPUs, or private-network access.
  4. Run heavy or scheduled work as a job, not on the dev cluster. See the nightly ETL decision on the cost map.

Guardrails that matter more than the choice

  • A cluster policy that forces auto-termination (60 minutes at most), caps the number of machines, allows only a few machine types, and requires tags.
  • A dev catalog with sampled or synthetic data, so nobody scans production-sized tables to try an idea.
  • A budget policy and tags on every serverless workload, so dev spend is visible by team.
  • An alert on anything running longer than a set number of hours, using the compute system tables.
  • Never put a scheduled production job or a refreshing dashboard on a dev cluster. Activity keeps an idle cluster from auto-terminating.

What goes wrong

ProblemWhyFix
The "shared" cluster never stopsA forgotten loop, streaming query or auto-refresh counts as activity, so auto-termination never triggersPolicy, alerts, and no scheduled work on dev compute

FAQ

Questions people ask

How many types of serverless does Databricks have?

Four for your own code and SQL: serverless SQL warehouses, serverless notebooks, serverless jobs and serverless pipelines. Other features such as Model Serving and Predictive Optimization are separate serverless products with their own settings and billing.

What can I configure on serverless jobs?

Performance mode, the environment version and libraries, the job timeout and retries, notifications, tags and a budget policy. You cannot choose machine types, worker counts, Photon or init scripts.

A warehouse is slow. Do I make it bigger or add clusters?

Make it bigger when a single query is slow or spills to disk. Add clusters when queries wait in a queue. Size helps one query, clusters help concurrency.

When should I use classic compute instead of serverless?

When you need Scala or RDD code, custom images or init scripts, custom networking, always-on low-latency streaming, runs longer than 7 days, or the lowest hourly price on spot for large steady work.
