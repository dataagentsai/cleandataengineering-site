The shift-left bundle: design, tools and status

The shift-left bundle for PySpark and Databricks: spec, bindings and adapters, check families, tools with verdicts, why not SonarQube, git layout and status.

Where it stands

Status: the spec is written and the runner works

The plan, the reuse check and the eight starting decisions are done, and so is the spec: 131 checks in 13 families, with ids that name no product, each linked to the data assurance obligations it gives evidence for. They cover Python, PySpark, notebooks, SQL, dbt, materialized views and metric views. 20 block from day one, 82 warn and 29 only report. For Databricks, 76 of the 131 are found by rules that already exist, 50 we write, and 5 tools are on trial. The full list is in the repo's catalog index. Then a sample repo with planted problems and a hidden answer key, so catch rates are measured, not claimed. The repo is open: github.com/dataagentsai/shift-left-bundle.

Spec-driven

Spec, bindings, adapters

It follows the same shape as the other open specifications on this site. The catalog says what to check and why, and names no product. A binding per platform (Databricks first, then Azure) maps each check to a tool and its rule. The runner talks to every tool through one interface, so swapping a tool means writing one adapter, not changing the checks.

FamilyAsksStarting gate
COST-CODE, COST-PLAN, COST-CONFIGDoes the code, the plan or the job config waste money?warn; cartesian joins and config problems block
SEC, SECRET, DEPIs it unsafe, leaking secrets, or using vulnerable libraries?block
PURE, TESTIs the logic pure and tested, and do the tests catch bugs?report; coverage on changed lines blocks below 80%
CPLX, CLEAN, STYLEIs it tangled, unclean or inconsistent?warn; safe fixes automatic
SETUPWhat is the repo missing?report

Deterministic first: every check is a tool or a script with a fixed answer. A language model is used only to explain a finding or draft a refactor, never to decide pass or fail.

A common question

Why not SonarQube?

SonarQube needs a server and a database, pull-request analysis is in its paid editions, and it knows nothing about Spark cost or Databricks. What it gives, rules, a dashboard and "clean as you code", comes lighter here: Ruff and Opengrep for rules, SARIF findings on the pull request for the dashboard, and diff-cover with a baseline for clean as you code. Because the output is SARIF, a team that already runs SonarQube can import the findings.

Git

How the repo is laid out, and how a team uses it

shift-left-bundle/
  .pre-commit-hooks.yaml     teams install the bundle from here (a few lines in their config)
  catalog/checks/*.yaml      the spec, versioned on its own
  bindings/databricks.yaml   bindings/azure.yaml   (the only place product names appear)
  rules/                     Opengrep, SQLFluff, Ruff and import-linter configuration
  src/shiftleft/             runner: interfaces, adapters, purity, empty-table harness, report
  plugins/repo_review/       the gap-report checks
  templates/                 pre-commit config, GitHub Actions and Azure DevOps pipelines
  examples/sample-project/   planted problems; tests/answer-key.yaml

Short-lived branches merge into a protected main through pull requests, with the bundle's pull-request job as a required check. Teams pin a version tag of the bundle, so a new rule never breaks them by surprise.

FAQ

Questions people ask

Do I need SonarQube for a PySpark project?

No. Ruff, Opengrep, SQLFluff, gitleaks, pip-audit and coverage tools cover the same ground with no server, and SARIF output shows findings on the pull request. SonarQube also has no Spark cost rules.

What is spec-driven about this bundle?

The checks are written once, with ids and reasons and no product names. Each platform gets a binding that maps checks to tools, so adding Azure or another platform is a new binding, not new checks.

Can I use it today?

Yes, as a preview: `shiftleft scan . --stage pr`, `shiftleft purity .` and `shiftleft draft-tests .` work today, as does the pre-commit hook. Version 0.1 follows a run on a real repo. Follow the GitHub repo.
