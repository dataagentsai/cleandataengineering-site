The split

57 checks come from open-source tools, 77 we wrote

The rule from the start was to reuse what the industry already trusts and build only what nobody ships. So most of the general checks, such as Python lint, security, secrets, vulnerable libraries and SQL style, are other people's rules that we switch on and configure. What we wrote is mostly specific to data work: cost in Spark code, plans and job config; whether logic is pure and tested; metric views; and what a data repository is missing.

FAQ

Questions people ask

Which open-source tools does a shift-left setup for PySpark need?

Ruff for Python lint, clean code and security; SQLFluff and sqlglot for SQL; gitleaks for secrets; osv-scanner for vulnerable libraries; coverage.py and diff-cover for tests on changed lines; and a PySpark linter such as SparkDoctor for Spark-specific patterns.

What do the open-source tools not cover for data engineering?

Spark cost in code, plans and job config; whether logic is written as pure functions and tested; plan problems found on empty tables; metric views; and what a data repository is missing.
