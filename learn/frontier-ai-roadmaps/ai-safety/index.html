Frontier AI roadmaps · AI safety and security

AI safety and security: the roadmap

You find how AI systems can fail or be attacked, measure it honestly, add controls, and show the evidence that the controls work. This page gives you eight small steps, each with a clear finish line, and five small projects. Each project ends in one number you can publish.

The job, in a picture you can hold in your head. A safety engineer is a careful inspector. They try to break the system the way a real person or attacker would, count how often it breaks, fit a guard, and then test again. At the end they leave a page that a regulator or a customer can read and check.
This may suit you if: You like asking what could go wrong, and you can be patient and fair. You write clearly, and you are happy to prove your own fix does not work.
Start in 30 minutes: Open any chatbot you built, write ten tricky inputs, and note which ones it handles badly. Practise on systems you own only.

Week 0 to 4

First, the base every role shares

Do these five things first. They are the same for all four roles, so nothing you do here is wasted if you change your mind.

StepWhat to doYou are done when
1. Python you can readWrite ten small programs: read a file, count words, call a web API, sort a list of records. Use plain Python, no framework.You can write a loop, a function and a dictionary without looking anything up.
2. Git and GitHubPut every small program in one repository. Commit each change with a one-line message.A stranger can open your repository and run something from the README.
3. Tensors and PyTorch basicsMake a tensor, multiply two of them, take a gradient of one number. Do the first official PyTorch tutorial.You can explain in two sentences what a gradient is for.
4. Run a model on your own machineInstall a local runner (Ollama or llama.cpp) and ask a small open model ten questions.You know the model's size on disk and how many answers per minute it gives.
5. Keep a measurement notebookOne file where every experiment gets: the question, the setup, the number, and what surprised you.Your last three experiments are written down so someone else could repeat them.

The roadmap

Eight small steps

The eight steps in order. Do one at a time; each one is small enough for a weekend or two.

1. Learn six ways AI fails

Write one example each for: wrong but confident answers, jailbreaks, prompt injection, leaking private data, unsafe tool use, and unfair answers.

You are done when: You can show each failure on a toy system in one screen.

Open the matching guide on this site

2. Read the two key lists

Read the OWASP Top 10 for LLM Applications and skim MITRE ATLAS (a catalogue of attack methods on AI systems).

You are done when: You can say which three items matter most for the system you have built.

3. Attack your own toy chatbot

Write ten prompt-injection attempts against a chatbot you built. Log what each did.

You are done when: You have a table of attempt, result and why.

4. Build a tiny test with a pass or fail

Turn your attempts into a script that runs them all and prints the attack success rate.

You are done when: Anyone can rerun the script and get the same number.

Open the matching guide on this site

5. Add one defence and test again

Add an input filter, an output check or a limit on which tools the agent may use. Rerun the test.

You are done when: You can show the rate before and after, and the attacks that still get through.

Open the matching guide on this site

6. Threat-model one agent

List what it protects, how things get in, and how each could be abused. Add a test for each threat.

You are done when: You have one page: threats found, and how many your controls stop.

Open the matching guide on this site

7. Map your controls to a standard

Pick NIST AI RMF or ISO/IEC 42001. Match each of your controls to a clause and link the evidence.

You are done when: A reader can follow each claim to a test result.

Open the matching guide on this site

8. Write a short incident review

Invent or find a small failure. Write what happened, the cause, the fix and what you now check.

You are done when: It reads in under two pages and has no blame in it.

Small projects

Five projects, each ending in a number

Keep each project small. Put the code and data in a public repository and write a one-page note on what you found. Where a project has code that can be tested, write the tests as one table of inputs and expected results, with one loop that runs every row. That keeps tests short and easy to extend.

S1. A 50-attack test set

About one weekend

You build
Fifty prompt-injection and jailbreak attempts for a toy assistant, in a file.
You learn
How attacks are phrased, and how to log them.
Number you publish
Attack success rate on one model.

S2. Defences compared

About two weeks

You build
Three or four defences run against the same attack set.
You learn
What each defence blocks, and what it breaks.
Number you publish
Attack success rate with and without each defence.

About two to three weeks

You build
An agent with least-privilege tools and a script that tries to break out.
You learn

Number you publish
Escapes blocked out of attempts made.

About two weeks

You build
One real agent, its threats listed against OWASP and MITRE ATLAS, each with a test.
You learn
Threat modelling for AI systems.

Threats found, and how many your controls stop.

What to leave for later

Temptations, with a verdict

TemptationVerdictWhy
Attacking systems you do not ownDropPractise only on your own systems or ones with published permission. Follow each programme's rules.
Collecting framework namesDropUse two frameworks properly instead of listing ten.
Alignment theory firstDelayIt is deep research. Start with measuring and defending real systems; theory is easier once you have seen failures.
Reporting one lucky numberDropUse enough examples, show the cases that fail, and publish your data and script.

FAQ

Questions people ask

Is this a research job or an engineering job?

Both exist. Evaluation, red-teaming and applied security are mostly careful engineering and writing. Alignment and interpretability research usually asks for a research record.

What tools do postings name?

In a sample of 2026 postings, garak, PyRIT, promptfoo and Giskard appear for red-teaming, alongside OWASP, MITRE ATLAS and NIST AI RMF. Inspect, from the UK AI Security Institute, is widely used for evaluations. It is a sample, not a survey.

Do I need a security background?

It helps a lot. Many postings ask for offensive-security grounding, with certifications such as OSCP preferred rather than required. If you do not have it, steps 3 and 4 are where to build it.
