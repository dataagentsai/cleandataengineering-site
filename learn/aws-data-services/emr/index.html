Amazon EMR (on EC2, Serverless, on EKS)

AWS's managed big-data service for Spark, Hive, Trino, Flink and HBase, run on your own clusters, serverless, or on Kubernetes.

DatabricksDatabricks classic and serverless compute
Open sourceApache Spark, Hive, Trino on your own Hadoop or Kubernetes

In plain words

What it is

Amazon EMR runs open-source big-data engines for you. The main one is Apache Spark, which splits a large dataset into many pieces and processes them in parallel across machines. EMR also runs Hive for SQL over files, Trino and Presto for fast interactive SQL, Flink for streams, and HBase as a wide-column database. AWS packages tested versions of these engines into a release, installs them, and connects them to S3, IAM and CloudWatch.

EMR comes in three forms. EMR on EC2 builds a cluster of virtual machines in your account; you pick the instance types, how many, and whether some are Spot instances, which are spare capacity sold at a deep discount that AWS can take back. EMR Serverless has no cluster: you create an application, submit jobs, and EMR finds the workers and releases them when the job ends. EMR on EKS runs Spark jobs as pods on a Kubernetes cluster you already run on Amazon EKS.

A concrete example. A manufacturer collects vibration and temperature readings from presses in five plants, about two billion rows a day, landed in S3 as Parquet. Every night an EMR Serverless Spark job reads the day's readings, joins them to the machine master from SAP, computes hourly averages and alarms per press, and writes the result as Iceberg tables. Analysts query them with Athena. The job uses about 400 vCPUs for 40 minutes and then nothing until the next night.

A rental workshop fully stocked with open-source tools; you can rent the whole building, a bench by the hour, or a corner of a workshop you already own.

Big picture

Where it fits

The lit lane is where Amazon EMR works. Boxes on the left feed it; boxes on the right use what it produces.

EMR sits in the processing lane, the same place as Glue and Databricks. In a classic AWS lake, movers drop files into S3 landing, EMR Spark jobs build bronze, silver and gold, the Glue Data Catalog holds the table definitions, and Athena, Redshift or QuickSight read the results. Orchestration is usually Step Functions or Airflow on MWAA.

On this site's reference platform, Databricks does the processing, with Unity Catalog for access, lineage and audit, and Lakeflow Jobs for orchestration. One engine for batch and streaming means one set of quality rules, one lineage graph and one bill per data product. Adding EMR next to it would bring a second Spark, a second catalog path and a second set of clusters to tune, so new work does not go there.

Two places where EMR stays. Existing EMR pipelines keep running while each subject is rebuilt as a Databricks pipeline, runs in parallel for two weeks, reconciles counts and sums, and is switched off. And some open-source engines have no place in Databricks: an HBase store behind an application, or a Trino cluster that another team uses as a query layer over many sources. Those can stay on EMR, reading the platform's tables as Iceberg through UniForm.

How it works

The ideas you need

IdeaWhat it means
ReleaseA numbered bundle of engine versions, such as emr-7.14.0 with Spark 3.5. Each release has a support end date; the newer emr-spark-8.x line carries Spark 4.
Primary, core and task nodesOn EMR on EC2, the primary node runs the cluster managers, core nodes run work and hold HDFS data, and task nodes only run work, which makes them safe for Spot.
Instance fleetA way to list several instance types and purchase options for each node group, so EMR can find capacity across types and Availability Zones.
Managed scalingEMR adds and removes nodes on an EC2 cluster based on the workload, between a minimum and maximum you set.
EMR Serverless applicationA named, versioned Spark or Hive environment that jobs are submitted to. It starts workers per job, and can keep some pre-initialised to cut start time.
Virtual clusterOn EMR on EKS, a link between EMR and one Kubernetes namespace, so Spark jobs run as pods beside other workloads.
EMRFS and S3EMR reads and writes S3 directly as its main storage, so clusters can be short-lived and the data outlives them.
Runtime roleAn IAM role passed with each job or step, so different teams on one cluster only see their own data.

Choosing

When to use it, and when not

Use it when

  • You already run EMR pipelines that work and plan to migrate them to Databricks one subject at a time.
  • You need an open-source engine that Databricks does not offer, such as HBase, Hive LLAP or a long-running Trino cluster.
  • A team runs everything on Kubernetes and wants Spark jobs to share an existing EKS cluster through EMR on EKS.
  • A platform without Databricks needs Spark with full control over versions, configuration and instance types.
  • You need very large, steady batch jobs where tuned Spot fleets on EC2 make the bill noticeably lower, and the team can operate them.

Avoid it when

  • Avoid EMR for new pipelines on this platform; Databricks already provides the engine, catalog, quality rules and orchestration.
  • Avoid long-running EMR on EC2 clusters that sit mostly idle; you pay for every instance-second whether or not jobs run.
  • Avoid EMR on EKS unless you already run EKS well; it adds Kubernetes skills on top of Spark skills.
  • Avoid putting HDFS on core nodes as the main store; when the cluster ends or a node fails, that data is at risk.
  • Avoid two catalogs with two access models; if EMR must read platform tables, read them as Iceberg with clear, narrow permissions.

Production grade

What goes wrong in production

ProblemWhat breaksWhat to do
Spot interruptionsAWS reclaims Spot instances. If core nodes or the primary node are Spot, the cluster or its HDFS data can be lost mid-run.Keep the primary and core nodes On-Demand; put Spot only on task nodes; use instance fleets with many instance types across zones.
Idle clustersA cluster created for a nightly job is left running all day, or an interactive cluster is forgotten over a weekend.Use transient clusters that end after their steps, set an idle auto-termination, or move the job to EMR Serverless.
Release end of supportOld releases stop getting patches, and old Spark versions stop matching new connectors and table formats.Track releases per cluster and application. Upgrade with a parallel run, or treat the date as the migration deadline to Databricks.
Serverless quota surprisesA new account starts at 16 concurrent vCPUs for EMR Serverless; a big job queues or fails on its first day.Request a higher Max concurrent vCPUs per account quota before go-live and set a maximum capacity per application.
Shuffle and skewOne key, such as one very busy press, holds most of the rows; one task runs for an hour while others finish in a minute.Look at the Spark UI first. Turn on adaptive query execution, salt hot keys, and size shuffle storage for Serverless jobs.
Configuration drift between clustersEach cluster was launched by hand with slightly different settings, so the same job behaves differently in dev and prod.Define clusters and applications as code with CloudFormation, CDK or Terraform, and pin the release label.
Many small filesJobs write thousands of tiny files, and readers slow down.Write Iceberg tables and run compaction, or coalesce before writing.

Cost

How you pay

EMR charges per second with a one-minute minimum. On EC2 you pay the EC2 instance price, EBS storage and an EMR fee per instance-hour on top, and the EMR fee differs by instance type. Spot instances cut the EC2 part by up to 90 percent against On-Demand, at the risk of interruption. EMR Serverless bills vCPU-hours, GB-hours of memory and extra storage for the time workers run. EMR on EKS adds an EMR fee per vCPU and GB to the cost of the EKS nodes. Check the EMR pricing page for list prices in your region.

What drives the bill

  • Instance hours on EMR on EC2, including idle time between jobs and while clusters start.
  • The share of Spot versus On-Demand, and whether Savings Plans cover the steady part.
  • vCPU and memory per worker on Serverless, which is often set too high and never measured.
  • Shuffle-heavy jobs that need more disk and longer run time.
  • NAT gateway traffic when clusters in private subnets reach S3 without a gateway endpoint.

Cost traps

  • Clusters left running with no auto-termination.
  • Pre-initialised capacity on Serverless applications that keeps warm workers billing all day.
  • Running old EMR and new Databricks pipelines in parallel for longer than the agreed two weeks.
  • Comparing only the EMR fee with a Databricks DBU price, without the EC2, idle and operations time behind each.

Prices change; check the AWS pricing page for your region before deciding.

Security and governance

Keeping it safe

  • Give each cluster an EC2 instance profile with narrow S3 access, and use runtime roles so each job or step runs with its own IAM role.
  • Use an EMR security configuration to turn on encryption at rest for S3 and local disks and in-transit encryption between nodes, with KMS keys you own.
  • Launch clusters in private subnets with no public IPs; reach S3, STS and other AWS services through VPC endpoints. EMR Serverless can attach to your VPC for private sources.
  • Use Lake Formation or Apache Ranger integration only if EMR must enforce table and column permissions; avoid running that alongside Unity Catalog grants for the same tables.
  • CloudTrail logs EMR API calls; turn on S3 logging of step and application logs, and keep personal data tokenised before it reaches EMR outputs.

Decisions

Situations and verdicts

SituationChoiceVerdict

Forty existing EMR Spark jobs feeding warehouse loadsKeep them running; rebuild one subject at a time on Databricks, two-week parallel run, then switch offKeep if you have it: stable jobs keep running while the move happens in measured steps.
An HBase store that serves a product-lookup applicationKeep it on EMR, reading platform tables as Iceberg where neededKeep if you have it: Databricks does not run HBase, and moving the application is a separate decision.

FAQ

Questions people ask

What is the difference between EMR on EC2, EMR Serverless and EMR on EKS?

EMR on EC2 gives you a cluster of virtual machines you size and pay for while it runs. EMR Serverless has no cluster; you submit jobs and pay for the workers each job uses. EMR on EKS runs Spark jobs as pods on a Kubernetes cluster you already operate.

Is EMR cheaper than Databricks?

Per hour of machine, EMR on EC2 with Spot can look cheaper. The full comparison must include idle clusters, start-up time, the people who tune and patch them, and the governance, lineage and quality features you would rebuild. Measure a real pipeline both ways before deciding.

Does EMR support Spark 4?

Yes, through the AWS runtime for Apache Spark line: emr-spark-8.0.0 brought Spark 4.0.2 in May 2026, and emr-spark-8.1.0 carries Spark 4.1.1. The emr-7.x line stays on Spark 3.5.

Can EMR read Delta tables written by Databricks?

EMR includes Delta Lake and Iceberg libraries. On the reference platform the simpler path is UniForm, which lets Delta tables be read as Iceberg, with read-only access granted to the EMR role.

Should I use Spot instances on EMR?

Yes for task nodes on fault-tolerant batch jobs, using instance fleets with several instance types. Keep the primary and core nodes On-Demand so an interruption does not kill the cluster or lose data.
