Amazon Redshift (provisioned, Serverless, data sharing)

AWS's managed SQL data warehouse, as clusters or Serverless; on this platform kept for existing BI while new work moves to Databricks SQL.

RoleQuery, warehouse and APIs
StatusGenerally available. DC2 nodes are no longer available (docs removed 2 Nov 2026); RA3 and the new Graviton-based RG nodes (since May 2026) remain. Python UDFs reached end of support after 30 Jun 2026.
Verdict on this siteKeep if you have it

Google CloudBigQuery
DatabricksDatabricks SQL warehouse (serverless) on Delta tables in Unity Catalog
Open sourceNo direct match; ClickHouse, Trino over Iceberg, or PostgreSQL with columnar extensions for small cases
Verdict: Keep if you have it. If Redshift already serves many reports, keep it and let it read our tables as Iceberg through UniForm, or receive them through Delta Sharing, while reports move. Put new gold tables and new BI on the Databricks SQL warehouse, and shut the cluster down when the last report has moved.

In plain words

What it is

Amazon Redshift is a data warehouse: a database built for questions that read millions of rows and add them up, such as total sales by region and month, rather than for saving one order at a time. It stores data by column instead of by row, compresses it heavily, and spreads every query across many machines working in parallel. People connect to it with SQL from BI tools such as Power BI, Tableau or QuickSight.

It comes in two shapes. A provisioned cluster is a fixed set of nodes, which are servers, that you choose and pay for by the hour; the current node families are RA3 and the newer RG, both of which keep data in Redshift Managed Storage on S3 and cache hot data on local SSDs. Redshift Serverless has no nodes to pick: you set a base capacity in RPUs (Redshift Processing Units) and pay per second while queries run.

A retail example: a chain of 400 stores has run Redshift for six years. Every night a job loads point-of-sale lines, stock counts and promotions from SAP and the store systems. Two hundred reports in Tableau read from it, and the finance team has stored procedures that build the monthly margin pack. That is a working, valuable system. The question for this platform is not whether Redshift is good. It is whether to keep feeding it new work now that Databricks holds the governed gold tables.

Redshift can also share data. Data sharing lets one Redshift warehouse read another's tables live, without copying, even across accounts. Redshift can now read and write Apache Iceberg tables in S3, which is how it reaches Databricks tables on this platform.

A long-established department store with loyal customers; you keep it open while the new mall next door fills up, and you stop stocking new lines there.

Big picture

Where it fits

The lit lane is where Redshift works. Boxes on the left feed it; boxes on the right use what it produces.

Redshift sits in the serving lane beside the Databricks SQL warehouse and Athena. In the reference design Databricks builds bronze, silver and gold as Delta tables in S3. Redshift is not on the main path. It is kept where it already serves reports, and it reads the gold tables instead of having its own nightly loads rebuilt.

There are two ways for Redshift to read our tables. The first is UniForm: Databricks writes Iceberg metadata beside each Delta table, the Glue Data Catalog federates to Unity Catalog, and Redshift queries the tables as external Iceberg tables through a resource link in the default Glue catalog. The second is Delta Sharing, the open protocol Databricks uses to share tables with other tools; check how your Redshift version and tools consume it before relying on it. Either way, there is one copy of the data and Databricks owns it.

The migration plan on the reference platform is simple. New gold tables and new dashboards go on Databricks SQL, with Metric Views, Genie and AI/BI. Existing reports keep running on Redshift, reading from the lake. Reports move one by one. When the last one has moved, the cluster is shut down. Zero-ETL integrations, which copy Aurora, RDS or DynamoDB into Redshift automatically, are an AWS-native alternative path that this platform does not use.

How it works

The ideas you need

IdeaWhat it means
Columnar storageEach column is stored and compressed on its own, so a query that needs three columns out of eighty reads only those three.
RA3 and RG nodesCurrent provisioned node types. RA3 is Intel-based; RG is Graviton-based and arrived in May 2026. Both separate compute from Redshift Managed Storage.
Redshift Managed StorageThe storage layer behind RA3, RG and Serverless: data lives in S3 and hot blocks are cached locally. Billed per GB-month on its own.
RPURedshift Processing Unit, the capacity unit of Serverless. You set a base (from 4) and a maximum; billing is per RPU-hour, per second.
Distribution key and sort keySettings that decide which node holds each row and in what order rows are stored; good choices avoid moving data between nodes and let queries skip blocks.
WLMWorkload management: queues and priorities that decide which queries run now and which wait. Automatic WLM is the default.
Concurrency scalingExtra temporary capacity that Redshift adds when many queries queue; each cluster earns one free hour a day.
Data sharingLive, read-only access from one Redshift warehouse to another's tables without copying, across accounts and Regions.
SpectrumThe feature that queries data in S3 from Redshift. On RA3 it runs on a separate fleet; on RG it runs on the cluster's own nodes.

Choosing

When to use it, and when not

Use it when

  • You already run Redshift with many reports, stored procedures and trained users, and moving them all at once would be risky.
  • Existing Redshift reports need fresh numbers from the new gold tables, and reading them as Iceberg avoids building a second load pipeline.
  • A business unit outside the Databricks platform consumes data through Redshift data sharing and cannot change its tools this year.
  • You need an AWS-only warehouse with no Databricks at all, for example in a small separate account; then Serverless is the simplest start.

Avoid it when

  • You are starting new BI on this platform; the Databricks SQL warehouse reads gold directly with Unity Catalog masks, lineage and Genie.
  • You would have to load the same gold data into Redshift tables every night; that creates a second copy that drifts and costs twice.
  • You still rely on Python UDFs; they reached end of support after 30 June 2026, so rewrite them as SQL or Lambda UDFs first.
  • Data access rules live in Unity Catalog; Redshift does not enforce them, so you would maintain grants in two places.

Production grade

What goes wrong in production

ProblemWhat breaksWhat to do
Two warehouses, two truthsGold on Databricks and a separately loaded copy in Redshift drift apart; finance and sales report different margins.Never load gold into Redshift tables; read it as external Iceberg tables or through Delta Sharing, so there is one copy, and track which reports remain.
Slow external Iceberg queriesReports that were fast on local tables become slow on lake tables, especially on RG, where lake queries share the cluster's compute.Compact and cluster the Delta tables, keep UniForm metadata current, add materialized views in Redshift for hot reports, and size the RG cluster for lake load.
Queueing at month endFinance closes the month, hundreds of queries arrive, and WLM queues them; dashboards time out.Use automatic WLM with query priorities, turn on concurrency scaling with a usage limit, or use Serverless with a sensible maximum RPU.
Bad distribution and sort keysLarge joins shuffle data between nodes and scans read every block; one query takes the cluster down for minutes.Use AUTO distribution and sort keys, check SVV_TABLE_INFO for skew, and read the Advisor recommendations in the console.
DC2 and old node migrationOld DC2 clusters can no longer be bought or resized, and reserved nodes for them may not renew.Move to RA3, RG or Serverless by snapshot restore or elastic resize; test with the Redshift Test Drive tool first.
Python UDF end of supportReports that call Python UDFs fail once enforcement reaches the cluster.Find them in the system catalog and rewrite them as SQL UDFs or Lambda UDFs, or move the logic into Databricks gold.
Serverless bill creepA BI tool keeps sessions busy all day, so Serverless never idles and costs more than a small cluster would.Set a maximum RPU and a usage limit with alerts; compare a month of RPU-hours with a provisioned or reserved cluster.
Grants in two placesSomeone gets access to a column in Redshift that Unity Catalog masks; the governance story breaks.Expose only non-sensitive or pre-masked gold tables to Redshift through Lake Formation, and audit Redshift grants each quarter.

Cost

How you pay

Provisioned clusters bill per node-hour by node type, billed per second, plus Redshift Managed Storage per GB-month (0.024 US dollars per GB-month in the AWS example; list price, check your region). Reserved nodes for one or three years cut the hourly rate but are charged whether the cluster runs or is paused. Serverless bills per RPU-hour, per second, with a 60-second minimum, and includes lake queries; base capacity runs from 4 to 1,024 RPUs. Spectrum on RA3 is charged per TB scanned. Concurrency scaling beyond the free daily credit is charged per second. Snapshots beyond the free amount, data transfer and zero-ETL have their own charges.

What drives the bill

  • Node count and type, or RPU-hours on Serverless, which follow how long sessions keep the warehouse busy.
  • Managed storage volume, including tables nobody reads any more.
  • Concurrency scaling hours beyond the free credits.
  • Bytes scanned by Spectrum on RA3 when reports read lake tables.

Cost traps

  • Paying for a reserved cluster and Databricks SQL for the same reports during a migration that never finishes.
  • Loading gold into Redshift tables doubles storage and compute and adds a pipeline to maintain.
  • Paused clusters still pay for storage and reserved nodes.
  • Serverless with no maximum RPU or usage limit lets one runaway query or chatty BI tool set the bill.

Prices change; check the AWS pricing page for your region before deciding.

Security and governance

Keeping it safe

  • Use IAM roles for Redshift to read S3 and Glue, IAM Identity Center or IAM authentication for users, and role-based access control inside the database; avoid shared admin passwords and keep any secrets in Secrets Manager.
  • Encrypt clusters and Serverless namespaces with a customer-managed KMS key, and require SSL for all connections.
  • Keep the warehouse private: no public access, a subnet group in private subnets, and Redshift-managed VPC endpoints for other VPCs or accounts.
  • Turn on audit logging (connection, user and user-activity logs) to CloudWatch or S3; CloudTrail records API calls.
  • For personal data, expose only masked or non-sensitive gold tables through Lake Formation, and use Redshift dynamic data masking for any local tables that remain.

FAQ

Questions people ask

Can Redshift read Databricks Delta tables?

Yes, through Iceberg. Turn on UniForm so Delta tables also have Iceberg metadata, let the Glue Data Catalog federate to Unity Catalog, and query them in Redshift through a resource link in the default catalog. Delta Sharing is the other route; check tool support first.

Is Redshift being retired?

No. Redshift is active and gained Graviton RG nodes, Iceberg v3 reads and writes, and Iceberg materialized views in 2026. What is retired is the old DC2 node type and Python UDFs.

Redshift Serverless or provisioned?

Serverless suits uneven use and small teams because it bills only while queries run. A busy cluster used all day is usually cheaper as provisioned RG or RA3 nodes with reservations. Compare a month of real RPU-hours.

Should we migrate Redshift to Databricks?

On this platform, yes, gradually. New work goes to Databricks SQL, and existing reports move one by one while Redshift reads from the lake, so nothing is loaded twice.

What replaces Redshift Python UDFs?

SQL UDFs for simple logic, Lambda UDFs for code, or moving the logic upstream into Databricks gold tables.
