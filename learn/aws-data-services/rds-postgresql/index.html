Amazon RDS for PostgreSQL

Community PostgreSQL on a managed server AWS patches and backs up; a common DMS source, dropped as this platform's metadata store.

RoleOperational stores
StatusGenerally available. PostgreSQL 18 has been available since Nov 2025. PostgreSQL 13 left standard support on 28 Feb 2026 and is billed for Extended Support; PostgreSQL 14 follows on 28 Feb 2027.
Verdict on this siteKeep if you have it
AzureAzure Database for PostgreSQL flexible server
Google CloudCloud SQL for PostgreSQL
DatabricksLakebase (Databricks managed PostgreSQL)
Open sourcePostgreSQL
Verdict: Keep if you have it. Keep it as a source: MES, quality and ordering systems on RDS PostgreSQL are read by DMS with change capture into S3 landing. Drop it as the platform's metadata database: it has the same drawback as Aurora, one more AWS service to run, connect and back up, with no gain over Lakebase.

In plain words

What it is

Amazon RDS for PostgreSQL is ordinary PostgreSQL, the open-source relational database, running on a server that AWS manages. RDS stands for Relational Database Service. You pick an instance size, such as two virtual CPUs and 8 GiB of memory, and a storage volume, and AWS installs PostgreSQL, applies patches in a maintenance window you choose, takes daily backups and keeps transaction logs so you can restore to any second within your retention period.

Unlike Aurora, the storage is a normal block volume attached to one instance. For high availability you turn on Multi-AZ, which keeps a standby copy in another Availability Zone and fails over to it, usually within a minute or two. A newer Multi-AZ cluster option uses two readable standbys and fails over faster. Because it is community PostgreSQL, almost every extension and tool works the same way it does on your laptop.

A retail example: a regional chain runs its loyalty programme on RDS for PostgreSQL. It holds members, points balances and redemptions, and the loyalty app writes to it all day. The data platform needs those tables for customer analytics. It does not query the loyalty database during the day. DMS copies the tables once and then reads the change log, landing changes in S3, and Databricks builds bronze and silver from them, with names and emails masked by Unity Catalog policies.

A rented flat where the landlord fixes the boiler and keeps spare keys; you still choose the size and pay rent whether you are home or not.

Big picture

Where it fits

The lit lane is where RDS PostgreSQL works. Boxes on the left feed it; boxes on the right use what it produces.

On the reference platform RDS for PostgreSQL is mainly a source. Operational systems such as MES, quality, loyalty and ordering run on it, owned by application teams. The ingestion pattern is DMS: a full load followed by ongoing change data capture into the S3 landing area, using PostgreSQL logical replication. Small reference tables without change capture can instead be pulled by the platform's own puller job in Databricks. Occasional exploratory queries can use Lakehouse Federation from Databricks without copying.

It was also on the list for the metadata database, the relational store that declares sources, datasets, rules and owners and holds watermarks and the run log. RDS was marked Drop for that role. It is cheaper and simpler than Aurora, with slower failover and no automatic scaling, but it has the same drawback: one more AWS service to run, connect privately and back up. Lakebase, a managed PostgreSQL inside Databricks, was chosen on 4 Nov.

It should not become a live store for the fast lane either. Exposing an RDS table through Lakehouse Federation while the live app reads it directly was marked Drop on the real-time mode page: governance on paper only.

How it works

The ideas you need

IdeaWhat it means
DB instanceOne managed server running PostgreSQL, with a size you choose and pay for by the hour whether busy or idle.
Multi-AZA synchronous standby in another Availability Zone that takes over if the primary fails; the standby serves no reads in the classic option.
Read replicaAn asynchronous copy that serves reads, in the same or another Region; it can lag behind the primary.
Parameter groupThe set of PostgreSQL settings for an instance, such as rds.logical_replication, which DMS change capture needs turned on.
Logical replicationPostgreSQL's way of publishing row changes from its write-ahead log so tools like DMS can stream inserts, updates and deletes.
Replication slotA marker that holds write-ahead log until the consumer has read it; if the consumer stops, log files pile up and fill the disk.
Extended SupportPaid patching for a major version after its end of standard support, charged per vCPU-hour and rising in year three.
Blue/green deploymentA managed copy kept in sync with production, used to test a major upgrade and switch over in about a minute.

Choosing

When to use it, and when not

Use it when

  • An application needs community PostgreSQL with managed patching and backups, and the load is small and steady.
  • A source system already runs on it; read it with DMS change capture and leave it alone.
  • You need a specific PostgreSQL extension or version that Aurora does not yet offer.
  • Cost matters more than very fast failover, and a minute or two of failover is acceptable.

Avoid it when

  • It would be a new metadata database for this platform; Lakebase was chosen and RDS was marked Drop.
  • You need many readers sharing one storage copy, or storage that grows on its own past 64 TiB; use Aurora.
  • The workload is analytics over millions of rows; that belongs on Delta tables and a SQL warehouse.
  • Load is idle most of the day; a provisioned instance bills every hour, while Aurora Serverless v2 can pause.
  • It would hold the fast lane's live values behind Lakehouse Federation; the site marks that Drop.

Production grade

What goes wrong in production

ProblemWhat breaksWhat to do
Disk filled by a stalled slotA DMS task stops but its replication slot stays; write-ahead log grows until the volume fills and the database stops writing.Alarm on OldestReplicationSlotLag and TransactionLogsDiskUsage, turn on storage autoscaling with a maximum, and drop slots of retired tasks.
CDC not enabledDMS cannot capture changes because rds.logical_replication is off or tables lack primary keys.Set the parameter in a custom parameter group and reboot in a window; agree primary keys with the application team.
Extended Support billAn instance on PostgreSQL 13 moved into Extended Support on 1 Mar 2026 and the bill rose with no change in use.Track the release calendar and upgrade with blue/green deployments; PostgreSQL 14 enters Extended Support on 1 Mar 2027.
Heavy reads from the platformAnalysts query the live database directly through Federation or a BI tool and slow the application.Read through DMS into S3 instead, or point federated queries at a read replica.
Burstable instance throttlesA db.t-class instance runs out of CPU credits during a big DMS full load and crawls.Use a general-purpose instance for production sources, or schedule the full load out of hours.
Failover drops the CDC slot positionAfter a Multi-AZ failover, logical replication slots may need to be recreated depending on version, and DMS needs a restart.Use versions that sync slots to the standby where available, and test DMS behaviour after a forced failover.
Storage cannot shrinkA volume grown for a one-off load stays at that size and keeps billing.Size storage autoscaling with a sensible maximum; shrinking needs a dump and restore or blue/green to a smaller volume.

Alternatives

What to compare it with

AlternativePick the alternative whenPick RDS PostgreSQL when
Amazon Aurora PostgreSQLYou need faster failover, up to 15 readers on shared storage, storage beyond 64 TiB or a database that pauses when idle.A small, steady database is enough and you want the lowest cost.
Lakebase (Databricks managed PostgreSQL)The database is for the platform itself, such as metadata, or a live store that must be in Unity Catalog.The database belongs to an application team running on AWS.
Self-managed PostgreSQL on EC2You need superuser access, unusual extensions or settings RDS does not allow.You want patching, backups and failover done for you.
Azure Database for PostgreSQL flexible serverYou are running the same workload on Azure.You are on AWS.
Google Cloud SQL for PostgreSQLYou are running the same workload on Google Cloud.You are on AWS.

Cost

How you pay

You pay per instance-hour by instance class, doubled for a Multi-AZ standby, plus storage per GB-month by type (gp3 or io2) and any provisioned IOPS or throughput above the baseline. Backup storage up to the database's size is included; beyond that it bills per GB-month. Read replicas bill as separate instances. Extended Support adds a charge per vCPU-hour for major versions past their end of standard support. Reserved instances and Database Savings Plans lower the hourly rate for steady use. List prices, check your region.

What drives the bill

  • Instance class and whether Multi-AZ doubles it.
  • Allocated storage and provisioned IOPS.
  • Number of read replicas.
  • Backup retention and manual snapshots.
  • Extended Support for old major versions.

Cost traps

  • Extended Support charges for PostgreSQL 11, 12 and 13 instances nobody upgraded.
  • Storage that autoscaled during a full load and never shrinks.
  • A read replica created for one report and forgotten.
  • Manual snapshots kept forever, billed per GB-month.

Prices change; check the AWS pricing page for your region before deciding.

Security and governance

Keeping it safe

  • Keep instances in private subnets with public access off, and allow only the DMS replication instance's and the application's security groups.
  • Encrypt storage with a KMS key at creation; an unencrypted instance needs a snapshot copy and restore to encrypt.
  • Store the DMS user's credentials in Secrets Manager with rotation, or use IAM database authentication; grant only replication and SELECT rights.
  • Force TLS with rds.force_ssl and use the current RDS certificate authority bundle.
  • Enable pgAudit or log_statement settings for tables with personal data, and send logs to CloudWatch Logs.
  • Mask personal data on the platform side with Unity Catalog policies after it lands; the source owner keeps responsibility for the source.

FAQ

Questions people ask

Is RDS for PostgreSQL the same as Aurora PostgreSQL?

No. Both run PostgreSQL for the application, but RDS uses a normal volume on one instance while Aurora uses shared, self-healing storage across three zones. Aurora fails over faster and scales reads further; RDS is cheaper and simpler.

When does PostgreSQL 14 on RDS leave standard support?

On 28 Feb 2027, per the RDS release calendar. From 1 Mar 2027 it is billed for Extended Support until 28 Feb 2030. PostgreSQL 13 already moved on 1 Mar 2026.

How do I get RDS PostgreSQL data into Databricks?

Use DMS for a full load and change capture into S3 landing, then build bronze and silver in Databricks. For small tables without change capture, a scheduled pull job works, and Lakehouse Federation suits occasional queries.

Why not use RDS PostgreSQL for the metadata store?

It would work, but it adds an AWS service to run, connect privately and back up. Lakebase gives the same PostgreSQL inside Databricks, governed by Unity Catalog.
