Amazon Timestream (LiveAnalytics and for InfluxDB)

AWS's time-series databases: LiveAnalytics, closed to new customers, and managed InfluxDB 2 and 3; dropped as the live store here.

RoleOperational stores
StatusTimestream for LiveAnalytics: closed to new customers since 20 Jun 2025; existing customers continue. Timestream for InfluxDB: generally available, with InfluxDB 3 Core and Enterprise since Oct 2025 and Enterprise clusters of up to 15 nodes since Mar 2026.
Verdict on this siteDrop
AzureAzure Data Explorer, or Eventhouse in Microsoft Fabric
Google CloudBigtable for time-keyed data, or BigQuery
DatabricksDelta tables with liquid clustering on time and device; Lakebase for latest values
Open sourceInfluxDB, TimescaleDB, QuestDB, Prometheus for metrics
Verdict: Drop. LiveAnalytics is closed to new customers, so it is not an option. Timestream for InfluxDB works, but it means instances to size and Influx skills to learn, while DynamoDB already holds the live board's latest values and 48-hour chart for about $50 a month, and history lives in Delta tables. Revisit only if the team already runs InfluxDB.

In plain words

What it is

A time-series database stores measurements stamped with a time, such as a temperature every second from each press, and is built to answer questions like the average per minute over the last hour, or the latest value for each sensor. It writes very fast, compresses repeated readings well, and has functions for time windows, gaps and interpolation.

Amazon Timestream is the name for two different products. Timestream for LiveAnalytics is AWS's own serverless engine with a memory tier for recent data and a magnetic tier for history. AWS closed it to new customers on 20 Jun 2025. Existing customers can keep using it and add users and accounts under the same payer account, but a new platform cannot sign up. Timestream for InfluxDB is AWS running the open-source InfluxDB engine for you. It offers InfluxDB 2, a single instance or a Multi-AZ pair, and InfluxDB 3, built on Apache Arrow and Parquet files in S3, in a Core edition for recent data and an Enterprise edition with clusters, compaction and long history.

A manufacturing example: a mixing line has 40 sensors, each sending a reading every second. Engineers want a chart of the last six hours and alerts when viscosity drifts. A time-series database would hold those readings and answer the chart query in milliseconds. On this platform, though, the same need is already covered: the live board's chart comes from DynamoDB, and the long history from silver and gold Delta tables in Databricks.

A lab notebook with a page per sensor and a line per second, indexed by the clock, instead of a filing cabinet indexed by customer.

Big picture

Where it fits

The lit lane is where Timestream works. Boxes on the left feed it; boxes on the right use what it produces.

Timestream appears in one place on the site: the comparison of live stores for the streaming design's fast lane. That lane takes plant readings from Kinesis through Managed Flink and must put the latest state and a 48-hour chart on screens within seconds. DynamoDB won that comparison, with Lakebase as the alternative. Timestream for LiveAnalytics was marked Drop because it is closed. Timestream for InfluxDB was marked Drop unless the team already knows Influx, because it brings instances to size and new skills for a job DynamoDB already does.

History is a separate question, and the answer there is the lakehouse. Every reading lands in bronze through the platform lane, is cleaned into silver and summarised into gold. Delta tables clustered on time and device answer historical questions at much lower storage cost and stay governed in Unity Catalog. A time-series database would be a second copy of that history to secure and pay for.

If a platform already runs Timestream for LiveAnalytics, the plan is migration, not growth. AWS recommends InfluxDB 3 Enterprise for most LiveAnalytics workloads and InfluxDB 2 for small, low-latency monitoring. On this platform the simpler path is usually to move the live part to DynamoDB and the history to Delta tables.

How it works

The ideas you need

IdeaWhat it means
Time seriesA sequence of readings from one source over time, such as press 17's temperature, identified by its tags.
Measurement and tagsIn InfluxDB, a measurement is like a table; tags are indexed labels such as plant and press; fields are the readings themselves.
CardinalityThe number of distinct series, meaning distinct tag combinations. High cardinality, such as one series per tyre serial number, strains InfluxDB 2.
Retention periodHow long data is kept before it is deleted automatically, such as 30 days of one-second readings.
DownsamplingRolling raw readings up into coarser ones, such as one-minute averages, to keep history small.
Memory and magnetic storeLiveAnalytics' two tiers: a fast tier for recent writes and a cheaper tier for history, moved by retention settings.
InfluxDB 3 Core and EnterpriseCore is a single node aimed at recent data with no compaction; Enterprise adds clusters of up to 15 nodes, read replicas, compaction and long history.
Flux, InfluxQL and SQLQuery languages: InfluxDB 2 uses Flux and InfluxQL; InfluxDB 3 uses SQL and InfluxQL, not Flux.

Choosing

When to use it, and when not

Use it when

  • You already run Timestream for LiveAnalytics; keep it working and plan a migration, since it will not take new customers.
  • The team already runs InfluxDB and its tools, such as Telegraf agents and Grafana dashboards, and wants AWS to manage the servers.
  • Engineers need fast ad hoc time-window queries on recent readings that DynamoDB's key lookups cannot answer and ClickHouse is not an option.
  • An operations team monitors equipment health metrics outside the data platform and wants a familiar time-series engine.

Avoid it when

  • You are a new customer looking at Timestream for LiveAnalytics; it is closed to you.
  • The need is a live board with latest values and a 48-hour chart; DynamoDB does that for about $50 a month.
  • The need is long history and analytics; Delta tables in Unity Catalog are cheaper and governed.
  • Nobody on the team knows Influx; Flux, InfluxQL and InfluxDB 3 SQL each have their own habits.
  • Ingest will exceed about 1 million records a second on one cluster; AWS says InfluxDB 3 Enterprise would then need sharding across clusters.

Production grade

What goes wrong in production

ProblemWhat breaksWhat to do
Closed serviceA design document still lists Timestream for LiveAnalytics; a new account cannot create it.Remove it from options. Existing users should follow AWS's migration guide to InfluxDB, or move live data to DynamoDB and history to Delta.
Cardinality blow-upSomeone tags readings with a batch id or tyre serial, the number of series explodes and InfluxDB 2 slows down or runs out of memory.Keep identifiers with many values as fields, not tags. Use InfluxDB 3 if very high cardinality is truly needed.
Core used for historyA team keeps months of data in InfluxDB 3 Core, which has no compaction, and queries get slower over time.Use Core only for recent data, typically a few days; use Enterprise for longer history, or keep history in Delta.
Query dialect surprisesQueries written for LiveAnalytics or Flux do not run unchanged on InfluxDB 3.Test every business-critical query on a development instance before migrating, as AWS's guide advises.
Sizing instancesTimestream for InfluxDB bills instances and storage like a database server, and an undersized instance drops writes at peak.Load-test at peak write rate with realistic tags; watch CPU and memory; size for the morning shift change, not the average.
A second copy of historyReadings are kept both in the time-series database and in Delta tables, doubling storage and access reviews.Set a short retention period in the time-series store and treat Delta as the record.

Cost

How you pay

Timestream for InfluxDB bills like a database server: per instance-hour by instance size, per GB-month of storage, and for Multi-AZ standbys or extra cluster nodes. InfluxDB 3 keeps data as Parquet in S3-backed storage, and Enterprise is billed per node in the cluster. Timestream for LiveAnalytics, for existing customers only, bills for writes, memory-store and magnetic-store storage, and query compute. The site estimates Timestream for InfluxDB at about $100 or more a month for a small live store; list prices, check your region.

What drives the bill

  • Instance size and count, which must cover peak write rate.
  • Retention period and raw resolution, which set storage.
  • Edition: Enterprise clusters cost more than a single Core node.
  • Multi-AZ or read replicas for availability.

Cost traps

  • Running a time-series store and Delta history side by side pays twice for the same readings.
  • Instances sized for the peak stay on all month.
  • High-cardinality tags force a bigger instance than the data volume suggests.
  • Long retention of one-second readings when one-minute averages would do.

Prices change; check the AWS pricing page for your region before deciding.

Security and governance

Keeping it safe

  • Deploy Timestream for InfluxDB instances in private subnets with no public access, and limit inbound traffic to named security groups.
  • Encryption at rest is on; use a customer managed KMS key if your policy requires it, and require TLS from clients.
  • Store the InfluxDB admin token and user credentials in Secrets Manager; do not share one all-powerful token across jobs.
  • Use IAM policies for the AWS control plane and InfluxDB's own users and tokens for data access; review both.
  • CloudTrail records management calls; sensor readings rarely hold personal data, but operator ids attached as tags would, so keep them out.

FAQ

Questions people ask

Is Amazon Timestream being discontinued?

Timestream for LiveAnalytics closed to new customers on 20 Jun 2025; existing customers keep running and AWS still maintains it. Timestream for InfluxDB is open and growing, with InfluxDB 3 added in Oct 2025.

What should I use instead of Timestream for LiveAnalytics?

AWS recommends Timestream for InfluxDB 3 Enterprise for most workloads, and InfluxDB 2 for small, low-latency monitoring. On this platform, DynamoDB serves live values and Delta tables hold history.

Is InfluxDB 3 SQL the same as Timestream SQL?

No. InfluxDB 3 supports standard SQL through Apache DataFusion and InfluxQL, but AWS states the dialect does not match LiveAnalytics one to one. Test queries before moving.

Can Databricks read Timestream?

Not natively as a governed source. Export data to S3 or write the same stream into bronze through the platform lane, which this design already does.
