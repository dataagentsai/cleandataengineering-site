Amazon Simple Notification Service (SNS)

A managed publish and subscribe service that pushes each message to every subscriber: queues, functions, email, SMS and HTTPS endpoints.

RoleStreaming and events
StatusGenerally available. The default maximum message size is still 256 KiB, but a topic can now be set to accept up to 1 MiB.
Verdict on this sitePursue
AzureEvent Grid (and Azure Monitor action groups for alerts)
Google CloudPub/Sub push subscriptions (and Cloud Monitoring notification channels)
Databricksnone: Databricks job and SQL alert notifications cover alerts inside Databricks
Open sourceApache Kafka for fan-out, or Alertmanager for alerts
Verdict: Pursue. Pursue for alerts: CloudWatch alarms on the AWS movers page on-call through SNS, and the fast lane sends SMS and email alerts through it. Drop it as a log for analytics: SNS pushes and forgets, so standard topics have no replay and no reader can catch up later. Kinesis Data Streams carries the events.

In plain words

What it is

Amazon SNS is a publish and subscribe service. A producer publishes a message to a topic, which is a named channel such as plant-alerts. Every subscriber to that topic receives its own copy straight away. Subscribers can be SQS queues, Lambda functions, Amazon Data Firehose streams, HTTPS endpoints, email addresses, phone numbers for SMS, and mobile apps. The producer does not know or care who is listening; adding a new subscriber needs no change to the producer.

SNS pushes. It does not wait for subscribers to ask. If a subscriber is down, SNS retries for a while according to a delivery policy, and after that the message can go to a dead-letter queue, which is an SQS queue that catches failed deliveries. A standard topic does not keep messages after delivery. That is the key difference from a log such as Kinesis: once SNS has delivered, there is nothing left to re-read.

Subscribers can also filter. A filter policy is a small JSON rule on a subscription, such as only messages where severity is critical and plant is Pune. SNS checks each message against each filter and delivers only matches. There are also FIFO topics, which keep strict order per message group, remove duplicates and, unlike standard topics, can archive messages and replay them to subscribers.

A concrete example from a manufacturing plant: a CloudWatch alarm watches how far behind the readers of the sensor stream are. When the lag passes five minutes, the alarm publishes to an SNS topic called platform-oncall. That topic sends an SMS to the engineer on call, an email to the data team list, and a copy to an SQS queue that a small function reads to open a ticket. One alarm, three channels, no custom code in the alarm.

A public address system in a factory: one announcement, heard at once by everyone tuned in, and not recorded for later.

Big picture

Where it fits

The lit lane is where SNS works. Boxes on the left feed it; boxes on the right use what it produces.

On the reference platform SNS lives in the observability and alerting corner, not in the data lanes. The platform design routes CloudWatch alarms for the AWS movers, such as DMS lag, AppFlow failures, SiteWise ingestion and Kinesis reader delay, to on-call through Amazon SNS. Databricks job notifications and SQL alerts cover what happens inside Databricks, and both end up in the same team channel and pager.

In the streaming fast lane, SNS is one of the alert outlets. The site's streaming design lists SNS for SMS and email and EventBridge for routing to ticketing and chat tools, both marked Pursue for alerts. In the lightest fast-lane option, Kinesis readings go to a Lambda that checks limits and publishes to SNS when a press runs too hot, with no Flink at all.

SNS also appears in plumbing you may not build yourself. Databricks Auto Loader, in file notification mode, can set up S3 event notifications that flow through SNS into SQS, so that several queues can receive the same bucket events. What SNS is not, here, is a source for analytics. The site's verdict is that SQS, SNS and EventBridge are dropped as the log, because a pushed message cannot be replayed or read by a second consumer that joins later.

How it works

The ideas you need

IdeaWhat it means
TopicA named channel that producers publish to; SNS delivers each message to every subscription on it.
SubscriptionOne endpoint attached to a topic: an SQS queue, a Lambda function, a Firehose stream, an HTTPS URL, an email address, a phone number or a mobile app.
Fan-outThe pattern of sending one message to many consumers at once, typically several SQS queues that each process it in their own way.
Filter policyA JSON rule on a subscription that lets through only messages whose attributes or body match, so each subscriber gets only what it needs.
Delivery policyRules for how often and how long SNS retries an HTTPS endpoint that fails before giving up.
Dead-letter queueAn SQS queue attached to a subscription that keeps messages SNS could not deliver, so they are not silently lost.
FIFO topicA topic that keeps strict order per message group, removes duplicates, and can archive and replay messages; it delivers only to SQS queues and a few other targets.
Message archiving and replayA FIFO-only feature that keeps published messages for a set period so a subscriber can ask for them again.

Choosing

When to use it, and when not

Use it when

  • Use it to send alarm notifications from CloudWatch to the people on call by SMS, email or a paging tool's HTTPS endpoint.
  • Use it to fan one event out to several SQS queues, so each team or function processes the same notice independently.
  • Use it when a simple rule-based alert in the fast lane, such as pressure above limit, must reach operators' phones within seconds.
  • Use it to deliver S3 event notifications to more than one queue, for example one for Auto Loader and one for an audit function.
  • Use a FIFO topic with SQS FIFO queues when several services must receive the same commands in the same order.

Avoid it when

  • Avoid it as the event log for analytics: a standard topic keeps nothing after delivery, so there is no replay and no late-joining reader.
  • Avoid it for high-volume sensor data; per-message and per-delivery charges add up, and Kinesis is designed for that volume.
  • Avoid it as the main channel to a chat tool or incident system when you need content-based routing to many SaaS targets; EventBridge API destinations do this better.
  • Avoid SMS for anything non-critical: it costs per message, has a low default spend limit and country-specific rules.

Production grade

What goes wrong in production

ProblemWhat breaksWhat to do
Alert stormsA flapping alarm or a broken check publishes hundreds of messages, phones buzz all night and people start to ignore alerts.Alarm on sustained conditions with several evaluation periods, use composite alarms, and send only critical severity to SMS.
SMS stops sendingNew accounts start in the SMS sandbox and have a spend threshold of 1 US dollar a month, so alerts silently stop once it is reached.Leave the sandbox, raise the spend threshold through a quota request, and alarm on SMSMonthToDateSpentUSD and NumberOfNotificationsFailed.
Email delivery throttledEmail subscriptions are limited to 10 messages a second each, a hard limit; a burst of alerts queues up or fails.Use email only for summaries; send bursts to an SQS queue or a paging service over HTTPS.
Lost deliveriesAn HTTPS subscriber is down longer than the retry policy, and messages are dropped with only a metric to show for it.Attach a dead-letter queue to every important subscription and alarm on NumberOfNotificationsRedrivenToDlq.
Unconfirmed subscriptionsEmail and HTTPS subscriptions must be confirmed; someone forgets, and the on-call list never gets alerts.Use SQS or Lambda subscriptions for machine paths, review pending subscriptions, and test alerts with a monthly fire drill.
Filter policy mistakesA typo in a filter policy means a subscriber receives nothing, or everything.Keep filter policies in infrastructure code, test them with sample messages, and watch NumberOfNotificationsFilteredOut.
Message too largeAlert messages that include full payloads exceed the default 256 KiB and publishing fails.Send a short summary and a link; if needed raise the topic's MaximumMessageSize to 1 MiB or use the extended client with S3.

Cost

How you pay

SNS bills per publish request and per delivery. Each 64 KB chunk of a published message counts as one request. Deliveries are priced by endpoint type: deliveries to SQS and Lambda carry no per-message charge, though data transfer is billed, HTTPS and email deliveries carry a small per-million charge, and SMS and mobile push are priced per message by destination country and carrier. FIFO topics are billed on published messages, on subscription messages and on payload data. Filtering on attributes is free; filtering on the message body is billed on data scanned. FIFO archiving is billed on data stored and days kept. Use list prices from the pricing page and check your region.

What drives the bill

  • The number of messages published and their size in 64 KB chunks.
  • The number of subscriptions each message is delivered to, and their endpoint types.
  • SMS volume and destination countries, usually the biggest line for alerting.
  • FIFO archiving retention and replays, if used.

Cost traps

  • An alert storm sent by SMS can cost more in a night than the topic costs in a year.
  • Fan-out multiplies cost: one message to 20 subscriptions is 20 deliveries.
  • Using SNS to carry sensor readings bills every reading, where Kinesis bills by throughput.
  • Data transfer to HTTPS endpoints outside AWS is charged on top of delivery charges.

Prices change; check the AWS pricing page for your region before deciding.

Security and governance

Keeping it safe

  • Control who can publish and subscribe with IAM and a topic access policy; allow CloudWatch or S3 to publish only with aws:SourceArn and aws:SourceAccount conditions.
  • Turn on server-side encryption with a KMS key; publishers such as CloudWatch alarms then need permission to use that key, a common cause of silent failures.
  • Use an interface VPC endpoint for SNS so functions and clusters in private subnets publish without going through a NAT gateway.
  • Require HTTPS endpoints for webhook subscriptions and verify SNS message signatures on the receiving side.
  • SNS data protection policies can detect and mask personal data such as phone numbers or emails in messages; keep alert text free of customer details anyway.
  • Publish and subscription changes are recorded in CloudTrail; review who can add subscriptions, because a new email subscriber receives every alert.

FAQ

Questions people ask

What is the difference between SNS and SQS?

SNS pushes one message to many subscribers at once; SQS holds messages until one consumer pulls and deletes each one. They are often used together: SNS fans a message out to several SQS queues, and each queue's consumer works at its own pace.

Can SNS replay messages?

Only FIFO topics, which support message archiving and replay to subscribers. Standard topics keep nothing after delivery. For data that analytics may need to re-read, use Kinesis Data Streams or Kafka.

What is the SNS message size limit?

256 KiB by default. You can raise a topic's MaximumMessageSize attribute to 1 MiB, and use the extended client library to send payloads up to 2 GB through S3.

Why did my SNS SMS alerts stop?

Most often the account is still in the SMS sandbox or has hit the default monthly spend threshold of 1 US dollar. Request production access and a higher spend limit, and alarm on SMSMonthToDateSpentUSD.

Should I use SNS or EventBridge for alerts?

Use SNS for direct push to SMS, email and SQS. Use EventBridge when alerts must be routed by their content to many targets such as ticketing systems or chat tools. Many platforms use both, as this site's design does.
