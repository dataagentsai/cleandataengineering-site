AWS Glue Workflows and triggers

Chains Glue jobs and crawlers with triggers on a schedule, on demand or on an event, inside the Glue console.

RoleOrchestration
StatusGenerally available; no announced retirement. Starting a workflow from an Amazon EventBridge event, with batching of events, is supported.
Verdict on this siteDrop
AzureAzure Data Factory pipelines and triggers
Google CloudCloud Composer or Workflows
DatabricksLakeflow Jobs (tasks, triggers, run history)
Open sourceApache Airflow, Dagster
Verdict: Drop. Glue Workflows only orchestrate Glue jobs and crawlers, and this platform does not use Glue jobs for transformation. Lakeflow Jobs runs every Databricks task, and EventBridge handles AWS-side triggers, so a third orchestrator adds nothing but another place to look when a run fails.

In plain words

What it is

Orchestration means running steps in the right order at the right time: first load the orders, then load the customers, and only when both have finished, build the daily sales table. If a step fails, stop and tell someone. A tool that does this is an orchestrator.

AWS Glue Workflows is the orchestrator built into AWS Glue. A workflow is a small graph of three kinds of things. Jobs are Glue ETL scripts. Crawlers scan files in S3 and record their tables in the Glue Data Catalog. Triggers decide when the next thing starts. A trigger can fire on a schedule written as a cron expression, on demand when someone presses start, on an event from Amazon EventBridge such as a file arriving in S3, or conditionally when earlier jobs or crawlers succeed, fail or stop.

A concrete example from a retailer. At two in the morning a scheduled trigger starts a crawler over last night's point-of-sale files. When the crawler succeeds, a conditional trigger starts two Glue jobs in parallel, one for store sales and one for returns. When both succeed, another conditional trigger starts a job that builds the daily margin table. The Glue console draws this as a graph and shows each run with the status of every node.

Workflows can also carry run properties, which are small named values that every job in the run can read and update, such as the business date being processed. Blueprints let you generate many similar workflows from one template with parameters.

A line of dominoes set up inside one room: neat for the pieces in that room, but it cannot knock over anything outside it.

Big picture

Where it fits

The lit lane is where Glue Workflows works. Boxes on the left feed it; boxes on the right use what it produces.

Glue Workflows sit in the orchestration band that runs across every lane of the platform. In a Glue-centred AWS design, they start crawlers after files land, run the bronze, silver and gold Glue jobs in order, and refresh the catalog for Athena and Redshift Spectrum.

On this site's reference platform the processing engine is Databricks, so the orchestrator lives there too. Lakeflow Jobs runs the lander, silver, gold, quality checks and metric view refreshes, with schedules, file-arrival and table-update triggers, retries, alerts and run history in system tables. On the AWS side, Amazon EventBridge reacts to events such as a DMS task finishing or a file landing, and calls the Databricks Jobs API. Step Functions is used only when a mover needs several AWS steps. Glue Workflows have no job to do in that picture, which is why the site marks them Drop.

If a company already runs Glue Workflows, they retire together with the Glue jobs they drive. As each subject is rebuilt as a Databricks pipeline and its parallel run reconciles, the matching workflow is disabled and then deleted. There is no reason to rebuild a Glue workflow to call Databricks.

How it works

The ideas you need

IdeaWhat it means
WorkflowA named graph of Glue jobs, crawlers and triggers that runs as one unit and has its own run history.
TriggerThe thing that starts jobs or crawlers. Types are scheduled, on demand, EventBridge event and conditional.
Conditional triggerFires when watched jobs or crawlers reach a state such as succeeded, failed, stopped or timed out, with all or any logic.
Start triggerThe first trigger of a workflow. Each workflow has one start trigger, which is scheduled, on demand or an EventBridge event.
Event batchingFor an EventBridge start trigger, wait for a number of events (1 to 100) or a time window (up to 900 seconds) before starting one run.
Run propertiesSmall named values shared by all jobs in one workflow run, such as the business date, readable and writable from job code.
BlueprintA template plus a Python script that generates a workflow from parameters, so many similar pipelines share one definition.
ResumeAfter fixing a failed node, you can resume a workflow run from that node instead of starting over.

Choosing

When to use it, and when not

Use it when

  • You already run Glue jobs and crawlers chained by workflows, and they will keep running only until the Databricks migration of each subject.
  • A small AWS-only team needs a few Glue jobs in order and has no other orchestrator in the account.
  • Several Glue jobs must start after a crawler has updated the catalog, and everything involved is inside Glue.
  • You want a simple graph view of Glue runs in the console without adding Airflow or Step Functions.

Avoid it when

  • Avoid Glue Workflows when the work runs in Databricks; Lakeflow Jobs orchestrates Databricks tasks natively with lineage and run history.
  • Avoid them when a pipeline spans many AWS services or outside systems; a workflow can only run Glue jobs and crawlers.
  • Avoid them when you need rich branching, loops over a list of datasets or human approval steps.
  • Avoid them for event-heavy ingestion where duplicates matter; Glue does not guarantee delivery or remove duplicate EventBridge events.
  • Avoid building new blueprints as your metadata framework; the reference design keeps that framework in Databricks.

Production grade

What goes wrong in production

ProblemWhat breaksWhat to do
Silent partial runsA conditional trigger waits for all upstream jobs; one fails, the downstream job never starts, and nobody notices because the workflow is not marked as an alert.Send Glue job state changes from EventBridge to an alert channel. Add an explicit on-failure trigger that notifies the owner.
Lost or doubled eventsGlue does not guarantee delivery of EventBridge events and does not remove duplicates, so a file can be processed twice or not at all.Make every job idempotent and keep a file log of what was processed. Reconcile counts against the source each day.
Failed batch is not retriedWith event batching, if the run started by a batch fails, those events are not retried; a new run starts only when the next batch arrives.Record which files each run covered and replay them with a manual run after a failure.
Large graphs become slow and fragileAWS recommends keeping a workflow to 100 or fewer jobs, crawlers and triggers combined. Large graphs are hard to read and slow to load.Split by subject area. Better, move orchestration to Lakeflow Jobs during the migration.
Crawler schema driftA crawler sees a new column or a changed type and changes the table; the next job in the workflow breaks.Set the crawler to log rather than update on schema change, or drop crawlers and let the job write the table definition.
Changes made by hand in the consoleSomeone edits a trigger in production; the change is not in Git, and the next deployment silently reverses it.Define workflows in CloudFormation, CDK or Terraform and block console edits in production with IAM.
Two orchestrators during migrationSome subjects run in Glue Workflows and some in Lakeflow Jobs; a gold table depends on both and runs before its input is ready.Use a table-update or file-arrival trigger in Lakeflow Jobs on the Glue output, so the dependency is on data, not on a clock.

Alternatives

What to compare it with

AlternativePick the alternative whenPick Glue Workflows when
Databricks Lakeflow JobsThe work runs in Databricks. It is the reference orchestrator: tasks, triggers, retries, alerts and run history in system tables, deployed with Asset Bundles.Never on this platform; Glue Workflows only make sense if all the work is Glue jobs.
Amazon EventBridge Scheduler and rulesYou need to start a mover or a Databricks job on a schedule or when an AWS event happens, with no graph.You need several Glue jobs in a fixed order with shared run properties.
AWS Step FunctionsA flow crosses several AWS services, such as starting an AppFlow flow, waiting, calling a Lambda and then a Databricks job.Everything is a Glue job or crawler and you want the Glue console view.
Amazon MWAA (managed Airflow)The company already runs Airflow and orchestrates many systems beyond AWS and Databricks.You want nothing to operate and only chain a few Glue jobs.
Azure Data Factory pipelines or Google Cloud ComposerThe platform is on Azure or Google Cloud; these are the closest equivalents there.Your data and accounts are on AWS.

Cost

How you pay

Glue Workflows and triggers carry no separate charge. You pay for what they start: Glue job DPU-hours, crawler DPU-hours and Data Catalog requests and storage, at the list prices for your region. EventBridge events that start workflows are billed by EventBridge. So the cost of a workflow is the cost of its jobs and crawlers, plus the cost of any reruns.

What drives the bill

  • The Glue jobs and crawlers in the graph, which are the whole bill.
  • Crawlers that rescan full buckets on every run instead of only new folders.
  • Reruns of a whole workflow after a late failure, when resuming from the failed node would do.
  • Event batching set to one event per run, which starts a full run for every file.

Cost traps

  • Thinking orchestration is free because the workflow has no line on the bill; the jobs it starts are the cost.
  • Running the old Glue workflow and the new Databricks pipeline in parallel for longer than the agreed two weeks.
  • Scheduled triggers left on in dev and test accounts after the team stopped using them.
  • Crawlers kept only to refresh a table nobody queries any more.

Prices change; check the AWS pricing page for your region before deciding.

Security and governance

Keeping it safe

  • Each job and crawler in a workflow runs with its own IAM role; the workflow itself does not grant access. Keep roles per subject, not one powerful shared role.
  • Control who can create, change or start workflows and triggers with IAM actions such as glue:StartWorkflowRun and glue:UpdateTrigger, and allow changes only from the deployment pipeline in production.
  • An EventBridge start trigger needs a role EventBridge can assume to call Glue; scope it to that one workflow.
  • Run properties are visible to anyone who can read the run; never put passwords or tokens in them. Use Secrets Manager.
  • CloudTrail records workflow and trigger changes and starts, which answers who changed a schedule and when.

Decisions

Situations and verdicts

SituationChoiceVerdict
New pipelines on the AWS and Databricks platformLakeflow Jobs for all Databricks work; EventBridge for AWS-side triggersDrop Glue Workflows: the work is not in Glue, so its orchestrator has nothing to run.
Thirty existing Glue workflows feeding Athena reportsLeave them running until each subject's Databricks pipeline reconciles, then disable and delete the workflowKeep if you have it, for the migration window only; do not add new nodes to them.
A gold table needs one Glue output and one Databricks output during migrationA table-update trigger in Lakeflow Jobs on the Glue output tablePursue with care: depend on data arrival, not on two clocks in two tools.
A team proposes blueprints to generate many similar pipelinesThe metadata-driven framework in Databricks, driven by the config tablesDrop blueprints: one framework in one place, with lineage and quality results tied to the run id.

FAQ

Questions people ask

Is AWS Glue Workflows deprecated?

No. AWS has not announced a retirement, and it can still start from EventBridge events with batching. The Drop verdict here is about fit: on a platform where Databricks does the processing, Glue Workflows have nothing to orchestrate.

Glue Workflows or Step Functions?

Glue Workflows only run Glue jobs and crawlers. Step Functions can call over two hundred AWS services and any HTTPS API, with branching, loops and error handling. If the flow touches anything beyond Glue, Step Functions is the better AWS-native choice.

Can a Glue workflow start a Databricks job?

Only indirectly, by running a Glue Python shell job that calls the Databricks Jobs API. That adds a job to maintain and pay for. EventBridge or Lakeflow Jobs triggers do the same thing more simply.

How do I migrate Glue Workflows to Databricks?

Move them with their jobs. Rebuild each subject's jobs as Databricks pipelines, express the order as tasks in a Lakeflow Job generated from metadata, run old and new side by side for two weeks until counts and sums reconcile, then disable the Glue workflow.

Do Glue Workflows cost extra?

No. Workflows and triggers are free; you pay for the Glue jobs, crawlers and catalog use they start.
