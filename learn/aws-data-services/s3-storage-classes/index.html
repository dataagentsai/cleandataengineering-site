Amazon S3 storage classes and lifecycle (Intelligent-Tiering, Glacier)

Price tiers for the same S3 object, plus lifecycle rules that move or delete objects as they age.

RoleStorage and table formats
StatusGenerally available. The S3 Glacier storage classes are current; the original vault-based Amazon Glacier service no longer accepts new customers, and AWS points new archive work to the Glacier classes inside S3. Reduced Redundancy Storage still exists but AWS recommends against it.
Verdict on this sitePursue
AzureBlob Storage access tiers (Hot, Cool, Cold, Archive) and lifecycle management
Google CloudCloud Storage classes (Standard, Nearline, Coldline, Archive) and Autoclass
Databricksnone: Databricks reads whatever class S3 serves; Delta VACUUM and Predictive Optimization manage table history, not storage class
Open sourceMinIO lifecycle and tiering rules
Verdict: Pursue. Lifecycle rules are how the platform keeps its retention promises: landing files deleted 30 days after they reach bronze, personal-data landing deleted after a day, bronze kept 3 years in S3 Standard and then in S3 Glacier Instant Retrieval until year 8. Never put files of a live Delta table into Glacier Flexible Retrieval or Deep Archive: Spark cannot read them without a restore.

In plain words

What it is

Every object you store in Amazon S3 has a storage class. The class does not change what the object is or how you name it. It changes three things: what you pay each month to keep it, what you pay each time you read it, and how fast you can get it back. S3 Standard is the default: no minimum time, no fee to read, millisecond access. The colder classes charge less to store and more to read, and some make you wait minutes or hours before the bytes come back.

A lifecycle rule is a small piece of bucket configuration that says, for objects under a prefix or with a tag, after so many days move them to another class, or delete them. S3 runs the rule for you every day. Nobody writes a job and nobody has to remember. S3 Intelligent-Tiering is a special class that does the moving itself: it watches each object and moves it to a cheaper tier when nobody has read it for 30 days, and to a cheaper one again at 90 days, with no fee when it is read again.

A concrete example from a tyre manufacturer. Curing presses in the plants send sensor readings every few seconds, and nightly SAP extracts arrive as files. The raw files land in a landing bucket and are loaded into bronze Delta tables within the hour. After that, nobody needs the landing copy, so a lifecycle rule deletes it 30 days later. Bronze tables are read often for the first months, then almost only by auditors and by the rare replay, so after three years their files move to S3 Glacier Instant Retrieval, which is still readable in milliseconds by Spark, and after year 8 they are deleted.

A warehouse with a front shelf, a back room and a locked basement: same boxes, cheaper rent the further back they sit, but fetching from the basement takes a day and costs a porter.

Big picture

Where it fits

The lit lane is where S3 storage classes works. Boxes on the left feed it; boxes on the right use what it produces.

Storage classes sit in the store lane, under every bucket of the platform. They are not a separate service you call; they are a property of each object and a set of rules on each bucket. The movers (DMS, AppFlow, Transfer Family, Firehose) write into landing in S3 Standard. Databricks writes bronze, silver and gold Delta tables into one bucket per catalog, also in S3 Standard. Lifecycle rules then age that data according to the retention table the platform agreed with the data owners.

The rules differ by layer. Landing is short-lived: files are deleted 30 days after bronze has them, and folders that carry personal data are deleted after one day, with old versions expiring the same day. Bronze is the replayable record, so it stays longest: three years in Standard, then Glacier Instant Retrieval until year 8. Silver and gold are rebuilt from bronze when needed, so their old file versions are cleaned by Delta VACUUM after 30 days rather than archived. The audit bucket keeps its copies for 7 years under Object Lock.

The important boundary is between classes Spark can read directly and classes it cannot. S3 Standard, Standard-IA, Intelligent-Tiering (its automatic tiers) and Glacier Instant Retrieval all answer a normal GET in milliseconds, so a Delta table can sit on them and still work. Glacier Flexible Retrieval, Glacier Deep Archive and the optional archive tiers of Intelligent-Tiering need a restore first. A query that touches one of those files fails, so they are only for exports and copies that nobody queries.

How it works

The ideas you need

IdeaWhat it means
Storage classA per-object setting such as STANDARD, STANDARD_IA, INTELLIGENT_TIERING, GLACIER_IR, GLACIER or DEEP_ARCHIVE that sets price, retrieval fee and access speed.
Lifecycle ruleBucket configuration that transitions objects to another class, or expires (deletes) them, a set number of days after creation or after they stop being current.
TransitionA lifecycle move from one class to a colder one. Each transition is billed as a request per object.
ExpirationA lifecycle delete. On a versioned bucket it adds a delete marker; a separate noncurrent-version rule removes old versions for real.
Minimum storage durationThe shortest time you are billed for: 30 days for the Infrequent Access classes, 90 days for Glacier Instant and Flexible Retrieval, 180 days for Deep Archive.
Minimum billable object sizeStandard-IA, One Zone-IA and Glacier Instant Retrieval bill any object smaller than 128 KB as if it were 128 KB.
Intelligent-TieringA class that moves each object between Frequent, Infrequent (after 30 days unread) and Archive Instant Access (after 90 days) tiers for a small monitoring fee per object, with no retrieval fee.
RestoreA request that makes a temporary readable copy of an archived object in Glacier Flexible Retrieval or Deep Archive; it takes minutes to hours and costs a retrieval fee.

Choosing

When to use it, and when not

Use it when

  • Use lifecycle expiration on every landing prefix, so raw files and their old versions disappear on the schedule the retention table promises.
  • Use Glacier Instant Retrieval for old bronze files that must stay queryable for audits or replays but are read a few times a year.
  • Use Intelligent-Tiering for large shared areas with unknown read patterns, such as an exports bucket or a data science scratch area, where most objects are well above 128 KB.
  • Use Glacier Deep Archive for copies that exist only for legal reasons, such as a yearly export of finished tables that nobody queries.

Avoid it when

  • Avoid Glacier Flexible Retrieval and Deep Archive for files of any table that a query, a VACUUM or a time-travel read may touch; the read fails until someone restores the file.
  • Avoid the Infrequent Access and Glacier Instant classes for buckets full of small files, such as raw sensor JSON of a few kilobytes, because each object is billed as 128 KB.
  • Avoid colder classes for data that is deleted soon, because an object deleted before its minimum duration is billed for the full minimum anyway.
  • Avoid lifecycle transitions on the managed table buckets for silver and gold; Delta VACUUM already removes old files, and archiving live files only adds retrieval fees.

Cost

How you pay

Each class has its own price per GB-month of storage, per request (PUT, GET, transition) and, for the colder classes, per GB retrieved. The colder the class, the lower the storage price and the higher the read and transition costs. Infrequent Access and Glacier classes also have a minimum storage duration and, for some, a minimum billable size of 128 KB. Intelligent-Tiering adds a small monthly monitoring fee per object of 128 KB or more and has no retrieval fee. Lifecycle rules themselves are free; the transitions they trigger are billed as requests. Check list prices for your region.

What drives the bill

  • Total GB in each class, which for this platform is dominated by bronze history.
  • Number of objects transitioned, because every transition is a request; many small files make this large.
  • GB retrieved from Infrequent Access and Glacier classes, including reads by Spark scans and restores for audits.
  • Noncurrent object versions kept by versioned buckets until a rule removes them.

Cost traps

  • Objects under 128 KB billed as 128 KB in Standard-IA, One Zone-IA and Glacier Instant Retrieval.
  • Early-delete charges when an object leaves a class before its minimum duration.
  • Glacier Flexible Retrieval and Deep Archive add about 40 KB of extra metadata per object, part of it billed at the Standard rate.
  • Full-table Spark scans over Glacier Instant Retrieval data pay a retrieval fee per GB every time.
  • Incomplete multipart uploads stay billed until an abort rule removes them.

Prices change; check the AWS pricing page for your region before deciding.

Security and governance

Keeping it safe

  • Storage class does not change who can read an object; IAM, bucket policies, Unity Catalog grants and KMS still decide access, so archived data keeps its protection.
  • Objects keep their encryption when they move between classes; with SSE-KMS each transition and restore can call KMS, so bucket keys help keep KMS request costs down.
  • Lifecycle expiration is how retention and erasure promises become real for landing files that held personal data; Macie scans landing to catch files kept in the wrong place.
  • Changes to lifecycle configuration (PutBucketLifecycleConfiguration) are recorded in CloudTrail; alert on them for the landing, table and audit buckets.

FAQ

Questions people ask

Can Spark or Databricks read data in S3 Glacier?

It depends on the class. Glacier Instant Retrieval answers normal reads in milliseconds, so Spark reads it directly but pays a retrieval fee per GB. Glacier Flexible Retrieval and Deep Archive need a restore first, and a read without one fails.

What is the difference between Amazon Glacier and S3 Glacier?

The S3 Glacier storage classes live inside S3 buckets and use the S3 API. The original Amazon Glacier service used vaults and its own API; it no longer accepts new customers, and AWS recommends the S3 Glacier classes instead.

Is S3 Intelligent-Tiering always cheaper?

No. It saves money on large objects whose reads drop off, with no retrieval fee. Objects under 128 KB never move tier, and every larger object pays a small monitoring fee, so a bucket of hot or tiny files can cost more.

Do lifecycle rules delete old versions on a versioned bucket?

Only if you ask. A normal expiration adds a delete marker; you need a NoncurrentVersionExpiration rule to remove old versions, and a rule to clean up expired delete markers.

Should Delta table buckets have lifecycle rules at all?

Yes, but narrow ones: noncurrent-version expiry, abort incomplete uploads, and for bronze a transition of old history to Glacier Instant Retrieval. Leave deleting table files to Delta VACUUM, which knows which files the table still needs.
