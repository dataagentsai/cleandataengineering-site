AWS IoT Core

A managed MQTT front door that gives every device its own identity, routes its messages with rules, and sends commands back.

RoleIngestion and CDC
StatusGenerally available. Note that two older neighbours, AWS IoT Events and AWS IoT Analytics, have reached end of support; IoT Core itself is unaffected.
Verdict on this sitePursue with care
AzureAzure IoT Hub (or Event Grid MQTT broker)
Google Cloudnone since Google Cloud IoT Core was retired in 2023; use a partner MQTT broker into Pub/Sub
Databricksnone: Databricks reads what IoT Core rules land in Kinesis or S3
Open sourceEMQX, HiveMQ CE or Eclipse Mosquitto as the MQTT broker
Verdict: Pursue with care. Pursue for connected products such as tyre sensors on fleet vehicles, and for sending commands back to devices, because it gives each device its own certificate and a two-way channel. Drop it for plant machine readings: there a Greengrass gateway writes straight to Kinesis, which avoids per-message charges of roughly a thousand dollars a month.

In plain words

What it is

AWS IoT Core is a managed message broker for devices. A device is anything with a chip and a network connection: a sensor clipped inside a tyre, a temperature probe in a cold store, a smart shelf in a retail shop. Devices usually speak MQTT, a small publish and subscribe protocol designed for weak networks and low power. A device publishes a message to a topic, which is just a name such as fleet/truck-0412/tyres, and anything subscribed to that topic receives it. IoT Core runs that broker for you at very large scale, so you never install or patch a broker server.

Its second job is identity. Every device gets its own X.509 certificate, a digital ID card that it presents when it connects. A policy attached to the certificate says which topics that device may publish and subscribe to. If one truck is stolen, you revoke one certificate and the rest of the fleet carries on. This is the main reason to use IoT Core rather than letting devices write directly to a cloud service with a shared key.

Its third job is routing. The rules engine runs a small SQL statement over each incoming message and sends the result to other AWS services: Kinesis Data Streams, Amazon Data Firehose, S3, DynamoDB, Lambda and others. Finally, IoT Core can talk back to devices through device shadows (a stored copy of the state each device should have) and jobs (a way to send a task, such as a firmware update, to many devices).

A concrete example: a tyre maker fits pressure and temperature sensors to tyres on customer fleet trucks. Each truck has a small telematics box that collects readings from its tyres, batches ten readings into one message, and publishes it every minute over a mobile network to IoT Core. A rule forwards every message to a Kinesis stream. From there a Flink job raises a low-pressure alert within seconds, and Databricks lands the same data in bronze tables every fifteen minutes.

A building reception desk that checks each visitor's own badge, writes down who said what, and passes each note to the right department.

Big picture

Where it fits

The lit lane is where IoT Core works. Boxes on the left feed it; boxes on the right use what it produces.

On the reference platform IoT Core sits at the very left edge of the move-in lane, as the front door for devices that live outside the plant: connected tyres on fleet vehicles today, and any product that needs commands sent back to it later. It receives MQTT messages, checks each device's certificate and policy, and a rule forwards the messages to Kinesis Data Streams, the stream belt that both the live lane and the platform lane read.

Plant machines take a different path on purpose. Curing presses and mixers talk to a plant gateway running SiteWise Edge on AWS IoT Greengrass, and the gateway writes straight to Kinesis with an IAM role. The site's streaming design estimates that sending every press reading through IoT Core would add about a thousand dollars a month in message and rule charges for no extra benefit, because identity per gateway is enough inside a plant. So IoT Core is in the design, but only where per-device identity and a channel back to the device are worth paying for.

Downstream, nothing reads IoT Core directly. Managed Service for Apache Flink and Databricks Structured Streaming read the Kinesis stream; Firehose can turn the same stream into files in S3 for the slower path. CloudWatch collects IoT Core metrics and logs so the operations team can see connection drops and rule failures alongside the other movers.

How it works

The ideas you need

IdeaWhat it means
MQTTA lightweight publish and subscribe protocol for devices on slow or unreliable networks. IoT Core supports versions 3.1.1 and 5.
TopicA text name that messages are published to, such as fleet/truck-0412/tyres. Subscribers can use wildcards to receive many topics at once.
ThingThe registry entry for one device: its name, type and attributes. A certificate and a policy are attached to it.
X.509 certificateThe device's own digital identity, used in mutual TLS so both the device and IoT Core prove who they are.
IoT policyA JSON document, like an IAM policy, that says which client IDs and topics a certificate may connect, publish and subscribe to.
Rules engineSQL statements that select and reshape incoming messages and send them to AWS services through rule actions.
Basic IngestA reserved topic prefix ($aws/rules/<rule>) that sends a message straight to a rule without the publish step, so no messaging charge applies.
Device shadowA JSON document that stores a device's reported state and the desired state you want it to reach, even while it is offline.
JobsA way to send a task, such as a firmware or settings update, to a list or group of devices and track progress.
Fleet provisioningA way for devices to get their own certificate on first boot, using a shared claim certificate or a trusted factory process.

Choosing

When to use it, and when not

Use it when

  • You have many devices outside your own network, such as vehicles or shop equipment, and each needs its own identity that you can revoke alone.
  • You need to send commands or settings back to devices, not only receive data from them.
  • Your devices speak MQTT over mobile or patchy networks and need a broker that handles reconnects and persistent sessions.
  • You want a simple rule to fan device messages out to Kinesis, S3 or DynamoDB without running any servers.
  • You must prove to auditors which device sent which message, because each connection is tied to one certificate.

Avoid it when

  • The data comes from machines inside a plant that already have a gateway; let the gateway write directly to Kinesis and skip the per-message fees.
  • You are moving files or database tables; use Transfer Family, DataSync or DMS instead of squeezing them into small messages.
  • Every reading would be sent as its own message at high frequency; at that scale messaging and rule charges dominate unless you batch on the device.
  • Your apps call over HTTPS with user logins; API Gateway with a Cognito or IAM authorizer fits that better than device certificates.

Production grade

What goes wrong in production

ProblemWhat breaksWhat to do
Per-message cost surpriseCharges are per message in 5 KB steps, plus per rule triggered and per action. A fleet that sends one small reading per message costs far more than one that batches.Batch several readings into one message on the device, keep messages near 5 KB, emit only changes, and use Basic Ingest topics to skip the messaging charge.
Certificate sprawl and expiryThousands of certificates are created, a few are leaked or near expiry, and nobody knows which device owns which.Use fleet provisioning with a template, tag things with owner and site, rotate certificates with jobs, and turn on Device Defender audit checks.
Over-broad IoT policiesA policy allowing iot:* on all topics lets one stolen device read or spoof the whole fleet.Use policy variables so a device may only publish to topics containing its own thing name, and only connect with a client ID equal to that name.
Silent rule failuresA rule action fails, for example Kinesis throttles, and messages are dropped without anyone noticing.Configure an error action on every rule that writes to S3 or SQS, and alarm on the RuleMessageThrottled and failure metrics.
Duplicate client IDsTwo devices, or one device after a reboot, connect with the same client ID and keep kicking each other off.Make the client ID equal to the thing name, enforce it in the policy, and watch the disconnect reasons in AWS IoT logs.
Per-connection throttlingA device publishes faster than 100 messages a second on one connection and the excess is discarded.Batch on the device; if you truly need more, spread load over more connections or route bulk data another way.
Ordering and duplicatesMQTT QoS 1 means at least once, so the same reading can arrive twice, and readings from a reconnecting device can arrive late.Put a device timestamp and sequence number in every message and deduplicate in silver, not at the broker.
Offline devices and lost messagesPersistent sessions keep queued messages only for a limited time, one hour by default, so long outages lose commands.Use device shadows for desired state instead of one-off messages, and raise the session expiry quota if your vehicles go dark for longer.

Alternatives

AlternativePick the alternative whenPick IoT Core when

Cost

How you pay

IoT Core charges on four meters. Connectivity is charged per million connected minutes, which is tiny per device. Messaging is charged per million messages, metered in 5 KB steps, so a 12 KB message counts as three. Device shadow and registry operations are charged per million operations in 1 KB steps. The rules engine is charged per rule triggered and per action run, also in 5 KB steps. Messages sent to Basic Ingest topics carry no messaging charge. The site's design uses about one dollar per million messages and a fraction of that per rule action, list price, check your region.

What drives the bill

  • How many messages each device sends, which is set by reading frequency and how much you batch per message.
  • Message size, because every 5 KB step is charged again.
  • How many rules fire per message and how many actions each rule runs.
  • Shadow updates, especially if devices report state every few seconds.

Cost traps

  • Sending one reading per message: the site estimates about nine thousand dollars a month for connected tyres unbatched, and about one thousand with ten readings per message.
  • Routing plant machines through IoT Core when a gateway could write to Kinesis directly, adding about a thousand dollars a month for nothing.
  • Several rules subscribed to the same topic, each charged separately for every message.
  • Verbose logging at DEBUG level sent to CloudWatch Logs for the whole fleet, which can cost more than the messages.

Prices change; check the AWS pricing page for your region before deciding.

Security and governance

Keeping it safe

  • Give every device its own X.509 certificate, keep private keys in a secure element or TPM where the hardware allows, and never share one certificate across a fleet.
  • Write IoT policies with the thing name variable so each device can only connect as itself and only use its own topics.
  • Rule actions use an IAM role; scope that role to the one Kinesis stream or bucket the rule writes to.
  • Use VPC interface endpoints for IoT Core data so back-end services inside the VPC reach it without public routes; devices themselves connect over TLS on port 8883 or 443.
  • Turn on AWS IoT Device Defender audit for weak policies and shared certificates, and CloudTrail for control-plane changes such as new policies.
  • Vehicle location and driver data can be personal data; keep it out of topic names, and tokenise it in the lander before bronze.

FAQ

Questions people ask

Is AWS IoT Core the same as AWS IoT Analytics or IoT Events?

No. IoT Core is the broker and routing service and is fully supported. IoT Analytics and IoT Events were separate services that have reached end of support; the replacements are Kinesis, Flink and Databricks for analysis and alerts.

How much does AWS IoT Core cost per device?

Connection time costs very little; the bill is driven by how many messages each device sends and how many rule actions each message triggers. Batch readings into one message near 5 KB and the per-device cost drops many times over.

Can Databricks read from AWS IoT Core directly?

Not directly. A rule sends messages to Kinesis Data Streams or to S3 through Firehose, and Databricks reads from there with Structured Streaming or Auto Loader.

Do I need IoT Core if I use Greengrass?

A Greengrass device uses IoT Core for its identity, deployments and optional MQTT messaging, but the data itself can go straight to Kinesis through stream manager. That direct path is what the reference platform uses for plant data.

What is the difference between IoT Core and Kinesis?

IoT Core is the front door: it knows each device, speaks MQTT and can talk back. Kinesis is the belt behind it: an ordered, replayable log that many readers consume. Most device platforms use both.
