Amazon Managed Service for Apache Flink

Runs Apache Flink jobs for you: event-time windows, state and joins over streams, with checkpoints so a restart loses nothing.

In plain words

What it is

Apache Flink is an open-source engine for processing streams of events as they arrive, one event at a time, rather than in large batches. Its strength is state: it can remember things between events, such as the running average pressure of a curing press over the last minute, or whether a barcode scan has already arrived for a press cycle that started ten seconds ago. It keeps that memory safe by taking checkpoints, which are regular snapshots of all its state written to durable storage, so that after a crash it resumes exactly where it stopped.

Amazon Managed Service for Apache Flink runs Flink for you. You upload your application, written in Java, Python or Flink SQL, and choose how much capacity it gets. AWS starts the cluster, stores checkpoints, restarts the job when a machine fails, and scales the job if you allow it. You never patch a server. Until August 2023 the same service was called Amazon Kinesis Data Analytics, which is why many older articles and some API names still use that name.

A concrete example: a tyre plant has 2,000 curing presses, each sending twenty signals every five seconds. Operators want a screen that turns red within seconds when a press runs too hot for longer than thirty seconds, and supervisors want one-minute averages per press. A Flink job reads the readings from Kinesis Data Streams, groups them by press, waits a short time for late readings using a watermark, computes one-minute windows, compares them with the limits for the current recipe, and writes both the latest values and any alert into DynamoDB. From there the change is pushed to the screen.

What makes this hard without Flink is event time. Readings do not arrive in perfect order: a gateway may buffer for a few seconds, or a network blip may delay a batch. Flink sorts this out by the time the reading was taken, not the time it arrived, so a one-minute window means the right minute even when data is late.

Big picture

Where it fits

The lit lane is where Managed Flink works. Boxes on the left feed it; boxes on the right use what it produces.

On the reference platform Flink lives only in the fast lane, the path that puts plant readings and alerts on screens within one to three seconds. Readings flow from the plant gateway into Kinesis Data Streams, Flink reads them, and its output goes to a small live store in DynamoDB. DynamoDB Streams then hands each change to a Lambda function that pushes it to browsers through an API Gateway WebSocket, or through AppSync Events. The site estimates this whole lane at roughly 530 dollars a month, of which Flink with three processing units is about 250 dollars (list price, check your region).

The platform lane, which builds bronze, silver and gold tables in Databricks every fifteen minutes, deliberately does not read Flink's output. It reads the same raw stream from Kinesis itself, so a bug in the fast lane can never corrupt the numbers of record. The only things Flink sends to the lake are facts it creates: alerts raised and acknowledged, and one-minute service-level summaries, which go through Firehose into bronze as their own dataset.

Reference data travels the other way. Limits per recipe and the press master list are published from silver or gold every fifteen minutes or daily into DynamoDB or into Flink broadcast state, so the fast lane has its own copy and never calls the platform while running. Simple limit checks that need no memory, such as pressure above a fixed maximum, can run in a Lambda function reading Kinesis beside Flink, which is nearly free.

Databricks real-time mode is the main rival. It would let one engine, Spark, serve both lanes. The site currently says Drop for now and revisit if the team wants one engine, because it needs a fixed always-on cluster and costs more than Flink for a small plant stream.

How it works

The ideas you need

IdeaWhat it means
Kinesis processing unit (KPU)The unit of capacity and billing: one virtual CPU, 4 GiB of memory and 50 GiB of running application storage.
ParallelismHow many copies of each step run at once. Total parallelism divided by parallelism per KPU decides how many KPUs you pay for.
CheckpointAn automatic, regular snapshot of the job's state and its read positions, used to recover after a failure without losing or repeating results.
SnapshotA checkpoint you keep on purpose, taken when you stop or update the application, so a new version can start from the old state.
Event time and watermarkEvent time is when a reading was taken. A watermark is Flink's statement that no reading older than a certain time is still expected, which lets windows close.
WindowA slice of the stream grouped by time, such as every minute per press, over which Flink computes counts, averages or maximums.
Keyed stateMemory Flink keeps per key, for example per press, stored in RocksDB on local disk and included in every checkpoint.
Back pressureWhen a later step or the sink cannot keep up, earlier steps slow down; latency grows until the bottleneck is fixed.
Broadcast stateA small table, such as limits per recipe, copied to every parallel worker so each event can be checked without a remote lookup.

Choosing

When to use it, and when not

Use it when

  • You need time windows, running aggregates or pattern detection over a stream, with results in seconds rather than minutes.
  • You must join two streams within a time bound, for example a press cycle start and the barcode scan that should follow it.
  • You need correct results when events arrive late or out of order, which calls for event time and watermarks.
  • You want exactly-once results into a sink that supports it, backed by checkpoints, without running a Flink cluster yourself.
  • Your stream already lives in Kinesis or MSK and your team can write Java, Python or Flink SQL.

Avoid it when

  • The logic is a stateless check on each event, such as a single threshold; a Lambda function reading Kinesis is simpler and costs almost nothing.
  • The result only needs to be fresh within fifteen minutes or an hour; a Databricks streaming table run on a schedule is cheaper and keeps one engine.
  • Nobody on the team can support a Flink job; an always-on stateful service needs someone who understands checkpoints and back pressure.
  • You want to write Delta tables governed by Unity Catalog as the main output; Databricks itself does that better.

Production grade

What goes wrong in production

ProblemWhat breaksWhat to do
Checkpoints get slower and then failState grows over time, often because a window has no end or a join has no time-to-live, and each checkpoint takes longer until it times out and the job restarts in a loop.Set time-to-live on state, bound every join with time, watch lastCheckpointDuration and lastCheckpointSize, and alarm before checkpoints approach the timeout.
Back pressure from the sinkDynamoDB throttles or a slow HTTP call blocks the job, so readers fall behind and alerts arrive late.Write only changes, not every reading; batch writes; use async I/O for lookups; watch backPressuredTimeMsPerSecond and DynamoDB throttles together.
Late or silent sourcesOne plant gateway stops sending, the watermark stops advancing, and windows for every press never close.Configure idle-source handling for watermarks, and add a heartbeat per plant so a silent source raises its own alert.
Upgrades that break stateA code change renames an operator or changes a state type, and the new version cannot restore the old snapshot.Give every operator a fixed id, test restores from a production snapshot in a lower environment, and keep the previous version ready to roll back.
Flink 2.x migrationFlink 2.2 is a major version with breaking changes: Java 17 only, older APIs removed, and some connectors such as JDBC and OpenSearch had no 2.x release at launch.Check every connector you use for a 2.x release before upgrading, follow the AWS upgrade guide, and test state compatibility on a copy.
Paying for idle capacityYou pay for allocated KPUs every hour, plus one extra KPU per application for orchestration, even when the plant is quiet at night.Right-size parallelism from measured CPU and back pressure, enable autoscaling with care, and merge small jobs where it is safe.
Restart stormsA poison record, such as a malformed reading, throws an error on every attempt and the job restarts again and again.Catch parse errors and send bad records to a side output stored in S3, and alarm on fullRestarts and downtime.

Cost

How you pay

You pay an hourly rate for each KPU allocated to the application, plus one extra KPU per application for orchestration. Running application storage is billed per GB-month (50 GB comes with each KPU) and durable backups, meaning snapshots you keep, are billed per GB-month too. The site uses about 80 dollars a month per KPU as a rough figure, so a small job with two working KPUs plus orchestration is about 250 dollars a month (list price, check your region). Data transfer and the services Flink reads and writes, such as Kinesis and DynamoDB, are billed separately.

What drives the bill

  • Number of KPUs, which follows from parallelism and how many parallel tasks share one KPU.
  • Number of applications, because each one carries its own orchestration KPU.
  • State size, which drives storage, checkpoint time and sometimes the need for more memory.
  • Writes to the sink; writing every reading into DynamoDB instead of only changes multiplies the sink bill.

Cost traps

  • Autoscaling scales up on high CPU but can leave you at the higher size for a long time; check the KPUs metric weekly.
  • Many tiny applications each pay the orchestration KPU; one job with several outputs is often cheaper.
  • Development and test applications left running around the clock cost the same as production.
  • Kept snapshots accumulate; set a retention policy for old snapshots.

Prices change; check the AWS pricing page for your region before deciding.

Security and governance

Keeping it safe

  • The application runs with an IAM service execution role; grant it read on the one Kinesis stream and write on the one DynamoDB table, nothing wider.
  • Attach the application to private subnets in your VPC so it reaches Kinesis, DynamoDB and S3 through VPC endpoints, with no public internet path.
  • Checkpoints and snapshots are encrypted by the service; application code and dependencies in S3 should sit in an encrypted bucket with the platform KMS key.
  • Keep secrets such as database passwords in Secrets Manager and read them at start-up; never put them in runtime properties in plain text.
  • Control-plane calls such as UpdateApplication and StopApplication are logged in CloudTrail, which shows who changed or stopped the job.
  • Readings are usually not personal data, but connected-product streams can carry vehicle or customer ids; drop or hash them before the live store if screens do not need them.

FAQ

Questions people ask

Is Managed Service for Apache Flink the same as Kinesis Data Analytics?

Yes. AWS renamed Kinesis Data Analytics for Apache Flink to Managed Service for Apache Flink in August 2023. The separate Kinesis Data Analytics for SQL applications was discontinued, and its applications were deleted from 27 January 2026.

Which Flink versions does it support?

The newest is Flink 2.2, supported since 31 March 2026, alongside recent 1.x versions. Flink 2.2 needs Java 17 and some connectors lacked 2.x releases at launch, so check yours before upgrading.

When should I use Lambda instead of Flink for Kinesis?

Use Lambda when each record can be judged alone, such as one fixed limit. Use Flink when you need windows, joins, late-event handling or state across many records.

How much does a small Flink job cost?

Roughly 80 dollars a month per KPU plus one orchestration KPU per application, so a small job is about 160 to 400 dollars a month. These are rough list prices; check your region and measure.

Can Flink write Delta tables for Databricks?

It can with the Delta connector, but the reference platform does not do that. Databricks reads the raw stream from Kinesis itself, and Flink sends only alerts and summaries to bronze through Firehose.
