Eval Harness Tutorial · Architecture

One question, three languages

An ops lead asks: “what share of turns failed in the last 15 minutes, for each agent?” On Azure that is a KQL query. On Prometheus it is a PromQL expression. On a warehouse it is SQL. Three teams writing it three times will get three slightly different numbers, and nobody will know which is right.

So we write the question once, as a small recipe called a metric. It says three things and names no tool: what to count, how, and what to split it by. A writer for each language turns the recipe into a query. A test then proves every query gives the number that plain Python gives on the same traces.

Try it: one metric, three queries

This is turn_error_rate, written by the three writers when this page was built.

KQL, for App Insights

union AppRequests, AppDependencies
| where TimeGenerated > ago(15m)
| extend step = case(tostring(Properties["gen_ai.operation.name"]) == "invoke_agent", "turn", "")
| where step != ""
| extend agent = tostring(Properties["gen_ai.agent.name"]), failed = Success == false
| summarize rate = todouble(countif(failed)) / count() by agent

PromQL, for Prometheus

(sum by (gen_ai_agent_name) (increase(gen_ai_client_operation_duration_seconds_count{gen_ai_operation_name=~"invoke_agent", error_type!=""}[15m])) or sum by (gen_ai_agent_name) (increase(gen_ai_client_operation_duration_seconds_count{gen_ai_operation_name=~"invoke_agent"}[15m])) * 0) / sum by (gen_ai_agent_name) (increase(gen_ai_client_operation_duration_seconds_count{gen_ai_operation_name=~"invoke_agent"}[15m]))

SQL, for a table of call records

select agent, avg(case when failed then 1.0 else 0.0 end) as rate from calls where kind in ('turn') group by agent order by agent

What the live run taught us
  • kind is a reserved word in KQL. The first query failed to parse; the column is now called step.
  • App Insights keeps the conversation id in a column of its own (SessionId), not with the other attributes. All 104 turns had it there. Our reader only looked among the attributes, which is why an earlier run reported “no conversation ids”. The reader now reads the column.
  • Azure stores a step's length in whole milliseconds, so sums match to the millisecond, not beyond.

Percentiles from counters are estimates

A detail store keeps every step's time, so it can give the exact middle value. A number store keeps only how many steps fell into each time bucket (up to 1 second, up to 2.5 seconds, and so on), so it can only say which bucket the answer is in. Take four turns that took 2, 4, 9, 1.5 seconds:

Typical (p50)Slow (p95)
From every step's time (detail store)3 s8.25 s
From bucket counts (number store)2.5 s9 s

Counts, rates and totals are exact in both. Only percentiles differ, and a dashboard should say which kind it is showing.

Two things that differ between agents

The recipe stays the same. These two are named in the binding, not assumed:

OpenTelemetry GenAI conventionsThe reference agent harness
A turn isa span whose operation is invoke_agenta span named agent.turn
A model call isoperation chatgen_ai.chat
A tool call isoperation execute_toolagent.tool or agent.tool.local
A turn failed whenthe span has an error statuserror status, or agent.turn.result is failed
The agent's name isgen_ai.agent.namethe service that sent the span
The conversation isgen_ai.conversation.idsession.id

The counters need a name too. The default is the GenAI conventions' duration histogram, gen_ai_client_operation_duration_seconds, labelled by step, agent, model, tool and error.
