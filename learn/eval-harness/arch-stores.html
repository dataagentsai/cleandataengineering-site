Where the signals go: one store or two

Think of a shop. Every sale prints a receipt: what was sold, when, to whom. The till also keeps a running total for the day. You can add up the receipts to get the total, but you can never get a receipt back out of a total. And if you throw away nine receipts in ten to save space, adding up what's left gives the wrong total.

An agent's telemetry works the same way:

  • A span is a receipt: the full record of one model call or tool call.
  • A counter is the till total: how many calls, how many failed, how long they took.
  • An event is a note pinned to a receipt. Our verdicts and decisions are events.

Some platforms keep receipts and totals in one place. Others keep them in two. The eval harness must work the same either way, so it must not be designed around either one.

The roles a platform fills

RoleWhat it keepsWhat it answersAzure todayOpen stack todayDatabricks (planned)
Detail storeEvery span and eventOpen one conversation; what happened, in order; why a rule failedApp InsightsLangfuseMLflow traces
Number storeCountersRates, totals, response times, alerts that run every minuteApp Insights, counted from the spans when askedPrometheusTables, counted with SQL
History storeCall records kept for monthsCost rules over days, long trendsLog AnalyticsDuckDB or ClickHouseDelta tables

One tool may fill two or three roles. That is the whole difference between shape A and shape B, and it lives in the binding file, not in the checks.

Five rules that keep it flexible

  1. The agent sends once and never names a store. It writes spans, counters and events in the OpenTelemetry format. What happens next is routing.
  2. The binding names a tool for each role and says what that tool can do: does it keep every span or a sample, does it hold the customer's words, how long does it keep data, how fresh is it.
  3. Each question says what it needs, not which tool answers it. A planner sends it to the cheapest role that can answer it on this platform. If no role can, the answer is “can't be answered here”, never a wrong number.
  4. Every verdict is written twice from one call: as an event on the trace, so you can open the conversation, and as a counter, so you can count and alert cheaply.
  5. Totals are added up before anything is thrown away. If traces are sampled, counters come from the agent or the Collector, never from the sample. A check that looks at only a share of conversations records that share on its verdicts.
Why rule 3 matters most

Of the 62 ops questions, 44 are about totals and 18 need to open a conversation. On Azure today both kinds go to App Insights. On the open stack the first kind goes to Prometheus and the second to Langfuse. The question is written once; only the route changes.

Which shapes we support

ShapeExampleVerdict
A · One store does both, keeps every spanApp Insights todayPursue. The default on Azure: nothing extra to run.

Number store only, no tracesPrometheus aloneLimited. Totals only. No conversation can be opened and no rule about what the agent did can run.
LakehouseMLflow traces and Delta tables on DatabricksPursue later. One SQL store fills all three roles.

What a binding file would say

# stacks/azure.yaml (shape A)
stores:
  detail:  {tool: app_insights, keeps: all, words: false}
  numbers: {tool: app_insights, from: spans}       # counted when asked

# stacks/open.yaml (shape B)
stores:
  detail:  {tool: langfuse, keeps: all, words: true}
  numbers: {tool: prometheus, from: collector}     # added up on the way in

This is the shape only; the exact keys settle when it is built.

Your review · One store or two
  1. D15: Should a binding name stores by role (detail, numbers, history), as drawn? My suggestion: yes.
  2. D16: Who adds up the counters? My suggestion: the Collector where there is one; the store at question time when it is a single store that keeps every span; never from a sample.
  3. D17: Should every verdict be written as an event and a counter from one call? My suggestion: yes.
  4. D18: Which shape do we present first to an Azure client? My suggestion: shape A, with shape B as the stated next step and its three triggers.
