The big picture

Five layers, and all of them must say yes

People say "permissions" as if it were one thing. In Databricks it is five separate checks, and a failed request usually means one layer said no while you were looking at another.

{{LAYERS}}
LayerQuestionWhere you set it
1. IdentityWho is asking: a person, a group, or a service principal (a non-human identity for jobs and apps)?Account console, identity provider sync
2. EntitlementsMay this identity use this kind of feature in this workspace (notebooks, SQL, create compute)?Workspace settings, identity and access
3. Workspace object ACLsMay it open, run, edit or manage this notebook, job, cluster or warehouse?The Permissions button on each object
4. Unity CatalogMay it read or change this table, volume or function? Which rows and columns?GRANT, row filters, column masks, ABAC policies
5. StorageMay anything read the cloud files directly?Storage credentials and external locations

Layer 1: identity

Users, groups, service principals and the three admins

IdentityWhat it isUse it for
UserA person, identified by emailInteractive work
GroupA set of users, service principals and other groupsAll grants. Account groups can get Unity Catalog data access and workspace permissions.
Service principalAn identity for code, with no password and no person behind itProduction jobs, pipelines and apps
  • Identities live in the account and are assigned to workspaces. Identity federation is on by default for new workspaces.
  • Sync from your identity provider. The docs recommend automatic identity management (Microsoft Entra ID and Okta), where the provider stays the source of truth. SCIM provisioning is the fallback, and it does not support nested groups or service principals.
  • Old workspace-local groups cannot be given Unity Catalog data access or used across workspaces. Convert them to account groups.
  • Limits: accounts created on or after 17 November 2025 can hold up to 50,000 users and service principals combined and 10,000 groups. Older accounts: 10,000 and 5,000.

The docs recommend giving the metastore admin role to a group, not a person. Workspace admins also own the default workspace catalog, so they can manage everything in it.

Layer 4: Unity Catalog

The hierarchy and the rule for reading a table

{{HIERARCHY}}
To do thisYou need
Read a table or viewUSE CATALOG, USE SCHEMA, SELECT
Write to a tableUSE CATALOG, USE SCHEMA, MODIFY
Create a tableUSE CATALOG, USE SCHEMA, CREATE TABLE on the schema
Create a schemaUSE CATALOG, CREATE SCHEMA on the catalog
Run a functionUSE CATALOG, USE SCHEMA, EXECUTE
Read files in a volumeUSE CATALOG, USE SCHEMA, READ VOLUME

Inheritance

  • A privilege on a catalog applies to every current and future schema, table, view, volume and function in it. On a schema, to everything inside.
  • Metastore-level privileges do not flow down to data. They cover metastore actions like CREATE CATALOG. The exception is READ METADATA.
  • Ownership does not flow down. A catalog owner does not own its schemas, though they can manage them.
  • Views: a user reading a view does not need privileges on its underlying tables. The view owner's privileges are used.
  • Workspace binding wins. A catalog not bound to a workspace cannot be reached from it, even with an explicit SELECT (see s10).

Who may grant on an object: its owner, the owner of the containing catalog or schema, a MANAGE holder, or a metastore admin. The creator of an object becomes its owner, so give production objects to a group or service principal so they survive someone leaving. Transfer with ALTER TABLE main.sales.orders OWNER TO `data-eng`. For views, functions and models, only a metastore admin can hand them to anyone else; other owners can hand them only to themselves or a group they belong to.

GRANT, REVOKE, SHOW GRANTS

GRANT USE CATALOG ON CATALOG main TO `finance-team`;
GRANT USE SCHEMA, SELECT ON SCHEMA main.gold TO `finance-team`;   -- covers every current and future table in gold
REVOKE SELECT ON SCHEMA main.gold FROM `finance-team`;
SHOW GRANTS `finance-team` ON SCHEMA main.gold;
SHOW GRANTS ON TABLE main.gold.orders;                            -- needs READ METADATA, MANAGE or ownership to see everyone's
-- a service principal is named by its application ID, in backticks
GRANT SELECT ON TABLE main.gold.orders TO `fab9e00e-ca35-11ec-9d64-0242ac120002`;

No SQL DENY. I found no DENY statement in the docs. Denials exist only as ABAC DENY policies (Beta, s7). Access is therefore built by granting the right amount, not by granting broadly and denying parts.

Starting state

Users start with no access to data. Workspace users get USE CATALOG on the workspace catalog, and USE SCHEMA plus the main CREATE privileges on its default schema. The docs also say all users have USE CATALOG on main. The sample catalog samples is read-only.

Layer 3: workspace objects

Folder visibility. Someone with CAN VIEW on an object inside a folder can see the parent folder's name without any permission on the folder. The docs also warn that membership of account groups will soon affect workspace object permissions, so review existing grants.

  • A user needs at least one access entitlement to enter a workspace. Consumer access is assigned individually, not through the users group.
  • Cluster policies limit the settings and cost a person can pick. Everyone has the Personal Compute policy by default. Editing a policy does not change existing compute until you enforce it, and job compute is enforced immediately.

Row and column security

Row filters, column masks, ABAC and dynamic views

Grants decide which tables. These decide which rows and columns inside a table the person sees.

Table-level filter or maskABAC policyDynamic view
What it isA SQL function attached to one table or columnA rule on a catalog, schema or table that matches governed tagsA view whose SQL checks who is asking
Covers new tables automaticallyNoYes, through tagsNo
Who is exemptNot stated in the pages I readPrincipals listed under EXCEPTAnyone who can read the base table
StatusStandardCore feature not labelled GA on the pages I read; DENY, views and metastore-level policies are BetaStandard
-- table-level row filter (from the docs)
CREATE FUNCTION salary_filter(dept STRING) RETURNS BOOLEAN RETURN dept IS NULL;
ALTER TABLE employees SET ROW FILTER salary_filter ON (department);

-- ABAC column mask on every column tagged pii=ssn in a schema, for one group (from the docs)
CREATE POLICY mask_ssn ON SCHEMA prod.customers
  COLUMN MASK ssn_to_last_nr TO us_analysts EXCEPT admins
  FOR TABLES MATCH COLUMNS has_tag_value('pii', 'ssn') AS ssn
  ON COLUMN ssn USING COLUMNS (4);

-- dynamic view: use account-level group membership
CREATE VIEW sales_redacted AS
SELECT user_id, CASE WHEN is_account_group_member('auditors') THEN email ELSE 'REDACTED' END AS email
FROM sales_raw;
  • A policy never grants access. The person still needs SELECT. It only hides rows and columns they could otherwise read.
  • One distinct filter and one mask can resolve per person per table or column, or access is blocked with an error.
  • Tags are a security boundary. Whoever can apply a tag can change which policies apply, so give APPLY TAG and tag assignment sparingly.
  • Pipelines run as their owner. Streaming tables and materialized views evaluate policies as the pipeline owner or run-as identity. Add that identity to EXCEPT, or the stored data may be permanently masked.
  • ABAC needs serverless, or standard or dedicated compute on Runtime 16.4 or later. Older runtimes cannot read ABAC-secured tables.
  • Limits to know for table-level filters: not on views, not with time travel, no deep or shallow clones, not shareable through OpenSharing, no path-based file access. Dynamic views: use is_account_group_member, not is_member, and do not grant people the base tables.
  • Quotas for ABAC: 10,000 policies per metastore, 100 per catalog or schema, 50 per table, 20 principals per policy.

For the same idea inside metric views, see row-level security with metric views.

Layer 5: storage

Storage credentials and external locations

ObjectWhat it isKey privileges
Storage credentialA long-lived cloud credential, such as an IAM roleCREATE EXTERNAL LOCATION on it and on the metastore; keep the rights narrow
External locationA storage path plus a credentialREAD FILES, WRITE FILES (needs READ FILES too), CREATE EXTERNAL TABLE, MANAGE
External table or volumeA pointer to data at an external locationThe usual table and volume privileges
GRANT READ FILES, WRITE FILES ON EXTERNAL LOCATION raw_landing TO `ingest-team`;
GRANT CREATE EXTERNAL TABLE ON EXTERNAL LOCATION raw_landing TO `data-eng`;

The rule that matters most: do not give people or service principals direct access to the cloud buckets behind Unity Catalog managed tables or volumes. It bypasses the controls, leaves no audit or lineage, and writes from outside can corrupt data. Let Unity Catalog be the only identity that touches those files, and share file access through volumes (/Volumes paths).

An external location can be marked read-only, which can take up to 60 minutes to apply.

Jobs and apps

Service principals and run-as

  • Why: a job that runs as a service principal uses that identity, not a person's. The docs say this stops jobs failing when someone leaves or a group changes.
  • Create and assign: account admins add service principals, and workspace admins can add them to a workspace. Grant them Unity Catalog privileges and group membership like users, and give them access to the compute or warehouse they use.
  • Managers: creating a service principal makes you its manager, but you still must give yourself its user role to run jobs as it.
  • OAuth M2M: generate a secret for the service principal (up to 5 secrets, lifetime up to 730 days, unused ones deleted after 90 days). Request a token at the workspace /oidc/v1/token endpoint. Tokens last 3,600 seconds, and the SDKs and CLI refresh them. Set a scope when you create the secret, since it cannot be changed later.
  • Secret scopes grant READ, WRITE or MANAGE on the whole scope, not single secrets, so anyone who can read one secret can read them all.

Isolation

Workspace binding

By default every catalog is open to every workspace on the metastore. Switch a catalog to ISOLATED and bind it to chosen workspaces, so production data cannot be reached from the dev workspace even by someone who holds a grant.

databricks catalogs update prod --isolation-mode ISOLATED
databricks workspace-bindings update-bindings catalog prod \
  --json '{"add": [{"workspace_id": 123, "binding_type": "BINDING_TYPE_READ_WRITE"}], "remove": []}'
  • Access level is read-write (default) or read-only. External locations can be bound too, but not read-only.
  • Setting bindings needs a metastore admin, the catalog owner, or MANAGE.
  • A binding is checked when a privilege is used, so unbinding later does not break existing external tables.

Audit

Who has what, and who changed it

  • Current grants: SHOW GRANTS on an object, and the Permissions tab in Catalog Explorer. You see everyone's grants only with READ METADATA, MANAGE or ownership; others see their own.
  • Which policies apply: SHOW EFFECTIVE POLICIES ON SCHEMA prod.customers.
  • History: system.access.audit (Public Preview) records events. Filter on event_date for speed.
SELECT event_time, action_name, user_identity.email AS actor, response.status_code
FROM system.access.audit
WHERE service_name = 'unityCatalog'
  AND action_name IN ('createPolicy', 'deletePolicy', 'createEntityTagAssignment', 'deleteEntityTagAssignment')
  AND event_date >= current_date() - 30
ORDER BY event_time DESC;

I did not confirm the action names for grant and permission changes, so look at the distinct action_name values in your own table before building an alert.

When something is denied, check in this order

  1. Identity and groups: who is the request really running as? A job runs as its owner or run-as identity.
  2. Entitlement: does it have Workspace access or Databricks SQL access in this workspace?
  3. Object ACL: CAN ATTACH TO on the cluster, CAN USE on the warehouse, CAN RUN on the notebook.
  4. Unity Catalog: USE CATALOG, USE SCHEMA, then SELECT. Run SHOW GRANTS.
  5. Workspace binding: is the catalog bound to this workspace?
  6. Compute: is the access mode and runtime able to enforce filters, masks and ABAC?
  7. Storage: for external files, does the location grant READ FILES?
