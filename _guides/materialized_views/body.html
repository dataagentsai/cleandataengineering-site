What it is

A saved answer that the engine keeps up to date

A materialized view (MV) is a query whose result is stored like a table. Readers query it fast, like any table, and Databricks refreshes it when you ask, on a schedule, or when the sources change. A normal view recomputes on every read. An MV pays once at refresh time instead.

Standalone MVPipeline-defined MV
Created withCREATE MATERIALIZED VIEW in a SQL warehouse or notebookThe same keyword inside a Lakeflow pipeline's source code
Who runs the refreshA backing pipeline Databricks creates for you (shown as type MV/ST under Jobs & Pipelines)Your pipeline
ScheduleSCHEDULE or TRIGGER ON UPDATE in the statementThe pipeline's own schedule or trigger
Good forOne summary table owned by one teamA chain of bronze, silver and gold steps that refresh together

The result sits in cloud storage and Unity Catalog holds its metadata and query. A few helper tables for incremental refresh live in an internal catalog.

Where it runs

Which compute does the refresh

{{WHERE}}
QuestionAnswer from the docs
Which warehouse can create a standalone MV?A Pro or Serverless SQL warehouse, with Unity Catalog. A classic warehouse works for streaming tables but not for MVs.
Which compute does the refresh run on?Serverless. A refresh is run by a serverless pipeline, whether the MV is standalone or defined in a Lakeflow pipeline. For a standalone MV, your workspace does not need serverless pipelines turned on; one is used automatically.
Can it run on classic compute?A pipeline-defined MV can be set up on classic compute, but then every update is a full recompute. Incremental refresh needs serverless.
Can I use a notebook?A notebook on serverless compute, Databricks Runtime 18.1 or later, can create and refresh MVs, with limits: no per-table cost attribution, no async refresh, and a table must be refreshed on the compute type that created it.
Other requirementsUnity Catalog, a region that supports serverless SQL warehouses, and the serverless terms accepted.

Refresh types

Incremental refresh, full recompute and the rest

The two kinds of update

UpdateWhat it doesHow you start it
Refresh (the default)Tries to read only what changed; falls back to a full recompute if it has toREFRESH MATERIALIZED VIEW name, a schedule, a trigger, or a pipeline update
Full refreshAlways recalculates everything and resets all checkpointsREFRESH MATERIALIZED VIEW name FULL, or a pipeline update with full refresh chosen

Both give the same data. The difference is cost and method. Full refresh is also how you pick up a changed UDF library (see s5).

The techniques, as named in the event log

Technique nameMeaning
ROW_BASED, PARTITION_OVERWRITE, WINDOW_FUNCTION, APPEND_ONLY, GROUP_AGGREGATE, GENERIC_AGGREGATEIncremental: only changed data was processed, by this method
FULL_RECOMPUTEEverything was recomputed
NO_OPNothing in the sources changed, so nothing ran

The docs list these names but do not say how each incremental technique works inside. The UI shows the same result as Incremental, Full recompute or No change.

The refresh policy: who decides

PolicyBehaviourUse when
AUTO (default)The cost model picks the cheaper of incremental and fullMost cases
INCREMENTALIncremental whenever possible; falls back to full if the plan no longer allows it. Create fails if the query could never be incremental.You want incremental but can live with an occasional fallback
INCREMENTAL STRICTIncremental or fail. The refresh stops with an error instead of recomputing everything.A surprise full recompute is not acceptable

CREATE MATERIALIZED VIEW sales_summary
  REFRESH POLICY INCREMENTAL STRICT
  AS SELECT region, SUM(CAST(revenue AS DECIMAL(18,2))) AS total_revenue, COUNT(*) AS orders
     FROM main.sales.orders GROUP BY region;

What is supported for incremental refresh

SELECT with deterministic built-in functions and immutable UDFs, GROUP BY, non-recursive WITH, UNION ALL, inner, left, right and full outer joins, WHERE and HAVING, window functions with PARTITION BY, and QUALIFY. Sources can be Delta tables, managed Iceberg tables, other MVs and streaming tables.

Other limits of MVs

  • Not low-latency. Updates take seconds or minutes.
  • No CLONE. An MV cannot be the source or target of a clone.
  • No OPTIMIZE or VACUUM by you; maintenance is automatic. No identity or surrogate-key columns. No renaming or changing the owner.
  • Aliases required on every expression (SUM(x) AS total, not bare SUM(x)).
  • Constraints are informational. Primary and foreign keys are not enforced, though the optimizer can use them (declare with RELY only if they are true).
  • A SUM over a column that becomes all NULL returns 0, not NULL.
  • Expectations: the two doc pages disagree on whether an MV with expectations can refresh incrementally. Test with EXPLAIN.

Cost

What a refresh costs

  • What you are billed: the refresh runs "on serverless compute, billed as serverless Lakeflow pipelines DBUs", on a pipeline separate from your warehouse. Cost scales with the volume of data processed, not the warehouse size. You may see serverless charges even when the warehouse you used is a dedicated one.
  • Price per DBU: the docs I read give no rate for this, so no dollar rate is quoted here. Look up the current Lakeflow pipelines serverless rate for your cloud and plan.
  • Why incremental matters (illustration, not a bill): take a 1 TB source with 1% new data a day. An incremental refresh reads about 10 GB. A full recompute reads 1 TB, about 100 times more. If the work is roughly proportional to the data read, the full recompute costs on the order of 100 times more each day.
  • Storage: the result is stored data, so there is a storage footprint. The docs I read do not say how it is billed.

-- DBUs per refresh pipeline of one MV (from the Databricks docs; fill in your names)
WITH p AS (
  SELECT usage_metadata.dlt_pipeline_id AS pipeline_id
  FROM system.billing.usage
  WHERE usage_metadata.uc_table_catalog = 'main'
    AND usage_metadata.uc_table_schema  = 'sales'
    AND usage_metadata.uc_table_name    = 'sales_summary'
  LIMIT 1)
SELECT u.sku_name, u.usage_date, SUM(u.usage_quantity) AS dbus
FROM system.billing.usage u JOIN p
  ON u.usage_metadata.dlt_pipeline_id = p.pipeline_id
GROUP BY ALL ORDER BY usage_date;

How to know

Six ways to see whether a refresh was full

  1. Before you build: EXPLAIN. Run EXPLAIN CREATE MATERIALIZED VIEW ... with your whole statement (Databricks Runtime 17.3 or later). It prints The Materialized View can be incrementally refreshed. or cannot, then a list of blockers with codes such as OPERATOR_NOT_INCREMENTALIZABLE or INPUT_NOT_IN_DELTA. It checks the shape of the query only, not what the cost model will do later.
  2. After each refresh: the event log. 
    SELECT timestamp, message
FROM event_log(TABLE(main.sales.sales_summary))
WHERE event_type = 'planning_information'
ORDER BY timestamp DESC;
-- e.g. "Flow 'sales' has been planned to be executed as ROW_BASED."
    For a standalone MV only the owner can query its event log directly; share it through a view.
  3. Why it chose that: the detail. The same event holds a technique_information list. Each entry has maintenance_type, is_chosen, is_applicable and incrementalization_issues, so you can read why incremental was not chosen. The docs show a parsing query on their monitoring page; I have not run one.
  4. The cost model said no. When incremental was possible but rejected, look in the event log for INCREMENTAL_PLAN_REJECTED_BY_COST_MODEL events. Reasons include CHANGESET_SIZE_THRESHOLD_EXCEEDED, TABLE_SIZE_THRESHOLD_EXCEEDED and EXCESSIVE_OPERATOR_NESTING.
  5. In the UI. The pipeline or Catalog Explorer view has an Incrementalization column (Incremental, Full recompute, No change). A lightbulb opens the Issues panel. The query profile shows a FLOW_FULL_RECOMPUTE insight explaining why. DESCRIBE TABLE EXTENDED name shows the latest refresh and its type, though the docs do not name the field.
  6. Make it fail. With REFRESH POLICY INCREMENTAL STRICT, a refresh that cannot be incremental stops with the error class MATERIALIZED_VIEW_NOT_INCREMENTALIZABLE and a reason such as ROW_TRACKING_NOT_ENABLED, WINDOW_WITHOUT_PARTITION_BY, UDF_NOT_DETERMINISTIC or EXPRESSION_NOT_DETERMINISTIC.

Also watch the bill: a sudden rise in DBUs for the MV's pipeline in system.billing.usage (s6) is often a quiet switch to full recompute.

Tips and tricks

Practical advice

  • Run EXPLAIN in code review, for every new MV and every change to one.
  • Choose a schedule or trigger that matches the change. SCHEDULE EVERY 1 DAY or a CRON for batch. TRIGGER ON UPDATE [AT MOST EVERY interval] to refresh when sources change (minimum one minute, up to 10 upstream sources per MV, upstreams must be Delta tables, MVs, streaming tables or managed views over them).
  • Use CLUSTER BY or CLUSTER BY AUTO rather than PARTITIONED BY. The docs recommend liquid clustering for MVs.
  • Use ASYNC (REFRESH MATERIALIZED VIEW name ASYNC) for long refreshes you do not want to wait on. The default is SYNC.
  • Declare keys with RELY only when they are true: the optimizer can drop needless joins and aggregations.
  • Use row filters and column masks in the CREATE statement, not added later.
  • Do not run FULL on sources that lose history, such as Kafka. Existing data is truncated and may not come back.
  • After a UDF library upgrade, run REFRESH MATERIALIZED VIEW name FULL on every dependent MV. Databricks cannot see that change.
  • Use PRIVATE MVs inside a pipeline for steps you do not want published.
  • Permissions: to refresh you must own the MV or hold REFRESH on it, and the owner needs SELECT on the base tables.
CREATE MATERIALIZED VIEW main.sales.daily_revenue
  CLUSTER BY AUTO
  REFRESH POLICY INCREMENTAL STRICT
  SCHEDULE CRON '0 0 2 * * ?' AT TIME ZONE 'UTC'
  AS SELECT order_date, SUM(CAST(amount AS DECIMAL(18,2))) AS revenue
     FROM main.sales.orders GROUP BY order_date;   -- sketch: not run
