System tables

System tables in detail

System tables are read-only tables in a catalog called system, inside Unity Catalog. Databricks fills them with operational data about your account: what was used, what it cost, who did what, what ran. You read them with ordinary SQL.

  • The account admin enables each schema, and you grant access like any other table.
  • They are owned and maintained by Databricks. You cannot edit them, add columns or fix a wrong row.
  • The billing tables cover the whole account. Many operational tables cover the workspaces of one region and metastore.
  • Retention is limited, typically around a year, so copy anything you want to keep longer.
  • Data arrives with a delay (minutes for some, hours for billing). Do not use them for real-time alerts.

The most useful query shape: cost per job

Join usage to list prices on SKU and date, then multiply:

SELECT u.usage_metadata.job_id, SUM(u.usage_quantity * p.pricing.default) AS list_cost FROM system.billing.usage u JOIN system.billing.list_prices p ON u.sku_name = p.sku_name AND u.usage_start_time >= p.price_start_time AND (p.price_end_time IS NULL OR u.usage_start_time < p.price_end_time) WHERE u.usage_date >= current_date() - 30 GROUP BY 1

The result is a list-price estimate, not your invoice (see the hidden-information list).

Why querying system tables always costs money

Reading a system table is a query, and a query needs compute. There is no free metadata endpoint. So even the act of asking "what did I spend?" makes a small spend.

  • It needs a running warehouse or cluster. A serverless SQL warehouse burns DBUs while it is up. A dashboard on a schedule keeps it awake.
  • The tables are large. Audit logs, node timelines and query history can have billions of rows. An unfiltered scan reads a lot of data.
  • They are managed by Databricks, and shared to you. You cannot add your own indexes or physically reorganise them. You can only filter by date and columns.
  • Every repeat costs again. The same dashboard opened by ten people runs ten times, unless the result cache catches it.

It is a small cost if you design for it. Done well, the whole cost-tracking system costs a few dollars a month. Done carelessly (a wide dashboard on a big warehouse refreshing every few minutes) it becomes a visible line item of its own.

Copying system tables cheaply, and is Lakebase the answer?

Short answer. Lakebase does not remove the cost of reading system tables. Reading them needs compute, and it still needs compute to copy them. Lakebase can only make later reads cheaper. For a cost dashboard, a small Delta table plus a tiny serverless warehouse is usually cheaper and simpler.

Freshness has a ceiling you cannot beat. Billing usage reaches the system table with a delay of hours. Copying it every minute only copies the same rows many times. Match the copy schedule to how fast each source table updates.

One trap when copying billing data. system.billing.usage can restate earlier rows. A row has a record_type of original, retraction or restatement, and a record_id. If you only append, corrections double count. Copy with a MERGE on record_id, or sum with the record types applied. Also, re-read the last day or two on each run to catch late rows.

System tables

Why are system tables not Delta with UniForm, so reading is free?

Format is not what makes a query cost money. Compute is. Even a perfectly open Delta or Iceberg table needs some engine to read it, and whichever engine you use burns CPU somewhere. UniForm makes one Delta table readable as Iceberg or Hudi too, so other engines can read it. That helps with which engine you use, not with whether you pay for one.

Why Databricks delivers system tables as managed, read-only shared data (I am reasoning from how the product works, not quoting Databricks):

  • The data lives in Databricks' storage, not yours. That keeps storage cost, schema upgrades and access control in one place. If it were in your bucket, you would pay for storage, and they would need write access to every customer's storage.
  • One central pipeline serves everyone. Databricks can add columns and fix data for all customers without touching customer buckets.
  • Governance. Reads go through Unity Catalog and the sharing layer, so permission checks and audit are consistent.
  • Read-only guarantee. A customer cannot corrupt their own audit or billing history.

What would actually make reading cost nothing is an engine you already pay for. Options that exist today: copy to your own Delta table and read it with something cheap, deliver usage logs to your own bucket and read them with DuckDB or Athena (Athena charges per scan, DuckDB on a laptop is free), or look at the account console.
