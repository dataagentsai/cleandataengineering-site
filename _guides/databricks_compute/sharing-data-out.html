Sharing data in and out

Two directions, and three layers

Two questions get mixed up. Part A: how can someone else read data that Databricks owns? Part B: how can Databricks read data that someone else owns? Each has its own set of methods. Every method below has a picture of how it works inside, a list for when to use it, and a list for when not to.

LayerThe question it answersNames you will meet
1. Reading the data"Can they read my table, safely, without me copying it?"Delta Sharing, Marketplace, SQL warehouse, Lakehouse Federation
2. Computing without seeing"Can we answer one question together without either of us showing our rows?"Clean room
3. File format and catalog"Can another engine read the same files?"UniForm, Iceberg REST catalog, catalog federation, managed Iceberg tables

Delta Sharing is a protocol (layer 1). A clean room is a product that uses it (layer 2). UniForm is a file format trick (layer 3) and shares nothing by itself.

Part A · others read what Databricks owns

A1. Delta Sharing, Databricks to Databricks

Both sides use Unity Catalog. The recipient mounts your share as a catalog in their own workspace and queries it like any other table. Nothing is copied.

Under the hood

  • It is a live read of your table, not a snapshot. The recipient sees new commits as you make them.
  • The recipient can read tables, views, volumes, notebooks and AI models, and can read the table history or stream the changes.
  • Access is read-only, and you can revoke it at any time. Links expire in minutes, so revoking takes effect quickly.
  • Governance, audit and lineage stay in Unity Catalog on both sides.
Use it whenDo not use it when
  • The partner is also on Databricks with Unity Catalog
  • You want live data with no pipeline and no copy
  • You need to revoke or audit access
  • You share inside one company across accounts or clouds
  • The partner is not on Databricks (use open sharing)
  • The partner must not see rows at all (use a clean room)
  • The partner is in another region or cloud and will read big tables repeatedly: transfer fees add up, so replicate once
  • You need the partner to write back

Cost, performance and security

Cost and performanceSecurity
  • No pipeline and no copy, so no extra storage for the recipient.
  • You pay for storage and for the storage requests their reads make. They pay for their compute.
  • Reads go straight from storage in parallel, so scan speed is good. The first query adds a short round trip to the sharing service.
  • Cross-region or cross-cloud reads are charged by the cloud provider, normally to the data's owner.
  • Access is a grant to one named recipient. It is read-only and can be revoked.
  • Signed links are short-lived and cover only the files for that query.
  • Access is recorded in audit logs. No token exists to leak.
  • Once rows are read the recipient can copy them. To limit this, share a view with row and column rules, not the base table.

A2. Delta Sharing, open sharing

The same protocol, but the recipient is not on Databricks. They use a credential and any tool that has a Delta Sharing client.

Under the hood

  • The credential is a token with an expiry. You must rotate it and treat the file like a password.
  • The protocol is open, so any tool with a client can read. Databricks does not need to be on the other side.
  • You can share a table, a view, or a slice, and use dynamic views for row and column filtering.
  • Compute for reading is the recipient's, billed to them. The storage requests land on your bucket.
Use it whenDo not use it when
  • The partner is on another platform, or on nothing but a Python notebook
  • You want governed, revocable, audited access
  • The partner is a different company
  • The partner is on Databricks (use the Databricks to Databricks route, with no token to rotate)
  • The partner is a warehouse engine such as Athena or Redshift with no client (see the AWS section below)
  • You cannot manage token rotation

Cost, performance and security

Cost and performanceSecurity
  • Same cost shape as A1: your storage requests and transfer, their compute.
  • Very wide client support, but each client's speed depends on its own engine.
  • The bearer token works like a password. Anyone holding it can read until it expires or you revoke it.
  • Set a short expiry, rotate it, and add an allowed IP list for the recipient where you can.
  • Prefer federated login through your identity provider over long-lived tokens.
  • Share views, not base tables, if rows or columns must be limited.

A3. Clean room, taught from zero

Everything so far hands the other side rows. A clean room is for when you must not.

The problem it solves

A shop knows who bought what. A brand knows who saw its online advert. Together they could answer a valuable question: "Of the people who saw the advert, how many bought?" To answer it, somebody has to match the two customer lists. But neither side may hand its list to the other. Customer lists are private, and privacy law forbids passing them around.

The old ways, and why they fail

  • Swap the lists. Now each side holds the other's customers. This is exactly what you were not allowed to do.
  • Give both lists to a third party. You moved the risk to someone else, and you must trust them completely.
  • Hash the emails and swap those. Better, but the other side can still test any email they already know against the hashes.

The clean room idea

Build a locked room. Both sides place their data inside it, and neither can look at the other's rows. The only thing that runs in the room is a piece of code that both sides have read and approved. Only the result of that code comes out, for example a count, never the rows.

Under the hood

PromiseHow it is kept
Raw data is not handed overEach side keeps its tables in its own account. They are shared into the room using Delta Sharing, so the other side can see names and columns but not rows. Rows are only touched by approved code.
Only agreed code runsA notebook is proposed by one side and must be approved by the others before anyone can run it. Changing the code means approving again.
Results are limitedThe approved notebook runs on serverless compute that Databricks manages, and only its output tables come out, to the party that ran it.
You can prove what happenedRuns and approvals are recorded in an audit log.

Where a clean room can still leak. The room guarantees who approved what code. It does not judge whether the output is safe. A notebook that simply wrote out one customer per row would be approved and would run. So the privacy rule has to be written into the notebook and checked by the reviewers: for example, never output a group smaller than 100 people, and never output a column that identifies a person.

Industry idea, Databricks product

"Data clean room" is an industry idea that began in advertising. Snowflake, AWS, Google, LiveRamp and others sell their own versions, and they enforce privacy in different ways (query rules, thresholds, encryption). Databricks Clean Rooms is Databricks' version, built on Delta Sharing and Unity Catalog. When a client says "clean room", ask which one they mean.

Use it whenDo not use it when
  • Two parties must analyse data together and neither may reveal raw rows: ads measurement, shared-customer overlap, joint research, fraud signals across a bank and an insurer
  • You can state the question in advance, because the approved code is the room
  • The other party is allowed to see the rows. Use Delta Sharing; it is simpler and cheaper.
  • You only want to publish a dataset to many buyers (use Marketplace)
  • You do not yet know the question you want to answer together
  • Nobody will review the code properly. Then the room gives false comfort.

Cost, performance and security

Cost and performanceSecurity
  • Each run uses serverless compute that is billed, and each side still pays for its own storage.
  • It is built for scheduled or on-demand batch analysis, not for interactive lookups. Expect start-up time per run.
  • Agree who pays for runs before you build the room.
  • The strongest privacy of any route: neither side sees the other's rows.
  • Only approved code runs, and each change needs approval again. Runs are audited.
  • The weak point is the notebook itself. Review it for minimum group sizes and for any column that identifies a person.
  • Limit what the output may contain, and who may read the output tables.

A4. Marketplace

A catalogue of listings built on top of Delta Sharing. It adds discovery, requests, approvals and optional payment. The data still moves by sharing.

Under the hood

  • Marketplace is a listing and approval layer, not a different transport. Reads are Delta Sharing reads.
  • Listings can carry notebooks, models and sample queries so a consumer can try the data fast.
  • You still carry the sharing, storage-request and transfer costs of every consumer's reads.
Use it whenDo not use it when
  • Many consumers, some you do not know yet
  • You are selling or publishing a dataset or an AI model
  • You want a place consumers can discover and try the data
  • One known partner. A direct share is simpler.
  • The data is private and must not be browsable
  • You cannot afford many consumers reading across regions

Cost, performance and security

Cost and performanceSecurity
  • Costs grow with the number of consumers, because each one's reads hit your storage and may cross regions.
  • Free listings can still run up transfer fees for you.
  • A public listing is visible to everyone. Never list data that is sensitive, even if you intend to approve requests.
  • Use private listings and approval for anything controlled.
  • State the terms of use in the listing. The platform can revoke access, but it cannot stop misuse of data already read.

A5. UniForm and the Iceberg REST catalog

This lets your own other engines read the same files you already have, as an Iceberg table, under Unity Catalog permissions.

Under the hood

  • UniForm writes Iceberg metadata after each Delta commit, pointing at the same Parquet files. There is one copy of the data in two formats.
  • The metadata is produced after the commit, so an Iceberg reader can be a little behind. Test the lag before promising freshness.
  • Managed Iceberg tables are natively Iceberg in Unity Catalog, with no Delta log at all. They are a different table type, not a view of a Delta one.
  • The consumer must be trusted. It receives storage credentials, so the permission check happens at the catalog, not on every file.

Use it whenDo not use it when
  • Your own Snowflake, Trino, Flink or EMR should read tables Databricks writes
  • You want one copy and no pipeline
  • You are moving toward an open lakehouse with several engines
  • The reader is another company (use Delta Sharing)
  • You need a recipient, expiry and revoke built in
  • You cannot test the metadata lag against your freshness promise

Cost, performance and security

Cost and performanceSecurity
  • No Databricks compute is used for reads. The other engine's compute is billed to them.
  • Direct Parquet reads are fast when files are well sized. Many small files slow every engine, so compact them.
  • UniForm adds a small amount of work after each write to produce the Iceberg metadata.
  • Check that table features you use, such as deletion vectors and column mapping, are supported by the Iceberg reader.
  • The engine receives short-lived storage credentials, so you must trust that engine and whoever runs it.
  • Row filters and column masks are enforced by Databricks compute. An engine reading files directly bypasses them, so tables that use them generally cannot be exposed this way. Check the current rules.
  • Scope the credentials to the table, keep them short-lived, and watch access logs on the bucket.

A6. SQL warehouse API, JDBC and ODBC

The consumer does not get tables. It sends SQL and gets answers back. Databricks does the reading with its own compute.

Under the hood

  • Every query uses warehouse compute and is billed, so many small queries on a stopped warehouse can cost more than expected from start-up time.
  • Row filters and column masks apply because it is Databricks that runs the query.
  • Result size and result cache both matter: the same query repeated may be answered from cache.
Use it whenDo not use it when
  • Apps, dashboards and services that need answers, not tables
  • You want all governance applied by Databricks
  • The consumer is small and cannot run an engine
  • Bulk extraction of whole tables. It is slow and uses warehouse time. Share or export instead.
  • The consumer wants to join your data with theirs using their own engine
  • You need sub-second lookups for thousands of users (use a serving layer)

Cost, performance and security

Cost and performanceSecurity
  • Warehouse compute is billed by the second. A stopped warehouse adds start-up time to the first query.
  • Photon and the result cache make repeat queries cheap and fast.
  • Concurrency is limited by warehouse size and clusters. Spikes queue up.
  • Pulling large tables through it wastes warehouse time and is slow.
  • The strongest enforcement of the Part A routes: Databricks runs the query, so row filters, column masks and grants all apply.
  • The consumer sees only results. Every query is in the audit log.
  • Use a service principal with least privilege per app, OAuth rather than shared personal tokens, and private networking or IP allowed lists.

A7. Push to another system

Instead of waiting for someone to read, your job writes the rows into the system that needs them: an operational database, a queue, a CRM or a serving store.

Under the hood

  • The target gets a copy. If the source changes, the copy is wrong until the next push.
  • Retries happen. Make every write idempotent with a business key, or use the sink's exactly-once feature where it exists.
  • Too many parallel connections can overload the target. Cap the number of write partitions.
Use it whenDo not use it when
  • An operational system must hold the data in its own store
  • The target must be fast and independent of Databricks
  • Events must reach a queue or a stream
  • Only analysts read it. Share it instead and avoid a second copy.
  • You cannot make the writes idempotent
  • The target cannot take the load

Cost, performance and security

Cost and performanceSecurity
  • You pay job compute plus the target's write cost. Network transfer applies if the target is elsewhere.
  • Speed is set by the target's write rate. More parallel connections is faster but can overload it.
  • Target credentials belong in a secret scope, never in the notebook.
  • After the push the data lives outside Unity Catalog. Row filters and masks do not follow it.
  • Use TLS to the target and a write-only account limited to the tables it needs.
  • Personal data is now in a second place that must be deleted too.

A8. File export

You write files to a bucket or an SFTP drop and the other side collects them. It is the oldest way and the weakest.

Under the hood

  • A snapshot goes stale the moment it is written.
  • Add a manifest or a marker file when the folder is complete, or the receiver may read half-written files.
  • Expire old folders. Every export is a copy somebody else may keep for ever.
Use it whenDo not use it when
  • The receiver can only take a file (a regulator, an old system)
  • A one-off hand-over where live access is not worth building
  • Anything where a live route exists
  • Data that must be revocable
  • Large volumes repeated daily. It gets expensive and drifts.

Cost, performance and security

Cost and performanceSecurity
  • Compute to write, storage for the copies and transfer for the download. Every run makes a new copy.
  • Large sequential Parquet files are fast to write and fast to download.
  • The weakest route. Once downloaded there is no audit and no revoke.
  • Encrypt at rest, give the receiver short-lived signed links or a scoped credential, and expire old folders.
  • Keep personal data out of file names. Remove or mask sensitive columns before export.

B1. Lakehouse Federation (query federation)

Databricks queries an external database in place. An admin makes a connection and a foreign catalog, and the remote tables then look like tables in Unity Catalog.

Under the hood

  • No data is stored in Databricks. Each query reads the source again, so the source carries the load.
  • Pushdown decides the speed. A filter or aggregate that cannot be pushed down means pulling many rows across the network.
  • Governance is Unity Catalog's: grants on the foreign catalog, with the connection's own credential used on the remote side.
  • Credentials sit in the connection, so one account at the source serves everyone allowed to use the connection.
Use it whenDo not use it when
  • Exploring or prototyping before you decide what to ingest
  • Occasional joins of your lakehouse data with a small reference table
  • One-off analysis
  • Source data must stay where it is
  • The same big query runs often. Ingest instead, so the source is not hit each time.
  • Large joins across the network
  • The source database is busy production and cannot take analytic reads
  • You need history, time travel or Delta features on that data

Cost, performance and security

Cost and performanceSecurity
  • Cost is warehouse compute, the load on the source, and network transfer. There is no storage cost in Databricks.
  • Speed depends on pushdown. A filter that is pushed down is fast, and one that is not drags many rows across the network.
  • Each run is slower than reading Delta, and cannot use Delta data skipping or caching of the source.
  • A heavy federated workload can slow or cost money on the source side.
  • The connection uses one account at the source for everyone allowed to use the connection. A user may see more than their own source rights allow.
  • Use a least-privilege, read-only source account limited to the schemas you want to expose.
  • Grant the foreign catalog only to the right groups.
  • Open the source firewall only to Databricks' network, or use private connectivity. Credentials sit in the connection, not in notebooks.

B2. Catalog federation

The data is files in cloud storage, but another catalog (a Hive metastore, AWS Glue, Snowflake's open catalog or another Iceberg REST catalog) owns the metadata. Databricks asks that catalog which files, then reads the files itself.

Under the hood

  • Compared with query federation, the other engine's compute is not used at all, so it carries no load.
  • Reading is allowed to follow the other catalog's metadata, so what you see can be briefly behind its latest commit.
  • Unity Catalog governs who in Databricks may read. You must still give Databricks permission on the bucket.
  • Check which catalogs and table formats are supported in your region before you rely on this.
Use it whenDo not use it when
  • Another engine owns and writes the table, and you want to read it from Databricks with no copy
  • A lake that is governed by Glue or Snowflake today
  • You are migrating slowly and both worlds must see the same data
  • The source is a normal database, not files (use query federation)
  • You need to write to the table from Databricks
  • The other catalog cannot be reached from your network

Cost, performance and security

Cost and performanceSecurity
  • Your compute and storage request charges at their bucket. The other engine's compute is not used.
  • Direct Parquet reads are near-native speed when file sizes are good.
  • Metadata lookups add a round trip, and results may trail the other engine's latest commit.
  • You need cross-account access to their bucket. Use a read-only role limited to the table paths.
  • The other catalog's own permissions are not mirrored. Define who in Databricks may read, using grants on the foreign catalog.
  • Row and column rules defined in the other engine are not enforced when Databricks reads files directly.

B3. External locations, external tables and volumes

You point Unity Catalog at a folder in cloud storage, give it a credential, and then define tables or volumes over that folder. Databricks reads in place.

Under the hood

  • Set-up is once per folder: a storage credential (an IAM role or managed identity) and an external location with the path.
  • A table over files you do not manage gets none of the automatic maintenance that managed tables get. Compaction and clean-up stay your job.
  • Other writers can change the files while you read. A Delta table makes that safe, but a folder of CSVs does not.
Use it whenDo not use it when
  • Files are produced by other systems and you only need to read them
  • A shared lake that other engines also use
  • Raw landing folders, before ingestion
  • Unstructured files such as PDFs and images (volumes)
  • Nobody else uses the data. A managed table is cheaper to run, because Databricks looks after it.
  • The bucket belongs to another organisation you do not fully trust
  • You need strong consistency while another system rewrites the files

Cost, performance and security

Cost and performanceSecurity
  • You pay for storage requests, and nothing is optimised for you. Compaction and clean-up of files you do not manage stay your responsibility.
  • Managed-table features such as automatic maintenance mainly cover managed tables. Plan maintenance for external ones.
  • Speed depends on the folder's file layout and format.
  • The credential is scoped to a path and is the key to everything under it. Give the IAM role or managed identity only the folders you need.
  • Do not let external locations overlap, and restrict who can read raw paths directly, because that bypasses table-level grants.
  • Grants on the external table are checked by Unity Catalog, but anyone with the storage role outside Databricks is not.

B4. Delta Sharing as a recipient

This is A1 and A2 seen from the receiving side. A provider shares tables with you, and you mount the share as a read-only catalog.

Under the hood

  • It is read-only and live. You see what they publish, when they publish it.
  • You do not control the provider's history, retention, schema changes or when they revoke.
  • If the provider is in another region or cloud, every read can carry transfer fees. One fix is to copy once into your own region.
Use it whenDo not use it when
  • A partner or vendor publishes data you want to use without a pipeline
  • Public or commercial data from a marketplace
  • You need current data and cannot wait for a file drop
  • You need to modify, annotate or keep history the provider will not keep (copy it first)
  • You will scan the same big remote table many times (copy it once)
  • You need guaranteed availability outside the provider's control

Cost, performance and security

Cost and performanceSecurity
  • You pay for your compute. The provider pays for storage requests and often the transfer, so providers may limit heavy use.
  • Reads depend on network speed to the provider's storage. Repeated scans of a big remote table are slow and costly. Copy it once instead.
  • Treat shared data as untrusted input. Validate schema and values before joining it into your trusted tables.
  • The provider can see which of their tables you read.
  • Keep your own sensitive data out of the shared catalog, and grant read on the shared catalog only to those who need it.

B5. Lakeflow Connect (managed connectors)

Databricks runs the connection for you. It reads changes from a SaaS app or a database, lands them, and keeps your tables up to date incrementally.

Under the hood

  • It is a copy. You pay for the pipeline compute and the storage, and you gain speed and independence from the source.
  • For databases, change capture needs the source's change log enabled and a small gateway that reads it.
  • The list of supported sources grows and has limits per source. Check it before designing around a connector.
Use it whenDo not use it when
  • The source is a supported SaaS app or database
  • You want incremental loading with little code
  • Many sources, one pattern
  • Your source is not on the list. Use files, streams or JDBC.
  • You need to reshape the data before landing it
  • A tiny one-off pull. A notebook is faster to build.

Cost, performance and security

Cost and performanceSecurity
  • You pay pipeline compute, staging storage and the target tables. Source API call limits can cap how fast you load.
  • Incremental loads are far cheaper and faster than full reloads, and change capture puts little load on the source.
  • Create a dedicated read-only source user or app with the minimum scopes. Keep credentials in a Unity Catalog connection.
  • Personal data now lands in bronze tables. Apply masks and access grants on arrival.
  • Network access to the source must be allowed. Use private connectivity where offered.

B6. Auto Loader (files landing in storage)

Other systems drop files into a bucket. Auto Loader notices new files and ingests each one exactly once.

Under the hood

  • Listing mode is simple but slows down in a very large folder. Notification mode scales better and needs some cloud set-up.
  • The checkpoint is the memory. If you delete it, files are read again.
  • It can run continuously or as a scheduled batch that stops when there is nothing new.
Use it whenDo not use it when
  • Files arrive over time from other systems
  • Millions of small files you cannot track by hand
  • The schema may drift
  • A handful of files read once. A plain read is simpler.
  • The source is a database or a message stream
  • Files are overwritten in place. Auto Loader expects new files, not changed ones.

Cost, performance and security

Cost and performanceSecurity
  • Listing a huge folder gets slow and makes many storage requests. Use event notifications for big or busy folders, which need a small queue set-up cost.
  • Reading is parallel and scales with the cluster. A scheduled run that stops when idle is cheaper than a stream that never stops.
  • Whoever can write to the landing folder can inject data. Limit write access to the known sources.
  • Use the rescued data column or a quarantine table for bad records, and validate before promotion.
  • Encrypt the bucket and restrict who may read raw files.

B7. Streaming sources: Kafka, Event Hubs, Kinesis, Pub/Sub

Events live in a broker for a while. A Structured Streaming query reads them in order and remembers how far it got.

Under the hood

  • If the query is down for longer than the broker's retention, events are gone. Size retention for your worst outage.
  • Delta as the sink makes the write exactly-once, so replays do not duplicate rows.
  • Latency is seconds. Real-time lookups still belong in a serving layer.
Use it whenDo not use it when
  • Events arrive continuously and need to be queryable within seconds or minutes
  • You need replay after a failure
  • Data is daily or hourly and a batch is fine. A stream costs an always-on cluster.
  • You need answers in milliseconds for an app (use a serving layer)

Cost, performance and security

Cost and performanceSecurity
  • A running stream keeps a cluster on all day. Where seconds are not needed, a scheduled run that processes what has arrived is much cheaper.
  • Broker throughput units or partitions are a separate bill at the cloud.
  • Latency is seconds. Throughput scales with partitions and cluster size.
  • Broker credentials belong in secrets. Use TLS and a topic-level read-only permission.
  • Events can carry personal data. Apply masks when they land.
  • Producers can send malformed events. Parse defensively and send bad ones to a dead-letter table.

B8. JDBC and custom connectors in a job

You write the reading code. Spark opens several connections to the source and reads slices of a table in parallel.

Under the hood

  • Without a partition column, Spark uses one connection and one task, so a large table is read very slowly.
  • Each connection loads the source. Cap the partition count so you do not overload it.
  • Custom Python or REST code runs on the driver or in functions. Large API pulls need their own paging and retries.
Use it whenDo not use it when
  • No managed connector or federation covers the source
  • You need custom logic, paging or authentication
  • A one-off or rare extraction
  • A managed connector exists. It handles incremental loading and retries for you.
  • The table has no good numeric or date key to slice on
  • The source is production at its busiest hour

Cost, performance and security

Cost and performanceSecurity
  • The source carries the load of every slice query, and a missing partition column makes it one slow read.
  • Memory on the driver limits how much a custom API loop can hold. Keep results streaming into Delta.
  • Never put a password in the JDBC URL in a notebook. Use a secret scope or a Unity Catalog connection.
  • Use a read-only database user, and allow only Databricks' network at the source.
  • If you build queries from user input, parameterise them, or you invite SQL injection.

Why not Delta Sharing for Athena and Redshift?

Delta Sharing needs a client on the reading side: a connector that asks the sharing server for signed file links and downloads the files itself. Spark, pandas, Power BI and similar tools have one. To my knowledge Athena and Redshift do not, because they read through the AWS Glue catalog and Lake Formation instead. To use Delta Sharing with them you would build a Glue or EMR Spark job that reads the share and writes a copy into S3 or Redshift. That brings back a pipeline and a staleness window. Other reasons it fits badly inside your own AWS estate:

  • The reader must understand the table's Delta features, and some AWS-side readers lag behind newer ones.
  • Every read goes through signed links, which suits modest tables more than large warehouse scans.
  • Delta Sharing is built for crossing an organisation boundary. Inside your own estate that boundary only adds cost.

Use Delta Sharing for an AWS party that is a different organisation, or for one that reads through a Spark or pandas client.
