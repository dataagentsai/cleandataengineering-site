Why

Why serverless feels opaque

Classic compute runs on machines in your cloud account, so you can look inside them. Serverless runs in Databricks' account, so you get no machines to inspect. Databricks says Spark logs are not available for serverless notebooks and jobs (you only get client-side application logs), and the Spark UI is not available (the query profile replaces it). There is no host access and no way to install a monitoring agent.

What you want to seeClassic computeServerless
Spark UI (stages, tasks, skew)YesNo. Use the query profile and query insights.
Driver and executor logsYesNo Spark logs. Client-side application logs only.
Machine CPU and memory over timeYes, including system.compute.node_timeline for all-purpose and jobs computeNo machines to measure
Cluster start, resize and stop eventsYesNot applicable
Cost split by machine tagYes, tags reach the cloud billNo. Use budget policies and job or warehouse ids.
Cost per run, in DBUsYesYes. job_run_id is filled in for serverless jobs.
Per-query detailYesYes. Query history covers SQL warehouses and serverless notebooks and jobs.

So serverless is not blind. You trade machine-level detail for query-level and run-level detail.

An account admin can set a longer retention for system tables (in Beta at the time of the docs I read, with 395 days free). Billing and audit tables are the ones to copy out before they age off.

Extract

How to get it out programmatically

RouteUse it forNeeds a warehouse?
SQL on system tables (SQL connector or SDK)Billing, compute, lineage, audit and run timelinesYes. The smallest one works.
Query history API (GET /api/2.0/sql/history/queries)Queries on warehouses and serverless, with filters by time, user and status. It works without Unity Catalog.No, it is a control-plane call
Jobs API (/api/2.1/jobs/runs/list and run details)Run start and end, duration, task outcomesNo
Clusters API events (/api/2.0/clusters/events)Start, resize and terminate on classic clustersNo
Audit log deliveryWorkspace audit events delivered as JSON or into system tablesNo for JSON files. Yes to read the table.

Rules that keep it cheap and correct: pull only new rows using a time watermark, re-read the last few days because billing rows can be corrected late, and upsert by key.

A sketch (not run against a workspace, so test it first)

# 1) system table, incremental, smallest serverless warehouse
from databricks import sql
conn = sql.connect(server_hostname=HOST, http_path=WAREHOUSE_PATH, access_token=TOKEN)
cur = conn.cursor()
cur.execute("""
  SELECT * FROM system.billing.usage
  WHERE usage_date >= date_sub(current_date(), 3)   -- re-read recent days
""")
rows = cur.fetchall()          # upsert into your store by record_id

# 2) query history, no warehouse needed
from databricks.sdk import WorkspaceClient
from databricks.sdk.service.sql import QueryFilter, TimeRange
w = WorkspaceClient()
queries = w.query_history.list(
    filter_by=QueryFilter(query_start_time_range=TimeRange(start_time_ms=START_MS, end_time_ms=END_MS)),
    include_metrics=True)

# 3) job runs since the last watermark
for run in w.jobs.list_runs(start_time_from=START_MS, expand_tasks=False):
    pass                         # store run_id, start, end, state, job_id

Method and field names in the SDK change between versions, so check them against the version you install.

Best setup. Two small scheduled jobs: one that calls the APIs, and one that runs the daily system-table pull. Both write to your own store. Everything you ask later runs there, not on Databricks.

Checked

What was checked, and what was not

  • Serverless limitations (no Spark UI, no Spark logs on serverless notebooks and jobs, query profile instead)
  • System tables (schemas, retention, serverless fields)
  • Query history API, plus community and third-party descriptions of the Jobs and Clusters APIs
  • A monitoring vendor's summary of what serverless exposes

Not confirmed: the retention of node_timeline and query.history (sources disagree), the details of cluster log delivery to your storage, API rate limits, whether every endpoint needs no warehouse, the SDK method signatures, and the exact system table list for your region. Check each in your workspace.
