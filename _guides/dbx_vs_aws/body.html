The setup

Two stacks, compared like for like

Both stacks keep data as Parquet files in S3 and add a table layer on top. The question is who supplies the table format, the catalog, the engine, the upkeep and the governance, and what each choice costs you in money and in people.

Read this first. Features, prices and limits on both sides move quickly. The comparison is from the author's knowledge, not a live price check. Use it to decide what to measure, then run the same pipeline, the same SQL and the same Power BI report on both and compare monthly cost.

This page is the wide comparison. For the narrower question of who owns the catalog, see Iceberg lakehouse on AWS and Databricks: who owns the catalog?

Format

Format and openness

  • A is native Iceberg. Spark, Trino, Flink, Athena, Snowflake and DuckDB can read and write it, so no single product owns the table.
  • B is Delta. UniForm writes Iceberg metadata after each commit, so outside engines can read but not write. The metadata can lag a little, and some Delta features do not carry across. Databricks also offers managed Iceberg tables in UC; check how mature that is before you rely on it.

Compute

Compute, serverless and performance

  • A: EMR on spot instances and Graviton is the cheapest per hour. EMR on EC2 starts in minutes. EMR Serverless and Glue start faster. You tune memory, versions and libraries yourself.
  • B: Photon (a vectorised engine) usually speeds up scans, joins and MERGE. Serverless starts in seconds. You pay a DBU premium on top of the machines.
  • Each vendor publishes benchmarks that favour itself. Measure your own pipeline.

Winner: A for price per hour and control, B for start-up time and effort. Raw performance is a tie until you measure. See Databricks compute and cost.

Compression is not a differentiator. Both write Parquet and you can choose the same codec. File size and layout decide real speed and storage cost. Without S3 Tables, plain Iceberg on EMR means you schedule rewrite_data_files, expire_snapshots and remove_orphan_files yourself.

Winner: B for breadth (layout and automatic keys). A is simpler to predict. More: who maintains your tables, maintenance strategy, slow writes.

Write path

Optimized write and AQE

  • Optimized write is an extra shuffle before the write so files come out a good size. Iceberg has the same idea as a setting, the write distribution mode (hash or range). Same mechanism, different switch. Winner: tie.
  • AQE (adaptive query execution) is open-source Spark, on by default in recent versions, so EMR and Glue have it too. It merges small shuffle partitions, switches join strategy at run time and splits skewed partitions. Databricks adds some tuning on top. Winner: tie.
  • Neither fixes a bad partition count before a write or a bad table layout.

BI

Power BI, metric views and the semantic layer

  • B: Power BI has a native Databricks connector with Import and DirectQuery on a SQL warehouse. It passes the user's identity to UC and respects row and column rules. Photon and result caching handle concurrency well. UC metric views define measures once for SQL, dashboards and Genie (and mean more lock-in).
  • A: Power BI has no good direct Iceberg connector. You go through Athena (billed per TB scanned, awkward for DirectQuery), Redshift or a Trino service, usually with a gateway. You can also shortcut S3 into Fabric OneLake, which adds a second platform. There is no catalog-level metric layer.

Winner: B, clearly. More: Power BI vs Databricks AI/BI, metric views.

Hero features

What you miss if you leave Databricks out

  • Photon, Predictive I/O and liquid clustering
  • Lakeflow declarative pipelines, Auto Loader and Lakeflow Connect managed connectors
  • UC lineage, tag-based rules and system tables for cost and audit
  • Delta Sharing and clean rooms
  • Genie, AI/BI dashboards and metric views
  • Model serving, Vector Search and agent tools inside the same governed place
  • Databricks Apps and Lakebase (Postgres)
  • Serverless that starts in seconds, and repair run for failed jobs

Where AWS-native wins

  • Lower compute cost for large steady ETL on spot and Graviton
  • Real multi-engine Iceberg with several writers
  • One vendor, one bill, existing AWS commitments, IAM everywhere
  • Athena for occasional ad-hoc queries without a warehouse
  • Zero-ETL from AWS databases and Managed Flink for streaming
  • Less lock-in, with S3 Tables maintenance that needs no extra product

What this changes in the comparison. Four things matter most for the decision. (1) Managed Iceberg tables in UC are tied to Predictive Optimization, so "Iceberg on Databricks" is not independent of the managed stack. (2) UniForm stays read-only, so a multi-writer design must be Iceberg-native. (3) Fine-grained Lake Formation on EMR works but with a long list of conditions, so test your exact EMR release and mode. (4) Power BI on metric views is the least settled part of the Databricks story, so pilot it before promising it.

What this list cannot show. Support tickets and escalations raised by real customers are private to those customers, so neither vendor publishes them. The limits above come from public documentation and a few public user reports. Before you commit, ask each vendor's account team for known issues on your exact runtime and region, and pilot on your own data.

The pattern. Databricks wins where the value is one connected product: lineage, governance, declarative pipelines, Power BI, metric views. AWS-native wins where the value is cost, control and openness: compute price, multi-engine Iceberg, AWS integrations, no second vendor. The decision depends less on features and more on whether you have a platform team to do the assembly work.
