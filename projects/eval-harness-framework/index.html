Eval Harness Framework

One framework to check AI agents with any provider's evals, guardrails, cost and business rules.

Active · join meAI EngineeringForward-deployed ready

7 of 13 tasks done

1 · Purpose

The Eval Harness Framework checks AI agents for quality, security, cost and a business's own rules. It mixes checks from several providers in one run and gives one result format. It is for teams running agents who already use tools such as LangSmith, Langfuse or Application Insights and are tired of writing glue between them. It brings no database, UI or dashboards of its own: it reads from and writes back to the tools a team already has.

For: Teams running AI agents in production, AI platform teams, ops and quality leads.

2 · Business benefits

Write the glue onceOne adapter per provider replaces the custom code teams write each time they combine two eval tools.
Best check for each jobA team can take three checks from one provider and five from another, with one comparable result.
No new platform to buyResults go back into the team's existing tracing and dashboards, so nothing new to run or pay for.
Business rules, not just scoresOps teams write rules like "no cancel without an order lookup first" in YAML.
Cost and security in the same runCost rules and personal-data checks run alongside quality checks.

4 · Requirements

What it must do

  • Runs checks from Azure AI Evaluation, DeepEval, Ragas and Presidio through one request and result shape.
  • Loads which checks run, and where, from a YAML file a team can read on one screen.
  • Ships a customer-support preset that a team's file overrides field by field.
  • Checks whole conversations with five domain patterns, such as an action that needs another action first.
  • Lets a free hosted model act as judge, so no paid cloud account is needed.
  • Is already used by the support agent and the claims agent.

How well it must do it

  • No vendor SDK is imported outside its own adapter.
  • Every adapter must pass the same contract test table for its port.
  • Deterministic code checks come before judge models.
  • Version 1 must install with one command and produce a first report within an hour.
  • A feature is added only when a real team asks for it, or it replaces something.

9 · What you'll learn

  • How the main eval and guardrail tools differ in their data shapes.
  • How ports and adapters keep vendor code in one place.
  • Why checking and deciding are separate steps.
  • How to write a business rule that checks a whole conversation.
  • How OpenTelemetry carries evaluation results.
