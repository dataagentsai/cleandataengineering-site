1 · Purpose

This is a motor insurer's first-notice-of-loss (FNOL) assistant: the moment a policyholder first says "a bus hit my car". It registers the claim, gives a reference, answers status questions and pays small payouts; anything larger, or anyone hurt, goes to a person. It runs on Azure and reuses the support agent's harness library, which supplies about 84% of the code it runs. It proves the harness carries to a second domain and a second cloud, and it is the running example in the agent harness course.

For: Insurance and financial-services technology teams, Azure architects, course participants.

4 · Requirements

What it must do

  • Registers a motor claim from a conversation and returns a claim reference.
  • Answers claim status from the claims system without calling the model.
  • Pays payouts up to the limit at once and holds larger ones for a handler on the desk.
  • Hands any injury, or a request for a person, to a claims handler.
  • Lets policyholders sign in and see only their own claims.
  • Politely refuses questions about cover, which are left to an assessor.

How well it must do it

  • The claims system verifies a short-lived token on every call and trusts nothing the agent asserts.
  • Each app uses its own database role; no app runs as the admin.
  • A tool's idempotency key comes from the message, so a crash cannot register a claim twice.
  • The payout limit is read from configuration, so it changes without a redeploy.
  • Infrastructure is code, with each service's free allowance checked before it is added.
  • The same scenarios and four gates run on a laptop before anything reaches Azure.

5 · Architecture, very high level

Also: Chat page and handler desk → Agent: message · Agent → Claims system: tool call with token · Agent → Durable waits: payout over limit · Durable waits → Chat page and handler desk: approval request · Agent → State store: turn saved · Agent → Telemetry and alerts: trace
