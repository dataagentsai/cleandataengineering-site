Data modeling

Table layouts, dimensional models, materialized views and Unity Catalog Metric Views.

This section tests whether you can lay out big tables so files stay well sized and queries skip most data, and whether you can serve reports from pre-computed or governed definitions. The biggest way people lose marks is choosing a layout by habit (partition by date) instead of by the grain of the data and the columns queries actually use.

9.1 Design scalable Delta/Iceberg table layouts for large data assets by mapping partitioning to data grain, aligning clustering to relationship access patterns, and maintaining balanced file sizes through compaction.Table layout means how rows are grouped into files. Partitioning should follow the grain (the level of detail of one row, such as one order line or one daily snapshot). Clustering should follow the columns that queries join and filter on. Compaction means merging many small files into fewer well-sized ones so reads stay fast.A very large order-lines table is mostly filtered by customer and joined to a customer table, and streaming writes keep leaving small files. The question asks how to lay it out.Cluster on the customer key with Liquid Clustering, because that matches the relationship queries use, and let compaction keep files balanced: Predictive Optimization runs OPTIMIZE on managed tables, or you schedule OPTIMIZE yourself. Partition only on a low-cardinality column that matches the data's grain and that is always filtered. Clustering works for Delta and for managed Iceberg tables, with Iceberg support depending on version, so check the docs.Partitioning by the customer key because it is the main filter. Too many distinct values make tiny files and slow metadata operations.
Runner-up wins when: Partitioning by load date wins when downstream jobs and retention rules always work on whole days and the table is very large.

9.2 Design dimensional models for analytical workloads, leveraging Materialized Views for pre-computed aggregation and Unity Catalog Metric Views for governed, reusable metric definitions, to ensure efficient querying and aggregation.A dimensional model arranges analytics data as fact tables (events and amounts) joined to dimension tables (descriptions). A materialized view stores a query result and refreshes it, so repeated aggregations are pre-computed. A Unity Catalog metric view defines measures and dimensions once, with governance, so every tool computes a metric the same way.Many dashboards compute revenue per region and month from a large fact table, and different teams define revenue differently. The question asks how to make it fast and consistent.Use a materialized view for the heavy shared aggregation so it is computed once and refreshed incrementally when the query allows it, and a Unity Catalog metric view to hold the single governed definition of revenue and its dimensions. A metric view lets users group by any dimension, and can itself be materialized so eligible queries are rewritten to use it.Making a standard view for the aggregation. A standard view computes on every query, so it gives a shared definition but no speed-up.
Runner-up wins when: A standard view wins when the data is small and always needs to be fresh, because nothing needs refreshing.
