AGet the right content in

2.1

Choose the source documents

Retrieval can only return what you indexed: add the documents that hold the missing knowledge, and remove stale or duplicate ones.

If you know this from Azure/Claude: Same lesson as grounding data in Azure AI Search or a Claude RAG bot. The exam frames it as diagnosing which questions fail and which source would answer them.

How it works

  1. Group failing questions by topic
  2. Ask which document would contain the answer; check whether it's indexed
  3. Add authoritative, current sources; drop superseded versions
  4. Structured per-record facts (a delivery date for one order) belong in a table or tool, not in a vector index

Must know

  • Stale and current versions of the same document compete at retrieval time and cause wrong answers.
  • Store document-level metadata (source, version, date) with each chunk so you can filter.
  • Prompting can't create knowledge that no source contains.

Traps

  • Fine-tuning to add missing facts is the wrong fix for a knowledge gap.
  • Indexing everything 'just in case' adds noise and conflicting versions.

2.2

Extract content: the right package for the format

Match the extractor to the file: PDF text, mixed office files, HTML, or scanned images each have a natural tool, and Databricks adds ai_parse_document in SQL.

If you know this from Azure/Claude: Like choosing between Azure Document Intelligence read and layout models. New for you: ai_parse_document, a SQL AI Function that parses layout, text, tables and figures.

How it works

  1. Digital PDF text: a PDF library such as pypdf
  2. Mixed PDF, Word and PowerPoint with one library: unstructured
  3. HTML pages: BeautifulSoup or lxml
  4. Scanned images: OCR (Tesseract via pytesseract); in SQL, ai_parse_document covers PDFs, images, DOCX and PPTX

Must know

  • ai_parse_document inputs: PDF, JPG/JPEG, PNG, TIFF, DOC/DOCX, PPT/PPTX as binary content.
  • Read files with read_files(..., format => 'binaryFile') and pass the content column.
  • Output is a VARIANT with pages and elements (text, table, figure, title, section header, header/footer...); tables come back as HTML in version 2.0.
  • Limits: 500 pages and 100 MB per document; needs Databricks Runtime 17.3 or above in supported regions.

  • BeautifulSoup can't read scanned images; OCR is needed.

2.3

Filter extraneous content

Strip text that repeats on every page or carries no meaning before chunking, or it floods retrieval with useless matches.

If you know this from Azure/Claude: The same clean-up you'd do before indexing in Azure AI Search. Databricks-specific help: ai_parse_document labels page headers and footers as their own element types, so you can drop them.

How it works

  1. Find repeated text: page headers, footers, legal disclaimers, navigation menus, cookie banners
  2. Remove it after extraction and before chunking
  3. Keep meaningful structure: section titles, tables, figure captions
  4. Re-check retrieval on the questions that failed

Must know

  • Databricks guidance: preprocess extracted text to remove headers, footers and special characters.
  • Repeated boilerplate in every chunk makes unrelated chunks look similar to each other.
  • ai_parse_document element types include header and footer, which makes filtering straightforward.

Traps

  • A reranker can't fix an index full of boilerplate; clean the source first.
  • Don't strip section titles: they are the context that makes chunks retrievable.

BChunk and store

2.4

Chunking for document structure and model limits

Cut along the document's own structure, and keep each chunk inside the embedding model's token window.

If you know this from Azure/Claude: Identical trade-offs to chunking in Azure or a Claude pipeline. Databricks-specific: the embedding endpoints' windows (BGE 512, GTE 8,192 tokens).

How it works

  1. Use structure first: headings in Markdown or HTML, then paragraphs
  2. Cap chunk length at the embedding model's window; longer text is truncated
  3. Add modest overlap so facts at boundaries aren't split
  4. Tune size against retrieval results, not by instinct

Must know

  • Strategies: fixed-size (fast, rarely production-grade), paragraph, format-specific (headers), semantic (topic shifts).
  • Smaller chunks: precise but lose context. Larger: more context, more noise and cost.
  • Overlap preserves continuity across chunk boundaries but adds chunks.
  • databricks-bge-large-en: 512-token window, 1,024 dimensions. databricks-gte-large-en: 8,192 tokens, 1,024 dimensions.

  • A chunk longer than the embedding window isn't an error; the tail is silently truncated and never searchable.
  • More overlap means more vectors, not fewer.

2.5

Advanced chunking for better retrieval

Search with small, precise pieces but give the model enough context: parent-child chunks, context-enriched chunks and metadata.

If you know this from Azure/Claude: The small-to-big and contextual retrieval ideas you know from Claude and Azure. New for you: ai_prep_search (Beta) splits parsed documents into semantic chunks and adds document context to each.

How it works

  1. Parent-child: embed small chunks, return their larger parent section to the LLM
  2. Context-enriched: prepend document title or section path to the text you embed
  3. Store metadata (product, version, date) per chunk to filter at query time
  4. Measure the change with retrieval metrics

Must know

  • ai_prep_search output per chunk: chunk_id, chunk_to_retrieve (raw text), chunk_to_embed (context-enriched), metadata, pages.
  • Flatten to one row per chunk in Delta, then use chunk_to_embed as the embedding column and chunk_id as the primary key.
  • ai_prep_search is Beta and needs Databricks Runtime 18.2 or above.
  • Metadata enables filters, which narrow the search before ranking.

Traps

  • Embedding the enriched text but showing the model only the tiny chunk loses the benefit; return the parent or retrieve text.
  • Semantic chunking isn't free: it costs compute at ingest.

2.6

Write chunks to Delta tables in Unity Catalog

Read, parse, chunk, write one row per chunk with a primary key to a UC Delta table with Change Data Feed on, then point a Delta Sync index at it.

If you know this from Azure/Claude: New for you in its details: Azure indexers pull from blob storage; on Databricks the index syncs from a governed Delta table.

How it works

  1. Read files from a UC volume as binary
  2. Parse to text (ai_parse_document or a Python library) and clean it
  3. Chunk; add chunk_id, source path and metadata columns
  4. Write to catalog.schema.table with delta.enableChangeDataFeed = true; create a Delta Sync index

Must know

  • Standard vector search endpoints need Change Data Feed on the source table; row tracking turns it on automatically.
  • A Delta Sync index keeps itself in step with the source table.
  • Creating an index needs CREATE TABLE on the target schema; the workspace needs Unity Catalog and serverless compute.
  • Use a three-level name: catalog, schema, table.

Traps

  • Writing chunks to a path, not a UC table, means no governance and no Delta Sync.
  • Forgetting a stable primary key per chunk breaks incremental sync.

CRetrieve, measure and re-rank

2.7

Evaluate retrieval with tools and metrics

Measure retrieval separately from generation: are the retrieved chunks relevant, and do they contain everything needed?

If you know this from Azure/Claude: Like Azure's retrieval and groundedness evaluators. Databricks-specific: MLflow judges RetrievalRelevance, RetrievalSufficiency and RetrievalGroundedness.

How it works

  1. Build an evaluation set of questions (with expected facts where you can)
  2. Score retrieved context with RetrievalRelevance (no ground truth needed)
  3. With expected facts, score RetrievalSufficiency
  4. Track ranking metrics such as precision at k and recall at k as you change chunking

Must know

  • RetrievalRelevance: is retrieved context relevant to the request? No ground truth.
  • RetrievalSufficiency: does the context hold all facts needed for the expected answer? Needs ground truth.
  • RetrievalGroundedness: is the response supported by the retrieved context? No ground truth.
  • Precision at k: share of the top k that are relevant. Recall at k: share of all relevant chunks that appear in the top k.

Traps

  • Groundedness checks the answer against context, not whether retrieval found the right context.
  • Sufficiency needs expected facts; without labels, use relevance.

2.8

Re-ranking and hybrid search

A fast first stage fetches many candidates; a re-ranker scores them more precisely so the best few go to the LLM.

If you know this from Azure/Claude: The same idea as Azure AI Search's semantic ranker. On Databricks: pass DatabricksReranker(columns_to_rerank=[...]) to similarity_search.

How it works

  1. Retrieve broadly (for example 50 candidates) with ANN or hybrid
  2. Re-rank with the reranker over chosen text and metadata columns
  3. Send only the top few to the LLM
  4. Use query_type="hybrid" when exact terms such as codes matter

Must know

  • Reranking adds latency, typically under 1 second per query.
  • Hybrid search combines vector and keyword results with Reciprocal Rank Fusion; hybrid returns at most 200 results by default.
  • Default query type is ANN; FULL_TEXT is Beta.
  • Filters: a dictionary on standard endpoints, a SQL-like string on storage-optimized endpoints.
  • Vector Search is now named AI Search in the docs (formerly Databricks Vector Search); the exam guide uses the old name.

Traps

  • Passing 50 chunks straight to the LLM instead of re-ranking raises cost and buries the answer.
  • When latency is the top constraint, a reranker may be the wrong addition.
