AMasking and guardrails

5.1

Mask sensitive columns before the model sees them

Unity Catalog column masks and row filters decide what a query returns, so a RAG pipeline or a tool that reads a table only gets what the caller may see.

If you know this from Azure/Claude: Same idea as least privilege in Azure RBAC and keeping secrets out of the prompt in CCA-F. Databricks-specific: the mask is a SQL function bound to the column, so every reader (notebook, Vector Search sync, agent tool) gets the masked value.

How it works

  1. Write a SQL UDF that returns the real value or a masked one, for example based on group membership
  2. Bind it with ALTER TABLE ... ALTER COLUMN ... SET MASK <fn>
  3. For rows, bind a boolean UDF with ALTER TABLE ... SET ROW FILTER <fn> ON (<cols>)
  4. Build the chunk table or tool on top of the governed table, not a raw copy

Must know

  • A row filter is a SQL UDF; rows where it returns FALSE are left out.
  • A column mask is a SQL UDF that returns the value or a masked version; one mask per column.
  • Runtimes below 12.2 LTS return no data from tables with filters or masks.
  • For the same rule across many tables, Databricks recommends ABAC policies over per-table masks.

Traps

  • Copying the table to a new schema for the RAG index drops the protection you meant to keep.
  • Asking the LLM in the prompt not to reveal salaries is not masking: the model still saw the values.

5.2

Mask PII in free text: ai_mask() and the gateway PII guardrail

Masking PII in free text, rather than dropping whole documents, keeps the useful text, so answer quality stays up and personal data stays out.

If you know this from Azure/Claude: Like PII redaction in Azure Language. Databricks-specific: ai_mask() is a SQL AI Function for batch clean-up of source text. The AI Gateway PII guardrail can mask or block PII on live requests and responses.

How it works

  1. At ingestion: SELECT ai_mask(text, array('person','email','phone')) before chunking
  2. At serving: in AI Gateway, set PII detection to Mask (keep the request, hide the values) or Block (reject the request)
  3. Check a sample: no detector finds everything

Must know

  • ai_mask(content, labels) returns the text with the listed entity types replaced by [MASKED]; Public Preview; DBR 15.4 LTS or above.
  • AI Gateway guardrails are Public Preview. PII detection can be set to Block, Mask or None, on requests and responses.
  • Output guardrails don't support embeddings models or streaming.
  • Databricks warns there is no guarantee the PII detector finds all sensitive information.

5.3

Guardrails against malicious user input

Stack the defences: screen the input before the model, limit what tools can do, and screen the output before the user sees it.

If you know this from Azure/Claude: You know this from CCA-F (treat retrieved text and tool results as data) and from Azure Prompt Shields. Databricks-specific: the Unity AI Gateway has built-in guardrail policies, including jailbreak detection on requests. The legacy AI Gateway has safety filtering and PII detection.

How it works

  1. Input phase: a safety or jailbreak guardrail runs before the model is called
  2. Prompt design: keep system instructions apart from user and retrieved text, and say that the text is data
  3. Tools: give the agent the least privilege it needs (Unity Catalog grants on functions and tables)
  4. Output phase: a safety guardrail on the response; log everything to inference tables for review

Must know

  • Legacy AI Gateway guardrails (Public Preview): safety filtering and PII detection; a blocked request returns a default message.
  • Unity AI Gateway service policies (Beta) include system.ai.block_jailbreak (requests only), system.ai.block_unsafe_content (requests and responses) and system.ai.block_hallucination (responses only).
  • Custom policies can be a SQL function or an LLM-as-a-judge prompt.
  • Request-phase policies run before the model is invoked, so a blocked attack costs no model tokens.

Traps

  • A stern system prompt alone is not a guardrail; injected text can override it.
  • A jailbreak check on the response phase is too late, and the built-in one runs on requests only.
  • Rate limits stop floods, not clever prompts.

BData sources: licences and problem text

5.4

Licences for data sources and models

Before data or a model goes into a GenAI app, check that its licence allows that use: commercial use, redistribution, derived works and attribution.

If you know this from Azure/Claude: New for you: neither AI-103 nor CCA-F tests licensing. The idea is simple: where the data came from and what its licence says is a requirement, just like latency.

How it works

  1. List each source: owner, licence, allowed uses (commercial? training? redistribution?)
  2. Drop or replace sources whose terms forbid your use, or get a licence
  3. For models, read the model terms (for example a Llama community licence and acceptable use policy)
  4. Record the decision next to the data, for example as Unity Catalog comments or tags

Must know

  • Databricks: "Regardless of where a model is hosted, you are responsible for complying with the provider's applicable terms of use."
  • Foundation Model API model pages point to each model's terms, for example the Llama 4 Community License and Acceptable Use Policy.
  • Publicly reachable is not the same as licensed: scraped web pages can carry terms that forbid reuse.
  • Non-commercial (NC) and no-derivatives (ND) licences are the usual blockers for a commercial app.

Traps

  • "It's on the internet" or "it's open source" doesn't settle it; read the licence.
  • Citing the source in the answer doesn't fix a licence that forbids the use.

5.5

Problem text in a source: fix the data, not the prompt

If a source holds toxic, biased, outdated or sensitive text, remove, redact or replace it upstream rather than hoping the prompt will make the model ignore it.

If you know this from Azure/Claude: CCA-F's "fix it deterministically where you can" applies directly. Databricks-specific: you fix it in the Delta pipeline (filter rows, ai_mask(), a curated table) and the Vector Search index re-syncs.

How it works

  1. Find the problem rows: classifiers, ai_classify()-style tagging, keyword rules, SME review
  2. Choose the remedy: drop the document, redact the passage, or swap in a cleaner or newer source
  3. Write the curated result to a new Delta table; point the index at it
  4. Keep an output guardrail as the safety net, not the main fix

Must know

  • Retrieval pulls source text straight into the context, so bad text in the index becomes bad text in answers.
  • Delta Sync indexes stay in sync with the source table, so a fix upstream flows into the index.
  • Replacing a source with a licensed, cleaner equivalent is a valid answer when filtering would remove too much.

Traps

  • "Add an instruction telling the model to ignore offensive passages" is the classic wrong answer.
  • Fine-tuning the model to avoid the text is slow, costly and still leaves the text in the index.
