ABuild, log and register the chain

4.1

Chains: a simple chain, and a pyfunc with pre- and post-processing

A simple chain is prompt, then model, then output parser. When you need your own code before and after the model call, wrap it in a custom mlflow.pyfunc.PythonModel.

If you know this from Azure/Claude: Same idea as a Claude tool-use loop with your own code around the call. The Databricks part: you package the whole thing as an MLflow model, log it from code, and serve it.

How it works

  1. Simple chain (LangChain): prompt | ChatDatabricks(endpoint=...) | StrOutputParser()
  2. Custom logic: subclass mlflow.pyfunc.PythonModel; predict cleans the input, calls the LLM, then shapes the output
  3. Log it from code: mlflow.pyfunc.log_model(python_model="agent.py", ...), with mlflow.models.set_model(...) at the end of the file
  4. Test before serving with mlflow.models.predict(...) or mlflow.pyfunc.load_model(...)

Must know

  • predict is required; load_context loads extra context once; predict_stream streams.
  • Models from code saves a script instead of a pickled object, so it avoids pickle and Python-version problems. MLflow recommends it for GenAI agents and chains.
  • Packages you can't pip install go in code_paths.
  • For new agents Databricks recommends MLflow ResponsesAgent; MLflow infers a compatible signature for it.

Traps

  • Pickling a LangChain chain or a client object is the classic failure; log from code instead.
  • Pre- and post-processing belongs inside predict, not in the serving endpoint's settings.

4.2

The parts of a RAG application you log

To serve a RAG chain you need a model flavor, an embedding model, a retriever, dependencies, an input example and a signature.

If you know this from Azure/Claude: The RAG pieces are the ones you know from Azure AI Search and Claude. What's new is that MLflow packages them, and Unity Catalog refuses a version without a signature.

How it works

  1. Pick the flavor: pyfunc (custom or ResponsesAgent) or a framework flavor such as langchain
  2. Retriever: a Vector Search index, often exposed as VectorSearchRetrieverTool (from databricks_langchain or databricks_openai)
  3. Embedding model: the endpoint the index uses (managed embeddings) or one you call yourself (self-managed)
  4. Log with input_example (or type hints) so MLflow infers the signature, plus pip_requirements and the resources the chain calls

Must know

  • New model versions in Unity Catalog must have a signature.
  • An input_example lets MLflow infer the signature (MLflow 2.5+) and checks that predict works.
  • Declaring resources (index, LLM endpoint, UC functions) is what lets the served chain authenticate to them automatically.
  • Query text and the index must use the same embedding model.

Traps

  • A model logged with no signature and no input example can't be registered to Unity Catalog.
  • Don't put the vector index inside the model artifacts; the chain queries the index at run time.

4.3

Register to Unity Catalog with MLflow

Models live in Unity Catalog as catalog.schema.model. You promote them with aliases. Stages don't exist there.

If you know this from Azure/Claude: Like Foundry model versions, but governed by Unity Catalog grants. If you know the old workspace registry, unlearn Staging and Production stages.

How it works

  1. mlflow.set_registry_uri("databricks-uc") (the default on DBR 13.3 LTS+ or MLflow 3 when the default catalog is in UC)
  2. log_model(..., registered_model_name="prod.support.rag_bot") or mlflow.register_model(...)
  3. client.set_registered_model_alias("prod.support.rag_bot", "champion", 3)
  4. Load with models:/prod.support.rag_bot@champion; move the alias to promote or roll back

Must know

  • "Stages are not supported for models in Unity Catalog." Use aliases, and the three-level name for environments.
  • Create a model: USE CATALOG, USE SCHEMA and CREATE MODEL on the schema.
  • Load by alias or version: EXECUTE on the model plus USE CATALOG and USE SCHEMA.
  • Batch jobs that load @champion pick up the new version on their next run.

Traps

  • transition_model_version_stage is an answer from the old workspace registry; it's wrong for Unity Catalog.
  • A two-level name means you're still pointing at the workspace registry.

BVector Search

4.4

Vector Search: endpoints, indexes and sync

An endpoint is the compute; an index lives on an endpoint and is built from a Delta table (Delta Sync) or written to directly (Direct Vector Access).

If you know this from Azure/Claude: Same job as an Azure AI Search index. The Databricks part: indexes sync from Delta tables in Unity Catalog, and you choose between two endpoint types. Name change: the docs now say AI Search (formerly Vector Search); the exam guide still says Vector Search.

How it works

  1. Create an endpoint: endpoint_type="STANDARD" or "STORAGE_OPTIMIZED"
  2. Choose an index type: Delta Sync with Databricks-computed embeddings, Delta Sync with self-managed embeddings, or Direct Vector Access
  3. Delta Sync: choose pipeline_type TRIGGERED (sync when you call it) or CONTINUOUS
  4. Standard endpoints need Change Data Feed on the source table (tables with row tracking have it automatically)

Must know

  • Standard: about 320 million vectors at 768 dimensions; the only type that supports high QPS.
  • Storage-optimized: over 1 billion vectors, 10 to 20 times faster indexing, about 250 ms more query latency, and lower cost at large scale.
  • Storage-optimized endpoints don't support continuous sync, and the embedding dimension must be divisible by 16.
  • Direct Vector Access: you write vectors yourself with upsert; about 2 million vectors at 768 dimensions on a standard endpoint.
  • Requires a Unity Catalog workspace with serverless compute; up to 50 indexes per endpoint.
NeedChoose
Hundreds of millions to billions of vectors, cost first, a few hundred ms is fineStorage-optimized endpoint, triggered sync
High QPS, lowest latency, near real-time freshnessStandard endpoint, continuous sync
Vectors come from your own pipeline, not a Delta tableDirect Vector Access index, upsert

Traps

  • Continuous sync together with storage-optimized is an impossible combination.
  • A self-managed-embeddings index can't be converted to Databricks-managed embeddings later.

4.5

Create, query and keep an index fresh

Query with similarity_search: text or a vector in, top-k rows out, with optional filters, hybrid keyword search and reranking.

If you know this from Azure/Claude: Hybrid search plus a reranker is the same pattern as Azure AI Search's hybrid query plus semantic ranker. The Databricks part is the SDK calls and filter syntax.

How it works

  1. index = client.get_index(index_name="cat.sch.idx")
  2. index.similarity_search(query_text=..., columns=[...], num_results=5)
  3. Add query_type="hybrid" for vector plus keyword (combined with Reciprocal Rank Fusion), and a filters argument
  4. Triggered index: call index.sync() after the source table changes

Must know

  • Filters on a standard endpoint are a dictionary: {"title": ["Ares", "Athena"]}; on storage-optimized they're a SQL-like string: "language = 'en'".
  • Hybrid search returns at most 200 results; ANN up to 10,000.
  • Reranking: reranker=DatabricksReranker(columns_to_rerank=[...]).
  • Agent tool form: VectorSearchRetrieverTool(index_name=..., num_results=..., filters=..., query_type="HYBRID").
  • Client naming changed with the rename: newer docs use AISearchClient (package databricks-ai-search); older code uses VectorSearchClient. Index methods are the same.
client.create_delta_sync_index(
    endpoint_name="kb-endpoint",
    source_table_name="prod.support.kb_chunks",
    index_name="prod.support.kb_index",
    pipeline_type="TRIGGERED",
    primary_key="chunk_id",
    embedding_source_column="text",
    embedding_model_endpoint_name="databricks-gte-large-en")

index.similarity_search(query_text="reset router", columns=["chunk_id", "text"],
    num_results=5, query_type="hybrid", filters={"product": ["router"]})

Traps

  • A dictionary filter sent to a storage-optimized endpoint is the wrong syntax.
  • Full-text-only search is Beta; don't treat it as GA.

CServe, connect and ship

4.6

Serving an LLM app on Foundation Model APIs

Foundation Model APIs give you hosted LLMs and embedding models. Your agent calls them, and agents.deploy() puts the agent on a Model Serving endpoint.

If you know this from Azure/Claude: Pay-per-token versus provisioned throughput is the same trade-off as Azure's Standard versus provisioned (PTU) deployments.

How it works

  1. Prototype on pay-per-token (OpenAI-compatible; reach it from AI Gateway in the sidebar)
  2. Move to provisioned throughput for production throughput, performance guarantees, fine-tuned models or compliance (for example HIPAA)
  3. Register the agent in Unity Catalog, then from databricks import agents; agents.deploy(uc_name, version)
  4. Redeploy with the same UC model name to add a version to the same endpoint with no downtime

Must know

  • Pay-per-token has a priority service tier for latency-sensitive production (costs more, no commitment).
  • Provisioned throughput has on-demand and reserved (1- or 3-month) options, and serves fine-tuned or custom weights registered in UC.
  • agents.deploy() creates the endpoint, short-lived credentials for declared resources, MLflow tracing, a Review App, AI Gateway inference tables and production monitoring (beta).
  • scale_to_zero_enabled=True cuts idle cost but slows the first request.
  • External models are reached through their own serving endpoint (an external model endpoint).

Traps

  • Fine-tuned weights can't run on pay-per-token; they need provisioned throughput.
  • Newer docs recommend the Agent Bricks CLI and Agent Runtime (Databricks Apps compute) for brand-new agents; the exam guide's objectives describe Model Serving.

4.7

Batch inference with ai_query()

When the job is "run an LLM over every row of a table", use ai_query() in SQL or PySpark, not a loop of REST calls.

If you know this from Azure/Claude: New for you: Azure's nearest equivalent is the Batch API. Here the batch is a SQL query over a Delta table.

How it works

  1. SELECT ai_query('endpoint', CONCAT('Classify: ', body)) FROM tickets
  2. Send the whole dataset in one query; AI Functions handle parallelism, retries and scaling
  3. Set failOnError => false for big jobs; the result becomes a struct with response and errorMessage
  4. Use responseFormat for structured output from chat models, and modelParameters for settings like temperature

Must know

  • Works on Databricks SQL and Databricks Runtime (15.4 LTS+); not on SQL Classic warehouses.
  • The query's definer needs CAN QUERY on the endpoint.
  • Databricks recommends task-specific AI Functions first (for example ai_classify), then ai_query when they don't fit.
  • Some Databricks-hosted models are optimised for batch; real-time pay-per-token models aren't recommended for large batch production.

Traps

  • Calling the endpoint row by row from a Python loop or pandas UDF is the slow, fragile answer.
  • With the default failOnError => true, one bad row fails the whole query.

4.8

Who can call what: endpoint access and front ends

A served agent reaches its tools with credentials Databricks issues for the resources you declared, with the user's own identity (on-behalf-of), or with secrets you supply.

If you know this from Azure/Claude: Like Azure managed identity plus RBAC: no keys in code. The Databricks part is declaring resources at log time and the three serving-endpoint permission levels.

How it works

  1. Automatic authentication passthrough: declare resources in log_model(resources=[...]); Databricks creates a service principal with read access and short-lived OAuth tokens
  2. On-behalf-of-user (Public Preview, admin enables it): WorkspaceClient(credentials_strategy=ModelServingUserCredentials()), created inside predict
  3. Manual: put keys in Databricks secrets and pass {{secrets/<scope>/<key>}} as environment variables to deploy()
  4. Endpoint permissions: CAN VIEW, CAN QUERY, CAN MANAGE

Must know

  • Resource classes include DatabricksServingEndpoint, DatabricksVectorSearchIndex, DatabricksFunction, DatabricksGenieSpace, DatabricksSQLWarehouse, DatabricksTable, DatabricksUCConnection and DatabricksLakebase.
  • On-behalf-of-user declares scopes with UserAuthPolicy(api_scopes=[...]); the user is only known at query time, so don't create that client in __init__.
  • Front ends: a Databricks App signs users in with their workspace identity and keeps tokens on the server; the Genie apps for Slack and Microsoft Teams let people chat with Genie in channels.
  • Overriding security environment variables turns off automatic passthrough for the agent's other resources.

Traps

  • Passthrough uses the agent's service principal, so every user sees the same data. Per-user row filters need on-behalf-of-user.
  • A PAT in browser JavaScript or in the agent's code is always wrong.

4.9

Tools and memory: MCP servers and Lakebase

Give an agent tools through managed MCP servers (Databricks hosts them), external MCP servers (registered through a Unity Catalog connection) or custom ones (built on Databricks Apps). Give it memory with stores backed by Lakebase.

If you know this from Azure/Claude: MCP is the protocol you know from Claude. The Databricks part: managed servers sit behind Unity Catalog permissions, and memory is a managed Postgres-backed store, not your own database.

How it works

  1. Managed: point the agent at a URL such as /api/2.0/mcp/functions/{catalog}/{schema}/{function} or /api/2.0/mcp/genie/{space_id}
  2. External: register the server in the MCPs UI on an HTTP Unity Catalog connection; users need USE CONNECTION
  3. Custom: build your own tools, or turn a REST API into MCP tools, with Databricks Apps templates
  4. Memory: sessions hold one conversation's state; memory holds facts recalled in later conversations; both are managed stores backed by Lakebase

Must know

  • Managed workspace MCP endpoints (Genie, AI Search, Databricks SQL, UC functions) are Public Preview, and an admin must enable them.
  • Managed endpoints use the permissions on the underlying table, index, function or Genie space.
  • Registering an external MCP needs CREATE SERVICE on the schema plus a connection (CREATE CONNECTION or USE CONNECTION).
  • Sessions and memory are separate stores: deleting a session doesn't delete its memories. The older UC-governed managed memory is legacy.

Traps

  • Building a custom MCP server for something a managed server already exposes (UC functions, Genie) adds maintenance for nothing.
  • Session state doesn't carry over to a new conversation; cross-conversation recall needs the memory store.

4.10

Prompt registry and CI/CD

Version prompts in the MLflow Prompt Registry (stored in Unity Catalog), point environments at aliases, and test each agent part before you promote it.

If you know this from Azure/Claude: Same release discipline you'd use for Azure prompt flows or Claude system prompts in Git. The Databricks part: prompts are Unity Catalog objects with immutable versions and movable aliases.

How it works

  1. mlflow.genai.register_prompt(name="cat.sch.support_prompt", template="... {{question}} ...") makes a new immutable version
  2. mlflow.genai.set_prompt_alias(...) moves staging or production; the app loads prompts:/cat.sch.support_prompt@production
  3. Pipeline: unit-test tools and the retriever, evaluate in staging, then move aliases (model and prompt) for production
  4. Index refresh step: after the source Delta table is updated, call index.sync() on a triggered index

Must know

  • The Prompt Registry on Databricks is Beta (needs mlflow[databricks]>=3.1.0).
  • Template variables use double braces {{question}}; prompt.format(question=...) fills them; to_single_brace_format() converts for LangChain.
  • Prompt permissions: CREATE FUNCTION, EXECUTE and MANAGE on the schema.
  • Databricks LLMOps guidance: separate dev, staging and prod environments; you often promote the pipeline (prompts, chains, agents), not a model.
  • Bundles (Databricks Asset Bundles, now called Declarative Automation Bundles in the docs) define jobs, endpoints and indexes as code; deploy with databricks bundle deploy -t prod.

Traps

  • Hard-coding a prompt version number in the app means every prompt change needs a code release.
  • Rebuilding the index from scratch on every deployment wastes time; sync it.
