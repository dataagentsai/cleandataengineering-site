AFrameworks and models

3.1

LangChain on Databricks: which class does what

The databricks-langchain package wraps Databricks services as ordinary LangChain parts, so a chain or LangGraph agent can use them directly.

If you know this from Azure/Claude: The chain-and-tools idea is the same as tool use in Claude and agents in Foundry. What's Databricks-specific is the class names and that every part points at a Databricks endpoint, index or Unity Catalog object.

How it works

  1. Pick the LLM: ChatDatabricks(endpoint=...) points at a Model Serving or Foundation Model API endpoint
  2. Add retrieval: DatabricksVectorSearch(index_name=...), then .as_retriever()
  3. Add tools: UCFunctionToolkit turns Unity Catalog functions into agent tools
  4. Add structured data: GenieAgent sends a question to a Genie space

Must know

  • ChatDatabricks is the chat model; DatabricksEmbeddings is the embedding model wrapper.
  • DatabricksVectorSearch works with Delta Sync and Direct Vector Access indexes.
  • UCFunctionToolkit exposes Unity Catalog functions as tools, so governance stays in Unity Catalog.
  • DatabricksMCPServer and DatabricksMultiServerMCPClient connect an agent to Databricks MCP endpoints.
  • Docs now call Vector Search AI Search; the exam guide still says Vector Search.
You needClass
Chat LLM on a serving endpointChatDatabricks
EmbeddingsDatabricksEmbeddings
Retriever over an indexDatabricksVectorSearch(...).as_retriever()
Unity Catalog functions as toolsUCFunctionToolkit
Ask a Genie spaceGenieAgent

Traps

  • DatabricksEmbeddings makes vectors; it doesn't search an index. The retriever is DatabricksVectorSearch.
  • A Unity Catalog function becomes a tool through UCFunctionToolkit, not by pasting its SQL into the prompt.

3.2

Choose the LLM by what the application needs

Start from the application's attributes (task, input size, latency, cost, licence, quality bar), then pick the smallest model that meets them.

If you know this from Azure/Claude: Same reasoning as choosing a model in Foundry or picking Haiku vs Opus. Here the candidates are Foundation Model API endpoints and models in system.ai.

How it works

  1. Name the task: summarise, classify, extract, generate, reason with tools
  2. Size the input: longest prompt plus retrieved context must fit the context window
  3. Set the limits: latency target, cost per request, licence terms
  4. Test two or three candidates on your own evaluation set and compare

Must know

  • High-volume, narrow tasks (classification, extraction) usually suit a smaller instruct model.
  • Foundation Model API chat models differ in context window, for example 128K tokens for Llama 3.3 70B Instruct and GPT OSS 120B.
  • Instruct (chat-tuned) models are for serving; base models are for fine-tuning.
  • A bigger model costs more per token and adds latency; it's only worth it if your evaluation shows the quality gain.

Traps

  • "Most capable model" is rarely right when the stem stresses cost or throughput.
  • An embedding model can't answer questions; it only makes vectors.

3.3

Embedding model context length

The embedding model's window must cover your largest chunk and typical query; anything past the window is cut off before embedding.

If you know this from Azure/Claude: Same trade-off as choosing an Azure OpenAI embedding model: window, dimensions, cost. On Databricks the two pay-per-token embedding endpoints have very different windows.

How it works

  1. Find your largest chunk in tokens (and your longest expected query)
  2. Pick a model whose window covers it; text past the window is ignored
  3. If cost and latency matter more than quality, prefer the smallest window and dimension that still fits
  4. Embed documents and queries with the same model

Must know

  • gte-large-en: 1024 dimensions, 8,192-token window, embeddings not normalised.
  • bge-large-en: 1024 dimensions, 512-token window, normalised embeddings.
  • Qwen3-Embedding-0.6B (Public Preview): up to about 32K tokens, dimensions configurable up to 1024.
  • A bigger window doesn't help if every chunk is already short; it just costs more.

  • Choosing bge-large-en for 2,000-token chunks silently truncates them to 512 tokens.
  • Mixing models (documents with one, queries with another) puts vectors in different spaces.

3.4

Pick from a model hub, then by experiment metrics

Shortlist with the model card (task, languages, licence, size), then decide with numbers from your own MLflow experiments.

If you know this from Azure/Claude: Same as the Foundry model catalog and its model cards. On Databricks, ready models sit in Unity Catalog under system.ai, and comparisons live in MLflow runs.

How it works

  1. Browse system.ai in Catalog Explorer (or Marketplace) and read each model's card
  2. Drop models whose licence, languages or task don't fit
  3. Evaluate the survivors on the same dataset with mlflow.genai.evaluate()
  4. Pick the model that meets every hard limit, then the best quality among those

Must know

  • Databricks-provided models live in Unity Catalog under system.ai and are available to all account users by default.
  • Databricks recommends instruct versions for deployment and base versions for fine-tuning.
  • Serve a system.ai model from its model page with Serve this model.
  • Marketplace models arrive as read-only catalogs in Unity Catalog.

Traps

  • A leaderboard score or download count doesn't override a licence that forbids your use.
  • Pick the best score only among models that already pass the hard limits (latency, cost).

BPrompts, quality and guardrails

3.5

Augment and adjust prompts

Pull key fields and the intent out of the user's message, fetch the matching facts, and put them in the prompt; then shape the output with instructions, examples or a schema.

If you know this from Azure/Claude: Straight from Claude and Azure prompt work: context in, clear instructions, few-shot examples, structured outputs. Databricks adds response_format on Foundation Model API chat endpoints.

How it works

  1. Classify intent and extract key fields (order ID, product, date)
  2. Look up the facts for those fields and add them to the prompt as labelled context
  3. Compare the baseline output with the desired one; name the gap (format, tone, length, content)
  4. Close the gap: instructions, a few examples of the exact output, or response_format with a JSON schema

Must know

  • response_format with type: json_schema (and strict: true) or json_object requests structured output.
  • Supported on Foundation Model API pay-per-token and provisioned throughput chat endpoints.
  • For Claude models on Databricks: json_schema only, no streaming, and not combined with tools.
  • Few-shot examples fix format and tone faster than longer instructions.

Traps

  • Lowering temperature makes output steadier, but it doesn't teach a format.
  • Fine-tuning to add fresh per-user facts is the wrong tool; fetch them at request time.

Quick check: s3-q09 · s3-q10 · Source: docs: machine-learning/model-serving/structured-outputs

3.6

Guardrails on serving endpoints

AI Gateway guardrails screen requests and responses on a serving endpoint: a safety filter for harmful content and PII detection that blocks or masks.

If you know this from Azure/Claude: Like Azure content filters and Claude's own safety, but set on the endpoint. New for you: the exact settings and limits.

How it works

  1. Open the endpoint's AI Gateway settings
  2. Turn on Safety for input, output or both
  3. Set PII detection to Block, Mask or None
  4. Test with streaming off if you rely on output guardrails

Must know

  • Guardrails on serving endpoints are Public Preview (legacy AI Gateway page).
  • PII detection: Block rejects the request or response; Mask replaces the sensitive values and lets it through.
  • Output guardrails are not supported for embedding models or for streaming.
  • The newer Unity Gateway governs model and MCP services with service policies (built-in, custom, external), checked on input and output.

Traps

  • Inference tables and rate limits are AI Gateway features too, but they record or throttle; they don't filter content.
  • "Mask" and "Block" aren't the same: Block stops the answer, Mask lets it through with values hidden.

3.7

Read responses for quality and safety; pick chunking from evaluation

Read real responses and sort what's wrong into quality issues (wrong, ungrounded, incomplete, off-format) and safety issues (harmful, leaks data); then let evaluation numbers, not taste, choose the chunk size.

If you know this from Azure/Claude: Same failure taxonomy as the Azure evaluators (groundedness, relevance, safety) and CCA-F review loops. On Databricks the scores come from MLflow judges such as RetrievalGroundedness and Safety.

How it works

  1. Sample real questions and answers; read them with the retrieved context beside them
  2. Tag each problem: ungrounded, irrelevant, incomplete, unsafe, leaks data, off-format
  3. For retrieval problems, run the same evaluation over two or three chunking set-ups
  4. Keep the set-up with the best retrieval and answer scores at acceptable cost

Must know

  • An answer that sounds right but isn't supported by the retrieved text is a groundedness (hallucination) problem.
  • Sharing another person's data or giving dangerous instructions is a safety issue, however polished the answer.
  • RetrievalSufficiency asks whether the retrieved context holds what's needed; it needs expected facts.
  • If answers span sections, small chunks split them; evaluate larger or structure-aware chunks.

Traps

  • Long or wordy answers are a quality issue, not a safety issue.
  • Choosing chunk size by gut feel; the objective says choose it from evaluation.

CAgents, evaluation and Genie

3.8

Build agents with MLflow and the Agent Framework

Write the agent in any framework, wrap it in MLflow ResponsesAgent, log it from code, and trace every step.

If you know this from Azure/Claude: Like building a Foundry agent or a Claude Agent SDK loop, but packaged as an MLflow model. New for you: ResponsesAgent and models-from-code.

How it works

  1. Write the agent (LangGraph, OpenAI Agents SDK, plain Python) in agent.py
  2. Wrap it in ResponsesAgent; end the file with mlflow.models.set_model(AGENT)
  3. Log it with mlflow.pyfunc.log_model(python_model="agent.py", ...), register to Unity Catalog, deploy
  4. Turn on tracing (autolog) to see each LLM and tool call

Must know

  • Databricks recommends MLflow ResponsesAgent for authoring agents.
  • ResponsesAgent lets MLflow infer a signature that works with Databricks product features.
  • Models-from-code logs the script path, not a pickled object; it suits GenAI agents with no trained weights.
  • Docs now recommend the Agent Bricks CLI for new agents; the ResponsesAgent path is labelled legacy but still documented.
# agent.py
import mlflow
from mlflow.pyfunc import ResponsesAgent

class SupportAgent(ResponsesAgent):
    def predict(self, request): ...

AGENT = SupportAgent()
mlflow.models.set_model(AGENT)

# driver notebook
mlflow.pyfunc.log_model(name="agent", python_model="agent.py")

Traps

  • Pickling a LangChain or LangGraph object is fragile; log from code instead.
  • A custom PythonModel with a home-made input format loses the automatic agent signature.

3.9

Evaluation phase vs monitoring phase

Evaluation scores a fixed dataset before release; monitoring runs the same scorers on a sample of live traces after release.

If you know this from Azure/Claude: Same split as Azure's offline evaluation vs continuous evaluation. On Databricks both use MLflow scorers: mlflow.genai.evaluate() before, registered scorers with .start() after.

How it works

  1. Before release: build an evaluation dataset (with expected answers where you can)
  2. Run mlflow.genai.evaluate() and compare app versions
  3. After release: scorer.register(name=...), then .start(sampling_config=ScorerSamplingConfig(sample_rate=...))
  4. Read assessments on traces and monitoring dashboards; feed bad cases back into the dataset

Must know

  • Production monitoring scores a configurable sample of incoming traces; results attach to each trace as feedback.
  • Suggested sample rates: 0.05–0.2 for expensive judges, 1.0 for critical safety checks.
  • At most 20 active scorers per experiment; allow 15–20 minutes for first results.
  • Judges that need ground truth (Correctness, RetrievalSufficiency, ToolCallCorrectness) suit evaluation datasets with expectations, not unlabelled live traffic.

Traps

  • Re-running evaluate() nightly on a fixed dataset isn't monitoring live traffic.
  • Putting Correctness on live traffic fails: there's no expected answer to compare with.

3.10

Genie in multi-agent systems

Let a Genie space answer questions over structured tables, as one worker agent beside retrieval and tool agents, called through GenieAgent or the Genie Conversation API.

If you know this from Azure/Claude: New for you: Genie is Databricks' natural-language-to-SQL over Unity Catalog tables. The supervisor/worker pattern itself is the same as Claude subagents or Foundry connected agents.

How it works

  1. Create a Genie space over the right tables and a SQL warehouse
  2. Add it as a worker: GenieAgent(genie_space_id=...) or a supervisor's Genie subagent
  3. Use on-behalf-of-user authorization so queries run with each user's permissions
  4. From custom code, call the Conversation API and poll until COMPLETED

Must know

  • Genie checks data access with the caller's Unity Catalog permissions, so answers include only data they can see.
  • The Conversation API returns generated SQL, query results and visualisations; poll every 1–5 seconds until COMPLETED, FAILED or CANCELLED.
  • The API doesn't retry failed requests; add backoff. Start a new conversation per session.
  • Auth: OAuth U2M when a user is present; a service principal (M2M) for headless use.

Traps

  • Embedding table rows into a vector index to answer numeric questions; that's Genie's job.
  • A shared service principal for a user-facing agent returns data some users mustn't see.
